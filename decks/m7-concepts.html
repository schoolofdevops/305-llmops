MODULE 7  ·  SHIP THE MODEL — KITOPS, OCI ARTIFACTS & SIGNING

The model has been a loose file — this makes it an artifact you can prove

It is your on-call week, payments is degraded, and OpsMate answers from a model file in a directory. A teammate asks the question you cannot answer: which model is that — the base you started with, or the M6 tune that lost and was never meant to ship? Who put it there? Has it changed since? A loose file cannot answer the three questions that matter when something breaks.

Gourav Shah  ·  School of DevOps & AI  ·  Lesson + Lab + Quiz

M7·01

A filename is not a version — the courier without a manifest

A parcel with just a name scrawled on the side is a problem the moment it leaves your hands. A parcel that travels properly carries a manifest: a label of what is inside, a tracking number unique to this parcel, and a tamper-evident seal. Copying a model file onto a server is shipping the parcel with a name and nothing else.

A filename travels like a parcel with a name scrawled on the side — trustworthy only in your own hands; an artifact carries a manifest of a label, a unique address, and a seal, so a chain of hands can trust it.

M7·02

A model on disk is a bundle, not one thing — one recap, not a re-teach

You already know this from M2, so this is a callback. A model is a small bundle of files that only mean something together — and shipping it well means shipping the whole bundle as one versioned unit, plus what was true about this model when it was built.

A model is a bundle — weights, tokenizer, config, chat template — so shipping it well means shipping the whole bundle plus its prompts and eval set as one versioned unit.

M7·03

OCI artifacts ride the rails you already have — and inside are layers

You do not need a new system. The container world already solved package a bundle, address it by a unique ID, push and pull it, verify it did not change — that is OCI, and a model packaged that way rides the same rails as your images. Inside, the goods are separately-listed crates: layers. Read the sizes — the whole point is in them.

OCI packages any bundle as an artifact that rides your existing image rails, and inside it is layers — a 610 MB weights crate beside KB metadata crates, each separately addressable.

M7·04

The Kitfile is a Dockerfile for models — every section becomes a layer

KitOps packages the bundle as an OCI artifact it calls a ModelKit, described by a Kitfile — to a ModelKit what a Dockerfile is to an image. Every top-level section becomes a layer, and every path is relative so the artifact stays portable.

KitOps packs a bundle into a ModelKit from a Kitfile — a Dockerfile for models where every section becomes a layer and every path is relative so the artifact stays portable.

M7·05

Selective pull — take one crate off the ship, not the whole thing

A ModelKit moves like any OCI artifact: kit push sends it, kit pull brings it back. The move that matters is selective pull. Because the manifest lists each layer by digest, the client fetches exactly the crate you ask for — the prompts without the weights.

Selective pull retrieves one layer by its digest — kit unpack --filter=code brings back 5 KB of prompts and leaves the 610 MB of weights on the registry.

M7·06

The wax seal proves origin, not quality — and binds to a digest, not a tag

Packaging answers what is inside and how to address it, not did anyone tamper with it. For that you sign. A wax seal does not hide the letter — anyone can read it — it proves two things: sealed by whoever holds the ring, and unopened since. Signing is tamper-evidence, not secrecy.

Signing is a wax seal: it proves the bytes came from the key holder and are unchanged — origin not quality, tamper-evidence not secrecy — and it binds to the digest, never a movable tag.

M7·07

A seal nobody checks is decoration — verify before you run

Signing is only useful if something downstream verifies before it runs. That bottom branch — no signature means refuse to deploy — is the whole point. cosign verify checks the digest: were the bytes changed, and were they signed by the key holder?

Signing only matters if something verifies before it runs — the gate refuses an unsigned or altered model, first in OpsMate's preflight, then as a Kubernetes admission policy in M8.

M7·08

Semver for models — textbook editions, plus the -candidate suffix

A version number should tell you what changed without diffing two artifacts. Semver carries over to models like editions of a textbook — with one honest caveat: the field has no universal standard, so you adopt a convention and state it.

Semver reads like textbook editions — MAJOR breaks references, MINOR improves within, PATCH is packaging only — plus the -candidate suffix for a build that is real and pushed but not yet promoted.

M7·09

The two tags — the registry records history, not just winners

Straight out of M6: you tuned a model, measured it honestly, and it lost — so it did not ship. Packaging forces the question, what happens to it now? Not delete it (lose the record), not leave it lying around (served by accident) — push both, as two tags of one repository.

You push both models as two tags — the signed base that serves and the unsigned M6 candidate the gate blocks — each carrying its golden set, so the registry preserves the whole history, not just the winner.

M7·10

Zot here, Harbor and ECR and HF in production — the address changes, not the format

The registry is where artifacts live, and you have choices. This lab runs Zot because it starts in seconds and needs no cloud. In production you would meet one of the others — and the point is that your artifact does not change, only where it is stored does.

The lab runs Zot but the artifact is portable — Harbor, ECR/GHCR, and Hugging Face are just different addresses for the same OCI artifact, because you did not invent your own format.
