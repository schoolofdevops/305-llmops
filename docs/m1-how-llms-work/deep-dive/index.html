Deep Dive — Attention, Sampling & the Hidden Chat Contract

The lab proved the two phases exist and let you time them. It showed tokens as the meter and the KV cache as the memory bill. This page goes below that. You will build a working feel for what attention actually does (the reason the KV cache holds keys and values), you will see why "set temperature to 0 for reproducible evals" is a half-truth that will burn you when you compare two engines, and you will read the chat template — the hidden wrapper every one of your messages goes through before the model ever sees it. These are the layers you reach for when an eval that passed yesterday fails today with no code change, or when a model that worked on Ollama gives different answers on vLLM.

Where this picks up

You need the same setup as the lab: Ollama running on the host and qwen3:0.6b pulled. If you did the lab teardown, nothing is lost — Ollama is still your host model server. Re-running any command here is safe; none of them change persistent state. If the model was idle, the first request pays the one-time load again (the keep-alive clock from the lab). That is all.

1 — Attention, without the maths wall​

The lesson said attention lets each token "look back" at the earlier ones. Here is the working picture of how, and it is the reason the cache is called the KV cache specifically.

Think of a room of people, each holding a small sign (a key) that says what they are about, and a note in their pocket (a value) with the actual content they would hand over. A new person walks in with a question written on their forehead (a query). They glance around, match their query against everyone's key sign, and the closer the match, the more they lean in and read that person's note. Their next move is a blend of the notes, weighted by how well each key matched their query. That is attention: query matches keys, and the matched values get blended. Query, key, value — the three come from every token.

Now the ops payoff. For any token already in the sequence, its key and its value never change once computed — the sign and the note are fixed. Only the query is new for the token being generated right now. So the model computes every past token's key and value once and keeps them. That store is the KV cache. It literally holds the keys and values, because those are the parts that get reused on every future step. You can watch the reuse pay off by generating a long answer and reading the steady per-token decode time — no slow-down as the sequence grows, because earlier keys and values are read from cache, not recomputed:

curl -s http://localhost:11434/api/generate -d '{
  "model": "qwen3:0.6b",
  "prompt": "List, with one short line each, ten everyday tips for saving electricity at home. /no_think",
  "stream": false,
  "think": false
}' | jq '{output_tokens: .eval_count,
         decode_ms: (.eval_duration/1e6 | floor),
         tpot_ms: (.eval_duration/.eval_count/1e6 | floor),
         tok_per_s: (.eval_count/(.eval_duration/1e9) | floor)}'

Expected output

{
  "output_tokens": 119,
  "decode_ms": 829,
  "tpot_ms": 6,
  "tok_per_s": 143
}

Your exact numbers will differ, but a steady tpot_ms (a few milliseconds per token) across a long answer is the cache working. If every token re-read the whole history from scratch, tpot_ms would climb as the sequence grew, and it does not. This is also why the KV cache is your capacity ceiling: it is the price you pay to keep decode flat.

2 — Temperature 0 is not "reproducible"​

Here is a mistake that bites eval pipelines. You want your golden eval suite to give the same score every run, so you set temperature: 0 and call it deterministic. Then you move the model from Ollama to vLLM, or upgrade a driver, and the scores shift by a point or two with no change to the prompts. You spend an afternoon hunting a bug that is not there.

First, the sampling knobs, plainly. After the model predicts the next token it does not get one answer — it gets a probability spread over the whole dictionary. The sampling parameters decide how you pick from that spread:

  • temperature — how flat or peaked the spread is. High temperature flattens it (more surprising, more varied). temperature: 0 means "always take the single most likely token", which is called greedy decoding.
  • top-p — keep only the smallest set of tokens whose probabilities add up to p, then pick from those. A dynamic shortlist.
  • top-k — keep only the k most likely tokens, then pick. A fixed-size shortlist.

Greedy decoding (temperature: 0) is deterministic on one engine, one build, one machine. Run the same greedy request twice on your host and you get the same text:

for i in 1 2; do
  curl -s http://localhost:11434/api/generate -d '{
    "model": "qwen3:0.6b",
    "prompt": "Name one benefit of drinking water regularly. Answer in one short sentence. /no_think",
    "stream": false,
    "think": false,
    "options": {"temperature": 0, "seed": 42}
  }' | jq -r '.response'
done

Expected output

Drinking water regularly helps maintain hydration and supports bodily functions.
Drinking water regularly helps maintain hydration and supports bodily functions.

Two identical lines (the exact sentence will differ on your run; what matters is that the two lines match each other). So far so good. But that guarantee is local. Across engines, the tiny floating-point differences in how each one runs the matrix maths can tip a near-tie between two candidate tokens the other way, and from that point the two answers diverge. Greedy removes the sampling randomness; it does not make two different engines compute bit-identical numbers. So temperature: 0 gives you repeatable scores on the same setup, which is what you want inside one CI job, but it is not a promise that Ollama and vLLM will score your eval set identically. When you compare engines in the serving module, pin the engine and build alongside the temperature, and treat a small cross-engine drift as expected, not as a regression. Frame your eval baselines as "on this engine, this build", and you will not chase ghosts.

3 — The chat template: the wrapper you never see​

When you send messages: [{"role": "user", "content": "hello"}], the model does not receive that JSON. It receives a single flat string, wrapped in special marker tokens that tell it where the system prompt ends, where the user turn starts, and where the assistant is expected to begin. That wrapper is the chat template, and it is baked into the model. Think of it as the printed form the counter clerk fills in from what you say: you speak plainly, but what goes into the system is a rigid form with boxes for "role" and "content" and a signature line. Get the form wrong and the request is misread, even though what you said was fine.

You can read the exact template shipped with the course model:

ollama show --template qwen3:0.6b

Expected output (the Go-template Ollama ships with the model; trimmed to the parts that matter here)

{{- range $i, $_ := .Messages }}
{{- $last := eq (len (slice $.Messages $i)) 1 -}}
{{- if eq .Role "user" }}<|im_start|>user
{{ .Content }}
{{- if and $.IsThinkSet (eq $i $lastUserIdx) }}
   {{- if $.Think -}}
      {{- " "}}/think
   {{- else -}}
      {{- " "}}/no_think
   {{- end -}}
{{- end }}<|im_end|>
{{ else if eq .Role "assistant" }}<|im_start|>assistant
{{ if (and $.IsThinkSet (and .Thinking (or $last (gt $i $lastUserIdx)))) -}}
<think>{{ .Thinking }}</think>
{{ end -}}
...
{{- if and (ne .Role "assistant") $last }}<|im_start|>assistant
{{ if and $.IsThinkSet (not $.Think) -}}
<think>

</think>

{{ end -}}

Look for the special markers (Qwen3 uses <|im_start|> and <|im_end|> around each role's turn) and for where the template opens the assistant's turn. Two ops facts fall straight out of this. First, this is where /no_think and the think parameter actually act — they toggle a branch in this template that either opens or suppresses a reasoning block before the answer. The control you used in the lab lives right here, in the wrapper. Second, this template is why a model has a fixed API contract: if a client sends the wrong markers, or you fine-tune on data that used a different template, the model gets a malformed form and quality quietly drops. When you package and fine-tune models later in the course, the chat template travels with the model as part of its contract, and matching it is not optional. A mismatched template is one of the most common and most invisible causes of "the fine-tuned model got worse".

4 — Thinking mode, one level down​

The lab measured what thinking mode costs. Here is the mechanism, so you can reason about it rather than just avoid it. Thinking mode does not change the model or add a separate reasoning engine. It flips the chat-template branch from section 3 so the model first generates a bounded block of reasoning tokens, then its answer. Those reasoning tokens are ordinary decode steps — same TPOT, same KV growth — there are just many more of them. Confirm the shape: with thinking on, the response carries a separate reasoning field and a much larger eval_count, while the visible answer stays short:

curl -s http://localhost:11434/api/generate -d '{
  "model": "qwen3:0.6b",
  "prompt": "Is 17 a prime number? Answer yes or no.",
  "stream": false,
  "think": true
}' | jq '{output_tokens: .eval_count, thinking_chars: (.thinking | length), answer: .response}'

Expected output

{
  "output_tokens": 457,
  "thinking_chars": 1304,
  "answer": "Yes, 17 is a prime number. A prime number is a number greater than 1 that has no divisors other than 1 and itself. When tested, 17 is not divisible by any number between 2 and 16, confirming that it is prime. \n\n**Answer:** Yes."
}

A large output_tokens, over a thousand thinking_chars of separate reasoning, and a short answer that carries the "yes". Your counts will differ, and this tiny model sometimes restates its reasoning in the answer too — but the shape holds: the bulk of the generation is the reasoning field, not the visible reply. This is why pinning think: false is a serving decision, not a style choice: with thinking on, your output token count per request swings wildly with the difficulty of the question, so your latency and your KV memory become unpredictable — the two things a production serving plan needs to be stable. You allow thinking only where the reasoning genuinely buys correctness, and you budget for its token blow-up when you do.

Where you will use this
  • The KV cache holds keys and values because those are the parts attention reuses on every step. Use it when: you are sizing a serving box or reading an out-of-memory kill on a model server — the KV growth per token is a real memory line, and long contexts or high concurrency are what fill it.
  • temperature: 0 is deterministic within one engine and build, not across them. Use it when: an eval score drifts a point after an engine swap or driver upgrade — pin engine and build in your eval baseline before you open a bug, and treat small cross-engine drift as expected.
  • The chat template is the hidden contract every message goes through, and it travels with the model. Use it when: a fine-tuned or newly-packaged model quietly gets worse — check the template matches the one it was trained and served with (ollama show --template) before you suspect the weights.
  • Thinking mode is extra decode tokens toggled by the template, not a separate engine. Use it when: latency or token cost per request is swinging unpredictably — check whether reasoning mode is on; pin it off for factual workloads so your capacity numbers stay stable.

Teardown​

Nothing here seeded persistent state, so there is nothing to remove. Ollama stays running as your host model server for M2. If you want to free the model's memory now, ollama stop qwen3:0.6b; otherwise it unloads itself after the keep-alive window. Leave the model pulled — the next module uses it.
