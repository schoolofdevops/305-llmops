Lab — See the Two Phases and What Each Token Costs

Resource path: 8 GB core — everything here runs

Every step in this lab runs on the 8 GB core path. No GPU, no cloud account, no container stack yet. The course model is qwen3:0.6b (about five hundred megabytes) and Ollama runs native on your machine. This is the Apple Silicon pattern, and we explain properly why in the serving module (M3). For now: Ollama on the host, nothing in a container.

Before you start

New here? Do the Setup section first: clone the labs repo, install the toolchain, and run the verification probe. All commands below run from the root of the labs repo (305-labs/). You need ollama, python3, uv, node, and curl responding.

Here is the on-call moment this lab is built for. Someone says the assistant "feels slow", the bill went up, and you have a capacity review on Friday. In this lab you make all three measurable. You count what you are billed on (tokens), you split one real request into its two phases and time each (prefill and decode), you see what "thinking mode" costs, and you watch the whole thing live on your own endpoint. By the end you can read a request the way you read a log line.

Step 1 — Preflight: Ollama up, model pulled​

The model runs on your host through Ollama. First confirm Ollama is answering, then make sure the course model is pulled. The lab's make up does both checks for you:

make -C labs/m1 up

Expected output

==> Checking Ollama is running at http://127.0.0.1:11434 ...
    Ollama is up.
==> Checking the course model qwen3:0.6b is pulled ...
    qwen3:0.6b is present. You are ready for the lab.

If make up tells you the model is missing, pull it now (about five hundred megabytes, one time):

ollama pull qwen3:0.6b

Expected output

pulling manifest
pulling <digest>... 100% ▕████████████████▏ 522 MB
verifying sha256 digest
writing manifest
success
The keep-alive clock

Ollama keeps a model loaded in memory for about five minutes after the last request, then unloads it to free RAM. The very first request after an idle gap pays a one-time load cost again. You will see this cost show up as a load_duration in the timing runs, and the X-Ray has a gauge for it. It is normal, not a bug.

Step 2 — Tokenizer playground: count what you pay for​

Tokens are the meter. This step makes the meter visible. First fetch the course model's real tokenizer (a small JSON file), then run the playground script over three samples:

curl -L -o labs/m1/tokenizer.json \
  https://huggingface.co/Qwen/Qwen3-0.6B/resolve/main/tokenizer.json

Expected output

  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
100 10.8M  100 10.8M    0     0  1407k      0  0:00:07  0:00:07 --:--:-- 1438k

The download size, speed, and elapsed time are point-in-time — yours will differ. What matters is that the file lands (a 100 in the final % Total column) and is a few megabytes, not a stray error page.

Now run the playground. uv run --with tokenizers pulls the one dependency into a throwaway environment, so there is no venv to manage:

uv run --with tokenizers labs/m1/tokens.py

Expected output

== Token counts — Qwen3-0.6B tokenizer (BPE) ==

sample      chars   tokens   chars/token
----------------------------------------
english        44        8          5.50
hindi          48       46          1.04
code           51       15          3.40

english, split into the pieces the model actually sees:
  'Why' | ' is' | ' my' | ' internet' | ' disconnect' | 'ing' | ' repeatedly' | '?'

Same idea, three ways to write it — three different token counts. Tokens are
what you are billed on and what fills the context window, not words or ideas.

== KV-cache memory — Qwen3-0.6B, FP16 KV ==

Per token: 2 (K and V) into 28 layers into 8 KV-heads
           into 128 head-dim into 2 bytes
         = 114,688 bytes/token (112.0 KiB/token)

context (tokens)      KV cache    per concurrent request
--------------------------------------------------------
             512        56.0 MiB                    56.0 MiB
           2,048       224.0 MiB                   224.0 MiB
           8,192       896.0 MiB                   896.0 MiB
          32,768      3584.0 MiB                  3584.0 MiB

This is the number you size a box against. Ten users each holding an 8k
context is ten into the 8k row — that memory is live the whole time they
stay connected. On a bigger model the per-token cost is far higher, and this
same table is how you decide how many concurrent users one GPU can hold.

Read the top table like an operator. The English line and the Hindi line ask the same everyday question, but Hindi costs several times the tokens, because this tokenizer's dictionary was built mostly on English text, so Hindi gets chopped into many small pieces. Your exact numbers will differ from run to run, but the shape holds: English is the cheapest, Hindi the dearest, code in between. If your product serves Hindi users, your token bill per message is higher than the English demo suggested. You just measured that instead of guessing it.

Now look at the english, split into the pieces line. Notice that disconnecting came back as two pieces, ' disconnect' and 'ing' — one word, two tokens. That is the model reading word-pieces, not words: the stem and the -ing suffix are separate dictionary entries. This is why token count never equals word count, and why you count tokens, not words, when you reason about cost.

Now the bottom table. That is the KV cache math from the lesson, printed for the real model. One token pins about a hundred and twelve kibibytes of memory. An eight-thousand-token context holds roughly nine hundred megabytes, and it stays held the whole time that request is alive. Ten users each at eight thousand tokens is ten into that row. This is the capacity number you will size a serving pod against later in the course.

Step 3 — The OpenAI contract, once​

Every model backend in this course speaks the same API: the OpenAI-compatible /v1/chat/completions. That is the whole point of the course design. When you swap Ollama for vLLM later, your client code does not change. Send one streaming request now so you have seen the shape. We give it the full tour in M2; here it is just the anchor.

curl -N http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3:0.6b",
    "stream": true,
    "messages": [{"role": "user", "content": "In one sentence, why is the sky blue? /no_think"}]
  }'

Expected output

data: {"id":"chatcmpl-354","object":"chat.completion.chunk","created":1784460570,"model":"qwen3:0.6b","system_fingerprint":"fp_ollama","choices":[{"index":0,"delta":{"role":"assistant","content":"","reasoning":"Okay"},"finish_reason":null}]}

data: {"id":"chatcmpl-354","object":"chat.completion.chunk","created":1784460570,"model":"qwen3:0.6b","system_fingerprint":"fp_ollama","choices":[{"index":0,"delta":{"role":"assistant","content":"","reasoning":", the"},"finish_reason":null}]}

... (many more "content":"" reasoning chunks — this endpoint streams the model's reasoning first; see the note below) ...

data: {"id":"chatcmpl-354","object":"chat.completion.chunk","created":1784460571,"model":"qwen3:0.6b","system_fingerprint":"fp_ollama","choices":[{"index":0,"delta":{"role":"assistant","content":"The"},"finish_reason":null}]}

data: {"id":"chatcmpl-354","object":"chat.completion.chunk","created":1784460571,"model":"qwen3:0.6b","system_fingerprint":"fp_ollama","choices":[{"index":0,"delta":{"role":"assistant","content":" sky"},"finish_reason":null}]}

data: {"id":"chatcmpl-354","object":"chat.completion.chunk","created":1784460571,"model":"qwen3:0.6b","system_fingerprint":"fp_ollama","choices":[{"index":0,"delta":{"role":"assistant","content":" appears"},"finish_reason":null}]}

data: {"id":"chatcmpl-354","object":"chat.completion.chunk","created":1784460571,"model":"qwen3:0.6b","system_fingerprint":"fp_ollama","choices":[{"index":0,"delta":{"role":"assistant","content":" blue"},"finish_reason":null}]}

... (many more content chunks — "The sky appears blue because of Rayleigh scattering ...") ...

data: {"id":"chatcmpl-354","object":"chat.completion.chunk","created":1784460571,"model":"qwen3:0.6b","system_fingerprint":"fp_ollama","choices":[{"index":0,"delta":{"role":"assistant","content":""},"finish_reason":"stop"}]}

data: [DONE]

The id, created, and system_fingerprint are point-in-time; yours will differ every run. Watch what streaming is: the answer arrives one chunk at a time, each delta.content a token or two, until a final chunk carries finish_reason: "stop" and the stream ends with [DONE]. That drip is the decode loop from the lesson, made visible over the wire. On this build the reasoning chunks ("content":"", "reasoning":"...") arrive first — the note below explains why — but the streaming shape is the same either way.

Reasoning may stream first on this endpoint

On this Ollama build (0.32.0) with qwen3:0.6b, the OpenAI-compatible route surfaces the model's reasoning in a separate delta.reasoning field, and /no_think in the message content does not reliably suppress it here — you may see a run of "content":"","reasoning":"..." chunks before the visible answer begins. That is a property of this endpoint's think handling on this build, not a mistake in your request. The authoritative think control this course relies on is the think parameter on the native /api/generate route, which you use in Steps 4 and 5 and which suppresses reasoning cleanly. The streaming shape — content chunks, then finish_reason: "stop", then [DONE] — is identical either way.

Step 4 — Split one request into prefill and decode​

This is the money shot. Ollama's own /api/generate endpoint returns per-phase timings on every request, so you can measure prefill and decode without any extra tooling. The fields you care about:

  • prompt_eval_count / prompt_eval_duration — the prefill phase (reading your prompt).
  • eval_count / eval_duration — the decode phase (writing the answer).
  • load_duration — the one-time model load, if this was the first request after idle.

All durations are in nanoseconds. You will run two requests that are opposites, and read the split.

Run A — prefill-heavy (long prompt, one-word answer)​

Send a long prompt (a runbook pasted several times) and force a one-word answer. Almost all the work is prefill:

PROMPT="$(printf 'Runbook: to restart the payments service, drain traffic, scale the deployment to zero, wait for pods to terminate, then scale back up and verify health checks pass. %.0s' {1..6})"
curl -s http://localhost:11434/api/generate -d "{
  \"model\": \"qwen3:0.6b\",
  \"prompt\": \"${PROMPT} Based only on the runbook above, answer in ONE word: what do you scale the deployment to first? /no_think\",
  \"stream\": false,
  \"think\": false
}" | jq '{prompt_tokens: .prompt_eval_count, output_tokens: .eval_count,
         prefill_ms: (.prompt_eval_duration/1e6 | floor),
         decode_ms: (.eval_duration/1e6 | floor),
         ttft_ms: (.prompt_eval_duration/1e6 | floor),
         tpot_ms: (.eval_duration/.eval_count/1e6 | floor),
         decode_tok_per_s: (.eval_count/(.eval_duration/1e9) | floor)}'

Expected output

{
  "prompt_tokens": 247,
  "output_tokens": 2,
  "prefill_ms": 161,
  "decode_ms": 6,
  "ttft_ms": 161,
  "tpot_ms": 3,
  "decode_tok_per_s": 303
}

Read it. Your exact numbers will differ by machine and by run, but the split is the point: prefill (about a hundred and sixty milliseconds here) dwarfs decode (about six). Nearly all the time went into reading the long prompt — here that is roughly a ninety-six to four split, prefill to decode. ttft_ms equals the prefill time and is high because the prompt is long. This is exactly your "slow for long questions" dashboard, reproduced on purpose.

Run B — decode-heavy (short prompt, long answer)​

Now flip it. A tiny prompt, but ask for a long answer. Almost all the work is decode:

curl -s http://localhost:11434/api/generate -d '{
  "model": "qwen3:0.6b",
  "prompt": "Explain why the sky is blue and the sunset reddish, in about 150 words. /no_think",
  "stream": false,
  "think": false
}' | jq '{prompt_tokens: .prompt_eval_count, output_tokens: .eval_count,
         prefill_ms: (.prompt_eval_duration/1e6 | floor),
         decode_ms: (.eval_duration/1e6 | floor),
         ttft_ms: (.prompt_eval_duration/1e6 | floor),
         tpot_ms: (.eval_duration/.eval_count/1e6 | floor),
         decode_tok_per_s: (.eval_count/(.eval_duration/1e9) | floor)}'

Expected output

{
  "prompt_tokens": 41,
  "output_tokens": 116,
  "prefill_ms": 27,
  "decode_ms": 839,
  "ttft_ms": 27,
  "tpot_ms": 7,
  "decode_tok_per_s": 138
}

Now the split has flipped: decode (over eight hundred milliseconds here) dwarfs prefill (a few tens of milliseconds). The prompt is tiny, so prefill is cheap; the answer is long, so decode is where the time goes. ttft_ms is comparatively low, so the first word shows up fast, but the total time is long because there are many decode steps. Notice tpot_ms stayed in the same few-milliseconds-per-token range across both runs — TPOT is a property of the model and machine, not of your prompt. What changed is how many decode steps ran.

What you just proved

The same model, same machine, two requests, opposite phase splits. "Slow to start" (Run A, high TTFT) and "slow to finish" (Run B, long decode) are different problems with different fixes. You size prompt length against TTFT and answer length against total decode time. You never again say just "it's slow".

Step 5 — What thinking mode costs​

Qwen3 can run in a "thinking" mode, where it writes out a chain of reasoning before its answer. That reasoning is real output tokens, and you pay for every one. Run the same one-word question twice, thinking off then on, and compare eval_count (the output tokens generated):

echo "think:false ->"
curl -s http://localhost:11434/api/generate -d '{
  "model": "qwen3:0.6b",
  "prompt": "What colour is a clear daytime sky? Answer in one word.",
  "stream": false,
  "think": false
}' | jq '{output_tokens: .eval_count, total_ms: (.total_duration/1e6 | floor), answer: .response}'

echo "think:true ->"
curl -s http://localhost:11434/api/generate -d '{
  "model": "qwen3:0.6b",
  "prompt": "What colour is a clear daytime sky? Answer in one word.",
  "stream": false,
  "think": true
}' | jq '{output_tokens: .eval_count, total_ms: (.total_duration/1e6 | floor), thinking_chars: (.thinking | length)}'

Expected output

think:false ->
{
  "output_tokens": 2,
  "total_ms": 280,
  "answer": "blue"
}
think:true ->
{
  "output_tokens": 176,
  "total_ms": 1131,
  "thinking_chars": 747
}

Both answers land on the same short colour (this run gave "blue" without thinking and "blue" with it). Your exact word may differ run to run — this is a tiny 0.6B model, and without thinking it will occasionally answer "sky" or capitalise differently — but the contrast is the point and it is stark: with thinking on, the model generated roughly ninety times the output tokens and took several times as long, all to reach a one-word answer. Those extra tokens are billed and they fill the KV cache. For genuinely hard reasoning tasks that trade is sometimes worth it. For a runbook assistant answering factual questions, it is pure waste, and it makes your latency and cost unpredictable from one request to the next. That is why this course pins non-thinking mode ("think": false on /api/generate). You measured the reason yourself rather than taking it on faith.

Step 6 — The X-Ray Tokens lens: watch it live​

You have read the numbers from the terminal. Now see them on a live board. The LLM Stack X-Ray is the course's one visualizer of your real stack — no simulation. It reads your own Ollama endpoint and grows one lens per module. The Tokens lens lands here in M1.

Start it (leave it running in this terminal; open a new one for anything else):

bash labs/tools/xray/serve.sh

Expected output

│
│  ollama  : http://127.0.0.1:11434
│            reachable ✓ {"version":"0.32.0"}
│
│  open    : http://127.0.0.1:8010/
│

Open http://127.0.0.1:8010/ in your browser. The page connects to your real Ollama through a same-origin proxy, so there is no CORS wall and no token to paste (this is the same trick kubectl proxy uses, and you will meet it again in the Kubernetes phase). Pick qwen3:0.6b in the model dropdown, then reproduce your two runs visually:

  • Prefill-heavy preset — paste a long prompt, ask for a one-word answer. Watch the phase-split bar sit almost entirely in prefill, and the TTFT gauge climb.
  • Decode-heavy preset — a short prompt, a long answer. Watch the bar flip to almost entirely decode, the token stream tick out one word at a time, and the tok/s gauge settle.
  • Tick the thinking mode box and re-run the one-word question. You will see italic thinking text stream first and a visibly longer TTFT, the Step 5 cost made visual.

Same three facts you measured in the terminal, now live from your own endpoint. This is the tool you will carry through the whole course; each module adds a lens.

Step 7 — Teardown​

Nothing here needs a heavy teardown. Stop the X-Ray server in its terminal:

Ctrl-C

Ollama keeps running (it is your host model server for M2 as well). The model unloads itself after about five minutes idle. If you want to free its memory right now:

ollama stop qwen3:0.6b

Expected output

(On success that command prints nothing visible — at most a few terminal control characters as its spinner clears.) The lab's make down says the same thing if you prefer:

make -C labs/m1 down

Expected output

Nothing to tear down for M1 — Ollama runs native and no containers were started.
The model unloads itself after the keep-alive window (about 5 minutes idle).
To free its memory now: ollama stop qwen3:0.6b
Troubleshooting
  • make up says Ollama is not reachable — Ollama is not running. Start it with ollama serve in a spare terminal, or launch the desktop app, then re-run. If it listens on a non-default address, the X-Ray takes OLLAMA_HOST_URL=http://host:port bash labs/tools/xray/serve.sh.
  • make up says the model is missing — pull it: ollama pull qwen3:0.6b. It is about five hundred megabytes, one time.
  • Port 8010 already in use — start the X-Ray on another port: PORT=8011 bash labs/tools/xray/serve.sh, then open that port.
  • think seems to change nothing — the think parameter only affects thinking-capable models. On qwen3:0.6b you will see the difference clearly. On a plain non-thinking model, the field is ignored and there is no reasoning to show.
  • First timed run has a huge total_ms — the model was cold and this request paid load_duration (the keep-alive window had expired). Run the same request again; the second one skips the load and shows the true prefill/decode split.
  • jq: command not found — install jq (brew install jq on macOS, apt-get install jq on Debian/Ubuntu). It is on the setup checklist.
  • Step 3 streams reasoning chunks even with /no_think — on Ollama 0.32.0 the OpenAI-compatible /v1/chat/completions route puts the model's reasoning in a separate delta.reasoning field, and /no_think in the message content does not reliably suppress it there. This is expected on this build and does not affect the streaming shape you are here to see. When you need reasoning genuinely off, use the native /api/generate route with "think": false (Steps 4 and 5), which suppresses it cleanly.
  • Step 5 think:false answer is not the word you expected — qwen3:0.6b is a tiny model. Without thinking it usually answers "blue" but will sometimes say "sky" or change capitalisation. That is normal for a half-billion-parameter model; the exhibit is the token-count blow-up between thinking off and on, not the exact word. Re-run it a couple of times and you will see the answer settle while the token gap stays large.
