Deep Dive — The Metric Families, Semconv Pinning, the Token Bill, and Sampling

The core lab gave you the two instruments, that is the Grafana wall and the Phoenix waterfall, and the habits to read them. This Part 2 goes under the hood of four things you have to get right when you run this in production, and the core lab could only point at: which metric families you actually watch and how they map across engines, how to build against a semantic convention that is still moving without your traces breaking, the exact path from a usage block to a per-request bill, and how to keep only the traces worth keeping under real traffic. Everything here runs against the M10 stack you already stood up. The checks live in labs/m10/deep-dive.checks.json.

The metric families — llamacpp and vLLM, read side by side​

The dashboard you provisioned reads llama.cpp's families. But OpsMate's serving engine is meant to swap (M3's rule: the endpoint contract holds, so the backend can change from Ollama to llama.cpp to vLLM without touching client code). When the engine swaps, the metric names change even though the concepts do not. And a dashboard that hardcodes one engine's names would go blank against another. So the skill is knowing the concept each panel measures, then finding that concept's family in whichever engine you are on.

With the model server running, list the families it actually exposes:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig port-forward service/opsmate-model 8080:8080 &
sleep 3
curl -s http://localhost:8080/metrics | grep -E '^# HELP llamacpp:' | head -20

Expected output (the llamacpp family list — names are stable within the engine, values are point-in-time; the engine exposes more families than the six the dashboard reads, so you will see timing and slot counters alongside them)

# HELP llamacpp:prompt_tokens_total Number of prompt tokens processed.
# HELP llamacpp:prompt_seconds_total Prompt process time
# HELP llamacpp:tokens_predicted_total Number of generation tokens processed.
# HELP llamacpp:tokens_predicted_seconds_total Predict process time
# HELP llamacpp:n_decode_total Total number of llama_decode() calls
# HELP llamacpp:n_tokens_max Largest observed n_tokens.
# HELP llamacpp:prompt_tokens_seconds Average prompt throughput in tokens/s.
# HELP llamacpp:predicted_tokens_seconds Average generation throughput in tokens/s.
# HELP llamacpp:requests_processing Number of requests processing.
# HELP llamacpp:requests_deferred Number of requests deferred.
# HELP llamacpp:n_busy_slots_per_decode Average number of busy slots per llama_decode() call

Here is the concept-to-family map across the two engines you are most likely to meet. Read it as "the panel measures X; on llama.cpp it is this family, on vLLM it is that one":

Concept (the panel)llama.cpp familyvLLM family (Prometheus)
Prompt tokens read (prefill volume)llamacpp:prompt_tokens_totalvllm:prompt_tokens_total
Answer tokens generated (decode volume)llamacpp:tokens_predicted_totalvllm:generation_tokens_total
Decode throughput (tokens/s)llamacpp:predicted_tokens_secondsderive: rate(vllm:generation_tokens_total[1m])
Requests in flightllamacpp:requests_processingvllm:num_requests_running
Requests queuedllamacpp:requests_deferredvllm:num_requests_waiting
KV-cache utilization(not exposed as a gauge)vllm:gpu_cache_usage_perc
Time to first tokenderive from prompt_seconds_totalvllm:time_to_first_token_seconds (histogram)

Two honest differences fall out of this table, and both matter when you move a dashboard:

  • vLLM exposes histograms. llama.cpp mostly exposes gauges and counters. vllm:time_to_first_token_seconds is a real histogram, so on vLLM you can query true percentiles (histogram_quantile(0.95, ...)), and the per-phase SLO from the lesson becomes a first-class query. On llama.cpp you approximate TTFT from the prompt-processing timing. When you get onto vLLM (a GPU cluster, M2's frontier), the SLO-per-phase discipline gets easier, because the engine hands you the histogram.
  • KV-cache utilization is a vLLM gauge with no llama.cpp equivalent. vllm:gpu_cache_usage_perc is the M1 KV-cache budget as a live percentage, which is the single most important saturation signal on a GPU server, and the one an autoscaler watches in M11. llama.cpp on CPU does not surface it the same way, which is why the M10 dashboard uses the queue (requests_deferred) as its saturation proxy instead. Keep in mind that the panel you rely on changes when the engine does.

So here is the rule to remember: build the dashboard around the concept, write down the family per engine, and expect the exact query to change on a swap. A dashboard is not portable for free. The metric model behind it is.

OTel GenAI semantic conventions — status, and how to pin against a moving target​

The core lab was honest that the attribute names on your spans (llm.token_count.*, openinference.span.kind, input.value) follow OpenInference conventions, and that a parallel OpenTelemetry GenAI semantic conventions effort is standardising this across the industry, and is still changing. Here is what that means in practice, and what to do about it.

Let me put it plainly. As of this course build, the OTel GenAI semantic conventions are not yet stable. They are marked experimental, and attribute names have changed between releases (for example, the gen_ai.* namespace and the exact token-count keys have moved). OpenInference (what Phoenix reads) is more settled, but is its own convention, not the OTel standard. So you are building on a surface that can shift under you. Ignoring it is not an option, because this is how the industry is coming together. But trusting it to stay put is not an option either.

The engineering answer is version pinning, and it is exactly what OpsMate's requirements.txt does. Confirm the pins:

grep -E 'opentelemetry' labs/opsmate/app/requirements.txt

Expected output (majors pinned; the minor floats within the major so it keeps building, but a breaking name change lives across a major bump you control)

opentelemetry-sdk>=1.27,<2
opentelemetry-exporter-otlp-proto-grpc>=1.27,<2
opentelemetry-instrumentation-fastapi>=0.48b0,<1

The strategy in three rules:

  1. Pin the major, float the minor. >=1.27,<2 means a breaking change (a renamed attribute, a new namespace) arrives only when you deliberately move to the next major, never silently on a pip install. Your traces keep their shape between deploys.
  2. Set the attribute names in one place (OpsMate sets them by hand in main.py, not scattered through the code) so that when you do adopt a new convention version, you change the names in one function, not in fifty call sites.
  3. Keep what your dashboards and queries read separate from what the standard calls it. If a Phoenix query or a cost aggregation keys off llm.token_count.total, and the standard renames it to gen_ai.usage.total_tokens, you change the emitting code and the query together, on your schedule. The pin is what buys you "on your schedule".

The takeaway is not "wait for the standard to settle down", because you would wait years and ship nothing. It is "adopt it, pin it, and keep the names in one place, so a rename is a one-line migration". That is the same discipline you apply to any fast-moving dependency. Telemetry conventions are just another one.

Per-request cost accounting — from usage block to the bill​

The core lab put llm.token_count.* on the generate span. This is where that becomes a real invoice you can defend to finance. The chain has three links, and each is a real object you can inspect.

Link 1, the usage block. Every completion the engine returns carries its own token count. Confirm it directly:

curl -s http://localhost:8080/v1/chat/completions -H 'Content-Type: application/json' \
  -d '{"model":"qwen3-0.6b","messages":[{"role":"user","content":"list two checks for a 503"}],"max_tokens":64}' \
  | jq '.usage'

Expected output (the three counts — prompt, completion, total; values are point-in-time, and llama.cpp adds a prompt_tokens_details block with its prefix-cache hit count)

{
  "completion_tokens": 64,
  "prompt_tokens": 17,
  "total_tokens": 81,
  "prompt_tokens_details": {
    "cached_tokens": 0
  }
}

Link 2, the attribute. The app lifts exactly those three numbers onto the LLM span (llm.token_count.prompt/completion/total, the code in main.py). Now the cost of the request is not in a log line you have to parse. It is a structured, queryable field on the trace.

Link 3, the aggregation. The bill is a sum over those attributes, grouped however you sliced the spans. The formula for one request, at a blended token rate, is simple:

cost(request) = (prompt_tokens + completion_tokens) / 1000 * price_per_1k_tokens

Work a real example to see the shape:

python3 -c '
prompt, completion = 412, 88
price_per_1k = 0.0002              # example blended rate, USD per 1k tokens
cost = (prompt + completion) / 1000 * price_per_1k
print(f"one request: {prompt+completion} tokens -> ${cost:.6f}")
print(f"1M such requests/month     -> ${cost*1_000_000:,.2f}")
'

Expected output (the per-request cost is tiny; the point is that it aggregates — a million requests is a real number)

one request: 500 tokens -> $0.000100
1M such requests/month     -> $100.00

Now the two things this makes possible that a monthly invoice cannot:

  • Attribution. Because the token count is a span attribute, you sum it grouped by whatever else is on the span, that is endpoint, user, prompt-length bucket. When the bill jumps thirty percent, you group last week's traces against this week's by prompt-length bucket and see that the long-prompt requests doubled. The invoice tells you the total moved. The traces tell you who and why. In Phoenix this is a query over the span attributes. In a warehouse (where you would export spans at scale) it is a GROUP BY.
  • Prevention. A per-request cost attribute lets you set an alert before the invoice. A request that burns eight thousand tokens is visible the moment it happens, not four weeks later. This is the raw material for the spend controls M12 puts at the gateway.

Here is the main idea to keep: the usage block is the meter reading, the span attribute is the meter reading written into your records, and the aggregation query is the bill. You built the first two in the lab. The third is a SUM.

Sampling production traffic — keep the traces worth keeping​

Everything above assumed you trace every request. At real traffic that is too much data and too much cost. Trace storage is not free, and a hundred percent of a million requests a day is mostly boring successful requests that look the same. So you sample: keep some traces, drop the rest. The question is which ones, and for LLM traffic the answer is different from ordinary web sampling.

There are two types of sampling, and the difference is when the keep-or-drop decision is made:

  • Head sampling decides at the start, before the request runs, that is a blind coin flip: "trace 5% of requests." Cheap and simple, and it is what a default OTel TraceIdRatioBased sampler does. Its weakness is exactly the LLM problem: it is blind to how the request turned out, so it would keep 5% of the boring requests and drop 95% of the interesting ones, including the slow, expensive, and failed ones you most wanted.
  • Tail sampling decides at the end, once the request is done and you know its duration, its token count, and whether it errored. Now you can keep the traces that matter: "keep every request over 5 seconds, every request over 4000 tokens, every error, and 1% of the rest." For LLM traffic this is almost always what you want, because the distribution is heavy-tailed: the eleven-second, eight thousand token request is rare, and it is the one you need the case file for.

The cost of tail sampling is that you must hold the spans until the request completes before deciding. That is why it runs in a collector (the OpenTelemetry Collector's tailsamplingprocessor) sitting between your app and Phoenix, buffering spans and applying keep-rules, rather than in the app itself. On the M10 lab stack you trace everything (traffic is tiny), but the production shape is: app → OTel Collector (tail-sampling policies) → trace backend. The policy you write there comes straight from the lesson: keep the slow phase and the expensive request, drop the boring ones, the same reason you read the tail, not the median.

So here is the rule to remember: head sampling for volume you do not care about, tail sampling for LLM traffic where the rare request is the whole point. A 5% head sample of OpsMate would throw away the incident you are on call for.

Where you will use this​

  • Moving a dashboard between engines (the metric-family map). The day OpsMate goes from CPU llama.cpp to GPU vLLM, or you inherit a service on a different engine, the dashboard would be blank until you re-map the families. You will reach for the concept-to-family table.
  • A telemetry upgrade breaks your traces (semconv pinning). An OTel or OpenInference bump renames an attribute and your cost query silently returns nulls. Pinned majors and names kept in one place turn that from an outage into a one-line migration you schedule.
  • Finance asks why the bill moved (per-request cost accounting). You group traces by prompt-length bucket and show the shift, before the invoice, with evidence.
  • Trace storage cost or volume becomes a problem (sampling). You put an OTel Collector in front of your backend and write a tail-sampling policy that keeps the slow, expensive, and errored requests and drops the boring bulk.

Each of these is a real Monday, not a hypothetical. And each is the production-grade version of a habit the core lab gave you.
