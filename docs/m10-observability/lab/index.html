Lab — See the Platform: Metrics, the Dashboard Wall, and the Trace Waterfall

Resource path: 8 GB core — everything required runs

Every required step runs on the 8 GB core path: the slim single-node KIND cluster from M8, the base model pod, the OpsMate app pod, and the observability stack (Prometheus, Grafana, Phoenix). The spike measured cluster + model + Prometheus + Phoenix at 2.25 GiB; Grafana adds ~300 MB and the app ~256 MiB — comfortably in budget inside the 7.7 GiB VM. You bring the Compose stack down first (one heavyweight stack at a time). Host Ollama must be running for embeddings (the app calls it, the M3/M4 pattern).

Before you start

All commands run from the root of the labs repo (305-labs/). You need docker, kind, kubectl, kit, curl, jq, and uv responding — check the Setup section if any are missing, and start Ollama (ollama serve or the desktop app) with nomic-embed-text pulled. You must have completed M6/M7 (they produced and pushed the signed opsmate/model:1.0.0 this lab serves and scrapes). Every kubectl carries --kubeconfig labs/opsmate/k8s/kubeconfig — the isolated-kubeconfig discipline from M8, not a typo.

This is the module where OpsMate becomes something you can see. You will replay the M8 cluster and model server, build and load the OTel-instrumented app onto the cluster and drive /ask through it, apply the observability stack and hit a designed Phoenix crash you read and fix, watch the Grafana dashboard wall move under the M3 load test, read a trace waterfall in Phoenix and the token cost of one request, make the P50 lie visible with mixed load, find your own prompt text in a trace and make the redaction decision, open the Traces lens on the X-Ray tool, and tear down. By the end you can answer the Monday questions — is it slow, why did the bill move, where did the eleven seconds go — with evidence.

Now the app joins the cluster. First look at what changed in the app since M4 — it is OTel-instrumented, and every bit of that is gated on one env var:

326:        _set_input(ask_span, q)

docker build -t opsmate-app:m10 labs/opsmate/app

The app manifest reaches host Ollama through the same M8 hostAliases pattern — but note: this is not a designed-wrong exhibit (M10's designed crash is the Phoenix one in Step 3). Step 3 — Apply the observability stack, and the designed Phoenix crash​

Open labs/opsmate/k8s/observability.yaml and read it top to bottom — it is three services in one file (Prometheus + its scrape ConfigMap, Grafana + its provisioned datasource and dashboard JSON, and Phoenix). Note the banner near the top: the Phoenix Deployment ships without the PHOENIX_PORT env on purpose. Apply it as shipped and watch Phoenix crash:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig apply -f labs/opsmate/k8s/observability.yaml
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig get pods -l app=phoenix -w

Expected output (Phoenix goes Error then CrashLoopBackOff — Prometheus and Grafana come up fine; Ctrl-C the watch once you see the restart count climb)

NAME                      READY   STATUS    RESTARTS      AGE
phoenix-7844c9fdf-kq5ss   0/1     Running   1 (14s ago)   33s
phoenix-7844c9fdf-kq5ss   0/1     Error     2 (42s ago)   81s

Read the crash log — this is the designed exhibit, and the log names the fix (it is a Python traceback ending in a ValueError from Phoenix's own config code):

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig logs -l app=phoenix --tail=6

Expected output (Phoenix cannot read the injected tcp://… string as its port — the ValueError explains exactly what Kubernetes did and how to fix it; the surrounding traceback lines are point-in-time)

  File "/phoenix/.venv/lib/python3.13/site-packages/phoenix/config.py", line 3164, in get_env_port
    raise ValueError(
    ...<5 lines>...
    )
ValueError: If you are deploying Phoenix with Kubernetes using a service named "phoenix", Kubernetes will automatically generate an environment variable `PHOENIX_PORT` of the form "tcp://<IP>:<PORT>" that is not the integer format Phoenix expects. To resolve this issue, explicitly set the `PHOENIX_PORT` environment variable to an integer value in your Kubernetes deployment configuration.

There it is in plain text. Because there is a Service named phoenix, Kubernetes injected PHOENIX_PORT=tcp://<ip>:6006 as a service-link env, and Phoenix reads PHOENIX_PORT as its own listen port. This is the lesson: service-link env injection is on by default, and it collides when a Service name matches a config var the app already uses. Fix it by uncommenting the env block in the Phoenix Deployment in observability.yaml — the lines marked # FIX::

          env:
            - name: PHOENIX_PORT
              value: "6006"

Re-apply and watch all three come up:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig apply -f labs/opsmate/k8s/observability.yaml
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig rollout status deployment phoenix --timeout=120s
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig get pods -l 'app in (prometheus,grafana,phoenix)'

Expected output (all three observability pods 1/1 Running; hashes point-in-time)

deployment "phoenix" successfully rolled out
NAME                          READY   STATUS    RESTARTS   AGE
grafana-75f64b4c9-lbl5x       1/1     Running   0          46m
phoenix-6f46474596-hj4pt      1/1     Running   0          34s
prometheus-77b69bb5ff-cn89p   1/1     Running   0          46m

Your explicit PHOENIX_PORT=6006 now wins over the injected service-link value, and Phoenix serves. The alternative fix — enableServiceLinks: false on the pod spec — stops the injection entirely; the Deep Dive discusses when to prefer each.

Step 4 — Prometheus: the scrape target is up, first queries​

Prometheus is now scraping the model server. Port-forward to it (one terminal) and confirm the target is up and the M3 llamacpp families are being collected:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig port-forward service/prometheus 9090:9090
curl -s --data-urlencode 'query=up{job="opsmate-model"}' 'http://localhost:9090/api/v1/query' | jq -r '.data.result[0].value[1]'
curl -s 'http://localhost:9090/api/v1/query?query=llamacpp:prompt_tokens_total' | jq -r '.data.result[0].value[1]'

Expected output (1 = the target is up; the token count is point-in-time — it reflects the /ask you already ran, so it is small and non-zero)

1
531
Why --data-urlencode on the first query

The first query contains a label matcher — {job="opsmate-model"} — whose {, ", and } are not URL-safe. Passed raw in the query string they reach Prometheus malformed and it returns an empty result (null), so let curl --data-urlencode encode them. The second query is a bare metric name with no special characters, so it works in the query string as-is.

up = 1 means Prometheus is reaching opsmate-model:8080/metrics on its 5-second interval — the M3 Engine lens, now cluster-scraped. llamacpp:prompt_tokens_total is a lifetime counter; yours will be whatever your requests have burned so far. These are the raw families the dashboard graphs.

Step 5 — The Grafana wall, and driving it under load​

Now the shared truth. Port-forward Grafana (one terminal) and open it:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig port-forward service/grafana 3000:3000

Open http://localhost:3000 in a browser. The dashboard OpsMate — Model Server (LLM signals) is already provisioned (login admin / admin if prompted; anonymous view is on so you may land straight on it). You will see five panels — decode tok/s, prompt tok/s, requests processing, requests deferred, and lifetime tokens — each with a description you can read by hovering its title. Right now the rates sit near zero because nothing is driving the engine. So drive it, with the M3 load test reused as-is. In another terminal, port-forward the model server and run the bounded load:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig port-forward service/opsmate-model 8080:8080
OPENAI_BASE_URL=http://localhost:8080/v1 MODEL=qwen3-0.6b REQUESTS=24 LEVELS=4,8,16 uv run labs/m3/loadtest.py

Expected output (throughput holds or climbs as concurrency rises; exact numbers are point-in-time and vary heavily by machine — on a busy CPU host the absolute req/s is far lower than a GPU box, but the shape is what matters)

Rising concurrency against ONE engine. Watch throughput and p95:
  concurrency=4   ok=24/24  throughput= 0.82 req/s  p50= 3.80s  p95= 6.43s  wall=29.15s
  concurrency=8   ok=24/24  throughput= 0.84 req/s  p50= 8.90s  p95=11.51s  wall=28.73s

The Grafana panels read these exact families off Prometheus. If you cannot watch the browser live, you can read the same numbers the panels graph straight from the query API (run these against your Prometheus port-forward on 9090 while — or just after — the load runs):

for m in llamacpp:requests_deferred llamacpp:requests_processing llamacpp:predicted_tokens_seconds llamacpp:prompt_tokens_seconds llamacpp:tokens_predicted_total; do
  printf '%s = ' "$m"
  curl -s "http://localhost:9090/api/v1/query?query=$m" | jq -r '.data.result[0].value[1] // "no-data"'
done

Expected output (values are point-in-time; deferred/processing are non-zero during load and settle to 0 after, the rates and lifetime total reflect the run)

llamacpp:requests_deferred = 0
llamacpp:requests_processing = 0
llamacpp:predicted_tokens_seconds = 11.5919
llamacpp:prompt_tokens_seconds = 27.1826
llamacpp:tokens_predicted_total = 4016

Now watch the wall while this runs (re-run the load test if it finished before you switched to the browser). The shape to read, live:

  • requests_deferred climbs as concurrency rises past what the engine can process at once — that is the queue forming. Requests are not slow, they are waiting.
  • decode tok/s holds roughly steady — the engine keeps generating at its rate because it batches; it does not collapse under load.
  • requests_processing pins at the engine's slot ceiling.

That is the whole metric lesson in one moving picture: the queue (deferred) grows while throughput (decode tok/s) holds. A single latency number would show only "p95 went up" and leave you guessing why. The wall shows you it is queueing, not a slow model — which is a completely different fix (add an engine, the M11 story) than "the model is slow" (change the model or the hardware).

Step 6 — The trace waterfall: where the time went, per request​

Now the case file. Port-forward Phoenix (one terminal) and open its UI:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig port-forward service/phoenix 6006:6006

Drive a few /ask requests through the app so there are fresh traces to read (use your app port-forward from Step 2 on 8001):

for q in "the payments api is throwing 500s" "how do I roll back a bad deploy" "a pod is in CrashLoopBackOff, what first"; do
  curl -s "http://localhost:8001/ask?q=$(printf '%s' "$q" | jq -sRr @uri)" >/dev/null
done
echo "3 asks sent"

Expected output

3 asks sent

Open http://localhost:6006 and click into the default project, then into one ask trace. You will see the waterfall: an ask span (CHAIN) with two children — retrieve (RETRIEVER) and generate (LLM) — laid out on a timeline. Read it the way you would read the eleven-second incident:

  • retrieve is a small fraction of the bar — the embed + vector lookup is cheap (well under a second; on a busy CPU host it may be a few hundred milliseconds, still tiny next to generate).
  • generate is nearly the whole bar — the model call is where the time goes (on this CPU host a single generate span ran ~18–28 seconds against retrieve's ~0.2s; on a GPU box both shrink, but the ratio holds).
  • Click the generate span and read its attributes: llm.token_count.prompt, llm.token_count.completion, llm.token_count.total — the token cost of this exact request (a few hundred tokens per answer here), lifted from the model's usage block.

You can confirm the same trace count from Phoenix's GraphQL API without the browser:

curl -s http://localhost:6006/graphql -H 'Content-Type: application/json' \
  -d '{"query":"{ projects { edges { node { name traceCount } } } }"}' | jq '.data.projects.edges[].node'

Expected output (the project holds the traces you drove; traceCount is point-in-time)

{
  "name": "default",
  "traceCount": 4
}

This is the answer to "where did the eleven seconds go" made mechanical: not a guess from a log, a timeline from the request itself, with the cost attached. The retrieve-was-fine, generate-was-slow reading is right there in the bar widths.

Step 7 — The P50 lie: mixed load, one median, two truths​

Now make the P50 lie from the lesson real. Send a mixed load — a batch of short questions and a few long ones (a pasted incident timeline) — and compare the overall median against the per-request reality. Run this small mixed driver against the app (your 8001 port-forward):

python3 - <<'PY'
import time, urllib.parse, urllib.request
short = "what is the rollback command"
# The long prompt is a genuine long prefill, but kept under the model server's
# 2048-token context (the app also prepends the 3 retrieved runbook chunks, so
# leave room) — enough to be visibly slow, not so long the engine rejects it.
long  = "here is a long incident timeline: " + ("the service began returning 503s at 02:14 and " * 20) + " what is the most likely root cause"
reqs = [short]*12 + [long]*3
lat = []
for q in reqs:
    url = "http://localhost:8001/ask?q=" + urllib.parse.quote(q)
    t = time.perf_counter()
    urllib.request.urlopen(url, timeout=240).read()
    lat.append((len(q) > 200, time.perf_counter() - t))   # (is_long, seconds)
allv = sorted(d for _, d in lat)
p50 = allv[len(allv)//2]
longs = [d for is_long, d in lat if is_long]
print(f"overall p50 (all 15 requests): {p50:5.2f}s")
print(f"long-request latencies       : {', '.join(f'{d:.2f}s' for d in longs)}")
PY

Expected output (numbers are point-in-time and scale with your hardware — on a fast box the shorts are ~1s and the median is ~1.3s; on a busy CPU host everything is slower, as below. The relationship is the lesson — the median sits among the short requests while the long ones are several times slower)

overall p50 (all 15 requests): 13.99s
long-request latencies       : 52.01s, 49.69s, 54.59s

Read what happened. The overall P50 lands among the 12 short requests, because the median of 15 requests ignores the 3 long ones entirely. Whatever your median is, a single-number SLO measured against it looks fine — on a fast box the P50 is ~1.3s and "P50 under 2s" is flat green; even here at ~14s the median hides the real problem. Meanwhile every long request — the senior-engineer-pastes-an-incident case, the one that matters most — is running 3–4× the median (here ~50 seconds) and blowing any reasonable target. The median could not see them; they are in the tail. Now open the Grafana wall during a long request and read the prompt tok/s panel spike: the long prompt is a long prefill, which is exactly where those seconds went. The per-phase signal explains the tail the P50 hid. This is why you never set a model SLO as one number.

Step 8 — Log hygiene: find your own prompt in a trace, then decide​

Go back to Phoenix (http://localhost:6006), open any ask trace, and click the root ask span. Read its input.value attribute.

What you will see: your exact question, stored verbatim as a span attribute — for example the payments api is throwing 500s, most likely cause?. For OpsMate that is incident text. For a medical, legal, or HR assistant that same field would hold something you are not allowed to store.

This is the decision the lesson set up, and now you make it. You have two honest options:

  1. Keep it. You are debugging answer quality, the data is not sensitive, and access to Phoenix is controlled. The full input is exactly what you need to reproduce a bad answer. This is a legitimate choice — made deliberately.
  2. Redact it. The app has a built-in toggle, OTEL_REDACT_INPUT: when true, the span records [redacted] in place of the prompt text — the shape of the request is still traced (token counts, durations, source count), the content is not. Turn it on and re-ask:
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig set env deployment/opsmate-app OTEL_REDACT_INPUT=true
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig rollout status deployment opsmate-app --timeout=120s
# Ctrl-C the Step-2 app port-forward FIRST — the rollout replaces the pod, but the old
# forward stays bound to the dead pod and silently returns nothing. Then re-establish:, then:
curl -s "http://localhost:8001/ask?q=this%20prompt%20should%20not%20appear%20in%20the%20trace" >/dev/null
echo "redacted ask sent — check the newest ask span's input.value in Phoenix"

Expected output

redacted ask sent — check the newest ask span's input.value in Phoenix

Open the newest ask trace in Phoenix: the span is still there, the token counts and durations are still there, but input.value now reads [redacted] instead of your text. The register recorded the visit, not the confession. Either choice is defensible; making it blindly is not. M12 automates the harder version of this — detecting PII and injection at the gateway — but the decision starts here, with you seeing the data in your own telemetry.

The redaction is a shape filter, not encryption

Redacting input.value drops the content from the trace. It does not touch the request in flight or the model's own logs — it is a telemetry-hygiene control, one layer. Real PII protection is defense in depth (M12). The point of this step is the habit: look at what your traces store, and decide, rather than defaulting.

Step 9 — The Traces lens on the X-Ray tool​

The X-Ray grew its M10 lens. The lens reads Phoenix through the tool's same-origin proxy, which expects the forward on 16006 (the tool's own default) — restart your Phoenix forward on that port, then start the tool and open the Traces tab:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig port-forward svc/phoenix 16006:6006 &
bash labs/tools/xray/serve.sh
# open http://127.0.0.1:8010/ → Traces

The left panel lists your recent traces — probe noise filtered out, each row carrying the root span's name, its latency, and the LLM span's token count (the per-request bill, right in the list). Click an ask trace: the waterfall draws every span as a bar on a shared timeline — ask [chain] spanning the whole request, retrieve [retriever] a thin fast bar, generate [llm] the wide slow one with its token count. This is the case file from the lesson, drawn live from your own stack, in the same visual language as every lens before it.

Everything the lens renders comes from Phoenix's GraphQL. Read the same inventory yourself, because this is the cross-check when the picture surprises you:

curl -s http://localhost:16006/graphql -H 'Content-Type: application/json' \
  -d '{"query":"{ projects { edges { node { name traceCount } } } }"}' | jq '.data.projects.edges[].node'

What you get: the default project and its live traceCount — drive a few more /ask requests and both the count and the lens list climb. Stop the tool with Ctrl-C when done.

Step 10 — Teardown​

Tear the cluster down. The registry and its kits persist, and the manifests plus the dashboard JSON stay in labs/ — they are the observability surface M11 builds autoscaling on:

make -C labs/opsmate k8s-down

Expected output

==> Deleting the KIND cluster 'opsmate' ...
Deleting cluster "opsmate" ...
Deleted nodes: ["opsmate-control-plane"]
    Cluster gone. The registry and its data on ./data/zot PERSIST — the
    signed kits survive, so the next module re-creates the cluster and
    pulls the same 1.0.0 artifact. (Cluster create is ~30s — cheap by design.)

Stop any port-forwards with Ctrl-C. Confirm the manifests survive teardown and the cluster is gone:

test -s labs/opsmate/k8s/observability.yaml && echo "observability manifest kept"
test -s labs/opsmate/k8s/app.yaml && echo "app manifest kept"
kind get clusters | grep -q opsmate && echo "cluster still up?!" || echo "cluster gone — teardown clean"

Expected output

observability manifest kept
app manifest kept
cluster gone — teardown clean

What M11 reuses: the app + observability manifests, the provisioned dashboard, and the requests_deferred gauge you learned to read — that gauge is the exact signal the M11 autoscaler acts on. OpsMate is now observable; the next module lets the observation drive the system.

Troubleshooting
  • Phoenix CrashLoopBackOff, log says PHOENIX_PORT was set to 'tcp://...' — the designed Step 3 exhibit (or you hit it for real). A Service named phoenix injects a service-link env PHOENIX_PORT that collides with Phoenix's own config. Uncomment the env: PHOENIX_PORT: "6006" block in observability.yaml's Phoenix Deployment (the # FIX: lines) and re-apply, so your explicit value wins. The alternative is enableServiceLinks: false on the pod spec, which stops all service-link injection.
  • kind load docker-image errors with a containerd digest / NotFound — the known load-tool flake (M8 spike). kind load imports with --all-platforms, which trips on a multi-arch image's attestation manifest whose digest is not in your single-platform local store. Retry the kind load once. If it persists, load a single-platform export straight into the node's containerd, skipping --all-platforms: docker save <image> -o /tmp/img.tar then docker exec -i opsmate-control-plane ctr --namespace=k8s.io images import --digests --snapshotter=overlayfs - < /tmp/img.tar. The image content is fine; only the --all-platforms step flakes.
  • Phoenix stuck in ContainerCreating for many minutes — the manifest pins arizephoenix/phoenix:version-7.9.0; if it is not already cached, the kubelet pulls ~300 MB, which is slow on a constrained connection. It is pulling, not stuck — give it time, or pre-pull it on the host (docker pull --platform linux/arm64 arizephoenix/phoenix:version-7.9.0) and load it into the node with the ctr images import path above so the kubelet finds it present (imagePullPolicy is IfNotPresent for a pinned tag).
  • /ask returns a 500 on a very long question, model log says 400 Bad Request / context exceeded — the model server runs with a 2048-token context (the M1 KV budget), and a long pasted prompt plus the 3 retrieved runbook chunks can exceed it, so the engine rejects the completion and the app surfaces a 500. This is expected for an over-long prompt on a small-context CPU model — the Step 7 driver keeps its long prompt bounded for exactly this reason. In production you would truncate or chunk the input before the model call; here, keep long prompts under the context and the request succeeds (slowly — that slowness is the point of Step 7).
  • App pod CrashLoopBackOff or /ask returns a 500 about embeddings — the app cannot reach host Ollama. The hostAliases IP in app.yaml must match your host: run docker exec opsmate-control-plane getent hosts host.docker.internal, set that IP, re-apply. Also confirm Ollama is running on the host with nomic-embed-text pulled (ollama list). Unlike the M8/M9 exhibits, this is NOT a designed-wrong placeholder — it just needs your real IP.
  • Ingest Job never completes (kubectl get job opsmate-ingest shows 0/1) — the app is not becoming ready, or embeddings are failing (see the previous note). Check kubectl logs job/opsmate-ingest (it prints "waiting for opsmate-app to be ready") and kubectl logs deployment/opsmate-app. The Job retries (backoffLimit: 6); fix the app's Ollama reach and it completes on a later attempt, or re-apply app.yaml to recreate it.
  • Prometheus target up = 0 — Prometheus cannot reach opsmate-model:8080. Confirm the model pod is 1/1 Running and its Service exists (kubectl get svc opsmate-model). The scrape uses the Service DNS name, so a not-ready model pod shows as a down target until it loads (~40s).
  • Grafana dashboard is empty / "No data" — the datasource provisioned but Prometheus has no samples yet, or the model server is idle. Drive the load test (Step 5) so the token rates are non-zero; the panels read live, so an idle engine shows flat lines, not an error. If the dashboard itself is missing, check kubectl logs deployment/grafana for a provisioning error and confirm the three grafana ConfigMaps applied.
  • Grafana first login loops on "change password" — anonymous view is enabled, so you can skip the login entirely for read-only viewing. If you did log in as admin/admin, click "skip" on the change-password prompt; the lab does not need a changed password.
  • Port-forward drops between steps — each kubectl port-forward is tied to one pod; a rollout restart, a pod restart, or closing the terminal ends it. Re-run the specific port-forward command. Keep each forward in its own terminal (learner-normal); the lab assumes one terminal per forward.
  • Phoenix shows no traces / traceCount: 0 — the app's OTEL_EXPORTER_OTLP_ENDPOINT is not set, or Phoenix was not up when you drove /ask. Confirm kubectl get deployment opsmate-app -o yaml | grep OTEL shows the endpoint, that Phoenix is 1/1 Running, then re-drive a few /ask requests — traces are batched and appear within a few seconds.
  • make k8s-up preflight refuses to start — under ~3 GB free the KIND phase is refused. The M10 stack (cluster + model + app + prom + grafana + phoenix) is the heaviest of the course so far (~2.5 GiB); close the Compose stack, browsers, and other containers. One heavyweight stack at a time.
