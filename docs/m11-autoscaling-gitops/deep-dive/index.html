Deep Dive — The Starvation Post-Mortem, KEDA Internals, and Reading a Workflow's True Status

The core lab had you cap the training pod, drain serving before you ran it, and read a workflow's status carefully. It told you to do those things. This Part 2 tells you why each one is load-bearing, by walking the three walls the module's spike actually hit before the lab was safe to ship: a training pod that took the cluster's control plane down with it, the machinery KEDA quietly runs under the ScaledObject you applied, and a workflow that reported failure while its work had already succeeded. Every number here is from a real run on the 8 GB path, marked provisional until the lab-runner re-captures it. The checks live in labs/m11/deep-dive.checks.json.

The starvation post-mortem — why the CPU cap is control-plane protection, not pod hygiene​

Start with the analogy, because it is the whole mental model. Your cluster node is a house, and the control plane — the kube-apiserver, etcd, the scheduler, the kubelet — is the house's own wiring and fuse box. Your workload pods are appliances plugged into that wiring. Now plug in one appliance that draws unlimited current: a space heater with no fuse. It does not just run hot. It browns out the whole house, and the first thing to flicker is the fuse box itself — the very thing you would use to cut the power. That is what an uncapped training pod does to a shared-node Kubernetes cluster, and the recovery is genuinely counterintuitive, so it is worth seeing the failure in full.

Here is what happened in the spike. The training pod was submitted with a memory limit but no CPU limit. fp32 LoRA training on CPU pins every core it can reach. Node CPU went to roughly 247% (on a multi-core node, well past saturation), and the training process was winning the scheduler's fight for cycles against everything else on the node — including the control plane.

The failure cascaded in the order that matters:

Read the cascade as a break-glass ladder, and notice that each rung exists precisely because the rung above it depends on something the starvation broke:

  1. kubectl scale / kubectl delete — dead. This is the trap. Your instinct under load is to kubectl scale deployment/... --replicas=0 the offending workload. But kubectl is a client that talks to the kube-apiserver, and the apiserver is the process you just starved. Its TLS handshakes were timing out, so every kubectl call hung. You cannot fix a starved control plane with the tool that depends on the control plane.

  2. crictl on the node — one layer down. crictl talks to the container runtime (containerd) directly, bypassing the apiserver. In a milder incident this is your recovery rung. Under this much pressure, even crictl stop returned DeadlineExceeded — the runtime itself was not getting enough CPU to service the stop request in time.

  3. pkill -9 on the node — the floor. The break-glass of last resort was to exec onto the node and pkill -9 the training process by name. No API, no runtime API, just the kernel killing a PID. It worked because it is the one operation that depends on nothing the starvation had broken.

The lesson under the incident

You do not recover a starved control plane by asking the control plane to help. Each rung of the ladder — kubectl, then crictl, then pkill — bypasses a dependency the rung above it needs. Know the ladder before you need it, because the moment you need it, the tool you would normally reach for is the one that is down.

requests vs limits, re-read for a batch pod on a shared node​

Most engineers set CPU requests and limits as a scheduling formality and move on. For a training pod on a control-plane-sharing node, that distinction is the difference between a governable cluster and a brick. Read them for what they actually are:

  • requests is the scheduler's reservation — the number it uses to decide the pod fits on the node. It is scheduling math. It does not throttle anything at runtime.
  • limits is the hard ceiling the kernel enforces — the Linux CFS (Completely Fair Scheduler) throttles the container's cgroup so it cannot burn more than its share, no matter how many cores it tries to grab.

For an ordinary web pod you tune the limit for the pod's own health. For a batch pod on a shared node, the CPU limit is not about the training pod at all — it is about keeping the node governable. limits.cpu: "2" says: this pod may have two cores' worth of throttled time and not a cycle more, so the apiserver, etcd, and kubelet always have cycles left to keep the node answerable. The fix that made the clean run possible was exactly that cap plus draining serving first:

        resources:
          requests:
            cpu: "1"
            memory: "2Gi"
          limits:
            cpu: "2"          # the control-plane protection — CFS throttles the
            memory: "4Gi"     # cgroup here so the apiserver always has cycles left

And the ordering matters as much as the cap. The lab drains serving before submitting the workflow — KEDA autoscaling.keda.sh/paused-replicas: "0" pins the model deployment to zero, and the observability deployments scale to zero — so the training pod is the only heavyweight tenant on the node while it runs. Cap plus drain: the apiserver stayed responsive throughout the spike's clean run.

Why a memory limit alone was not enough

The spike's first attempt already had a memory limit — that is why the earlier walls were OOMKills, not starvation. Memory limits protect against one failure mode: the kernel OOM-kills the offending pod, cleanly. CPU has no equivalent "kill the offender" reflex — an uncapped pod just takes cycles, quietly, from everything including the control plane. That asymmetry is why the CPU limit is the one that keeps the cluster recoverable.

KEDA internals — the machinery under the ScaledObject​

In the lab you applied a ScaledObject and a keda-hpa-opsmate-model appeared. That is not KEDA "being an HPA" — it is KEDA running a small metrics pipeline you should be able to draw, because when a scale decision surprises you, this is the path you debug.

Walk it once and the abstraction stops being magic:

  • KEDA registers as an external metrics API server. It installs an APIService for external.metrics.k8s.io, so the Kubernetes API aggregation layer routes external-metric queries to KEDA's metrics-server. This is why KEDA needs no prometheus-adapter and no PromQL recording-rule wiring — it is the adapter, purpose-built.
  • The generated HPA is a real object. keda-hpa-opsmate-model is an ordinary autoscaling/v2 HorizontalPodAutoscaler you can kubectl get hpa and inspect. Its metric source is type: External, pointing at the series KEDA exposes. KEDA owns it — editing it by hand fights the operator, which reconciles your change away. You change scaling behavior on the ScaledObject, never on the generated HPA.
  • The HPA does the arithmetic you already know. It asks external.metrics.k8s.io for the current value, KEDA answers by running sum(llamacpp:requests_deferred) against Prometheus, and the HPA compares it to the threshold. In the spike, deferred hit 12 against a threshold of 2, so the HPA read 12/2 and scaled out.
NAME                       REFERENCE                  TARGETS   MINPODS   MAXPODS   REPLICAS
keda-hpa-opsmate-model     Deployment/opsmate-model   12/2      1         2         2

paused-replicas and the scale-to-zero knobs​

Two parts of the ScaledObject you used without dissecting:

  • autoscaling.keda.sh/paused-replicas: "0" — an annotation that tells KEDA to stop reconciling and pin the target to a fixed replica count (0 here). This is the lab's one-heavyweight lever: setting it to "0" drains the model deployment cleanly and, crucially, stops KEDA from scaling it back up the moment the training pod makes the queue metric interesting. Remove the annotation and KEDA resumes. It is a pause button, not a delete.
  • pollingInterval and cooldownPeriod — the scale-to-zero knobs. pollingInterval is how often KEDA queries Prometheus; cooldownPeriod is how long KEDA waits after the last trigger fired before scaling the target to zero. KEDA will warn that these are irrelevant when minReplicaCount >= 1, and the reason is exact: they only govern the 0↔1 transition. Once your floor is 1, KEDA never scales to zero, so "how long before we go to zero" is a question that never gets asked. They matter only if you set minReplicaCount: 0 (or idleReplicaCount: 0) — which, for an interactive model server, you should not, because cold start is a model load measured in minutes.
The rule for model servers

Scale-to-zero is a batch / rare-endpoint pattern, not an interactive one. For an interactive model server keep the floor at 1 and treat pollingInterval/cooldownPeriod as informational — they do nothing at minReplicaCount: 1. If you see KEDA warn about them, it is telling you those knobs are dead weight in your config, not that something is broken.

Reading a workflow's true status — phase versus containerStatuses​

The last wall is the subtlest, and it is a habit you will use far beyond Argo Workflows. Analogy first: a courier's tracking board shows "Exception" on your package. You brace for the worst — but the exception is that the proof-of-delivery paperwork failed to sync back to the system. The package itself was already on the doorstep. The board is reporting the courier's bookkeeping, not the delivery. Read the wrong field and you re-ship a package that already arrived.

That is precisely what happened in the spike. The training workflow's .status.phase read Error, while the workflow's main container had exited Completed with code 0. The training had genuinely succeeded — loss went down, the adapter was written — but the phase lied.

The mechanism: Argo Workflows runs an executor alongside your main container that writes results (the workflowtaskresults custom resources) back to the API. The chart's default argo:default ServiceAccount had no RBAC for that:

Error (exit code 0): workflowtaskresults.argoproj.io is forbidden:
  User "system:serviceaccount:argo:default" cannot create resource
  "workflowtaskresults" in API group "argoproj.io"

The main container completed 0; the executor could not report that fact back, so the workflow controller marked the whole thing Error. The fix is a Role and RoleBinding granting workflowtaskresults create/patch — the rbac-executor.yaml the lab applies:

rules:
  - apiGroups: ["argoproj.io"]
    resources: ["workflowtaskresults"]
    verbs: ["create", "patch"]   # the executor writes results back through these

The transferable habit is this: when a wrapper reports a job's status, verify against the job's own exit signal before you trust the wrapper. For a pod, that means reading containerStatuses — the actual per-container exit codes — not only .status.phase:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig get pod <workflow-pod> \
  -o jsonpath='{.status.containerStatuses[?(@.name=="main")].state.terminated.exitCode}'

An exit code of 0 from the main container is ground truth about whether the training ran, regardless of what the phase says. Once the RBAC was in place, the two agreed: after the fix the workflow phase read Succeeded, the run did its 2 steps with the loss moving between them (the exact values and direction are noise at two steps on eight samples — the point is the steps executed), and the LoRA adapter safetensors was written in-cluster.

Where you will use this​

None of this is exotic. Each section maps to a moment you will hit operating a platform that shares nodes between serving and batch work:

  • A batch job takes the cluster down and kubectl stops answering. Reach for the break-glass ladder — crictl, then pkill on the node — instead of hammering a dead apiserver, and afterward add the missing CPU limit so it cannot recur. This is not specific to training: any uncapped CPU-hungry batch pod (a large ingest, a re-embedding job, a data migration) on a control-plane-sharing node is the same hazard.
  • An autoscaler scales at the wrong time, or not at all. Walk the KEDA path — ScaledObject → generated HPA → external.metrics.k8s.io → Prometheus query — and check each hop. kubectl get hpa shows the current/target the HPA actually read; query Prometheus directly to confirm the series; check the ScaledObject for a stray paused-replicas annotation someone left set.
  • A pipeline reports failure but the work looks done. Before you re-run an expensive job, read the main container's containerStatuses exit code. A wrapper's status is bookkeeping; the exit code is ground truth. This saves you from re-running a long training job because a results sidecar hit an RBAC wall.
  • You are sizing a shared node. Set CPU limits on every batch tenant as control-plane protection, and drain interactive serving (pause the autoscaler, scale observability down) before you let a heavyweight batch job run — one heavyweight tenant at a time is a scheduling discipline, not just an 8 GB-path constraint.
