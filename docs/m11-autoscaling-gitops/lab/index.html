Lab — Operate the Platform: Autoscale on Queue Depth, Promote Through Git, Train Under Guardrails

Resource path: 8 GB core — everything required runs; full-fidelity training is a 16 GB note

Every required step runs on the 8 GB core path: the slim single-node KIND cluster (recreated this module with a base-model mount), the model server, the M10 observability stack, KEDA, Argo CD (slim), gitea, and Argo Workflows (controller-only). The heavy pieces never run at once — you drive the autoscale cycle with serving up, then drain serving before the training workflow (one heavyweight at a time). The in-cluster training is a smoke profile (2 steps) that proves the pipeline runs; a real fine-tune is the 16 GB / host path you used in M6, not this shared-node job.

Before you start

All commands run from the root of the labs repo (305-labs/). You need docker, kind, kubectl, helm, kit, curl, jq, and git responding — check the Setup section if any are missing. You must have completed M6/M7 (they produced and pushed the signed opsmate/model:1.0.0, and the base weights under labs/opsmate/models/qwen3-0.6b that the training workflow fine-tunes). Every kubectl and helm carries an exported KUBECONFIG pointing at the isolated kubeconfig — the M8 discipline, so your default context is never touched. This module recreates the cluster so the base-model mount takes effect (see Step 1).

This is the operations module. OpsMate is observable (M10); now you make the observation drive the system. You will grow the cluster config with the base-model mount and recreate the cluster, replay the model + observability stack, install KEDA and autoscale the model server on queue depth — watching it go 1→2→1 under load. Then you stand up a GitOps control plane: Argo CD (slim) watching an in-cluster gitea repo, and promote a model version through a pull request — where you hit two designed exhibits (the presence-cache serving old bytes, and a per-kit filename crash) and fix both through git. You roll the promotion back with git revert. Finally you run the fine-tune as a governed Argo Workflows step under a CPU cap, having drained serving first — the guardrail that keeps a training pod from starving the control plane. By the end, OpsMate is v2.5: autoscaled on a real signal, promoted and rolled back through git, and training on a pipeline with real guardrails.

Set the kubeconfig once so every command in this lab inherits it:

export KUBECONFIG=labs/opsmate/k8s/kubeconfig

Step 1 — Grow the cluster config with the base-model mount, recreate, replay the stack​

The training workflow later in this lab fine-tunes the base model inside the cluster, so the node needs the base weights on its filesystem. You add that as a kind extraMount — and because extraMounts are read only at cluster-create, you recreate the cluster this module (the established KIND-phase design: cluster create is ~30s, cheap by design). Look at what grew in labs/opsmate/k8s/kind-config.yaml — the new extraMounts block under the node mounts ./models (the base Qwen3-0.6B) to /models:

grep -nA4 'extraMounts:' labs/opsmate/k8s/kind-config.yaml

Expected output (the models dir is mounted read-only into the node)

17:    extraMounts:
18:      - hostPath: ./models
19:        containerPath: /models
20:        readOnly: true

Bring the Compose stack down, recreate the cluster (picking up the mount), and confirm the base weights are visible on the node:

make -C labs/opsmate down
make -C labs/opsmate k8s-down
make -C labs/opsmate k8s-up
docker exec opsmate-control-plane ls /models/qwen3-0.6b/model.safetensors

Expected output (the base model is mounted into the node — this is what the training pod will read; the preflight/create lines are point-in-time)

/models/qwen3-0.6b/model.safetensors

Why Prometheus is the only observability pod that must be up for the autoscale cycle

KEDA reads llamacpp:requests_deferred from Prometheus. Grafana and Phoenix are the human-facing surfaces from M10 — nice to watch, but the autoscaler does not need them. Keeping only Prometheus up here also leaves the most headroom for the second model replica the load test will trigger.

Step 3 — Drive load, watch 1 → 2 → 1 on queue depth​

Now make the queue form. Port-forward the model server in one terminal:

kubectl port-forward service/opsmate-model 8080:8080

In a second terminal, watch the HPA and replicas live:

kubectl get hpa keda-hpa-opsmate-model -w

In a third terminal, drive the M3 load test — a gentler profile than the spike (concurrency 8, not 16: a single replica saturates hard at 16, and the teaching object is the deferred gauge climbing past the threshold, not throughput):

OPENAI_BASE_URL=http://localhost:8080/v1 MODEL=qwen3-0.6b REQUESTS=24 LEVELS=8 uv run labs/m3/loadtest.py

Expected output (throughput and latency are point-in-time and machine-dependent; the point is that concurrency 8 against one engine builds a queue)

Rising concurrency against ONE engine. Watch throughput and p95:
  concurrency=8   ok=24/24  throughput= 0.84 req/s  p50= 8.90s  p95=11.51s  wall=28.73s

Read the shape, not the exact numbers: throughput holds while the engine batches;
where p95 grows, the engine is queueing — confirm it in requests_deferred.

While that runs, the deferred gauge climbs past the threshold of 2 and the HPA scales out. In the watch terminal you will see it move — and the second pod comes up fast because the model is already unpacked on the PVC. Confirm that in the new pod's init log:

kubectl get pods -l app=opsmate-model
kubectl logs -l app=opsmate-model -c fetch-model --tail=2 --prefix | grep -i 'skipping\|present' | tail -1

Expected output (two model pods during load; the second pod's initContainer skips the unpack — the presence-cache making scale-out fast)

NAME                             READY   STATUS    RESTARTS   AGE
opsmate-model-7b657d5cc5-q4hhf   1/1     Running   0          6m
opsmate-model-7b657d5cc5-r8kk2   1/1     Running   0          71s
[pod/opsmate-model-7b657d5cc5-r8kk2/fetch-model] model already present on PVC — skipping unpack

Stop the load (let the loadtest finish, or Ctrl-C it). After the 60s scale-down stabilization window, KEDA scales back to 1:

sleep 90
kubectl get hpa keda-hpa-opsmate-model
kubectl get pods -l app=opsmate-model

Expected output (queue empty, HPA back to 1 replica)

NAME                     REFERENCE                  TARGETS     MINPODS   MAXPODS   REPLICAS
keda-hpa-opsmate-model   Deployment/opsmate-model   0/2 (avg)   1         2         1
NAME                             READY   STATUS    RESTARTS   AGE
opsmate-model-7b657d5cc5-q4hhf   1/1     Running   0          9m

You just ran an autoscaler on a signal that means something: the queue at the door, not the noise in the kitchen. Ctrl-C the watch and the port-forward.

The habit to carry

Never autoscale an LLM server on CPU%. Scale on the signal that maps to user pain — queue depth (requests_deferred), concurrency, or KV pressure. A queued request burns ~0 CPU while the user waits, so CPU% is flat exactly when you need the autoscaler to fire.

The environment repo holds what Argo CD reconciles: the model server manifest (with your resolved host IP — git is the source of truth, so it must carry the working value, not the placeholder) and the autoscale ScaledObject. Port-forward gitea, create the repo via its API, then clone and push the two manifests:

kubectl -n git port-forward svc/gitea 3000:3000 &
sleep 4
curl -s -u opsmate:opsmate123 -X POST http://localhost:3000/api/v1/user/repos \

Expected output

Now the Argo CD Application: point it at the in-cluster gitea repo, automated sync with prune off (a promotion should never let a stale delete remove a live object mid-lab), and let it adopt the objects you already applied:

kubectl apply -n argocd -f - <<'YAML'
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: opsmate-env
  namespace: argocd
spec:
  project: default
  source:
    repoURL: http://gitea.git.svc:3000/opsmate/opsmate-env.git
    targetRevision: HEAD
    path: manifests
  destination:
    server: https://kubernetes.default.svc
    namespace: default
  syncPolicy:
    automated:
      prune: false        # never let a stale git state delete a live object here

YAML

Expected output (Argo adopts the live objects and reports Synced/Healthy)

opsmate-env   Synced        Healthy

Argo CD now watches the repo. Change the model version in git and the cluster follows — which is exactly what the next step does, and where it goes wrong in an instructive way.

Step 6 — Promote the model via PR — and hit Exhibit A: the presence-cache lie​

Promote OpsMate from 1.0.0 to a candidate build. The naive move is a one-line tag bump: change the kit tag in model-server.yaml's initContainer from 1.0.0 to 1.0.0-candidate, on a branch, and merge it via a PR. Do that first — then watch what actually serves.

cd /tmp/opsmate-env
git checkout -q -b promote-candidate
sed -i.bak 's#opsmate/model:1.0.0#opsmate/model:1.0.0-candidate#' manifests/model-server.yaml && rm -f manifests/model-server.yaml.bak
git commit -aqm "promote: model 1.0.0 -> 1.0.0-candidate"
git push -q origin promote-candidate
curl -s -u opsmate:opsmate123 -X POST http://localhost:3000/api/v1/repos/opsmate/opsmate-env/pulls \
  -H 'Content-Type: application/json' \
  -d '{"title":"promote to 1.0.0-candidate","head":"promote-candidate","base":"main"}' | jq -r '.number' > /tmp/pr.num
curl -s -u opsmate:opsmate123 -X POST "http://localhost:3000/api/v1/repos/opsmate/opsmate-env/pulls/$(cat /tmp/pr.num)/merge" \
  -H 'Content-Type: application/json' -d '{"Do":"merge"}'
cd - >/dev/null
echo "PR #$(cat /tmp/pr.num) merged"

Expected output

PR #1 merged

Argo CD polls git roughly every 3 minutes; force an immediate reconcile with the refresh annotation (the poll-vs-webhook trade-off — a webhook would be instant, the annotation is the manual nudge):

kubectl -n argocd annotate application opsmate-env argocd.argoproj.io/refresh=hard --overwrite
kubectl rollout status deployment opsmate-model --timeout=180s

Expected output (the pod rolls to the new spec — git says 1.0.0-candidate)

deployment "opsmate-model" successfully rolled out

The pod rolled, git says 1.0.0-candidate, the dashboard is green. Now check what is actually being served — read the GGUF path in the running server's args:

kubectl get pod -l app=opsmate-model -o jsonpath='{.items[0].spec.containers[0].args}' | tr ',' '\n' | grep gguf

Expected output (THE LIE: the server is still pointed at the same file the old bytes live in — the init skipped the unpack because a GGUF was already on the PVC)

"/model/models/gguf/qwen3-0.6b-q8_0.gguf"

There it is. The promotion was a lie. The pod rolled and git claims the new version, but the initContainer's idempotency guard saw a GGUF already on the PVC and skipped the unpack — so the server is still serving the old 1.0.0 bytes. This is the presence-cache from Step 3, the feature that made scale-out fast, now telling you a jar has new contents because you changed its label. Confirm the init skipped:

kubectl logs -l app=opsmate-model -c fetch-model --tail=3 | grep -i 'skip\|present'

Expected output

model already present on PVC — skipping unpack

Fix it through git — make the unpack path carry the tag, so a new tag means a new directory the guard has never seen. Rewrite model-server.yaml in the repo so the guard, the unpack, and the server -m all key on a per-tag dir (/model/kits/1.0.0-candidate/...), commit, and let Argo reconcile:

cd /tmp/opsmate-env
python3 - <<'PY'
import pathlib
p = pathlib.Path("manifests/model-server.yaml")
s = p.read_text()
# guard + unpack + server all move under a per-tag dir so a new tag = a new path
s = s.replace("/model/models/gguf/qwen3-0.6b-q8_0.gguf",
              "/model/kits/1.0.0-candidate/models/gguf/qwen3-0.6b-q8_0.gguf")
s = s.replace("mkdir -p /model/models", "mkdir -p /model/kits/1.0.0-candidate/models")
s = s.replace("cp -r /tmp/kit/models/* /model/models/",
              "cp -r /tmp/kit/models/* /model/kits/1.0.0-candidate/models/")
p.write_text(s)
print("rewrote paths to per-tag dir")
PY
git commit -aqm "fix: per-tag unpack dir so a new tag actually unpacks"
git push -q origin main
cd - >/dev/null
kubectl -n argocd annotate application opsmate-env argocd.argoproj.io/refresh=hard --overwrite

Expected output

rewrote paths to per-tag dir

Step 7 — Exhibit B: the per-kit GGUF filename crash, fixed through git​

With the per-tag dir in place, the pod now actually unpacks the candidate kit — and crashes. Watch it:

kubectl rollout status deployment opsmate-model --timeout=120s || true
kubectl get pods -l app=opsmate-model
kubectl logs -l app=opsmate-model -c llama-server --tail=4 | grep -i 'error\|no such\|failed' | tail -1

Expected output (CrashLoopBackOff — the server cannot find the file it was told to load)

NAME                             READY   STATUS             RESTARTS   AGE
opsmate-model-6b9c8f7d5c-2xk9p   0/1     CrashLoopBackOff   2          75s
error while loading model: /model/kits/1.0.0-candidate/models/gguf/qwen3-0.6b-q8_0.gguf: No such file or directory

This is the M9 filename echo: the candidate kit ships its GGUF as opsmate-tuned-q8_0.gguf, not qwen3-0.6b-q8_0.gguf. The server (and the guard) are keyed on the old name, so the unpack lands a file the server never looks for. Confirm the real filename that got unpacked:

kubectl exec deploy/opsmate-model -c llama-server -- ls /model/kits/1.0.0-candidate/models/gguf/

Expected output (the candidate's actual filename)

opsmate-tuned-q8_0.gguf

Fix it through git — point the guard and the server -m at the candidate's real filename, commit, reconcile:

cd /tmp/opsmate-env
sed -i.bak 's#1.0.0-candidate/models/gguf/qwen3-0.6b-q8_0.gguf#1.0.0-candidate/models/gguf/opsmate-tuned-q8_0.gguf#g' manifests/model-server.yaml && rm -f manifests/model-server.yaml.bak
git commit -aqm "fix: candidate kit GGUF filename is opsmate-tuned-q8_0.gguf"
git push -q origin main
cd - >/dev/null
kubectl -n argocd annotate application opsmate-env argocd.argoproj.io/refresh=hard --overwrite
kubectl rollout status deployment opsmate-model --timeout=180s

Expected output (the candidate finally serves)

deployment "opsmate-model" successfully rolled out

Verify the candidate is genuinely serving the new bytes — the served path now carries both the tag and the candidate's filename:

kubectl get pod -l app=opsmate-model -o jsonpath='{.items[0].spec.containers[0].args}' | tr ',' '\n' | grep gguf

Expected output (the honest promotion: per-tag dir + candidate filename)

"/model/kits/1.0.0-candidate/models/gguf/opsmate-tuned-q8_0.gguf"

The promotion is now real: git says candidate, and the candidate bytes are what serve. Two exhibits, both fixed through git — no kubectl edit, because a change that is not in git would be undone by the next Argo sync.

Step 8 — Roll back with git revert — instant, because the cache that lied now helps​

A candidate that misbehaves must roll back fast. Because desired state is in git, rollback is git revert — no special tooling. Revert the whole promotion chain back to 1.0.0. The PR created a merge commit, so reverting that merge needs revert -m 1 (the mainline parent) — a real git gotcha worth meeting once:

cd /tmp/opsmate-env
# revert the two fix commits (per-tag dir, filename) first — plain reverts
git revert --no-edit HEAD HEAD~1
# then revert the promotion merge itself — mainline parent = pre-promotion main
MERGE=$(git log --grep='promote to 1.0.0-candidate' --merges --format=%H | head -1)
if [ -n "$MERGE" ]; then git revert --no-edit -m 1 "$MERGE"; else \
  sed -i.bak 's#opsmate/model:1.0.0-candidate#opsmate/model:1.0.0#' manifests/model-server.yaml && rm -f manifests/model-server.yaml.bak && \
  git commit -aqm "rollback: 1.0.0-candidate -> 1.0.0"; fi
git push -q origin main
cd - >/dev/null
kubectl -n argocd annotate application opsmate-env argocd.argoproj.io/refresh=hard --overwrite
kubectl rollout status deployment opsmate-model --timeout=120s

Expected output (back to 1.0.0)

deployment "opsmate-model" successfully rolled out

Confirm the rollback served fast, and read why in the init log:

kubectl get pod -l app=opsmate-model -o jsonpath='{.items[0].spec.containers[0].args}' | tr ',' '\n' | grep gguf
kubectl logs -l app=opsmate-model -c fetch-model --tail=2 | grep -i 'skip\|present'

Expected output (serving 1.0.0 again; the init SKIPPED because the old bytes never left the PVC)

"/model/models/gguf/qwen3-0.6b-q8_0.gguf"
model already present on PVC — skipping unpack

That is the symmetry worth remembering: the presence-cache that lied during promotion (old bytes served under a new label) is exactly what makes rollback instant (old bytes still on the PVC, no re-fetch). Same mechanism, opposite value, depending on whether you understand it.

The habit to carry

Put the model version in git and change it only through git. Promote with a PR (reviewable), roll back with git revert (instant). Never kubectl edit a GitOps-managed object — the next sync overwrites you. And know your cache: a "presence" guard makes scale-out and rollback fast, and makes naive promotion a lie.

Step 9 — Train under guardrails: drain serving, then run the fine-tune as a workflow​

The last piece is the training loop as a governed pipeline step. A training pod is a heavyweight batch job, and on the 8 GB path it shares the one node with everything else. The guardrail is a CPU cap so it cannot starve the control plane (the Deep Dive post-mortem is what happens without it), and one heavyweight at a time — you drain serving first.

Install Argo Workflows (controller-only, no server/UI) and apply the executor RBAC:

helm install argo-workflows argo/argo-workflows -n argo --create-namespace \
  --set server.enabled=false \
  --set controller.resources.limits.memory=150Mi
kubectl -n argo rollout status deployment argo-workflows-workflow-controller --timeout=180s
kubectl apply -f labs/m11/rbac-executor.yaml

Expected output (the controller is up; the executor SA + Role + RoleBinding are created)

deployment "argo-workflows-workflow-controller" successfully rolled out
serviceaccount/argo-workflow created
role.rbac.authorization.k8s.io/argo-workflow-executor created
rolebinding.rbac.authorization.k8s.io/argo-workflow-executor created

Build the training image and load it into the node (prebuilt, because installing torch at pod start took ~14 min in the spike — the pipeline must not re-resolve deps every run):

docker build -f labs/m11/Dockerfile.train -t opsmate-train:m11 labs/m11
kind load docker-image opsmate-train:m11 --name opsmate

Expected output (the image loads onto the node; build layers point-in-time)

Image: "opsmate-train:m11" with ID "sha256:..." not yet present on node "opsmate-control-plane", loading...

Now drain serving — one heavyweight at a time. Pause the model (KEDA's paused-replicas annotation parks it at 0) and scale the observability stack to 0, freeing the node's memory for the trainer:

kubectl annotate scaledobject opsmate-model autoscaling.keda.sh/paused-replicas="0" --overwrite
kubectl scale deployment prometheus grafana phoenix --replicas=0
kubectl wait --for=delete pod -l app=opsmate-model --timeout=120s
kubectl get pods -l app=opsmate-model

Expected output (serving drained to zero — the node is now free for training)

No resources found in default namespace.

Submit the workflow and watch it. The -w watch shows the phase; when it finishes, read the log:

kubectl create -f labs/m11/train-workflow.yaml
kubectl get wf -w

Expected output (the workflow runs the smoke fine-tune; Ctrl-C the watch when it reaches Succeeded)

NAME                  STATUS      AGE
opsmate-train-abcde   Running     10s
opsmate-train-abcde   Succeeded   1m

Read the training log — 2 steps, loss moving, the LoRA trainable-parameter line printed in-cluster:

WF=$(kubectl get wf -o jsonpath='{.items[0].metadata.name}')
kubectl logs -l workflows.argoproj.io/workflow=$WF -c main --tail=12

Expected output (the LoRA line and 2 steps of loss — the fine-tune really ran on the cluster; numbers point-in-time)

trainable params: 1,146,880 || all params: 597,196,928 || trainable%: 0.1920
  step    1  loss 5.4486  ...
  step    2  loss 4.3514  ...
If the workflow PHASE shows Error but training looks finished — read containerStatuses

If the phase reads Error with workflowtaskresults.argoproj.io is forbidden, the executor RBAC did not apply — but check the main container's exit code before assuming failure: kubectl get pods -l workflows.argoproj.io/workflow=$WF -o jsonpath='{.items[0].status.containerStatuses[*].state}'. The main container often shows Completed/exit 0 (training succeeded) while the phase reports Error because the executor could not write results back. Apply labs/m11/rbac-executor.yaml and re-submit. The Deep Dive dissects this phase-vs-containerStatuses reading.

Restore serving (un-pause KEDA, scale observability back) so the platform is whole again:

kubectl annotate scaledobject opsmate-model autoscaling.keda.sh/paused-replicas="1" --overwrite
kubectl scale deployment prometheus --replicas=1
kubectl rollout status deployment opsmate-model --timeout=180s

Expected output

deployment "opsmate-model" successfully rolled out
The habit to carry

A batch job on a shared node needs a CPU limit — the limit protects the control plane, not just the pod. And run one heavyweight at a time: drain serving before you train. KEDA's paused-replicas annotation is the drain lever; scaling the observability stack to 0 frees the rest.

Step 10 — Teardown​

Tear the cluster down. The registry and its kits persist; the Helm releases (KEDA, Argo CD, gitea, Argo Workflows) die with the cluster, and the manifests stay in labs/ for the capstone:

make -C labs/opsmate k8s-down

Expected output

==> Deleting the KIND cluster 'opsmate' ...
Deleting cluster "opsmate" ...
Deleted nodes: ["opsmate-control-plane"]
    Cluster gone. The registry and its data on ./data/zot PERSIST ...

Stop any port-forwards with Ctrl-C, and clean the scratch repo clone:

rm -rf /tmp/opsmate-env
kind get clusters | grep -q opsmate && echo "cluster still up?!" || echo "cluster gone — teardown clean"
test -s labs/opsmate/k8s/autoscale.yaml && echo "autoscale manifest kept"
test -s labs/opsmate/k8s/gitea.yaml && echo "gitea manifest kept"

Expected output

cluster gone — teardown clean
autoscale manifest kept
gitea manifest kept

What M12 builds on: the autoscaled, GitOps-managed model server you just operated. Next module puts a gateway in front of it — evals gate what gets promoted, guardrails filter what reaches the model, and the promotion PR you ran here gets an eval check before it can merge.

Troubleshooting
  • KEDA HPA shows <unknown>/2 targets — KEDA cannot reach Prometheus or the metric has no samples yet. Confirm Prometheus is 1/1 Running and the ScaledObject's serverAddress matches its Service DNS (http://prometheus.default.svc:9090). Drive a little load so llamacpp:requests_deferred exists as a series; a metric that has never been non-zero can read as no-data until the engine sees traffic.
  • Second replica never appears under load — the deferred gauge never crossed the threshold. A single replica may be keeping up at concurrency 8 on a fast box; raise LEVELS (e.g. LEVELS=8,16) briefly, or lower the ScaledObject threshold. Watch sum(llamacpp:requests_deferred) in Prometheus during load to confirm it climbs past 2.
  • applicationset-controller pod is running — you installed Argo CD without the slim values file, or with applicationSet.enabled=false (a no-op in this chart). Re-install with -f labs/opsmate/k8s/argocd-values.yaml, which uses applicationSet.replicas: 0.
  • gitea admin user create fatals — you ran it as root. Run it as the git user: su git -c "gitea admin user create ... --config /data/gitea/conf/app.ini".
  • Argo CD Application stuck OutOfSync / Unknown — the repo URL must be the in-cluster Service (http://gitea.git.svc:3000/...), not localhost:3000 (that is your port-forward, unreachable from the repo-server pod). Force a reconcile with the argocd.argoproj.io/refresh=hard annotation; the default git poll is ~3 minutes.
  • Promotion "worked" but the old answers keep coming (Exhibit A) — the designed exhibit. The init's idempotency guard skipped the unpack because a GGUF was already on the PVC, so old bytes serve under the new tag. Fix per-tag unpack dirs in git (Step 6), not with kubectl edit.
  • Candidate pod CrashLoops, No such file or directory on the GGUF (Exhibit B) — the candidate kit's GGUF filename differs (opsmate-tuned-q8_0.gguf, the M9 per-kit filename). Point the guard and server -m at the real filename in git (Step 7).
  • git revert of the promotion fails with "mainline required" — the PR created a merge commit; a merge revert needs the mainline parent: git revert -m 1 <merge-sha>. Step 8 handles this.
  • Training workflow OOMKilled — you are above the smoke profile or the node is not drained. Confirm --batch 1 --max-len 256 (batch 2 / max-len 512 OOMs at 4Gi with no swap), and that serving and observability are scaled to 0 before submitting.
  • Training workflow phase Error, workflowtaskresults ... is forbidden — the executor RBAC is missing. Apply labs/m11/rbac-executor.yaml and re-submit. Check the main container's exit code (containerStatuses) before assuming the training itself failed — it often already succeeded (exit 0).
  • kubectl hangs / TLS timeouts during training — the training pod is starving the control plane (you ran it uncapped or with too high a CPU limit on a small node). This is the Deep Dive incident. The workflow ships limits.cpu: "2"; do not raise it on the 8 GB path. If the node is already wedged, the break-glass is on the node itself (docker exec opsmate-control-plane, then pkill the training process) — see the Deep Dive.
  • kind load errors with a containerd digest / NotFound — the known multi-arch kind load flake (M8/M10). Retry once; if it persists, docker save opsmate-train:m11 -o /tmp/t.tar then docker exec -i opsmate-control-plane ctr --namespace=k8s.io images import - < /tmp/t.tar.
  • Host disk fills during the training image build (ENOSPC) — the CPU-torch image is ~3 GB and repeated builds grow the container runtime's disk. Reclaim with docker system prune and confirm free space with df -h before rebuilding.
  • make k8s-up preflight refuses to start — under ~3 GB free the KIND phase is refused. Close the Compose stack, browsers, and other containers. One heavyweight stack at a time.
