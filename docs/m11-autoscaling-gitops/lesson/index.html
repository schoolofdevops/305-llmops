Autoscaling & GitOps — Operating the Platform

Two things went wrong the same week, and both are the kind of thing that ends up in an incident review with your name on the timeline.

The first was a surge. A regional outage sent every on-call engineer to OpsMate at once, and the assistant slowed to a crawl right when people needed it. You had autoscaling wired — a perfectly ordinary HPA on CPU. It never fired. You pulled up the node graph afterward and CPU was sitting at forty percent the whole time. The autoscaler did exactly what you told it to. You told it the wrong thing. Requests were piling up in a queue the CPU number could not see, and one engine sat there at forty percent CPU while forty people waited.

The second was quieter and worse. Someone shipped a new model version — the fine-tuned OpsMate from M6, packaged as the 1.0.0-candidate kit (still unsigned — the signing and eval gates that would catch that are M12's story). The deploy went green. The change ticket said 1.0.0 → 1.0.0-candidate, promoted. And for two days users kept getting the old model's answers, and nobody could say for certain which version was actually serving, because the thing that told you the version was a ticket, not a fact you could check. "Promoted" was a sentence someone wrote, not a state of the system.

That is this module. Two jobs. Autoscale on a signal that means something — the queue at the door, not the noise in the kitchen. And make the serving model version a fact recorded in git, so "what is deployed right now" is a question with a checkable answer and "promote" is a pull request, not a sentence.

Resource path — 8 GB core runs everything required

Every required step runs on the 8 GB core path: the slim single-node KIND cluster, the model server, the M10 observability stack, KEDA, Argo CD (slim), gitea, and Argo Workflows for the training step. Two things stay small on purpose — KEDA scales 1 → 2 → 1 (not to a fleet), and the training step runs a smoke profile (--batch 1 --max-len 256 --max-steps 2) that proves the pipeline without a real fine-tune. Full-fidelity training — a real multi-epoch run — is the 16 GB / host path (the M6 host run); this module automates the pipeline, not a production-grade training job. One heavyweight stack at a time still holds: you drain serving before you train.

Why CPU% is the wrong signal — kitchen noise versus the queue at the door​

Start with the mistake, because it is the one almost everyone makes first, and it is the reason the surge in the incident review never triggered a scale-out.

Picture judging how busy a restaurant is by standing outside and listening to the kitchen. Pots banging, the fryer going, chefs calling orders — loud kitchen, must be busy. But the kitchen noise tells you how hard the cooks are working, not how many people are waiting. A kitchen can be roaring while the dining room is half empty, and it can be dead quiet while thirty people stand at the door because there is nowhere to seat them. If you want to know whether to open the second dining room, you do not listen to the kitchen. You look at the queue at the door.

CPU% is the kitchen noise. For a llama.cpp model server, decode saturates one core per in-flight request — one request runs one core hot, and that is it. A second request that arrives with no free slot does not raise CPU; it waits. It consumes almost no CPU while it sits in the queue, because it is not doing anything yet — it is parked. So the exact situation you most need to scale for — requests arriving faster than the engine can take them — is the situation where CPU stays flat. During the surge, one engine ran its core hot at forty percent node-average CPU while the queue behind it grew, and the CPU-based HPA, watching the kitchen, heard nothing worth acting on.

The signal that maps to user pain is the queue at the door: queue depth. And you already know where it lives, because you learned to read it in M10. The model server exports llamacpp:requests_deferred — the count of requests parked because every slot is busy. That is the gauge that climbed while CPU stayed flat. When it rises, requests are not slow, they are waiting, and waiting is fixed by adding an engine, not by giving the one engine more CPU it is not blocked on.

The habit to carry

Never autoscale an LLM server on CPU%. Decode pins one core per request and a queued request burns almost no CPU, so the metric is flat exactly when you are in trouble. Scale on the queue — llamacpp:requests_deferred — the same signal M10 taught you to watch. Concurrency (requests in flight against slot capacity) and KV-cache pressure are the other honest LLM-native signals; all three describe demand the engine can feel, which CPU% cannot.

KEDA — the maître d' who opens the second dining room​

So you want to scale on the queue. The mechanism is KEDA, and the cleanest way to hold it in your head is the maître d'.

A good maître d' watches the queue at the door, and when it forms, opens the second dining room. Watch the queue; when it builds, add capacity; when it drains, close the room again. That is the whole control loop, and KEDA is that maître d' for your Deployment.

You know what an HPA is, so this module does not re-teach it. The LLM-specific part is where the signal comes from and who owns the HPA. KEDA reads your M10 Prometheus series directly — you hand it the query sum(llamacpp:requests_deferred) and a threshold, and it does not need prometheus-adapter's metric-rule language sitting in between. And KEDA does not scale the Deployment itself. It generates an HPA and manages it for you. You write one object, a ScaledObject; KEDA creates a real keda-hpa-opsmate-model alongside it. In the lab you will kubectl get hpa and see the HPA KEDA built, reading the queue-depth external metric — both objects, side by side, so the indirection is visible rather than magic.

On the 8 GB path you scale min 1 / max 2 with a threshold of 2 — more than two parked requests per replica and KEDA adds the second engine. In the lab you drive load until requests_deferred climbs, watch 1 → 2, drain the load, and watch 2 → 1. Small numbers, but the loop is the real one: watch the queue, open the room, close it again.

Scale-to-zero, and the cold-start you cannot ignore​

The obvious next thought is: if the maître d' can close the second room, why not close the first one too when nobody is dining — scale to zero, pay for nothing? For a stateless web pod, that is often right. For a model server, it is a trap you have to reason about honestly.

The reason is cold start. A stateless web pod comes back in seconds — pull a small image, start a process, ready. A model server's cold start is image pull plus model load, and the model load is the expensive part: reading the weights off disk into memory and warming the runtime. That is minutes, not seconds. So the math is unforgiving: scale an interactive assistant to zero and the first user after an idle window waits minutes for a reply while the engine loads. That is not a scale event they will forgive.

The honest rule: scale-to-zero belongs to batch and rare endpoints — a nightly report generator, an endpoint hit twice a day — where a cold minute is fine. For an interactive service like OpsMate, keep at least one engine warm. That is why the lab runs min 1, not min 0.

The scale-to-zero knobs, and why they're quiet here

KEDA's pollingInterval (how often it queries Prometheus) and cooldownPeriod (how long after the last trigger before it scales to zero) only govern the 0 ↔ 1 transition. At minReplicaCount: 1 KEDA itself warns they are irrelevant — there is no scale-to-zero to time. They matter the moment you do run a batch endpoint at min 0; the Deep Dive takes them apart. Here, min 1 keeps an engine warm and those knobs sit idle.

Why the second engine comes up fast — the presence-cache, working for you​

There is a detail in the scale-out that looks like luck and is actually design, and it is worth naming because the same mechanism is about to cause trouble two sections from now.

When KEDA adds the second replica, it comes Ready fast — far faster than the first engine ever loaded. The reason is the M8 PVC pattern. The model is not baked into the image; an initContainer unpacks it from the signed ModelKit onto a PersistentVolume. The first pod did that unpack. The second pod's init looks at the PVC, sees the model already sitting there, and skips the whole download-and-unpack — it logs model already present on PVC — skipping unpack and goes straight to serving. The weights are already on disk; the new engine just opens them.

Call this the presence-cache: the init trusts what is already on the volume and does not re-fetch it. For scale-out that is a feature — it is exactly why the second dining room opens in seconds. Hold onto it, though, because that same "trust what's already on the volume" instinct is about to serve you a stale model and swear it is the new one.

Before you drive the real loop in the lab, drive the model of it. The simulator below lets you push the arrival rate past the point where one replica saturates, inject a burst, and watch the exact thing that makes autoscaling an LLM server hard: the queue forms first, KEDA reads it on the next poll and decides 1 → 2, but the second engine is still cold-starting — so relief lands seconds after the decision, and users wait through that lag even though the autoscaler did the right thing. Shrink the stabilization window and make it flap; set min 0 and watch the first request eat the full cold start.

GitOps where the desired state includes the model version​

Now the second failure — the promotion nobody could verify. The fix is GitOps, and the framing that makes it click is the signed delivery manifest pinned to the door.

Think of a bonded warehouse. What is supposed to be inside is not decided by whoever last walked in with a crate; it is decided by the manifest pinned to the door — the signed paper that says exactly what this building holds. Change the paper through the proper process and the building is made to match it. The paper is the source of truth; the building follows.

That is GitOps, and you know the shape of it. The twist for a model platform is what goes on the manifest. For an ordinary service the desired state is replica counts and an image tag. For OpsMate the desired state includes which signed ModelKit tag is serving — the model version is not a footnote, it is a line in the manifest. You keep that manifest in a git repo (the lab runs gitea in-cluster as the environment repo), Argo CD watches it, and the cluster is continuously made to match what git says.

So promotion becomes a pull request that bumps the kit tag from 1.0.0 to 1.0.0-candidate. And rollback becomes git revert — you undo the commit, Argo reconciles, the cluster goes back. "What is serving?" stops being a ticket you have to trust and becomes git log on the env repo. That is the whole point: the version is now a fact, checkable, with an audit trail.

One operational note you will feel in the lab: Argo's default git poll is around three minutes, so a merged PR does not reconcile instantly. You can wait, or you can force it with the argocd.argoproj.io/refresh annotation — the same job a git webhook would do in a real setup. Poll versus webhook is a latency-versus-plumbing tradeoff; the lab pokes it with the annotation so you are not waiting on the poll.

The promotion lie — swapping the label on a full jar​

Here is where the presence-cache comes back to bite, and it is the exhibit this module is built around. You will hit it live in the lab; meet the shape of it now so you recognize it.

You merge the PR. The tag in git is now 1.0.0-candidate. Argo reconciles, the model-server pod rolls, everything goes green. And the server keeps serving the old model.

The analogy is swapping the label on a full jar without changing the contents. You changed the paper on the door — the manifest says candidate — but the jar on the shelf is still full of the old batch, and nobody emptied it. Mechanically: the pod rolled, the init ran, and the init's idempotency guard — the presence-cache from a few sections ago — looked at the PVC, saw a GGUF already there, and skipped the unpack. It did its "trust what's on the volume" job perfectly. But "there is a model on the volume" is not the same as "the right model is on the volume." Git claims the new version; the disk holds the old bytes; the server opens the old bytes. The promotion is a lie, and it is a lie told by the exact feature that made scale-out fast.

The fix is to make the tag part of the path. Instead of one shared model directory, unpack each tag into its own directory — /model/kits/1.0.0/..., /model/kits/1.0.0-candidate/... — and thread the tag through the guard, the unpack, and the server's -m flag. Now the guard for candidate checks the candidate directory, finds it empty, and actually unpacks. The presence-cache still works; it just caches per version instead of pretending all versions are one.

The model version belongs in git — and on disk, per version

A green deploy is not a promoted model. If your unpack step keys on "is there a model on the volume," a tag bump will roll the pod and serve the old weights while git swears it shipped the new ones. Make the version part of the path — one directory per tag — so the presence check is per version. The tension is the lesson: the cache that makes scale-out fast is the same cache that lies about promotion until you version its key.

And the symmetry, because it is the quiet payoff. Once each version has its own directory on the PVC, rollback is instant. git revert puts the tag back to 1.0.0, Argo reconciles, the pod rolls — and this time the 1.0.0 directory is still sitting on the volume from before, so the init skips the unpack and the old-but-correct engine is Ready in seconds. The same presence-cache that lied during a careless promotion makes a correct rollback nearly free. Cache the version, and both directions win. (There is a second, smaller exhibit waiting in the lab — the candidate kit ships its GGUF under a different filename, an echo of the M9 packaging lesson — but the lab walks that one; the promotion lie is the concept to carry.)

Training as a pipeline step — the circuit breaker on a shared node​

Last job: move the training loop from a thing you run by hand on a laptop (M6) to a step the platform runs — an Argo Workflow inside the cluster. The concept that matters here is not "how do I run a job." You know that. It is the guardrail, and the analogy is the circuit breaker in a house.

A house shares one electrical supply across every outlet. Run a space heater, the microwave, and a hair dryer on the same circuit and you brown out the whole house — the shared supply cannot feed one greedy appliance without starving everything else. The circuit breaker exists to trip before that happens, so one appliance can never take down the house.

A training pod is the space heater. It shares the node's CPU with everything else on that node — including the Kubernetes control plane. And a fine-tune is not a polite workload; it will take every core it can reach. Run it uncapped on the shared node and it browns out the house: it starved the kube-apiserver so badly the cluster became unrecoverable by kubectl — the very tool you would reach for to stop it needs the apiserver the training pod was strangling. That incident is the Deep Dive's post-mortem; here, take the rule it produced.

The circuit breaker is a CPU limit. The training pod carries limits.cpu: "2" — it may be slow, but it can never take the node down, because the kernel caps it before it starves the control plane. Alongside the CPU cap: a memory profile sized for the 8 GB path, and the one-heavyweight-at-a-time discipline you have followed all along — you drain serving first before you train.

Draining serving has a neat detail. Remember KEDA's paused-replicas annotation? You set autoscaling.keda.sh/paused-replicas: "0" on the model server and KEDA pins it to zero replicas — the same annotation that is normally your "hold scaling steady" lever now doubles as your "get the model engine out of the way so training has the node" lever. Scale the observability stack to zero as well, and the node is clear for the training pod to run under its cap.

Drain before you train, on a shared node

A training pod is a heavyweight batch job competing with the control plane for the same cores. Cap it (limits.cpu) so it can never starve the apiserver, and drain the serving stack first — pause the model server with KEDA's paused-replicas: "0" and scale observability to zero — so one heavyweight workload runs at a time. On the 8 GB path this is a smoke profile that proves the pipeline; a real fine-tune is the 16 GB / host path.

Where this leaves OpsMate — and the hand-off to M12​

OpsMate is now v2.5, operated like a platform. It autoscales on a signal that means something — queue depth, the queue at the door, not the kitchen noise of CPU%. Its model version is a fact in git: promoted by pull request, rolled back by git revert, and — once the presence-cache is versioned per tag — actually the version git says it is. And its training loop is a pipeline step with a circuit breaker, so automating the fine-tune can never brown out the cluster it runs on.

That sets up M12 directly. You can scale it, you can promote and roll back its model, you can retrain it — but you have not yet put a front door on it. M12 adds the gateway: the single entry point where you run evals as a promotion gate (so a candidate model has to earn the tag bump you learned to make here), enforce guardrails, and control who and what reaches the model. You have learned to operate the platform. Next you learn to govern what goes through its door.
