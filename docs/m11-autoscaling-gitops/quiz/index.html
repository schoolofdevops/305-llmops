Autoscaling & GitOps — Quiz

Check your grasp of the module: why CPU% is the wrong autoscaling signal for an LLM server, how KEDA turns a Prometheus metric into an HPA, scale-to-zero versus model cold-start, GitOps where the model version lives in git (the presence-cache lie and its fix, promote via PR, roll back via git revert), and the training guardrails that keep a batch job from starving the control plane.

You are wiring an autoscaler for the OpsMate model server. During an incident surge the queue backs up and users wait, but the pod's CPU% barely moves — so a CPU-based HPA never adds a replica. Why is CPU% the wrong signal, and what should you scale on?

You apply the ScaledObject and then run `kubectl get hpa`. You see keda-hpa-opsmate-model that you never wrote. What is the relationship between your ScaledObject and this HPA?

Your teammate proposes setting minReplicaCount: 0 (scale-to-zero) on the model server to save resources when idle. For OpsMate — an interactive on-call assistant — why is that the wrong call, and where would scale-to-zero be right?

You promote OpsMate by bumping the ModelKit tag from 1.0.0 to 1.0.0-candidate in the git env repo via a PR. Argo CD syncs, the pod rolls, git says candidate — but users still get the old model's answers. What happened, and what is the fix?

You drained serving for training by setting `autoscaling.keda.sh/paused-replicas: "0"` on the ScaledObject. Training is done and you want autoscaling back — someone suggests setting the annotation to `"1"` to restore one warm replica. Why is that wrong, and what actually resumes autoscaling?
