Deep Dive — Agent Internals: Why Loops Happen, What the Gateway Eats, and How Schemas Bind Generation

The core lab had you watch a 0.6B model tool-call, trigger a loop and fix it, and run the whole lifecycle end to end. It showed you that those things happen. This Part 2 explains why, at the level you need to debug them in production: what a loop actually is in terms of the model's action space, which spec knobs survive the gateway's translation and which get silently eaten, how a JSON schema binds generation rather than just validating it afterward, and the ops notes for what breaks when this runs at scale. The checks live in labs/m13/deep-dive.checks.json.

Why loops happen — the tool schema is the action space​

In the lab you left tools in the request on the answer turn and the agent re-called the tool forever. It is tempting to read that as the model being "confused" or "stuck." It is neither. It is the model doing exactly what the request told it it could do.

On any given turn, the model's legal moves are a function of the request. A plain chat request has one legal move: emit text. A request that carries tools has two: emit text, or emit a tool call. The tool schemas in the request literally define the action space — the set of moves available this turn. When you feed a tool result back and ask for the answer with the tools still present, you have not changed the action space: calling a tool is still legal, and a model that has any uncertainty about whether it has enough information will often take that move again. Feed that result back with tools still present, and again. The loop is not a bug in the model; it is the orchestrator repeatedly offering a move and being surprised the model takes it.

This reframes termination correctly: termination is a property of the orchestrator, not the model. The model cannot "decide to stop calling tools" reliably, because as long as the option is on the table, taking it is a valid response to uncertainty — and small models are more uncertain, so more loop-prone. The orchestrator terminates the loop by removing the option: omit tools on the answer turn and the action space collapses to {answer}. There is no move left but to write the response. This is why the fix is one line and why no prompt engineering substitutes for it — you are not persuading the model, you are changing what is legal.

Production agents formalize this as a step budget: a hard cap on tool-call rounds (say, 5), after which the orchestrator forces the answer turn regardless of what the model wants. The omit-tools fix is the two-round version of the same principle. The general rule: an agentic loop must have an orchestrator-owned exit condition — a step count, a tool-omission, a timeout — because "the model will know when to stop" is not a property you can rely on. (In the lab you saw the loop's cost in the spend log; a step budget is what stops that cost from being unbounded.)

The dropped-knob translation — what LiteLLM forwards and what it eats​

The lab's Exhibit B was tool_choice: "none" getting silently dropped on the LiteLLM→Ollama path. That is not a one-off quirk; it is the newest member of a family you have been tracking since M2, and the family has a shape worth naming because it predicts which knobs to distrust.

Every request that crosses a translation boundary — your code speaks the OpenAI spec, LiteLLM re-speaks it to Ollama's API, Ollama re-speaks it to the model runtime — passes through a component that must map each parameter to something the next layer understands. A dropped knob leaves your config looking armed while it does nothing — and you only find out by testing behavior. This is the exact same failure class as three earlier exhibits, which is why it is worth seeing as a family rather than a series of unrelated surprises:

M2think: false on the /v1 chat routedropped — the model kept emitting hidden reasoning tokens, billed but unseen

The through-line: a parameter is a request, not a guarantee. The spec defines what you may ask for; whether the ask survives depends on every translation layer between you and the model. The operational discipline that falls out of this is the one the whole course keeps returning to — verify behavior, not configuration. "I set tool_choice: none" and "tool calls are suppressed" are different claims, and only the second is checked by evidence. When a knob matters for correctness (a loop fix, a guardrail, a cost control), assert it did what you asked with a test that would fail if the knob were dropped — which is exactly why the lab's fix is omitting the tools (a structural change the translation cannot drop) rather than asking the model not to use them (a knob it can).

How a schema actually binds generation — constrained decoding​

The lesson called structured outputs "the reliability primitive" and said a schema makes the model return valid JSON. That phrasing hides the interesting part: the model does not "try to" return valid JSON and usually succeed. When constrained decoding is in play, invalid JSON is impossible to emit — the schema binds the generation itself.

Recall how decoding works (M2): at each step the model produces a probability distribution over the whole vocabulary, and the sampler picks the next token from it. Constrained decoding inserts a step between the distribution and the pick: given the schema and the tokens generated so far, it computes which tokens are legal next and masks the rest to zero probability before sampling. If the model has emitted {"namespace": then the grammar says the next token must open a string value — so every token that is not a valid continuation is masked out, and the sampler can only pick from what the schema permits.

Two consequences matter operationally. First, the guarantee is structural, not statistical. With true constrained decoding you are not hoping the model is well-behaved; malformed output is off the table because the malformed tokens were never selectable. That is what makes structured outputs a reliability primitive and not just a prompt trick — the json.loads in your agent loop cannot throw on a syntax error. Second, not every "structured output" path is constrained decoding. Some stacks implement it as prompt-plus-retry (ask for JSON, validate, re-ask on failure) — which is best-effort and can return prose, so your loop still needs a parse-guard. The tool-calling path on most local runtimes (including the Ollama route you used) is grammar-constrained for the tool-call structure — the model cannot emit a malformed tool call — but the arguments inside are constrained only as far as the input schema is expressed as a grammar, which is why arg-hygiene (the "pod payments-api" strip) is still your job. Know which kind you have: constrained decoding lets you drop the parse-guard; retry-based structured output does not.

This is also the mechanistic reason a 0.6B model tool-calls competently. It does not need to be "smart enough to produce valid JSON" — the decoder makes the JSON valid. The model only needs to pick sensible values within the structure the grammar enforces. Capability moves from "can it format correctly" (handled by the constraint) to "does it choose the right tool and arguments" (the model's actual job) — and the lab showed the small model handles the second when the first is guaranteed for it.

Agent evals and sandboxing — the 303 frontier, named honestly​

The lesson pointed past this module to 303-agentops. Two of its topics are worth one paragraph of why here, because they are the reason a single read-only agent is a bridge and not the destination.

Agent evals grade trajectories, not answers. Every eval in this course graded an output: did the answer contain the right runbook, did it refuse the unanswerable question, did it beat the baseline. An agent that takes steps needs a different question: was the path sensible? An agent can reach a correct answer by luck after five wrong tool calls, or reach a wrong answer through impeccable reasoning — and an output-only eval scores those identically. Trajectory evals grade the sequence of decisions (did it call the right tool, in a reasonable order, without looping, without wasted steps), which is a strictly harder measurement problem and a whole subfield. Your gate.sh measures answers; it is the right tool for a chat assistant and the wrong tool for a multi-step agent.

Sandboxing is what read-only bought you for free. This module's safety came from tool design — the MCP server has no mutating verb, so the agent physically cannot break anything. That is the cheapest possible sandbox: capability-by-absence. The moment an agent's tools do mutate the world (restart a deployment, open a PR, run a shell command), absence is no longer available and you need real isolation — a sandbox that contains the blast radius of a tool the agent can misuse, with its own permission model, resource limits, and audit trail. The visitor-badge discipline scales to "let it look"; it does not scale to "let it act," and the jump between them is exactly what makes agent operations its own course.

Capstone ops notes — what breaks at scale​

The capstone ran the full lifecycle once, on one machine, at smoke scale. Three things that were invisible at that scale become the operational work at production scale, and naming them is the honest close.

  • The synthesize → tune → gate loop is a data pipeline, not a script. At smoke scale you ran three commands by hand. At scale, a new runbook landing should trigger the pipeline (the Argo Workflow from M11), and the pipeline needs the things every data pipeline needs: idempotency (re-running does not duplicate training data), lineage (which corpus version produced which model version — the signed kit's digest is your anchor), and a contamination guard that is enforced, not trusted (the synthesizer reading only the corpus and never the golden set must be a checked invariant, because a leak silently inflates the gate score and ships a model that only looks good).
  • The gate's floor is a moving baseline, and moving it is a governance decision. The capstone used the committed floor of 8. As the corpus grows and the model improves, that floor should rise — but who raises it, and on what evidence, is a policy question, not a config edit. A floor lowered quietly to make a red run green is the single most corrosive thing you can do to an eval gate; it turns the brake into decoration. The floor belongs in version control with a review on every change, so a raise or lower is a visible, defended decision.
  • One-take at smoke scale hides the wall-clock. The full lifecycle ran in minutes because every heavy step was a smoke profile. A real v1.2 train is hours, a real eval set is larger, and a real promotion touches a cluster serving live traffic. The capstone proves the wiring is correct; production adds the concerns the wiring must survive — training under a resource cap that protects the control plane (the M11 starvation post-mortem), a promotion that drains serving first (one heavyweight at a time), and a rollback that is instant because the old bytes never left the PVC. The lifecycle you validated is the skeleton; scale is the load it has to carry.

Where you will use this​

The next time an agent you operate spins — burning tokens, latency climbing, the same tool called over and over — you will not reach for a prompt tweak. You will look at whether the orchestrator has an exit condition, because you will know the loop is the action space staying open, not the model misbehaving. The next time a spec knob "doesn't work," you will test the behavior instead of re-reading the YAML, because you will recognize the dropped-knob family. And the first time you are asked to put an agent into production that can act, you will know the two questions that separate a demo from an operation: how is its trajectory evaluated, and what contains it when it is wrong — the two doors this module deliberately left for the next course to open.
