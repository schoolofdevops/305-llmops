Lab — A Guarded Agent, Then the Full-Lifecycle Capstone

Time

Roughly 2 hrs hands-on across both parts (Part A the guarded agent, Part B the full-lifecycle capstone), depending on your machine.

Resource path: 8 GB core — the tightest co-residency in the course

This lab has two parts with two different stacks. Part A (the agent) runs the M12 gateway stack (~1.9 GiB) and a slim KIND cluster (one node, one broken pod, no model server) at the same time — measured at ~4.1 GiB free on the 8 GB path, the tightest fit in the course. Part B (the capstone) tears Part A down and runs the KIND phase you know from M8–M11 against the persisted registry data. One heavyweight stack transition happens between the parts, and the lab walks it. Distributed agent tracing (span capture) is a 16 GB note — here you read the agent's cost and steps from the gateway's /spend/logs and the M12 Spend lens.

Before you start

All commands run from the root of the labs repo (305-labs/). You need docker, curl, jq, kind, kubectl, python3, kit, cosign, and host ollama responding — check the Setup section if any are missing. You must have completed M4/M5 (corpus + golden set + baseline), M6 (the train scripts), M7 (the registry with signed kits 1.0.0 / 1.0.0-candidate persisted on labs/opsmate/data/zot), M11 (the env-repo / Argo promotion flow), and M12 (the gateway stack and gate.sh). The KIND cluster in Part A uses an isolated kubeconfig at labs/opsmate/k8s/kubeconfig — your default context is never touched.

This is the last lab. In Part A you make OpsMate act: you bring up the gateway and a small broken cluster, drive a real MCP server by hand to see the protocol, then run the agent — it decides to call a tool, the tool inspects the live cluster, and the model grounds its diagnosis in what it found. You will trigger the agent loop on purpose, watch it burn spend rows, and fix it. In Part B you run the whole course in one take: a new runbook becomes a fine-tuned v1.2, packaged and signed as 1.2.0, put through the eval gate, promoted by PR, synced by Argo, and verified — then you assemble the portfolio artifact. The module, and the course, end with a full teardown to the clean machine you started from.

Part A — the guarded agent (OpsMate v3.5)

Step 1 — Bring up the gateway, and a slim broken cluster beside it​

Start from a clean machine. Bring the M12 gateway stack up (it is the front door every model call goes through), and resolve the host address the M8 way if you have not already this session:

docker compose -f labs/opsmate/gateway/compose.yaml up -d
# resolve the host IP the container must use for host Ollama (M8 two-paths), and
# write it into the gateway config (skip if your M12 run already did this session).
# Resolve from the pg container: it has getent AND, unlike the litellm container,
# no host-gateway override pinning host.docker.internal to the dead bridge IP
# (the M12 two-paths lesson — see the M12 lab). Give it a moment to come up first.
until docker exec gateway-pg-1 true 2>/dev/null; do sleep 1; done
HIP=$(docker exec gateway-pg-1 getent hosts host.docker.internal | awk '{print $1}')
sed -i.bak "s#http://[0-9.]*:11434#http://${HIP}:11434#g; s#http://host.docker.internal:11434#http://${HIP}:11434#g" \
  labs/opsmate/gateway/litellm-config.yaml && rm -f labs/opsmate/gateway/litellm-config.yaml.bak
docker compose -f labs/opsmate/gateway/compose.yaml restart litellm

Wait for the gateway to report live (prisma init takes 60–90 s cold):

until curl -fsS http://localhost:4000/health/liveliness >/dev/null 2>&1; do sleep 3; done
curl -s http://localhost:4000/health/liveliness
"I'm alive!"

Why a separate cluster name here

Part A uses opsmate-agent (a bare one-node cluster) rather than make k8s-up's opsmate cluster, because the agentic half does not need the base-model mount or the registry — the cluster is just something to look at. Part B uses the full make k8s-up cluster. Keeping them separate means Part A stays tiny and Part B is the platform you already know.

Step 2 — Apply the designed crashloop​

Apply the broken workload the agent will diagnose — a busybox payments-api in namespace shop that logs a FATAL db-connection line and exits 1:

kubectl apply -f labs/m13/crashloop.yaml
namespace/shop created
deployment.apps/payments-api created

Give the kubelet a few restart cycles, then confirm it is crashlooping — this is the live state the MCP server will read back:

sleep 30
kubectl -n shop get pods
NAME                           READY   STATUS   RESTARTS      AGE
payments-api-db4cdfff9-97bm6   0/1     Error    2 (25s ago)   34s

You should see a payments-api pod with a non-zero restart count and a CrashLoopBackOff or Error status. The exact restart count and pod-name suffix will differ on your machine — you are looking for the pattern (crashing, restarts climbing), not a specific value.

Step 3 — Drive the MCP server by hand — see the protocol​

Before the agent hides it, drive the MCP server yourself. MCP is JSON-RPC 2.0 over stdio — one JSON request per line in, one JSON response per line out. Send the three core methods as three lines and read the replies:

export KUBECONFIG=labs/opsmate/k8s/kubeconfig
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}' \
  '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"get_pod_status","arguments":{"namespace":"shop","pod":"payments-api"}}}' \
  | python3 labs/opsmate/mcp/mcp_k8s.py | jq -c .
{"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2024-11-05","capabilities":{"tools":{}},"serverInfo":{"name":"opsmate-k8s-inspector","version":"0.1"}}}
{"jsonrpc":"2.0","id":2,"result":{"tools":[{"name":"get_pod_status","description":"Live status of pods in a namespace: phase, readiness, restart count, last state.","inputSchema":{...}},{"name":"get_pod_logs","description":"Recent logs (last 20 lines, previous container if crashed) of a pod.","inputSchema":{...}}]}}
{"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"payments-api-db4cdfff9-97bm6|Running|2|{\"terminated\":{\"containerID\":\"containerd://0166...\",\"exitCode\":1,\"reason\":\"Error\"...}}"}]}}

Read what came back: the initialize reply names the server, tools/list returns exactly two tools (get_pod_status, get_pod_logs), and tools/call runs a real kubectl get against your live cluster and returns the actual pod row. That is the whole protocol. Now pull the crash log the same way:

printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"get_pod_logs","arguments":{"namespace":"shop","pod":"payments-api"}}}' \
  | python3 labs/opsmate/mcp/mcp_k8s.py | jq -r '.result.content[0].text'
starting payments-api...
FATAL: failed to connect to db payments-db:5432: connection refused

There is the diagnosable signal — the exact FATAL line naming the unreachable database. The MCP server has no mutating verb (no create, delete, patch, scale); it can only look. That read-only-by-construction design is the visitor badge from M8, applied to tool design.

Step 4 — Run the agent: the model decides, the tool looks, the answer grounds​

Now let the agent do the conversion and the loop. Run it against the gateway:

export KUBECONFIG=labs/opsmate/k8s/kubeconfig
python3 labs/m13/agent.py
Key discipline

agent.py defaults to the master key purely to keep this smoke run one command. In anything past a lab bench the agent is a client and gets its own virtual key (M12: no client holds the master key) — mint one and pass it as GATEWAY_KEY and the agent's turns become an attributable, budget-capped line in /spend/logs: GATEWAY_KEY=sk-... python3 labs/m13/agent.py.

[mcp] connected: opsmate-k8s-inspector v0.1
[mcp] tools: ['get_pod_status', 'get_pod_logs']
[llm] finish=tool_calls  tool_calls=2  (49 tok — a billable turn in /spend/logs)
[mcp] get_pod_status({'namespace': 'shop'}) -> payments-api-db4cdfff9-97bm6|Running|20|{"terminated":{"containerID":"containerd...
[mcp] get_pod_logs({'namespace': 'shop', 'pod': 'payments-api'}) -> starting payments-api...
FATAL: failed to connect to db payments-db:5432: connec...

[llm] grounded diagnosis (107 tok):
The payments-api pod is experiencing a crashlooping issue.
- Status: The pod is running in the `shop` namespace with a climbing restart count.
- Recent Logs: The logs indicate a failed connection attempt to the database
  (`payments-db:5432`) with an error message about a connection refused.

This suggests a connectivity issue with the database, which could be causing the
pod to crash. Further investigation is needed to verify the database connection.

Your run will differ — the restart count, the container ID, the exact wording, and whether the model called one tool or both all vary. What must hold is the pattern: the answer turn names this pod's actual failure (the payments-db:5432 connection refused, the exit code), not a generic runbook answer.

Read the trace top to bottom, because it is the whole module in one run:

  1. [mcp] connected and the two-tool list — the agent spawned the MCP server and discovered its tools.
  2. [llm] finish=tool_calls — turn 1: the model was offered the tools and decided to call one (or both), emitting a tool name and JSON arguments. Even at 0.6B, it picks the right tool.
  3. [mcp] get_pod_status(...) -> ... — the agent executed the call via MCP against the live cluster and fed the result back.
  4. [llm] grounded diagnosis — the answer turn, with tools omitted, produces a diagnosis that quotes the real log line and exit code. Not the generic runbook — this pod's actual failure.

The model may call one tool or both on any given run (the system prompt nudges it toward both; small models are frugal). Either is a valid trace — what matters is that the final answer is grounded in tool output, not guessed.

Step 5 — EXHIBIT A: trigger the loop mechanism, watch it burn a spend row​

The loop is not hypothetical — you will cause its first turn and see exactly why it would never stop. The fix in agent.py is a single line: the answer turn omits tools. Break that on purpose. Make a one-line edit to a copy and leave the tools in on the answer turn:

sed 's/d2 = chat({"messages": msgs, "think": False, "max_tokens": 1200})/d2 = chat({"messages": msgs, "tools": tools, "think": False, "max_tokens": 1200})/' \
  labs/m13/agent.py > /tmp/agent_loop.py
export KUBECONFIG=labs/opsmate/k8s/kubeconfig
python3 /tmp/agent_loop.py | tail -6
[llm] finish=tool_calls  tool_calls=1  (26 tok — a billable turn in /spend/logs)
[mcp] get_pod_status({'namespace': 'shop', 'pod': 'payments-api'}) -> payments-api-db4cdfff9-97bm6|Running|21|{"terminated":{"containerID":"containerd...

[llm] grounded diagnosis (0 tok):

The answer turn came back empty of prose. Look at why: with the tools still in the request, the model's answer turn returned finish_reason: "tool_calls" — it re-called a tool instead of answering. agent.py runs a single answer turn, so it just prints that empty result and stops; but the tell is unmistakable — the move it took on the answer turn was call a tool again, not write the answer. A driver that fed that result back and re-offered the tools (a real agent loop) would take the same move forever. That is the phone-menu cycle: every turn, calling a tool is still a legal option, so the model keeps picking it.

Now see the cost of even that one extra turn. Read the gateway's spend log and count the agent's turns:

curl -s -H "Authorization: Bearer sk-master-smoke" \
  "http://localhost:4000/spend/logs" | jq '. | length'
curl -s -H "Authorization: Bearer sk-master-smoke" \
  "http://localhost:4000/spend/logs" | jq -c '.[-3:] | .[] | {model, total_tokens: .total_tokens}'
46
{"model":"qwen3:0.6b","total_tokens":172}
{"model":"qwen3:0.6b","total_tokens":198}
{"model":"qwen3:0.6b","total_tokens":210}

Every tool-call turn is a billable row — the tool-decide turn and this re-call turn are two separate rows for one question. The exact count you see will differ (it grows by one row per model turn you make); the pattern is what matters. In a real re-executing loop, that row count climbs without bound. This is why the M12 Spend lens is the agent-cost dashboard: a tool that should answer in two turns but shows a row count that keeps climbing is a loop, visible in the ledger.

Step 6 — EXHIBIT B: the knob that gets silently dropped​

The obvious fix looks like tool_choice: "none" — the OpenAI parameter that says "do not call a tool this turn." Add it to the answer turn (tools still present) and watch it fail to help on the gateway path:

sed 's/d2 = chat({"messages": msgs, "think": False, "max_tokens": 1200})/d2 = chat({"messages": msgs, "tools": tools, "tool_choice": "none", "think": False, "max_tokens": 1200})/' \
  labs/m13/agent.py > /tmp/agent_toolchoice.py
export KUBECONFIG=labs/opsmate/k8s/kubeconfig
python3 /tmp/agent_toolchoice.py | tail -4
[llm] finish=tool_calls  tool_calls=1  (26 tok — a billable turn in /spend/logs)
[mcp] get_pod_status({'namespace': 'shop', 'pod': 'payments-api'}) -> payments-api-db4cdfff9-97bm6|Running|21|{"terminated":{"containerID":"containerd...

[llm] grounded diagnosis (35 tok):

The answer turn is identical to Exhibit A — still empty, still finish_reason: "tool_calls", the model still re-calling. tool_choice: "none" had no effect at all: if it had been honored, the answer turn would have been forced to finish_reason: "stop" with prose. It is silently dropped on the LiteLLM→Ollama path — the same class of compatibility drift you met in M2 (think: false not surviving the /v1 route), now at the gateway tier. A spec knob that quietly does not make it through translation is worse than one that errors, because the config looks armed. The lesson: verify behavior, do not trust that a parameter was honored.

Step 7 — The fix that survives: omit the tools​

The fix in the shipped agent.py is the one that works across the translation: on the answer turn, omit tools entirely. No tools in the request means calling one is not a legal move, so the only move left is to write the answer. Re-run the real agent to confirm it terminates cleanly:

export KUBECONFIG=labs/opsmate/k8s/kubeconfig
python3 labs/m13/agent.py | tail -20
[llm] finish=tool_calls  tool_calls=1  (26 tok — a billable turn in /spend/logs)
[mcp] get_pod_status({'namespace': 'shop', 'pod': 'payments-api'}) -> payments-api-db4cdfff9-97bm6|Running|21|{"terminated":{"containerID":"containerd...

[llm] grounded diagnosis (236 tok):
The `payments-api` pod is experiencing a crashlooping issue in the `shop` namespace.
The status indicates that the container was terminated with an error.
- Status: The `payments-api` pod is running, with a climbing restart count.
- Last State: The pod was terminated with an error (exit code 1).
- Recent Logs: the container failed to connect to the database, per the FATAL line.

This indicates the pod is not functioning correctly and requires further
investigation to determine the exact cause and next steps to resolve the issue.

With the tools omitted on the answer turn, finish_reason comes back "stop" and the model writes prose — a single answer turn, grounded in what the tools returned. Contrast that with Exhibits A and B, where the tools stayed in the request and the same answer turn came back finish_reason: "tool_calls" with empty prose. One line — tools absent — is the entire difference between terminating and looping.

Termination is the orchestrator's job, not the model's. You do not prompt your way out of a loop; you remove the option to loop. That single line — tools present on the decide turn, absent on the answer turn — is the whole discipline.

Arg hygiene — the tool contract is defensive

On some runs the model emits an argument like "pod": "pod payments-api" — it prepends the word "pod". The MCP server strips that noise (.replace("pod ", "")) before calling kubectl, so the tool works anyway. Defensive parsing of model-supplied arguments is part of a tool's contract: the model's output is untrusted input, and a robust tool normalizes it rather than trusting it. Your run may or may not hit this — it is state-tolerant.

Part B — the full-lifecycle capstone (OpsMate v1.2)

No new mechanism here — this is the whole course chained in one take. A new runbook lands, and OpsMate's model gets a new version the honest way. Every step is one you validated in an earlier module; the capstone is proving you can run them end to end without stalling.

Step 10 — A new runbook lands; synthesize training data from it​

Add the new runbook to the corpus and synthesize training pairs from it (M6). The synthesizer reads only the corpus — never the golden set — so the training signal stays uncontaminated:

cp labs/m13/cache-eviction.md labs/opsmate/corpus/cache-eviction.md
uv run labs/m6/synthesize.py
  [82/82] vpn-access.md :: Break-glass                      +3 kept  -0 rejected  (running total 224)

kept 224 pairs, rejected 18 (7% filtered out)
  train: 202  ->  labs/opsmate/train/train.jsonl
  eval:  22  ->  labs/opsmate/train/eval.jsonl
  rejects (inspect these): labs/opsmate/train/rejects.jsonl

next: uv run labs/m6/train_lora.py

The kept/rejected counts and totals will differ on your run — the model that writes the pairs is nondeterministic. What holds is the pattern: the synthesizer walks every corpus file (now including cache-eviction.md), quality-filters, and writes train.jsonl with a kept count well above the rejects.

The synthesizer quality-filters (length, format, dedupe, grounding) and writes labs/opsmate/train/train.jsonl. You now have training data that includes the new incident.

  - The signatures were verified against the specified public key
signed & verified 1.2.0 @ sha256:8652...

The digest is unique to your bytes. What matters is that cosign verify passes against the same digest you signed — a signature is only worth what a passing verify proves.

Check yourself

Two things prove this step landed. The tags-list curl above (curl -s http://localhost:5100/v2/opsmate/model/tags/list) now shows 1.2.0 sitting beside 1.0.0 and 1.0.0-candidate — the new version is in the registry. And cosign verify printed "The signatures were verified against the specified public key" against the digest you just signed. Registry has the kit, signature checks out: you can move on. If either is missing, do not proceed — a tag that is not there or a verify that does not pass means the pack or the sign did not take.

Step 13 — The gate must hold the floor​

Before v1.2 can be promoted, it has to pass gate.sh (M12) — the promotion brake. Bring the assistant up serving the tuned weights and run the gate against its /ask (retrieval in the path — gate what you ship):

# serve the candidate: the compose app with the tuned GGUF (see M6/M12 swap).
# OLLAMA_URL points the app's EMBEDDINGS at host Ollama — on Rancher/Colima/plain
# Docker Engine, host.docker.internal is the bridge, so set the host IP you resolved
# in Part A Step 1 (Docker Desktop users can omit it).
MODEL_GGUF=opsmate-tuned-q8_0.gguf OLLAMA_URL=http://192.168.5.2:11434 \
  docker compose -f labs/opsmate/compose.yaml up -d model app
until curl -fsS http://localhost:8001/health >/dev/null 2>&1; do sleep 2; done
APP_URL=http://localhost:8001 FLOOR=8 bash labs/m12/eval-gate/gate.sh; echo "gate exit: $?"

Read the verdict honestly. Which specific questions pass and the exact score will differ on your run (the smoke-profile weights and the 0.6B model are nondeterministic) — the gate scores the golden set deterministically (contains_any, no judge) and compares the count to the committed floor. If the candidate holds the floor, the gate exits 0 and promotion proceeds. If the smoke-profile v1.2 regressed (entirely possible — M6's tuned model lost to the baseline), the gate exits 1 and BLOCKS it. A BLOCK is not a lab failure — it is the gate doing its job, refusing a regression before it ships. Prove the gate bites by stripping retrieval:

TARGET=norag bash labs/m12/eval-gate/gate.sh; echo "norag gate exit: $?"
OpsMate eval gate — generation golden set vs the BARE MODEL (no retrieval — the M5 control)

  fail  gen-db-failover-find-primary
  PASS  gen-deploy-rollback-cmd
  ...

norag gate exit: 1

Same golden set, retrieval stripped: the score collapses below the floor and the gate exits 1. The +RAG value you measured back in M5 is now a live promotion brake — a candidate without grounding does not ship.

Check yourself

The decision is the exit code, not the prose. echo "gate exit: $?" after the gate run is the single fact that decides what happens next: gate exit: 0 means the candidate held the floor and promotion proceeds to Step 14; a non-zero exit means BLOCK, and that is the gate working, not a lab failure (the smoke-profile v1.2 can genuinely regress — M6's did). If you got a BLOCK, read the troubleshooting note at the foot of this lab before assuming something is broken.

Step 14 — Promote by PR, sync by Argo, verify​

If the gate passed, promotion is a PR that bumps the tag in the env repo, reconciled by Argo (M11) — never a kubectl edit. First tear the compose app down (Step 13's serving stack) so the KIND phase has the machine to itself — one heavyweight at a time — then bring the platform cluster up:

docker compose -f labs/opsmate/compose.yaml down    # free the machine for KIND
make -C labs/opsmate k8s-up
export KUBECONFIG=labs/opsmate/k8s/kubeconfig
==> KIND preflight (free memory) ...
==> Ensuring the registry (model source) is up on localhost:5100 ...
==> Creating the slim KIND cluster 'opsmate' (isolated kubeconfig: k8s/kubeconfig) ...
==> Waiting for the node to report Ready (up to 120s) ...
node/opsmate-control-plane condition met
    Node Ready. Cluster is up. Your default context was NOT touched.

Now drive the M11 promotion arc with 1.2.0 as the target tag: open the PR in the in-cluster gitea opsmate-env repo that bumps the model kit tag to 1.2.0, merge it, and let Argo CD sync it onto the cluster. The full M11 setup (Argo CD + gitea via Helm, the gitea admin user, the opsmate-env repo, the Argo Application) and the exact PR/sync commands are unchanged from M11 — refer to that lab; the capstone replays them with the new tag rather than re-teaching them.

The PR is NOT just a tag bump — repeat the per-tag path rewrite

M11's presence-cache fix hardcoded the tag into three places in the env repo's model-server.yaml — the init guard path, the unpack directory, and the server -m path (all /model/kits/1.0.0-candidate/... after M11). Your promotion PR must rewrite all three occurrences of 1.0.0-candidate to 1.2.0 alongside the kit unpack ...:1.2.0 tag bump. Bump only the tag and the 1.2.0 bytes land in the already-populated candidate directory, the presence guard skips the unpack, and the pod serves stale candidate bytes under a 1.2.0 label — the exact lie M11 taught you to kill. The GGUF filename is the same between the candidate and v1.2 kits (both opsmate-tuned-q8_0.gguf), so the tag directory is the only thing separating the two — which is why this rewrite is the load-bearing line of the PR.

With all four strings changed, 1.2.0 is a fresh path on the PVC, the initContainer genuinely re-unpacks the new bytes, and the promotion is real.

What Argo produces is a model deployment whose initContainer unpacks the signed 1.2.0 ModelKit. Verify the serving pod rolled to the new version (the deployment lives in the default namespace, as M11 built it):

kubectl rollout status deployment opsmate-model --timeout=300s
kubectl get pods
kubectl logs deploy/opsmate-model -c fetch-model | tail -5
deployment "opsmate-model" successfully rolled out
NAME                             READY   STATUS    RESTARTS   AGE
opsmate-model-695668f7ff-dd6rw   1/1     Running   0          29s

unpacking signed ModelKit opsmate/model:1.2.0 (model layer only) ...
Unpacking model opsmate-tuned to models/gguf/opsmate-tuned-q8_0.gguf
model on PVC:
-rw-r--r--  1 kit kit  609.8M  opsmate-tuned-q8_0.gguf

The initContainer log is the proof the pod is serving the promoted, signed v1.2 bytes — the 1.2.0 kit unpacked, not the base. The rollout is Ready, and because the promotion went through git (the gitea PR Argo reconciled), a rollback is a git revert — instant, because the old 1.0.0 bytes never left the registry. The dashboards (M10) show the served version the same way they did in M11.

Check yourself

The serve is real only if two things line up. kubectl rollout status deployment opsmate-model returned "successfully rolled out" and kubectl get pods shows the model pod 1/1 Running — the deployment took. And kubectl logs deploy/opsmate-model -c fetch-model ends with Unpacking model opsmate-tuned to models/gguf/opsmate-tuned-q8_0.gguf — the pod unpacked the 1.2.0 kit, not the base. Rollout Ready plus that unpack line together are what "serving the promoted version" means; a Ready pod whose fetch log names the base file is serving stale bytes, which is exactly the lie the Step 14 caution told you to kill.

Troubleshooting
  • Part A: gateway + cluster together OOM the machine — this is the tightest co-residency in the course (~4.1 GiB free). Close other apps. The Part A cluster must be the slim opsmate-agent (one node, one pod) — do not run make k8s-up for Part A (that brings up the model-mount cluster and the registry, which Part A does not need). If it still won't fit, this is the 16 GB comfort path.
  • agent.py errors with a connection refused to the gateway — the gateway isn't live yet (prisma init is 60–90 s) or the api_base still points at an unreachable host. Re-run the Step 1 getent resolve + sed + restart litellm, and confirm curl http://localhost:4000/health/liveliness answers.
  • The MCP tools/call returns ERROR: ... instead of a pod row — KUBECONFIG isn't exported to the isolated file, or the crashloop pod isn't up. Confirm export KUBECONFIG=labs/opsmate/k8s/kubeconfig and kubectl -n shop get pods shows the pod. The server reads KUBECONFIG from the environment.
  • The agent answers without calling any tool — the small model occasionally decides it can answer from the runbook alone. Re-run; the system prompt nudges it to gather live data. An answer with no tool call is un-grounded (it is guessing) — that is the reason the lab teaches tools, so it is a fine thing to observe, then re-run to get the grounded path.
  • Exhibit A doesn't loop / terminates on its own — some model builds are less loop-prone; the loop is a tendency, not a guarantee. If it terminates, read the last message: if it emitted tool_calls on the answer turn at all, that is the loop mechanism (the orchestrator would re-execute and re-offer). The spend-log length growing for one question is the reliable signal.
  • get_pod_logs returns "unable to retrieve container logs" — mid-crashloop, kubectl logs --previous can exit 0 with that text instead of the logs. The server falls back to the current container's logs (matching the text, not the exit code — the spike gotcha). If you still see it, wait for another restart cycle and retry.
  • Part B: make k8s-up fails "registry not reachable — run M7 first" — the KIND phase needs the persisted M7 kits as the model source. Confirm labs/opsmate/data/zot exists and docker compose -f labs/opsmate/compose.yaml up -d registry brings the registry up on localhost:5100.
  • kit pack rejects an absolute path — every path in a Kitfile is relative to the pack context (labs/opsmate). Pack with kit pack labs/opsmate -f "$TMPKIT" ... so models/... resolves inside the context; do not put absolute paths in the temp Kitfile.
  • gate.sh is BLOCK on the v1.2 candidate — this may be correct. The smoke-profile tune can regress (M6's did). Verify the assistant is actually serving the tuned GGUF (MODEL_GGUF=opsmate-tuned-q8_0.gguf) and retrieval works (/ask returns sources); if both are healthy and it still blocks, the candidate genuinely didn't beat the floor — record the BLOCK in the eval report (it is strong evidence the gate works) and, in a real project, train longer before promoting.
  • cosign verify fails after signing — the sign and verify must reference the same digest. Re-resolve DIGEST from the 1.2.0 manifest (tags can move; digests don't) and verify against @${DIGEST}, not the tag.
  • Teardown leaves a cluster behind — make k8s-down deletes the opsmate cluster; the Part A opsmate-agent cluster is deleted in Step 9. Run kind get clusters and kind delete cluster --name <name> for any stragglers. The registry data on ./data/zot is meant to persist.
