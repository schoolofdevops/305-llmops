Deep Dive — Quant Families, Context Economics, Licences & API Drift

The lab put two quants side by side, read a model card, and toured the API. This page goes below each of those. You will learn how the quant families actually differ — why the GGUF you ran targets your CPU and why the AWQ and GPTQ you will meet target a GPU — so you can pick the right quant for the right engine instead of downloading the one that will not load. You will compute what a big context window really costs in memory and drive the num_ctx knob to change it live. You will read the licence classes closely enough to answer "may we fine-tune and ship this?" without a lawyer for the common cases. And you will see exactly where "OpenAI-compatible" stops being compatible — the Responses API shape and tool-call semantics — so a client you write does not silently break on the next backend. These are the layers you reach for when a model will not load on vLLM, when a serving pod gets OOM-killed at a context you thought was safe, or when a compliance review stops your release.

Where this picks up

You need the lab's setup: Ollama on the host and qwen3:0.6b pulled. If you did the lab teardown, nothing is lost — the Q4 course model stays; only the Q8 quant was removed, and none of the commands here need it. Re-running anything here is safe; none of it changes persistent state. If the model was idle, the first request pays the one-time load again (the keep-alive clock). That is all.

1 — Quant families: K-quants vs AWQ vs GPTQ​

In the lab you saw the tag Q4_K_M and treated it as "4-bit". True, but the letters after the number carry real meaning, and knowing them is how you avoid downloading a quant your engine cannot run.

Start with the GGUF K-quants — the family Ollama and llama.cpp use, the one you ran. Read the tag in three parts:

  • Q4 — the target bit-width, roughly 4 bits per weight.
  • K — a K-quant, meaning the quantization is not uniform across the model. It keeps some parts (the attention weights that matter most for quality) at higher precision and squeezes the rest harder. The "K" is what makes a 4-bit model still usable — a naive flat 4-bit would lose far more.
  • M — the size within the family: S (small), M (medium), L (large). M is the common balance point. Q4_K_M means "4-bit K-quant, medium" — the default most people run because it sits at a sensible quality-for-size point.

So Q4_K_M and Q4_K_S are both 4-bit K-quants; the S one is a touch smaller and a touch lower quality. Q8_0 (the lab's other quant) is a plainer 8-bit scheme — the 0 marks an older, simpler format with no K-style mixing, which at 8 bits it does not really need. This is why "which 4-bit?" is a real question: the family and size letters change the trade.

Now the other world. AWQ and GPTQ are also quantization methods, but they are built for GPU serving, and they ship in safetensors, which is why vLLM (M3) consumes them and Ollama does not.

  • GPTQ (post-training quantization) — quantizes the weights after training, layer by layer, using a small calibration dataset to decide how to round each weight so the error stays low. Widely used, well supported on GPUs.
  • AWQ (activation-aware weight quantization) — similar goal, but it looks at which weights matter most to the activations (the values flowing through at runtime) and protects those, quantizing the rest harder. Often a little better quality at the same bit-width, and fast on GPU.

The dividing line to carry is hardware target, not quality ranking. GGUF K-quants are engineered so the CPU and Apple-Silicon Metal paths in llama.cpp run them efficiently — that is why they are the laptop format. AWQ and GPTQ are engineered so GPU kernels run them efficiently — that is why they are the production-GPU format. Point Ollama at an AWQ safetensors model and it will not load; point vLLM at a GGUF and you are fighting the tool. When someone hands you a quantized model, your first question is not "how good is this quant?" but "which engine is it for?" — and the format answers it.

2 — Context-window economics: what 40k actually costs​

The lab noted that the model card advertises a 40960-token context while Ollama runs it at 4096. This section makes that gap a number you can compute and a knob you can turn.

The cost of context is the KV cache from M1, and the formula is the one you already have: KV memory ≈ per-token cost into the number of tokens held. For qwen3:0.6b you computed the per-token cost in M1 at about 112 KiB (that is 2 for key-and-value, into 28 layers, into 8 KV-heads, into 128 head-dim, into 2 bytes for FP16). So the full advertised context costs:

40960 tokens into 112 KiB/token ≈ 4.5 GB of KV cache — for a single request at full context.

Sit with that. The weights of this 4-bit model are about 522 MB on disk. Running it at its maximum context would pin roughly nine times the weights' size in KV cache alone — for one request. That is why no sane default runs a model at its advertised maximum. The advertised context is a capability ceiling ("the model can attend this far"), not an operating point. You configure the context you actually need, because every token of headroom you reserve is memory you cannot give to another concurrent user.

You can drive this knob yourself. Ollama takes num_ctx in the request options to set the context for that model load. Request a larger context and watch the CONTEXT column in ollama ps change (and the loaded SIZE grow with it):

curl -s http://localhost:11434/api/generate -d '{
  "model": "qwen3:0.6b",
  "prompt": "Say hello in one word. /no_think",
  "stream": false,
  "think": false,
  "options": {"num_ctx": 8192}
}' | jq -r '.response'
ollama ps

Expected output

Hi!

NAME          ID              SIZE      PROCESSOR    CONTEXT    UNTIL
qwen3:0.6b    7df6b6e09427    1.5 GB    100% GPU     8192       4 minutes from now

Read what changed. You asked for num_ctx: 8192, and ollama ps now shows CONTEXT 8192 where the lab showed 4096 — and the loaded SIZE grew (about 1.5 GB here, up from roughly 1.0 GB at 4096) because the larger KV reservation is counted in the loaded footprint. (The one-word answer varies — "Hi!", "hello" — and the PROCESSOR column reads 100% GPU on Apple-Silicon Metal or 100% CPU on a plain CPU host, exactly as in the lab; neither changes the memory story.) Your exact size will differ, but the direction is fixed: more context configured, more memory held, before the model has served a single long request. This is the lever you reach for in the serving module when a pod's memory limit and its context setting have to be sized together. Set num_ctx to what your documents need (RAG in M4 will make you think hard about this), not to the maximum the card allows.

The context trap in one line

The context a model supports and the context you configure are different memory bills. Reserving context you do not use is memory you cannot give to concurrent users. Size num_ctx to your real workload, and treat the card's maximum as a ceiling, never a default.

3 — Licence classes, read closely​

The lab said Qwen3 is Apache-2.0 and that permits fine-tune and redistribute. Here is the close read, because "can we ship this?" is a question you will be asked directly, and getting it wrong is expensive.

The model card carries the licence text; you can read it straight from Ollama:

ollama show --license qwen3:0.6b | head -20

Expected output (trimmed; the full Apache-2.0 text is long)

                                 Apache License
                           Version 2.0, January 2004
                        http://www.apache.org/licenses/

   TERMS AND CONDITIONS FOR USE, REPRODUCTION, AND DISTRIBUTION
   ...

Now the three classes you meet in practice, read against the four questions that actually decide adoption — may you use it commercially, fine-tune it, redistribute it, and are there conditions:

Licence classCommercial useFine-tuneRedistributeConditions to watch
Apache-2.0 / MIT (e.g. Qwen3)YesYesYesMinimal — keep the licence and notices. Patent grant in Apache-2.0 is a plus for companies.
Community / custom (e.g. Llama)Yes, mostlyYesYes, with rulesAcceptable-use clause; sometimes a scale threshold (very large deployments need a separate agreement); naming/attribution requirements ("Built with Llama").
Research-only / non-commercialNoYes (research)RestrictedYou may experiment and publish research, but you may not ship it in a product. A common trap on newly released frontier models.

The operating rule: read the licence before you build, because the licence class decides whether your whole plan is legal, and the cost of finding out at the end — after you have fine-tuned (M6), packaged (M7), and prepared to ship — is a rebuild on a different base model, not a config change. For this course, Apache-2.0 on Qwen3 is what lets M6 fine-tune it and M7 sign and redistribute it as an OCI artefact without a licensing conversation. When you swap in your own base model later, the first thing you check is which row of this table it lands in — and for the community and research rows, you read the actual clauses, because "mostly yes" is where the conditions live.

4 — Where "OpenAI-compatible" stops being compatible​

The lab toured /v1/chat/completions and flagged one drift (Ollama's reasoning field). This section reads the two differences that actually break clients: the newer Responses API shape, and tool-call semantics.

The Responses API is a different shape​

Chat Completions models a conversation as a flat list of messages, and you get back choices[].message. The Responses API (OpenAI's newer surface, aimed at tool-using, multi-step agent interactions) restructures this. Instead of one list of messages and one answer, it models an interaction as a sequence of typed items — input items, output items, tool calls, tool results — under a single call that can carry state server-side across steps. The practical differences a client feels:

  • The request field is input, not messages, and it takes a richer item structure, not just {role, content}.
  • The response is a list of typed output items (output_text, tool calls, and more), not a single choices[].message.content — so the "read the answer" line of your client changes.
  • It can hold conversation state across turns server-side, which is the opposite of the stateless-resend-everything model Chat Completions uses.

A client written to pull .choices[0].message.content from Chat Completions reads nothing from a Responses payload, because that path does not exist there. This is not a bug in either API; they are two different contracts. When a provider moves you toward the newer surface, the migration is real client work, not a base-URL swap.

Tool-call semantics differ enough to break naive clients​

Tool calling (letting the model ask you to run a function and feed the result back — the agentic pattern you build in M13) is where compatibility frays most, because different APIs shape the same idea differently:

  • How the model asks — Chat Completions returns a tool_calls array on the assistant message, each with a function name and JSON-string arguments. Older builds used a single function_call object (now deprecated). Anthropic's native API expresses the same intent as tool_use content blocks. Same concept, different field names and nesting.
  • How you reply — Chat Completions wants a follow-up message with role: "tool" and a tool_call_id linking it to the call. Other APIs want a tool_result block referencing an id. A client that hard-codes one shape sends a malformed reply to the other.
  • What the arguments are — usually a JSON string you must parse, and models occasionally emit slightly invalid JSON, so a solid client validates rather than trusts.

The lesson to carry: "OpenAI-compatible" reliably covers the core of Chat Completions — roles, streaming, usage, finish reasons, the things you toured in the lab. It covers the edges — tool-call shapes, reasoning fields, the newer Responses surface — only partially and inconsistently across engines. A client meant to work against more than one backend either sticks to the well-supported core, or it abstracts the differences behind an adapter. That adapter, run as a service in front of many models, is a gateway — and it is exactly what you stand up in M12 to absorb this drift so your application code speaks one stable shape.

Where you will use this
  • Quant family follows hardware, not a quality ranking — GGUF K-quants for CPU/Metal, AWQ/GPTQ for GPU. Use it when: a model will not load on your engine — check the format against the engine before you suspect the download. GGUF belongs to Ollama/llama.cpp; AWQ/GPTQ safetensors belong to vLLM (M3).
  • Configured context, not advertised context, sets your KV memory — and num_ctx is the knob. Use it when: a serving pod gets OOM-killed or you are sizing a memory limit — compute per-token KV into your real context into concurrency, and set num_ctx to the workload, never the card's maximum.
  • Licence class decides use / fine-tune / redistribute — read it before you build. Use it when: a compliance or legal review lands on your model choice — know which of the three classes your base model is in, and read the actual clauses for community and research licences before committing a fine-tune plan (M6/M7).
  • "OpenAI-compatible" covers the core, not the edges (tool calls, Responses API). Use it when: a client that worked on one backend breaks on another — the break is almost always at the edges; stick to the core or put a gateway (M12) in front to translate.

Teardown​

Nothing here seeded persistent state. If you raised num_ctx in section 2, the larger context only applies to that model load and clears when the model unloads after the keep-alive window (or ollama stop qwen3:0.6b now). The Q4 course model stays pulled — M3 uses it to serve the identical model through vLLM behind the identical API.
