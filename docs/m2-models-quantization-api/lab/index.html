Lab — Two Quants Side by Side, and the Raw API Tour

Time

Roughly 45–60 min hands-on, depending on your machine.

Resource path: 8 GB core — everything here runs

Every step runs on the 8 GB core path. No GPU, no cloud, no container stack yet. You already have qwen3:0.6b (the 4-bit Q4_K_M course model, about 522 MB) from M1. In this lab you pull one more quant of the same model, qwen3:0.6b-q8_0 (the 8-bit version, about 832 MB), and put the two side by side. Both together is roughly 2.3 GB of loaded memory if you run them at once — comfortable on 8 GB, but run them one at a time and you will never feel it. Ollama runs native on your host, same as M1.

Before you start

New here? Do the Setup section first. All commands below run from the root of the labs repo (305-labs/). You need ollama, curl, and jq responding. Nothing from M1 needs tearing down — Ollama stays your host model server.

Here is the moment this lab is built for. Your team has to self-host a model, and you have been handed a laptop-class box. Someone asks: "Do we run the 8-bit or the 4-bit version — what does the smaller one actually cost us?" In this lab you answer it with numbers, not opinion. You measure both quants' memory and speed, eyeball their quality on the same questions, read each one's model card, and then take the full raw tour of the API every backend in this course speaks. By the end you can read a model like a spec sheet and talk to it like an operator.

Step 1 — Preflight: Ollama up, course model present​

The lab's make up confirms Ollama is answering and your M1 course model is still pulled:

make -C labs/m2 up

Expected output

==> Checking Ollama is running at http://127.0.0.1:11434 ...
    Ollama is up.
==> Checking the course model qwen3:0.6b (Q4_K_M) is pulled ...
    qwen3:0.6b is present. You are ready for the lab.

If make up says the model is missing, pull it (this is the same Q4 model from M1):

ollama pull qwen3:0.6b

Step 2 — Pull the second quant and list both​

You have the 4-bit model. Now pull the 8-bit version of the same model. It is a separate tag, qwen3:0.6b-q8_0, about 832 MB — a one-time download well inside your budget:

ollama pull qwen3:0.6b-q8_0

Expected output

pulling manifest
pulling 31db97972486: 100% ▕████████████████▏ 832 MB
verifying sha256 digest
writing manifest
success

The download size and digest are point-in-time; yours will differ. What matters is a clean success and a size near 800 MB, not a stray error. Now list both quants together and read their disk sizes:

ollama list | grep 'qwen3:0.6b'

Expected output

qwen3:0.6b-q8_0    f6358994266d    832 MB    9 seconds ago
qwen3:0.6b         7df6b6e09427    522 MB    3 hours ago

There is the memory math from the lesson, made real. Same model, same 751.63M parameters — the 8-bit version takes about 832 MB on disk, the 4-bit about 522 MB. The exact figures on your machine will differ slightly (quantized formats keep some parts at higher precision, so it is not exactly 2× and not exactly 1×), but the pattern holds: fewer bits per parameter, smaller file. The 8-bit model is roughly 1.6 times the size of the 4-bit one.

Step 3 — Same prompt, both quants: memory and speed​

Now the lab's core exhibit. Send the same everyday prompt to each quant through Ollama's native /api/generate route (with think: false pinned, the M1 discipline), and read the decode speed each reports. Then check the loaded memory of each.

First the 4-bit model:

curl -s http://localhost:11434/api/generate -d '{
  "model": "qwen3:0.6b",
  "prompt": "In about 100 words, explain why the sky is blue. /no_think",
  "stream": false,
  "think": false
}' | jq '{quant: "Q4_K_M",
         output_tokens: .eval_count,
         decode_tok_per_s: (.eval_count/(.eval_duration/1e9) | floor),
         load_ms: (.load_duration/1e6 | floor)}'

Expected output

{
  "quant": "Q4_K_M",
  "output_tokens": 95,
  "decode_tok_per_s": 185,
  "load_ms": 1491
}

Now the exact same request to the 8-bit model — only the model tag changes:

curl -s http://localhost:11434/api/generate -d '{
  "model": "qwen3:0.6b-q8_0",
  "prompt": "In about 100 words, explain why the sky is blue. /no_think",
  "stream": false,
  "think": false
}' | jq '{quant: "Q8_0",
         output_tokens: .eval_count,
         decode_tok_per_s: (.eval_count/(.eval_duration/1e9) | floor),
         load_ms: (.load_duration/1e6 | floor)}'

Expected output

{
  "quant": "Q8_0",
  "output_tokens": 64,
  "decode_tok_per_s": 142,
  "load_ms": 1472
}

Read the two side by side. Your exact numbers will differ by machine and run, but the direction is the point and it is the lesson's surprise made concrete: the 4-bit model decodes faster — about 185 tokens per second against the 8-bit model's 142, roughly 30% quicker. (The output_tokens differ too — 95 versus 64 — because each quant chose its own answer length for the same prompt; ignore that and read decode_tok_per_s, which is per-token and comparable.) This is the M1 fact paying off: decode is memory-bandwidth-bound, and a 4-bit weight is half the bytes of an 8-bit weight, so fewer bytes move per token and more tokens land per second. Lower precision did not cost you speed here — it gained you speed.

Now confirm the loaded-memory difference. Run ollama ps while a model is still warm (within the keep-alive window, right after the requests above):

ollama ps

Expected output

NAME               ID              SIZE      PROCESSOR    CONTEXT    UNTIL
qwen3:0.6b-q8_0    f6358994266d    1.3 GB    100% GPU     4096       4 minutes from now
qwen3:0.6b         7df6b6e09427    1.0 GB    100% GPU     4096       4 minutes from now

Two things to read here. First, the loaded SIZE (about 1.0 GB for Q4, 1.3 GB for Q8) is larger than the disk size from Step 2 — because loaded memory is weights plus the engine's runtime buffers plus the KV reservation for the CONTEXT shown (4096 tokens here), exactly the three-part box from the lesson. Second, the UNTIL column ("4 minutes from now") is the M1 keep-alive clock: Ollama holds each model in memory for about five minutes after its last request, then unloads it. If ollama ps is empty, your models have simply unloaded — send any request and they load again.

The PROCESSOR column reports where the weights are running. On an Apple-Silicon Mac it reads 100% GPU — Ollama uses the Metal path, which counts as a GPU here even though you never installed one. On a plain Intel or AMD laptop with no discrete card it reads 100% CPU. Either way the memory story above is identical; the column just names the compute backend your host gave the model.

Run one at a time on 8 GB

If both models show in ollama ps at once, they are both resident and together hold roughly 2.3 GB. That is fine on 8 GB, but you never need both loaded together for this lab — each Step sends to one quant at a time, and the other unloads itself after the keep-alive window. If memory ever feels tight, ollama stop qwen3:0.6b-q8_0 frees it immediately.

Step 4 — Same three questions, both quants: quality, read honestly​

Speed and memory favoured the 4-bit model. So what did the 4 bits cost? Quality headroom. This step lets you see it — or see how little of it shows on a model this small. Ask both quants the same three everyday questions and read the answers side by side.

for Q in \
  "What is the capital of Japan? Answer in one short sentence." \
  "Give one tip for sleeping better at night. One sentence." \
  "In two sentences, what is compound interest?"; do
  echo "=== $Q ==="
  for M in qwen3:0.6b qwen3:0.6b-q8_0; do
    printf '  [%s] ' "$M"
    curl -s http://localhost:11434/api/generate -d "{
      \"model\": \"$M\",
      \"prompt\": \"$Q /no_think\",
      \"stream\": false,
      \"think\": false
    }" | jq -r '.response' | tr '\n' ' '
    echo
  done
done

Expected output (your exact wording will differ every run — read the structure, not the words)

=== What is the capital of Japan? Answer in one short sentence. ===
  [qwen3:0.6b] The capital of Japan is Tokyo.
  [qwen3:0.6b-q8_0] Tokyo.
=== Give one tip for sleeping better at night. One sentence. ===
  [qwen3:0.6b] Start your day with a warm bath, then go to bed at a consistent time each night to promote natural sleep.
  [qwen3:0.6b-q8_0] Set your bedtime routine in advance and create a relaxing environment before bed.
=== In two sentences, what is compound interest? ===
  [qwen3:0.6b] Compound interest is the concept where interest is calculated on the initial principal and also on the accumulated interest from previous periods, leading to exponential growth.
  [qwen3:0.6b-q8_0] Compound interest is the interest is added to the principal amount, which means that both the initial principal and the accumulated interest are compounded over time.

Read this the way an operator should. Both quants get the facts right — Tokyo is Tokyo either way. On the open-ended questions the answers are different but both reasonable; the 8-bit version is sometimes marginally fuller or better-phrased, but on this tiny 0.6B model you would be hard pressed to call a clear winner blind. That is the honest result, and it is the teaching point: on a small model the Q4-vs-Q8 quality gap is subtle, which is exactly why Q4 is a sensible default here. Do not over-learn it — on a large model, or a more aggressive quant, the gap widens and shows most on hard reasoning and exact recall. The discipline is the same either way: you test both on your task and read the difference, rather than assuming the smaller one is fine or the bigger one is worth it.

Step 5 — The terminal model card​

Before you adopt any model you read its card — size, context, quantization, licence. Ollama prints one straight into your terminal. Read the 4-bit model's card:

ollama show qwen3:0.6b

Expected output (trimmed to the fields you read; your build may format slightly differently)

  Model
    architecture        qwen3
    parameters          751.63M
    context length      40960
    embedding length    1024
    quantization        Q4_K_M

  Capabilities
    completion
    tools
    thinking

  Parameters
    stop              "<|im_start|>"
    stop              "<|im_end|>"
    temperature       0.6
    top_k             20
    top_p             0.95
    repeat_penalty    1

  License
    Apache License
    Version 2.0, January 2004
    ...

Read every field the lesson named:

  • parameters 751.63M — the real count, not the "0.6b" branding. When you size memory, this is the number you multiply by bytes-per-parameter. Branding rounds down; the card tells the truth.
  • context length 40960 — the maximum this model supports. But look back at ollama ps in Step 3: it ran at CONTEXT 4096, not 40960. That gap is money. At the full 40960-token context, the KV cache alone (M1: about 112 KiB per token) would pin roughly 4.5 GB of memory — more than the whole rest of the model. You configure the context you need, not the maximum the card advertises. "Supports 40k" and "running at 40k" are different memory bills.
  • quantization Q4_K_M — confirms which precision this tag actually is.
  • Capabilities — this model can do completion, tools (function calling, M13), and thinking (the mode you pinned off in M1).
  • License Apache License 2.0 — permissive. You may use it commercially, fine-tune it (M6), and redistribute it (M7). This is why the course can build on it freely.

Now show the 8-bit variant and note that only one field moves:

ollama show qwen3:0.6b-q8_0 | grep -i quantization

Expected output

    quantization        Q8_0

Same card, same 751.63M parameters, same 40960 context, same Apache licence — one field changed: Q8_0 instead of Q4_K_M. That is quantization in one line: the same model, recorded at a different precision.

The before-you-adopt checklist

Every model, before it goes anywhere near production, gets read for four things off its card:

  1. Size — parameters into bytes-per-parameter. Does it fit the box, with room for runtime buffers and your KV cache?
  2. Context — what it supports vs what you will run it at. Long contexts are expensive in KV memory; configure only what you need.
  3. Quantization — which precision this exact tag is, and whether that trade suits your task (test it).
  4. Licence — what you may legally do: use commercially, fine-tune, redistribute. Read it before you build on the model, not after.

Step 6 — The raw API tour​

You have read the model. Now speak to it, properly, through the /v1/chat/completions contract every backend in this course understands. This is the anchor for everything from here on.

6a — One full body: read the usage meter​

Send a non-streaming request and read the whole JSON body. The usage block is the billing meter, made explicit:

curl -s http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3:0.6b",
    "stream": false,
    "messages": [
      {"role": "system", "content": "You are a concise assistant. /no_think"},
      {"role": "user", "content": "Name the largest planet in our solar system."}
    ]
  }' | jq '{content: .choices[0].message.content,
           role: .choices[0].message.role,
           finish_reason: .choices[0].finish_reason,
           usage: .usage}'

Expected output

{
  "content": "The largest planet in our solar system is Jupiter.",
  "role": "assistant",
  "finish_reason": "stop",
  "usage": {
    "prompt_tokens": 34,
    "completion_tokens": 175,
    "total_tokens": 209
  }
}

Read the meter. prompt_tokens (34 here) is what prefill read — your system message plus the question. completion_tokens is what decode wrote — and this is where this Ollama build springs a surprise worth its own paragraph. total_tokens is the sum, and it is the exact number a hosted provider would bill you and the exact number that filled your KV cache. When a bill or a latency surprises you, this is the first field you read. finish_reason: "stop" means the model finished naturally — a complete answer. Hold that value; you will break it on purpose in 6d.

Now the surprise. The visible answer is one short sentence — a dozen words, maybe 11 tokens of English. Yet completion_tokens reads far higher (175 on this run, and it will bounce between roughly 130 and 200 run to run). Where did the extra tokens go? Into a hidden reasoning trace. On this Ollama build the OpenAI-compatible /v1/chat/completions route does not honour the /no_think you put in the system message — it generates the model's full thinking pass, returns it in a separate reasoning field the content above does not show, and counts every one of those thinking tokens in completion_tokens. This is the M1 compatibility-drift finding hitting your bill directly: the /api/generate route with "think": false (Step 3) genuinely silenced thinking, which is why its output_tokens were small; the /v1 route on this build does not, so its completion_tokens carry a tax you cannot see in the answer. That is precisely why you read the usage meter and not the length of the text: you are billed for tokens the response never shows you. (Add jq '.choices[0].message.reasoning' to the command above to see the trace that ran up the count.)

6b — Multi-turn proves the API is stateless​

Now the property that matters most: the server remembers nothing. To ask a follow-up, you resend the whole history — including the model's own previous answer. Watch the assistant turn go back in:

curl -s http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3:0.6b",
    "stream": false,
    "messages": [
      {"role": "system", "content": "You are a concise assistant. /no_think"},
      {"role": "user", "content": "Name the largest planet in our solar system."},
      {"role": "assistant", "content": "The largest planet in our solar system is Jupiter."},
      {"role": "user", "content": "How many moons does it have, roughly?"}
    ]
  }' | jq -r '.choices[0].message.content'

Expected output

Jupiter has *seven large moons*, commonly known as the Ganymede.

The follow-up said "it", and the model knew "it" meant Jupiter — you can see it answer about Jupiter — but not because the server remembered the last call. (The moon count it gives may well be wrong or garbled; this is a 0.6B model and the point here is the pronoun resolution, not the accuracy of the fact. Read that it resolved "it" to Jupiter, and read past whatever number it invents.) It knew because you resent the entire conversation: the system message, the first question, the model's own "Jupiter" answer (the assistant turn), and only then the new question. Delete that assistant line and the model has no idea what "it" refers to. This is the call-centre-with-no-memory from the lesson, proven: the server holds nothing; the client carries the context. And the ops consequence is right here in front of you — this four-message request sent more tokens than the two-message one in 6a, and a real ten-turn chat would resend all nine prior turns on the tenth call. Long conversations get more expensive per turn, because every turn resends the whole history.

6c — Streaming, chunk by chunk​

Now stream the same kind of request and watch the answer arrive in pieces — the decode loop over the wire:

curl -N -s http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3:0.6b",
    "stream": true,
    "messages": [{"role": "user", "content": "In one sentence, what is a solar eclipse? /no_think"}]
  }'

Expected output (trimmed — many content chunks in the middle)

data: {"id":"chatcmpl-162","object":"chat.completion.chunk","created":1784463161,"model":"qwen3:0.6b","system_fingerprint":"fp_ollama","choices":[{"index":0,"delta":{"role":"assistant","content":"","reasoning":"Alright"},"finish_reason":null}]}

data: {"id":"chatcmpl-162","object":"chat.completion.chunk","created":1784463161,"model":"qwen3:0.6b","system_fingerprint":"fp_ollama","choices":[{"index":0,"delta":{"role":"assistant","content":"","reasoning":","},"finish_reason":null}]}

data: {"id":"chatcmpl-162","object":"chat.completion.chunk","created":1784463161,"model":"qwen3:0.6b","system_fingerprint":"fp_ollama","choices":[{"index":0,"delta":{"role":"assistant","content":"","reasoning":" the"},"finish_reason":null}]}

... (the reasoning trace streams first, then the content chunks arrive with the answer text in delta.content) ...

data: {"id":"chatcmpl-162","object":"chat.completion.chunk","created":1784463162,"model":"qwen3:0.6b","system_fingerprint":"fp_ollama","choices":[{"index":0,"delta":{"role":"assistant","content":""},"finish_reason":"stop"}]}

data: [DONE]

The id and created are point-in-time. Read the anatomy: each chunk carries a delta, the answer building up one or two tokens at a time, until a final chunk carries a delta with no more content and finish_reason: "stop", then the stream closes with [DONE]. Notice the very first chunks above carry "content":"" and put their text in a "reasoning" field instead — that is the same hidden thinking trace that ran up your completion_tokens in 6a, now streaming by in the open (the :::note below returns to it). The visible answer arrives once the reasoning finishes, in the delta.content of the later chunks. Streaming did not change what the model produced — 6a's non-streamed request produced the same kind of answer in one body. It changed when you see it: first token fast, rest as they come. That is why a chat UI feels responsive.

Compatibility drift, the M1 callback

On this Ollama build you may see extra "reasoning":"..." fields inside the early delta objects even with /no_think in the message — the same thing you met in M1. The OpenAI spec does not define a reasoning field; Ollama adds it. That is compatibility drift: an engine shaping the response its own way beyond the shared spec. It is harmless here, but it is exactly the kind of difference a client written for one backend can trip over on another — and the reason a gateway (M12) exists to smooth it over.

6d — Break the stop: finish_reason "length"​

finish_reason: "stop" meant the model finished. Now force it to not finish, by capping the output low with max_tokens. The model gets cut off mid-answer, and the field tells you so:

curl -s http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3:0.6b",
    "stream": false,
    "max_tokens": 10,
    "messages": [{"role": "user", "content": "Explain how a rainbow forms, in detail. /no_think"}]
  }' | jq '{content: .choices[0].message.content,
           finish_reason: .choices[0].finish_reason,
           completion_tokens: .usage.completion_tokens}'

Expected output

{
  "content": "",
  "finish_reason": "length",
  "completion_tokens": 10
}

Read it. completion_tokens is exactly your cap of 10, and finish_reason is now "length", not "stop". That single field is how you tell a complete answer from a truncated one, which look identical if you only read the text. In production, a spike of finish_reason: "length" means your max_tokens is too low and users are getting guillotined answers — a bug you would never spot without reading this field. stop = finished; length = ran out of room.

And this build makes the cut even starker: content comes back empty. Remember 6a — on the /v1 route this model spends its first tokens on the hidden reasoning trace. With max_tokens: 10, all ten tokens were consumed by that trace before the visible answer began, so the model hit the cap while still "thinking" and the user-facing content never started. (Run the same command through jq '.choices[0].message.reasoning' and you will see those ten tokens sitting in the reasoning field.) This is the two findings compounding: a max_tokens that looks generous for a one-line answer can be entirely eaten by reasoning you did not ask for and cannot see — the answer is not just truncated, it is absent, and only finish_reason: "length" and the usage meter tell you why. On a real workload you size max_tokens for the reasoning budget plus the answer, or you turn reasoning off at a route that actually honours it (Step 3's /api/generate with "think": false).

Step 7 — Teardown​

You proved what you needed with the 8-bit model; now reclaim its disk. Remove the Q8 quant and keep the Q4 course model (M3 needs it):

ollama rm qwen3:0.6b-q8_0

Expected output

deleted 'qwen3:0.6b-q8_0'

That frees about 832 MB. Confirm the course model is still present:

ollama list | grep 'qwen3:0.6b'

Expected output

qwen3:0.6b    7df6b6e09427    522 MB    3 hours ago

The lab's make down does the same removal if you prefer:

make -C labs/m2 down

Expected output

==> Removing the M2-only quant qwen3:0.6b-q8_0 (reclaims ~832 MB) ...
    Removed (or already absent). The Q4 course model qwen3:0.6b stays for M3.
Ollama keeps running as your host model server.
Troubleshooting
  • ollama pull qwen3:0.6b-q8_0 fails or stalls — it is an 832 MB download; a flaky network can interrupt it. Re-run the pull; Ollama resumes rather than restarting. Confirm the tag with ollama list — it must read qwen3:0.6b-q8_0 exactly (the -q8_0 suffix is the quant).
  • ollama ps is empty — your models unloaded after the keep-alive window (about five minutes idle, the M1 clock). This is normal, not an error. Send any request to a model and it loads again; then ollama ps shows it.
  • Both models loaded at once feels heavy on 8 GB — you never need both resident. Free the one you are not using: ollama stop qwen3:0.6b-q8_0. Each Step here sends to one quant at a time.
  • Q4 and Q8 answers look identical in Step 4 — that is the honest, expected result on a 0.6B model, not a mistake. The quality gap is subtle at this size. Re-run with your own harder questions if you want to probe for a difference; the point is that you measure it rather than assume it.
  • Step 6 streams reasoning chunks even with /no_think — expected on this Ollama build (the M1 finding). It does not affect the streaming structure. Use the native /api/generate route with "think": false (Step 3) when you need reasoning genuinely off.
  • completion_tokens in 6a is far bigger than the visible answer (130–200 for one sentence) — expected, not a bug. The /v1/chat/completions route on this Ollama build does not honour /no_think: it generates the full hidden reasoning trace and counts it in completion_tokens. The count bounces run to run because the trace length varies. Read .choices[0].message.reasoning to see the tokens you were billed for. If you need thinking genuinely off (and the small token count that comes with it), use /api/generate with "think": false as in Step 3 — the /v1 route does not suppress it here.
  • Step 6d returns an empty content (not a half-sentence) — expected on this build, and it follows from the point above. With max_tokens: 10, the model spends all ten tokens on the hidden reasoning trace before the visible answer starts, so content is "" while finish_reason is still "length" and completion_tokens is still 10. The truncation lesson holds — read finish_reason, not the text. Raise max_tokens (try 200) and you will see visible answer text appear once the reasoning budget is covered.
  • jq: command not found — install jq (brew install jq on macOS, apt-get install jq on Debian/Ubuntu). It is on the setup checklist.
