Models, Quantization & the OpenAI-Compatible Contract

Time

Lesson video ~25 min · Lab ~45–60 min hands-on, depending on your machine.

Your team has decided to self-host a model. Maybe the data cannot leave your network, maybe the hosted bill got too big, maybe you just want control. Either way the question arrives on your desk: which model do we run, and will it fit the box we have? You open a model hub and there are thousands of them. The same model comes in a dozen versions with cryptic tags — q4_k_m, q8_0, fp16, awq. One says 0.6B, another says 7B, another 70B. You have eight gigabytes of memory on the machine you were given. Nothing on the page tells you, in plain terms, which one fits and what you give up by squeezing it in.

That is the job of this module. By the end you will look at a model on a hub and read it the way you read a spec sheet: how much memory it needs, what you traded away to make it smaller, what the licence lets you do with it, and which serving engine can run it. And you will speak to it properly — through the one API that every backend in this course understands, the same API your ChatGPT client speaks under the hood. We build the reading skill first, then the speaking skill.

In M1 you learned what a model does at runtime — tokens, the prefill and decode phases, the KV cache that sets your capacity. This module is about the model itself as an artefact you pick, size, and deploy. Everything here builds on that runtime picture, so we will not re-explain it; we will use it.

Memory math — a model is mostly weights, and weights have a size​

Start with the first question, because it is the one that stops a deployment cold: will this model fit?

A model is, at heart, a giant pile of numbers called weights, that is the learned values that make the model do what it does. When people say a model is "0.6B" or "7B" or "70B", the B means billion, and the number is roughly how many of these weights the model has. That is the parameter count. More parameters usually means a more capable model, and it always means more numbers to store.

Now, storing a number takes space, and how much space depends on the precision, that is how many bits you spend on each number. This is the whole game. A number stored in full 16-bit precision (called FP16, that is 16-bit floating point) takes 2 bytes. The same number stored in 8-bit takes 1 byte. In 4-bit, half a byte. So the memory a model's weights need is simply:

weights memory ≈ number of parameters into bytes per parameter

Think of it like a photo library on your phone. The number of photos is fixed — that is your parameter count. But you can store each photo at full resolution or compressed. Full resolution looks best and fills the disk; compressed fits far more but each photo loses a little detail. The count of photos does not change. What changes is how many bytes you spend on each one. A model is the same: the parameter count is fixed by the model, but you choose how many bytes to spend per parameter.

Let us do the sum for the real course model. In M1 you ran qwen3:0.6b. Its actual parameter count — you will read this off the model card in the lab — is about 751.63 million, not exactly 0.6 billion (branding rounds down; the real count is bigger, and reading the true number is a skill this module teaches). Here is what those parameters cost at three precisions:

PrecisionBytes per parameterWeights memory (751.63M params)What it is
FP162~1.4 GBfull 16-bit, the original release format
Q8 (INT8)~1~0.8 GB8-bit, near-original quality
Q4~0.5~0.5 GB4-bit, the common laptop default

The exact figures shift a little because quantized formats keep some parts at higher precision — you will see the real disk sizes in the lab (about 832 MB for Q8, about 522 MB for Q4). But the pattern is what matters: cut the bytes per parameter and you cut the memory, close to proportionally. That is why a 4-bit model fits a laptop and a 16-bit one may not.

But weights are not the whole memory bill. Remember M1: when you actually serve the model, memory goes to three things.

This is why, in the lab, the size Ollama reports as loaded (about 1.0 GB for Q4, 1.3 GB for Q8) is bigger than the size on disk. Loaded memory is weights plus the engine's runtime buffers plus a reservation for the KV cache of the context you configured. When you size a box, you are budgeting for all three, not just the weights. Quantization shrinks the weights term — the biggest and most fixed one — which is exactly why it is the first lever you reach for.

Before you take that math on trust, drive it. The planner below is the same box drawn above, made interactive: pick a model size and precision, then set the context and the number of concurrent users you plan to serve, and watch the three bands stack up against an 8, 16, or 24 GB box. Try the same model at Q4, Q8, and FP16 to feel precision scale the weights band. Then leave the model fixed and push the context up — the KV band grows while the weights band does not, and a model that fit a moment ago will spill over the top. That last move is the one that catches teams out: "supports 40k context" and "running at 40k context" are two very different memory bills.

The habit to carry out of this section

Before you deploy any model, do the back-of-envelope sum: parameters into bytes-per-parameter gives you the weights, then add runtime buffers and the KV cache for your context (the M1 math). If that total does not fit your box, your options are a smaller model, a lower precision, or a shorter context — and now you know which lever moves what.

Quantization — the photo at lower resolution​

You just used quantization without naming the mechanism. Let us name it, analogy first.

Quantization is storing the model's weights at lower precision — fewer bits per number — to make the model smaller. The word sounds heavy but the idea is the one you already met: same photo, lower resolution.

Print a photograph at 300 dots per inch and it looks sharp; you cannot see the individual dots. Print the same photo at 72 dots per inch and it is still clearly the same photograph — the same faces, the same scene — but look closely and the fine detail is coarser, edges a little blocky. You used far less ink and the print is much smaller. You did not change what the picture is. You changed how finely each part of it is recorded. Quantization does exactly this to a model's weights: it records each weight more coarsely, so the model is smaller, and it is still the same model — but the finest detail of its "knowledge" is recorded less precisely.

Here is the part that surprises most people, and it is a direct callback to M1. You would expect the smaller, lower-precision model to be worse at everything, including speed. It is not. On the machines this course runs on, the 4-bit model decodes faster than the 8-bit one. In the lab you will measure it: Q4 at roughly 180 tokens per second, Q8 at roughly 140 — the 4-bit model close to 30% faster (your exact numbers will differ run to run; the gap is the invariant).

Why? Because of the one fact you locked in M1: decode is memory-bandwidth-bound. Each token the model writes, it must move the relevant weights in and out of memory. The limit is not raw compute; it is how many bytes you shift per step. A 4-bit weight is half the bytes of an 8-bit weight. Fewer bytes to move per token means more tokens per second. So quantization does not trade quality for speed — on bandwidth-bound decode it gains speed. What it trades is quality headroom.

And that trade must be read honestly, which is the second reason this section matters. On this tiny 0.6B model, the quality gap between Q4 and Q8 is subtle — in the lab you will ask both the same everyday questions and struggle to tell them apart. That is real, and it is why Q4 is a fine default for a small model. But do not over-learn it. On a large model, or one pushed to a very aggressive quantization (3-bit, 2-bit), the loss becomes visible — more so on hard reasoning and on exact recall than on casual chat. The rule to carry: quantization always costs some quality; how much you can see depends on the model size and how far you push it. You test on your own task, you do not assume.

The trade, stated plainly

Lower precision → smaller weights → faster bandwidth-bound decode and a smaller memory footprint → some loss of quality headroom, subtle on small models, more visible on large ones or aggressive quants. You choose the point on that curve for your task, and you verify it, rather than reaching for FP16 by reflex or Q4 by reflex.

Reading a model card — the label on the medicine strip​

You now know a model has a size and a precision. But a model on a hub carries far more than that, and reading it is a skill that saves you from adopting something you cannot legally ship or cannot technically run. The place all of this lives is the model card.

Think of a strip of medicine from the chemist. Before you take it you read the label: the dose, the expiry, who made it, what it is for, what it interacts with. You do not swallow an unlabelled pill. A model card is that label. Before you adopt a model into production you read: how big it is, how much context it supports, what licence governs it, who published it and from what. Skip the label and you find out the hard way — a licence that forbids your use case, a context window too small for your documents, a provenance you cannot vouch for in a compliance review.

You do not need a website to read a model card. Ollama ships one into your terminal. In the lab you will run ollama show qwen3:0.6b and read these fields:

  • Parameters — the real count. It reads 751.63M, not "0.6B". The branding rounds; the card does not. When you are sizing memory, you use the real number.
  • Context length — the model card reports 40960, the maximum context this model was built to handle. But the context Ollama actually runs it at (visible in ollama ps) is smaller — 4096 by default. That gap matters, and here is why: the KV cache from M1 grows with context. At the full 40960-token context, the KV cache alone would pin roughly 4.5 GB of memory (40960 tokens into the ~112 KiB-per-token figure you computed in M1). You do not pay for context you do not configure. So "the model supports 40k context" and "I am running it at 40k context" are two very different memory bills, and confusing them is how people run out of memory. You configure the context you need, not the maximum the card advertises.
  • Quantization — the field that says Q4_K_M on the default and Q8_0 on the variant. Same card, one field different. This is where you confirm which precision you actually pulled.
  • Licence — what you are legally allowed to do with the model. This one gets its own paragraph.

The licence is the field engineers skip and lawyers do not. Models come under different licence classes, and they permit very different things:

  • Apache-2.0 / MIT — genuinely permissive. You may use commercially, fine-tune, and redistribute, with minimal conditions. Qwen3 (the course model) is Apache-2.0, which is why this course can build on it freely — and why, when you fine-tune it in M6 and package and redistribute it in M7, you are within your rights.
  • Community / custom licences (for example the Llama licence) — usable commercially but with conditions: acceptable-use clauses, sometimes a size threshold above which you need a separate agreement, sometimes naming or attribution requirements.
  • Research-only / non-commercial — you may experiment but you may not ship it in a product.

The point is not to memorise licences. It is to read the field before you build on a model, because the cost of finding out later — after you have fine-tuned and shipped — is a rebuild, not a config change.

Engine and format — which runner can run this model​

You have picked a model, checked its size, read its licence. One question remains before you can serve it: what format is it in, and which engine runs that format? Getting this pairing wrong is the most common early stumble — you download a model, point your serving engine at it, and it refuses to load, because the format and the engine do not match.

Models ship in two dominant formats, and each has its natural engine:

  • GGUF — a single-file format built for running quantized models efficiently on CPU and on Apple Silicon (Metal). This is what Ollama and llama.cpp consume. The qwen3:0.6b you have been running is GGUF. It is the format that makes laptop-class serving practical, which is exactly why this course starts here.
  • safetensors — the format models are usually released in, holding full-precision (FP16) weights or GPU-oriented quantizations (AWQ, GPTQ — you meet those in the Deep Dive). This is what vLLM consumes, the production GPU serving engine you stand up in M3.

Read this as a decision framework, not a rule to memorise. When you are handed a model, your first two questions are "what format?" and "what am I serving it on?" — and those two answers pick your engine. GGUF on a laptop CPU means Ollama or llama.cpp. safetensors on a GPU means vLLM. In this module you prove the GGUF-and-Ollama side, live, on your own machine. In M3 you serve the identical model through vLLM and swap engines under an unchanged client — which only works because of the last idea in this lesson: the one API contract that sits above every engine.

The OpenAI-compatible contract — a call centre with no memory​

Everything above is about picking and sizing the model. This last section is about talking to it — and it is the load-bearing idea for the rest of the course, because every backend you serve, from Ollama today to vLLM in production, speaks the same API. Your client code never changes when the engine underneath changes. That is by design, and the design is the OpenAI-compatible API: the /v1/chat/completions endpoint your ChatGPT client speaks, that every serious serving engine now implements.

The single most important property of this API, and the one that surprises engineers coming from stateful systems, is that it is stateless. The model server remembers nothing between calls.

Picture a call centre where every call is answered by a different agent who has never spoken to you before and keeps no notes. If you rang yesterday about a broken connection and you ring again today, the new agent knows nothing about it. So to continue the conversation, you must repeat the whole story every single call: "Yesterday I reported my connection dropping, you asked me to restart the router, I did, and it is still dropping." Only then can they help. The agent holds no memory; the caller carries the context.

The chat API works exactly like this. Every request is answered fresh, with no memory of the last one. So to have a multi-turn conversation, the client resends the entire history every time. This is why a chat request is a list of messages, not a single string:

{
  "model": "qwen3:0.6b",
  "messages": [
    {"role": "system",    "content": "You are a concise assistant."},
    {"role": "user",      "content": "What is the capital of France?"},
    {"role": "assistant", "content": "Paris."},
    {"role": "user",      "content": "And its population?"}
  ]
}

Look at what happened. To ask the follow-up "And its population?", the client had to resend the system instruction, the first question, and the model's own previous answer (the assistant turn) back to the server. The model did not remember saying "Paris" — the client reminded it. Three roles do this work:

  • system — the standing instruction that frames every turn (tone, role, rules).
  • user — what the person said.
  • assistant — what the model said before, fed back in so the model can see its own prior turns.

This statelessness is not a limitation to work around; it is the property that makes serving scale. Because the server holds no session, any request can go to any replica — there is no "your conversation lives on server 3". It also means the ops consequence you will feel directly: every turn resends the whole history, so a long conversation sends more and more tokens each turn, and tokens are the meter (M1). A ten-turn chat is not ten cheap calls; the tenth call carries all nine turns before it.

Reading a response: usage, streaming, and finish reasons​

When you call the API without streaming ("stream": false), you get one JSON body back. Three parts of it earn your attention as an operator:

  • usage — the billing meter, made explicit. It reports prompt_tokens (what prefill read), completion_tokens (what decode wrote), and total_tokens. This is the exact number a hosted provider charges you on, and the exact number that filled your KV cache. When a bill or a latency number surprises you, this field is where you look first.
  • choices[].message — the answer itself, with its role (assistant) and content.
  • choices[].finish_reason — why the model stopped. stop means it finished naturally. length means it hit your max_tokens cap and was cut off mid-thought — a truncated answer, not a complete one. Reading this field is how you tell "the model finished" from "the model got guillotined", which look identical if you only read the text.

When you do stream ("stream": true), the answer arrives as many small chunks over the wire — that drip of words you watched in M1. Each chunk carries a delta with the next piece of content, and the final chunk carries the finish_reason. Streaming does not change what the model produces; it changes when you see it — first token fast, rest as they come. That is why a chat UI feels responsive even on a long answer: it shows you the decode loop live rather than waiting for the whole thing.

One honest wrinkle, and it is a callback to M1: "OpenAI-compatible" is a promise every engine mostly keeps, not perfectly. In M1 you saw Ollama's streaming route surface the model's reasoning in an extra delta.reasoning field that the OpenAI spec does not define. That is compatibility drift — an engine adding or altering fields its own way. It is minor here, but it is real, and it grows as engines add features (thinking modes, tool calls) faster than the shared spec settles. You keep this in mind when you write a client meant to work against more than one backend.

The API is a moving target​

The /v1/chat/completions form you just learned is the workhorse and will be for years. But it is not frozen. OpenAI has introduced a newer Responses API with a different form aimed at tool-using, multi-step "agentic" interactions — and provider-native APIs (Anthropic's, Google's) differ again in their own ways. Tool-call semantics in particular — how the model asks to call a function and how you feed the result back — differ enough between APIs that a client written naively against one breaks against another. The Deep Dive reads these differences properly.

For now, hold two facts. First, Chat Completions is the stable contract this course builds on end to end. Second, when you have many models behind many slightly-different APIs, the pattern that absorbs the drift is a gateway — one endpoint in front that presents a single API and translates to each backend. You stand one up in M12. This lesson is where you learn why it exists: the API contract is real, load-bearing, and moving, all at once.

What you'll do next​

In the lab you will pull the same course model at a second precision (qwen3:0.6b-q8_0) and put the two quants side by side on your own machine: their disk sizes, their loaded sizes, their decode speed — where you will watch the 4-bit model come out faster — and their answer quality on the same everyday questions, read honestly. You will open the terminal model card with ollama show and read every field this lesson named. Then you will take the full raw tour of /v1/chat/completions: the usage meter, a multi-turn request that proves the API is stateless by making you resend the history, a streamed response chunk by chunk, and a finish_reason: length you trigger on purpose. You finish by reclaiming the Q8 model's disk, leaving your course model clean for M3.

The skill you leave with is reading a model as an artefact — its size, its trade-offs, its licence, its format — and speaking to it through the one contract that outlives any single engine. That is the ground the rest of the course stands on.
