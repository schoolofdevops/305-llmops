Deep Dive — PagedAttention, the Batching Scheduler & the arm64 Crash

The lesson taught continuous batching, PagedAttention, and prefix caching as concepts, and the lab let you watch a queue form and a cache hit. This page goes under each of those. You will see how PagedAttention's block tables actually lay out memory and kill the fragmentation that caps a naive engine. You will walk the continuous-batching scheduler loop step by step, so "requests join and leave per step" becomes a mechanism you could describe to a colleague, not a slogan. Then the part most practitioners never see until it bites them in production: a forensic read of why the vLLM CPU image boots and then crashes on the Apple-Silicon path this course targets — the M1 KV math surfacing as a real error, a container-file-mount trap that eats hours, and the honest lesson that "the image exists for my architecture" is not "the image works on my host." You close by reading prefix caching as hard evidence, not a claim. These are the layers you reach for when a serving pod OOM-kills at a concurrency you thought was safe, when an engine will not start on a new architecture, or when someone asks why one GPU serves ten times the users it "should."

Where this picks up

You need the lab's setup: the OpsMate stack up (make -C labs/opsmate up) so llama-server is answering on 8080, and the GGUF model present. The vLLM section is a read, not a run — the crash it dissects is one you do not want to reproduce on an 8 GB laptop, and the evidence is folded in from the course spike. Nothing here changes persistent state; re-running the llama-server commands is safe.

1 — PagedAttention: block tables and the fragmentation it kills​

The lesson's analogy was cubbies plus an index card. Here is the real mechanism. A request's KV cache is not stored as one contiguous block. It is stored as a set of fixed-size blocks (vLLM's default is 16 tokens per block), scattered across GPU memory wherever there is room, and each request carries a block table — an array mapping its logical token positions to the physical blocks that hold them.

Walk one request. It starts with a 40-token prompt. At 16 tokens per block that needs three blocks (16 + 16 + 8, the third block half-used). The engine allocates physical blocks — say 12, 5, and 27, wherever they happen to be free — and writes the request's block table: [12, 5, 27]. As decode adds tokens, block 27 fills, and the engine grabs one more free block (say 3) and appends it: [12, 5, 27, 3]. The request never reserved space for tokens it had not generated. When the request finishes, all four blocks return to the free pool individually, ready for any other request.

Now the fragmentation math, because it is the number that justifies the whole scheme. Take the contiguous approach the paged one replaces. There, each request reserves a single block sized to the model's maximum sequence length, because the memory must be contiguous and you cannot know in advance how long the request will run. Two kinds of waste follow:

  • Internal waste (over-reservation). A request that reserves room for 2048 tokens but generates 100 leaves ~95% of its reservation unused for its whole lifetime — memory no other request can touch. Across many short requests, the majority of KV memory is reserved-but-empty.
  • External waste (fragmentation). As requests of different sizes come and go, the free memory left between live contiguous blocks ends up in pieces too small for the next request's full reservation. The memory exists, but it is unusable — the classic fragmentation an OS solves with paging.

Paging removes both. Blocks are allocated on demand (no over-reservation — you hold exactly the blocks your tokens fill, ±one partial block) and any free block fits any request (no external fragmentation — a 16-token block is interchangeable). vLLM's own measurement of the effect is the headline number: near-zero KV waste against roughly 60–80% waste in the naive scheme, which translates directly into several times more concurrent requests per GPU. That multiple is throughput, and throughput is cost per answer. This is why PagedAttention was the change that made high-concurrency LLM serving economical, and why every serious engine now does something like it.

The one-line version to carry into a capacity review

Contiguous KV wastes memory to over-reservation and fragmentation; paged KV holds only the blocks your tokens actually fill and lets any free block serve any request. The payoff is measured in concurrent requests per GPU — which is throughput, which is cost. When you size a serving box, the relevant number is not "how big is the model" but "how many concurrent KV blocks fit after the weights," and paging is what makes that number large.

2 — The continuous-batching scheduler, one step at a time​

The lesson said requests join and leave the batch every step. Here is the loop that does it. A continuous-batching engine runs a scheduler that, on every single decode step, does four things:

Read each stage against what you saw in the lab:

  • Admit. New arrivals in the waiting queue join the running batch if there are free KV blocks to hold their prompt. This is where requests_deferred comes from: when there is no room, arrivals wait here. The gauge you watched climb in Step 5 is the depth of this queue.
  • Step. The engine runs exactly one decode step — one token — for every request in the batch at once, as a single batched matrix operation. This is the efficiency: the GPU (or CPU) does one big step covering all active requests, not one small step per request in turn.
  • Retire. Any request that just produced its stop token, or hit its max_tokens, is done. It leaves the batch immediately and its KV blocks return to the pool — it does not wait for its batch-mates. This is why a short request trapped behind a long one under static batching finishes on time under continuous batching.
  • Preempt. The hard case: a running request needs another KV block to keep going and there are none free. The scheduler picks a victim, evicts its blocks (recomputing or swapping them later), and requeues it. This is graceful degradation under memory pressure rather than an out-of-memory crash — and it is why a well-behaved engine slows down instead of falling over when you overload it.

The property that makes this work is the one from the lesson: because the server holds no session state (M2's statelessness), a request is just "a block table plus a position," and adding or removing one from the batch each step is cheap. Now connect it to the numbers you measured. In Step 5 throughput climbed then flattened while p95 grew. The climb was the step stage getting more efficient — more requests sharing each batched step. The flattening was the admit stage stalling — no free blocks, arrivals deferred. And on a CPU that ceiling is low because each step is slow; on a GPU with PagedAttention it is high because steps are fast and far more requests fit in memory. Same scheduler, different ceiling — which is exactly the argument for vLLM-on-GPU in production and llama-server for portable CPU serving.

You can watch the retire and admit stages breathe on your own engine. Fire a burst and sample the in-flight and deferred gauges tightly:

( for i in $(seq 1 20); do
    curl -s http://localhost:8080/v1/chat/completions \
      -H "Content-Type: application/json" \
      -d '{"model":"qwen3-0.6b","max_tokens":64,"messages":[{"role":"user","content":"Count slowly to twenty."}]}' \
      >/dev/null & done; wait ) &
for n in $(seq 1 8); do
  curl -s http://localhost:8080/metrics \
    | awk '/requests_processing / && !/HELP/ {p=$2} /requests_deferred / && !/HELP/ {d=$2} END {print "processing="p" deferred="d}'
  sleep 0.4
done

Expected output (point-in-time — the numbers rise then drain as requests retire)

processing=0 deferred=0
processing=4 deferred=12
processing=4 deferred=8
processing=4 deferred=4
processing=4 deferred=1
processing=3 deferred=0
processing=1 deferred=0
processing=0 deferred=0

Read the drain. processing pins at the batch width the engine admits; deferred starts high (the burst arrived faster than the engine could admit it) and falls step by step as running requests retire and free blocks let the admit stage pull the next ones in. That staircase down is the scheduler loop, observed. In production this is precisely the shape you watch: a deferred that drains is a healthy engine under a spike; a deferred that stays pinned is an engine that needs another replica (M9).

3 — The arm64 crash story: what "the image exists" does not tell you​

This is the section most practitioners never get taught, because it only shows up when you try to run a production GPU engine on the wrong hardware — which you will, the first time you reach for vLLM on a laptop or a cheap CPU node. This course ran that experiment so you do not have to reproduce it blind. On the Apple-Silicon 8 GB path, the vllm/vllm-openai CPU image for arm64 exists, pulls, and boots — and then crashes on the first inference. Five configurations were tested; reading each failure honestly is the lesson.

AttemptConfigurationWhat happenedWhat it teaches
1latest-arm64, bf16, HF-cache mountBoot failed — the symlinked Hugging Face cache was unreadable through the container file mount ("Operation not permitted" resolving snapshot symlinks)Mount a plain model directory, not an HF symlink farm
2latest-arm64, bf16, plain dir, 2 GiB KVEngine init failed — honest error: less free memory than the KV cache requested after weights + compileThe M1 KV math, surfacing as a real ops error
3latest-arm64, bf16, 1 GiB KVAPI up, then crashed — /v1/models served, the first completion killed the engine worker (died inside a torch matrix op)A CPU-inference image being present ≠ working on this host
4latest-arm64, fp32, 1 GiB KVHung ≥19 min in "compilation" (a starvation loop), never servedFalling back to fp32 is not a fix; it hangs harder
5--enforce-eager and pinned v0.23.0-arm64Same first-completion crashNot a version regression; the CPU path itself is broken on this host

Three findings carry into how you make engine decisions.

Finding one — a KV-sizing error is the M1 math in the wild. Attempt 2 failed at engine init with a message that is worth quoting, because it is the M1/M2 memory math you have been doing by hand, now printed by a real engine refusing to start:

ValueError: To serve at least one request with the models's max seq len (2048),
(2.00 GiB KV cache is needed, which is larger than the available KV cache memory
(1.77 GiB). Based on the available memory, ... try increasing
`gpu_memory_utilization` or decreasing `max_model_len` when initializing the engine.

Read what it is telling you. The weights loaded, the runtime buffers allocated, and then the engine tried to reserve KV cache for a 2048-token context — and there was not enough left (1.77 GiB free against a 2.00 GiB request). This is exactly the three-part memory box from M2 (weights + runtime buffers + KV cache), and exactly the KV-sizing lever from M1, hitting a hard wall. The fix the engine itself suggests — decrease max_model_len (shorter context, smaller KV reservation) or raise the memory it is allowed to use — is the same lever you learned to reach for. This is why the memory math is not academic: an engine that will not start prints it back at you as a ValueError, and knowing the math is how you read the fix in the message.

Finding two — the HF-symlink-vs-mount gotcha, and why plain model dirs win. Attempt 1 never got to inference; it died on the file layout. Hugging Face's cache stores model files as a farm of symlinks (a snapshots/ dir pointing into a blobs/ store). Some container file-mount layers cannot resolve those symlinks — the mount surfaces them but refuses to follow them ("Operation not permitted") — so the engine sees dangling links instead of weights and cannot start. The fix is the one this course bakes into the lab: mount a plain, materialised model directory (real files, no symlinks), which is why labs/opsmate/models/qwen3-0.6b/ holds actual .safetensors and .json files, not an HF cache. It is also better pedagogy — you can see the artefacts — and it is a habit that saves you every time a model refuses to load "for no reason" inside a container. When a containerized engine cannot find weights that are clearly right there, suspect the symlink farm first.

Finding three — presence is not viability. Attempts 3, 4, and 5 are the real lesson, and it is a mindset, not a command. The arm64 CPU image is real — it exists in the registry, it pulls, its API comes up and serves /v1/models. Everything short of actual inference works. Then the first completion crashes the engine worker inside a low-level math kernel, and no amount of config (fp32, eager mode, an older pinned version) fixes it, because the CPU inference path itself is not viable on this VM host. The takeaway you carry into every "can we run X here?" decision: an image being available for your architecture tells you nothing about whether it works on your host. You verify by running the real workload — a completion, not a health check — before you commit an architecture to it. This is why the course spikes engines on the target hardware instead of trusting the registry, and why your M3 hands-on engine is llama-server (which does run everywhere this course goes) with vLLM taught fully and run where it fits.

The forensic habit

When a serving engine fails, read the failure stage, not just the fact it failed. Boot failure → suspect file layout and mounts (the symlink trap). Init failure with a memory number → the KV math, and the fix is in the message (shorter context or more memory). Serves-then-crashes-on-inference → the compute path is not viable on this host; stop tuning config and change the engine or the hardware. The stage tells you which of the three findings you are looking at.

4 — Prefix caching as evidence, not a claim​

The lab showed one cached_tokens hit. Here you read it as a controlled experiment, because "the cache works" is a claim, and an operator ships on evidence. The test: hold the system prompt identical and vary only the user turn, three times, and watch the cached count. If prefix caching is real, the shared system prefix should be served from cache on every call after the first, regardless of what the user asks.

SYS='You are OpsMate, an SRE assistant. Follow the runbook precisely. Cite the step number for every action. Prefer the least-disruptive fix first. /no_think'
for U in "Check one: is the service listening?" "Check two: are its dependencies healthy?" "Check three: what changed recently?"; do
  curl -s http://localhost:8080/v1/chat/completions \
    -H "Content-Type: application/json" \
    -d "$(jq -n --arg s "$SYS" --arg u "$U" \
        '{model:"qwen3-0.6b", messages:[{role:"system",content:$s},{role:"user",content:$u}]}')" \
    | jq -c '{user: "'"$U"'"[0:18], prompt: .usage.prompt_tokens, cached: .usage.prompt_tokens_details.cached_tokens}'
done

Expected output (cached counts are point-in-time; the shape is the evidence)

{"user":"Check one: is the","prompt":54,"cached":0}
{"user":"Check two: are its","prompt":54,"cached":41}
{"user":"Check three: what","prompt":55,"cached":41}

Read it as the experiment it is. The first call primes the cache — nothing cached, the whole prompt prefilled. The second and third calls, with different user questions but the same system prefix, each report a non-zero cached (41 here) — the shared system prompt served from cache while only the differing user tokens got real prefill. That is the mechanism proven: the cache keys on the prefix, so it survives a changing tail. In an application where a long standing instruction fronts every request — a runbook preamble, a persona, a tool schema — this is prefill you pay for once and reuse on every subsequent call, and it is a large standing saving at scale. (Your exact cached numbers depend on the tokeniser and how the build counts partial blocks; call one may even read a small non-zero value if earlier requests in your session warmed the cache. The invariant is the jump: near-zero on the first call, a large shared-prefix count on the repeats.)

The operational reading: prefix caching rewards you for structuring prompts prefix-stable — put the fixed material (system prompt, instructions, retrieved context that repeats) at the front, the variable material (the user's specific question) at the back. A prompt that shuffles its fixed content, or puts a timestamp at the very top, defeats the cache and re-prefills everything every time. This is a real design lever you will use in M4 (where RAG prepends retrieved chunks) and M12 (where the gateway can share a cache across callers): shape the prefix to be stable and the engine pays you back in prefill it skips.

Where you will use this
  • PagedAttention makes concurrent capacity, not model size, the number that matters — size a box by KV blocks after weights. Use it when: a serving pod OOM-kills at a concurrency you thought was safe — the fix is fewer reserved blocks (shorter max_model_len) or more memory, and paging is what lets the rest fit at all.
  • The batching scheduler admits, steps, retires, and preempts every token — deferred is the admit queue. Use it when: you are deciding whether one replica is full — a requests_deferred that drains is healthy under a spike; one that stays pinned is the signal to scale out (M9).
  • An image existing for your architecture is not the image working on your host — verify with a real completion. Use it when: you evaluate any new engine or architecture — run inference, not just a health check, before you commit; and read the failure stage (boot / init / inference) to know which problem you have.
  • Prefix caching rewards prefix-stable prompts — fixed material first, variable material last. Use it when: you design prompts that repeat a long preamble (RAG in M4, the gateway in M12) — structure the prefix to be byte-stable and the engine skips its prefill on every call after the first.
