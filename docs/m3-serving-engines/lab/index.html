Lab — Two Engines, One Client, and a Load Test

Time

Roughly 45–60 min hands-on, depending on your machine.

Resource path: 8 GB core — everything here runs

Every required step runs on the 8 GB core path: one llama-server container under a 2 GB memory limit (about 1.5 GiB in use), plus Ollama native on your host as in M1–M2. You run them one at a time, so you never hold both engines' full load at once. No GPU, no cloud. Step 7 (the vLLM attempt) is optional and clearly labelled — skip it with nothing lost if your hardware or memory does not fit.

Before you start

New here? Do the Setup section first. All commands run from the root of the labs repo (305-labs/). You need docker, curl, jq, uv, and ollama responding. Your M1/M2 course model (qwen3:0.6b on Ollama) should still be pulled — the engine-swap step uses it as the native engine.

Here is the moment this lab is built for. Your team has to serve one model to many users, and the decision on your desk is which engine runs it. In this lab you stop reading about engines and run two of them: Ollama native on your host, and llama-server in a container — the first service of the OpsMate stack you will grow for the rest of the course. You point one unchanged client at both, read the engine's real metrics, watch a queue form under a laptop-safe load test, and see it all live in the X-Ray. By the end you have a portable serving stack you built line by line and know how to observe.

Step 1 — Preflight: download the model, check your tools​

The containerized engine serves a GGUF file from disk. Download the official Qwen3-0.6B GGUF (Q8_0, about 610 MB) into the stack's model directory. This is the same model family from M1/M2, in the single-file GGUF format llama.cpp consumes:

(Already have the file from an earlier run? The size-and-magic check below is enough — skip the download; re-running it is harmless but re-fetches 610 MB.)

mkdir -p labs/opsmate/models/gguf
curl -L --fail -o labs/opsmate/models/gguf/qwen3-0.6b-q8_0.gguf \
  https://huggingface.co/Qwen/Qwen3-0.6B-GGUF/resolve/main/Qwen3-0.6B-Q8_0.gguf

Expected output

  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
100  609M  100  609M    0     0  1578k      0  0:06:35  0:06:35 --:--:-- 1501k

The rate and time are point-in-time — yours depend on your connection (this capture ran at about 1.5 MB/s over roughly six and a half minutes; a faster link finishes in well under a minute). What matters is a completed download near 610 MB. Confirm the file is real and not a truncated download by checking its size and its GGUF magic bytes:

ls -lh labs/opsmate/models/gguf/qwen3-0.6b-q8_0.gguf
head -c 4 labs/opsmate/models/gguf/qwen3-0.6b-q8_0.gguf; echo

Expected output

-rw-r--r--  1 you  staff   610M Jul 19 20:12 labs/opsmate/models/gguf/qwen3-0.6b-q8_0.gguf
GGUF

A real GGUF file begins with the ASCII magic GGUF. If head prints anything else (often the first bytes of an HTML error page), the download was interrupted — delete the file and re-run the curl. Now confirm the rest of your tools answer:

docker version --format '{{.Server.Version}}' && uv --version && ollama --version

Expected output (versions will differ)

29.5.2
uv 0.6.12 (e4e03833f 2025-04-02)
ollama version is 0.32.0

Step 2 — Hand-author the compose stack and bring it up​

This is the first service of a file that grows to M13, so you write it yourself. Open labs/opsmate/compose.yaml — a reference copy already sits in the repo, but read and understand every line, because you will be reading this same file in M10 when something is wrong. Here is the service block, walked line by line:

services:
  model:
    image: ghcr.io/ggml-org/llama.cpp:server   # official multi-arch llama-server
    container_name: opsmate-model
    command: >
      -m /models/qwen3-0.6b-q8_0.gguf           # the GGUF from Step 1
      --host 0.0.0.0 --port 8080                # listen on all interfaces, :8080
      -c 2048                                    # context window (KV budget, M1)
      --metrics                                  # expose Prometheus /metrics
      --alias qwen3-0.6b                         # the name clients send as "model"
    ports:
      - "8080:8080"                              # publish the API on the host
    volumes:
      - ./models/gguf:/models:ro                 # mount the model dir read-only
    mem_limit: 2g                                # hard memory cap (the M1 budget)
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost:8080/health"]
      interval: 5s
      timeout: 3s
      retries: 20
      start_period: 30s

Read what each block does. The image is the official multi-arch llama-server — the same tag pulls the right build on an arm64 Mac or an amd64 Linux node, which is what makes this portable. The command is llama-server's own flags: it serves the GGUF you downloaded, listens on 0.0.0.0:8080 (not localhost, or the container would only talk to itself), sets the context window to 2048 tokens (that is your KV budget from M1 — small on purpose for an 8 GB box), turns on --metrics, and gives the model the client-facing name qwen3-0.6b via --alias. The volume mounts your model directory read-only. mem_limit: 2g is the M2 lesson made enforceable — the container is told it may use 2 GB, and Docker kills it if it exceeds that, so a runaway cannot take your laptop down. The health check polls /health until llama-server reports the model loaded.

Bring it up with the stack's make up, which runs a preflight (free-memory and model-file check) and then waits for the health check to go green:

make -C labs/opsmate up

Expected output

==> OpsMate preflight
    ✓ Model file present and looks like a real GGUF.
    ✓ 2752 MB free (need ~2200 MB).
    Preflight passed.
==> Starting the OpsMate stack ...
[+] Running 2/2
 ✔ Network opsmate_default    Created
 ✔ Container opsmate-model    Started
==> Waiting for the model service to report healthy (up to 90s) ...
    Model service is healthy at http://127.0.0.1:8080/health.
    Stack is up. Try:  curl -s http://127.0.0.1:8080/health

The free-memory figure and timings are point-in-time (and the [+] Running 2/2 ✔ lines are the Compose v2 plugin's format — if your Docker uses the older standalone docker-compose, the same steps print as Container opsmate-model Started line by line instead; the Makefile auto-detects whichever you have). What you need is the preflight passing, the container started, and the health line printed. Confirm the engine is answering directly:

curl -s http://localhost:8080/health

Expected output

{"status":"ok"}

A status: ok means the model is loaded and the engine is ready to serve. If it says loading model for a few seconds on a cold start, that is normal — the health check waits for it.

Step 3 — One client, two engines: swap by changing one env var​

Now the endpoint-contract promise from M2, made physical. labs/m3/client.py is a plain OpenAI-compatible chat client. It reads two environment variables — OPENAI_BASE_URL and MODEL — and knows nothing else about the engine. Point it at your new llama-server container:

OPENAI_BASE_URL=http://localhost:8080/v1 MODEL=qwen3-0.6b \
  uv run labs/m3/client.py "In one sentence, what does an SRE runbook contain?"

Expected output (the answer wording will vary run to run)

engine  : http://localhost:8080/v1
model   : qwen3-0.6b
prompt  : In one sentence, what does an SRE runbook contain?

answer  : An SRE runbook contains a series of steps, instructions, and configurations for managing and maintaining a system.
finish  : stop
usage   : prompt=41 completion=27 total=68
cached  : 0 prompt tokens served from the prefix cache

The very first uv run on your machine prints a few dependency-install lines (Downloading openai …, Installed 16 packages …) before the output above — that is uv fetching the client's dependencies once and caching them; subsequent runs skip straight to the answer.

Now the whole point of this step. Run the exact same script against Ollama — the native engine from M1/M2 — by changing only the two env vars. The code does not change; not one line:

OPENAI_BASE_URL=http://localhost:11434/v1 MODEL=qwen3:0.6b \
  uv run labs/m3/client.py "In one sentence, what does an SRE runbook contain?"

Expected output (again, wording varies)

engine  : http://localhost:11434/v1
model   : qwen3:0.6b
prompt  : In one sentence, what does an SRE runbook contain?

answer  : An SRE runbook outlines processes, tools, documentation, and best practices for operational efficiency.
finish  : stop
usage   : prompt=43 completion=215 total=258

Notice the Ollama run prints no cached : line: its /v1 route does not report a prompt_tokens_details block, so the client has nothing to show — llama-server does, which is why the container run above ended with a cached : line and this one does not.

Read the two side by side. Same client, same question, two entirely different engines — Ollama native on Metal, llama-server in a container on CPU — and both answered behind the identical /v1/chat/completions contract. The only thing that changed was OPENAI_BASE_URL. That is the property M2 promised and the reason this course can move from Ollama to llama-server to vLLM without your application code knowing: the engine is swappable because the contract is stable. (Note the token counts differ: the Ollama /v1 route runs a hidden reasoning trace and counts it in completion, the M2 finding — llama-server here does not, so its counts track the visible answer. Same contract, different engine behaviour underneath.)

Step 4 — First look at engine metrics​

A production engine tells you what it is doing, and llama-server's --metrics flag exposes that in Prometheus format. This is the observability surface you will lean on for the rest of the course. Send one request, then read the metrics:

curl -s http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen3-0.6b","messages":[{"role":"user","content":"ping"}]}' \
  >/dev/null
curl -s http://localhost:8080/metrics | grep -E '^llamacpp:' | grep -vE '_bucket|_sum|_count'

Expected output (the grep above strips the # HELP/# TYPE comment lines, leaving just the llamacpp: samples; values are point-in-time — they only grow with traffic)

llamacpp:prompt_tokens_total 49
llamacpp:prompt_seconds_total 0.797
llamacpp:tokens_predicted_total 220
llamacpp:tokens_predicted_seconds_total 6.856
llamacpp:n_decode_total 220
llamacpp:n_tokens_max 201
llamacpp:prompt_tokens_seconds 61.4806
llamacpp:predicted_tokens_seconds 32.0887
llamacpp:requests_processing 0
llamacpp:requests_deferred 0
llamacpp:n_busy_slots_per_decode 1

The exact family names vary a little between llama-server builds — this one exposes n_tokens_max and n_busy_slots_per_decode and no kv_cache_usage_ratio; an older or newer build may show a slightly different set. The families the lab actually reads are stable across builds. Read the ones that matter, because these are the gauges you will watch under load and in the X-Ray:

  • prompt_tokens_total — every token the engine has prefilled across all requests (M1's prefill phase, counted).
  • tokens_predicted_total — every token it has decoded (M1's decode phase, counted). These two are your throughput counters: watch them climb.
  • requests_processing — how many requests are being served right now. At idle it is 0; under load it rises to the number the engine is batching together.
  • requests_deferred — how many requests are waiting because the engine is at capacity. This is the queue, and it is 0 until you saturate the engine — you will make it climb in Step 5.
  • n_busy_slots_per_decode — how many of the engine's parallel slots were active per decode step; at idle it reads 1, and it climbs toward the batch width as concurrency rises. (Some builds also expose a kv_cache_usage_ratio gauge — how full the KV cache is, M1's capacity number live; if yours has it, it reads 0 at idle and approaches 1.0 when the engine is out of KV room and must defer.)

Now the prefix-cache exhibit from the lesson. Send the same system prompt twice and read cached_tokens in the response usage. The second call should report a non-zero cached count — the shared opening served from cache instead of re-prefilled:

for i in 1 2; do
  curl -s http://localhost:8080/v1/chat/completions \
    -H "Content-Type: application/json" \
    -d '{"model":"qwen3-0.6b","messages":[
      {"role":"system","content":"You are OpsMate, an SRE assistant. Follow the runbook. Be concise and cite the step number. /no_think"},
      {"role":"user","content":"Say ready."}]}' \
    | jq -c '{call: '"$i"', cached: .usage.prompt_tokens_details.cached_tokens, prompt: .usage.prompt_tokens}'
done

Expected output (the cached count is point-in-time, but the pattern holds: 0 first, non-zero second)

{"call":1,"cached":0,"prompt":43}
{"call":2,"cached":42,"prompt":43}

Read it. The first call had nothing cached (cached: 0) — the engine prefilled the whole prompt. The second call, with the identical system prompt, reports cached: 42 — those 42 tokens of shared opening were served from the prefix cache instead of being re-computed. That is prefill you did not pay for on the repeat. In a real application where a long system prompt fronts every request, this is a standing saving on every call after the first. (The exact cached count depends on the tokeniser and the prompt; what matters is that the repeat's cached is non-zero where the first was zero.)

Step 5 — Bounded load test: watch the queue form​

One engine, one model, and now rising concurrency. labs/m3/loadtest.py sends a fixed, small number of identical requests at concurrency 4, then 8, then 16, and prints throughput and p50/p95 latency per level. It is laptop-safe by construction — a bounded request count, a hard per-request timeout, and short answers — so it will not run away with your machine.

Run it against llama-server:

OPENAI_BASE_URL=http://localhost:8080/v1 MODEL=qwen3-0.6b \
  uv run labs/m3/loadtest.py

Expected output (numbers are point-in-time and machine-dependent — read the pattern)

engine   : http://localhost:8080/v1
model    : qwen3-0.6b
profile  : 24 requests/level, levels [4, 8, 16], max_tokens=48

Rising concurrency against ONE engine. Watch throughput and p95:
  concurrency=4   ok=24/24  throughput= 3.00 req/s  p50= 1.15s  p95= 1.85s  wall= 8.00s
  concurrency=8   ok=24/24  throughput= 2.65 req/s  p50= 2.60s  p95= 3.35s  wall= 9.06s
  concurrency=16  ok=24/24  throughput= 2.68 req/s  p50= 4.06s  p95= 5.87s  wall= 8.94s

Read the pattern, not the exact numbers: throughput should hold or climb as
concurrency rises while the engine batches. Where it flattens and p95 grows,
the engine is queueing — confirm it live in the /metrics requests_deferred gauge.

Read the pattern, because the pattern is the lesson. As concurrency rose from 4 to 8 to 16, total throughput held roughly flat (around 2.7–3.0 req/s here — the engine batched what requests it could, continuous batching working) while p95 latency climbed steeply (from under 2s to nearly 6s — requests started waiting). Every request still succeeded (ok=24/24 at every level), but they finished later. That flat throughput with rising p95 is the CPU engine at its ceiling: it batches what it can, and the rest queue. Your absolute numbers depend heavily on what else the box is doing — this capture shared the machine with an idle KIND cluster, so the throughput floor is lower than a quiet laptop's; the pattern (throughput plateaus, p95 grows) is what carries. On a GPU with vLLM the ceiling is far higher, but the pattern is identical, and reading it is how you decide when one replica is full and you need a second (M9).

To see the queue while it happens, run the load test again in one terminal and poll the metrics in another:

# terminal A: start the load
OPENAI_BASE_URL=http://localhost:8080/v1 MODEL=qwen3-0.6b uv run labs/m3/loadtest.py
# terminal B: watch requests in flight and deferred, twice a second
while true; do curl -s http://localhost:8080/metrics \
  | grep -E '^llamacpp:requests_(processing|deferred)' | tr '\n' ' '; echo; sleep 0.5; done

The ^llamacpp: anchor keeps only the sample lines — llama-server also emits # TYPE llamacpp:… gauge comment lines before each metric, and a looser filter would interleave those comments into your output.

Expected output (terminal B — values move as the load runs; Ctrl-C to stop)

llamacpp:requests_processing 0 llamacpp:requests_deferred 0
llamacpp:requests_processing 1 llamacpp:requests_deferred 0
llamacpp:requests_processing 4 llamacpp:requests_deferred 0
llamacpp:requests_processing 4 llamacpp:requests_deferred 4
llamacpp:requests_processing 4 llamacpp:requests_deferred 3
llamacpp:requests_processing 4 llamacpp:requests_deferred 2
llamacpp:requests_processing 0 llamacpp:requests_deferred 0

There is the queue, live. requests_processing rises to the number the engine is batching at once (4 here); requests_deferred is everything waiting behind them — it sits at 0 while the engine keeps up at lower concurrency and fills once arrivals outrun the batch, then drains as running requests finish. When the load ends both fall back to 0. This is the exact signal you alert on in production: a requests_deferred that stays high means the engine is saturated and users are waiting — the trigger to scale out.

Step 6 — See it in the X-Ray: the Engine lens​

The X-Ray from M1 grew a new lens for this module. It reads your real llama-server /metrics through the same same-origin proxy trick, and shows those gauges moving. Start it (leave it running; open another terminal for the load):

bash labs/tools/xray/serve.sh

Open http://127.0.0.1:8010/ and click the Engine tab. It connects to your llama-server on 8080 through the proxy — no CORS, no token, the kubectl proxy trick again. You will see the token-total counters and the requests processing/deferred gauges at rest. Now drive them: re-run the load test in another terminal and watch the lens.

OPENAI_BASE_URL=http://localhost:8080/v1 MODEL=qwen3-0.6b uv run labs/m3/loadtest.py

As the load runs, watch the Engine lens: the prompt and predicted token rates spike, requests processing climbs to the batch size, and requests deferred fills with the queue — the same numbers from Step 5, now moving in front of you. This is the metrics-under-load picture you will keep coming back to: same lens, same gauges, richer stack each module.

Step 7 — Optional: run real vLLM (any architecture, but slow on CPU)​

Optional — works on arm64 too now, but budget real time. Short on either: skip and watch the recorded demo.

This step is optional, and it is honest about the tradeoff. vLLM's home is the GPU; its CPU build is a compatibility path, not a fast path. The course's own spike (planning/lab-tests/m3-spike.md) found the official vllm/vllm-openai CPU image boots and then crashes on inference on arm64 — but schoolofdevops/vllm-cpu-nonuma, a course-maintained image with a one-line patch for a container-NUMA bug, does not. It runs on this course's 8 GB arm64 path. The tradeoff is speed: a captured real run below took about 90 seconds for a 30-token reply (roughly 2.9 seconds per output token — call back to M1/M10's ITL) on this same machine, against llama-server's much faster decode. This is the point, not a bug: vLLM's CPU path is genuinely this much slower than a CPU-native engine, which is exactly why production vLLM runs on GPU and this course's CPU path uses llama-server. If you would rather not wait, watch the recorded vLLM demo in this module's video section instead — the deep dive's forensic section covers everything the demo shows, including vLLM's /metrics surface.

On a fitting box, vLLM ships an OpenAI-compatible server in a container too. vLLM reads the safetensors side of the engine–format matrix (M2), so first materialise the model into a plain directory — plain, because the HF cache's symlink layout does not survive some container mounts (the deep dive has the story):

# one-time: fetch the safetensors model into a plain directory (~1.4 GB)
uv run --with huggingface_hub python3 -c "
from huggingface_hub import snapshot_download
snapshot_download('Qwen/Qwen3-0.6B', local_dir='labs/opsmate/models/qwen3-0.6b',
                  allow_patterns=['*.safetensors','*.json','*.txt'])
print('model ready at labs/opsmate/models/qwen3-0.6b')"

The structure of the serving command mirrors llama-server — a model, a port, an OpenAI API — which is the whole point: the client from Step 3 works against it unchanged. Two flags earn an explanation: --privileged works around a numa_migrate_pages crash this image hits inside some container-runtime VMs (Rancher Desktop, Docker Desktop) — a real, broader-than-usual container permission, not a formality, so know you are granting it; --dtype float32 avoids a CPU kernel gap (rms_norm has no BFloat16 implementation on this build, so the default dtype crashes on the first token). Raise OMP_NUM_THREADS toward your machine's core count if you have more than a couple of cores free — it helps, though only modestly (doubling threads did not double throughput in testing):

docker run --privileged -p 8000:8000 --name vllm-demo \
  -v "$PWD/labs/opsmate/models/qwen3-0.6b:/model:ro" \
  -e VLLM_CPU_KVCACHE_SPACE=1 -e OMP_NUM_THREADS=5 -e OPENBLAS_NUM_THREADS=1 -e MKL_NUM_THREADS=1 \
  schoolofdevops/vllm-cpu-nonuma:0.9.1 \
  --model /model --served-model-name qwen3-0.6b --max-model-len 2048 \
  --dtype float32 --disable-frontend-multiprocessing

Wait for Application startup complete (about 50 seconds: image already local, then ~20s loading the safetensors checkpoint), then send one request. Budget real time for this — it is slow on purpose, see above:

curl -s --max-time 180 http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen3-0.6b","messages":[{"role":"user","content":"In one sentence, why is the sky blue?"}],"max_tokens":30}'

Expected output (captured on an 8 GB arm64 Mac under Rancher Desktop; your exact wording and timing will differ — Qwen3 answers with visible <think> reasoning first, and CPU throughput depends on your core count)

{"id":"chatcmpl-9a6f159cce4f48c6932b3dfab3bd971f","object":"chat.completion","created":1788845248,"model":"qwen3-0.6b","choices":[{"index":0,"message":{"role":"assistant","reasoning_content":null,"content":"<think>\nOkay, the user is asking why the sky is blue in one sentence. Let me start by recalling the basic reason. The sky is blue","tool_calls":[]},"logprobs":null,"finish_reason":"length","stop_reason":null}],"usage":{"prompt_tokens":18,"total_tokens":48,"completion_tokens":30,"prompt_tokens_details":null},"prompt_logprobs":null,"kv_transfer_params":null}

The response got cut off mid-sentence at finish_reason: "length" — that is max_tokens: 30 running out during the reasoning block, not an error; raise max_tokens if you want the full answer, at the cost of more wait.

Now read /metrics — the same OpenAI-compatible surface, plus vLLM's own family:

curl -s http://localhost:8000/metrics | grep '^vllm:'

The vllm: colon-prefixed naming is a version detail worth knowing, not a curiosity: older vLLM releases (pre-0.6) named these metrics with underscores instead (vllm_request_ttft_seconds, no colon). If you ever read vLLM metrics on a different pinned version and a dashboard query comes up empty, check the naming convention before assuming the metric is missing.

Look for vllm:num_requests_running and vllm:num_requests_waiting (0 at rest — trigger another request in a second terminal to watch them move, same trick as Step 6's Engine lens), vllm:gpu_cache_usage_perc (PagedAttention's occupancy, live, despite the "gpu" name — this build reports it for the CPU KV cache too), and vllm:time_per_output_token_seconds_sum/_count — divide sum by count for the real per-token time the request above just paid (83.7s ÷ 29 output-token steps ≈ 2.9s/token on this machine, the ITL number quoted above). It is the same serving picture as llama-server with production-grade internals, just far slower on this hardware path.

Stop it when done:

docker rm -f vllm-demo

If your machine cannot spare the memory or the wait, that is exactly what the note at the top of this step is for — skip it, watch the recorded demo, and the deep dive's forensic section still covers everything it would have shown you.

Step 8 — Teardown​

Tear the stack down. The container stops; the GGUF model file on disk stays, because M4 restarts this same stack and adds services beside it:

make -C labs/opsmate down

Expected output

==> Stopping the OpsMate stack ...
[+] Running 2/2
 ✔ Container opsmate-model    Removed
 ✔ Network opsmate_default    Removed
    Stopped. The GGUF model file on disk stays for the next module.

Stop the X-Ray server in its terminal with Ctrl-C. Ollama keeps running as your host model server — you do not tear that down. Confirm nothing is still holding port 8080:

curl -s --max-time 2 http://localhost:8080/health || echo "engine down — teardown clean"

Expected output

engine down — teardown clean
Troubleshooting
  • docker pull fails with denied / unauthorized from ghcr.io — you have a stale GitHub Container Registry credential cached. The image is public and needs no login. Fix it: docker logout ghcr.io, then re-run make -C labs/opsmate up. (This bit us in the spike; a leftover token was being sent and rejected.)
  • make up says the model file is missing or not a real GGUF — the download in Step 1 did not complete. head -c 4 on the file must print GGUF; if it prints HTML or nothing, delete labs/opsmate/models/gguf/qwen3-0.6b-q8_0.gguf and re-run the curl -L --fail. The --fail flag makes curl error out on an HTTP error page instead of saving it as the "model".
  • Port 8080 already in use — something else holds it (a stray container, another dev server). Find it with docker ps and stop it, or lsof -i :8080 for a native process. As a last resort change the published port in compose.yaml ("8081:8080") and use 8081 in the URLs.
  • Container gets OOM-killed / restarts in a loop — on a machine with under ~2 GB free, the 2 GB mem_limit cannot be met and Docker kills the container. Close other apps and re-run make up (its preflight will refuse to start below the floor and tell you the number). This is the memory limit doing its job, not a bug.
  • make up preflight refuses to start — it measured less free memory than the stack needs. Close browsers and other containers; they are the usual culprits. The preflight would rather stop early with a clear message than let the engine get killed mid-lab.
  • uv run is slow the first time — uv fetches the script's dependencies (the OpenAI client, httpx) on first run and caches them. Subsequent runs are instant.
  • Step 4 cached_tokens is 0 on the second call too — prefix caching needs the two prompts to share an exact prefix. Make sure the system message is byte-for-byte identical between the two calls (the for loop guarantees it). If your build predates prefix-cache reporting, the field may be absent — the metrics families in the first half of Step 4 are the reliable exhibit.
  • X-Ray Engine tab shows no data — it reads llama-server on 8080; make sure the stack is up (curl http://localhost:8080/health) before opening the tab, and reload after the load test starts. If llama-server listens elsewhere, LLAMACPP_URL=http://host:port bash labs/tools/xray/serve.sh.
