Serving Engines — Ollama, llama.cpp & vLLM

You have picked a model and you can talk to it. Now the job changes shape. Until now you have run the model for one person — you, at a terminal. In production, one copy of the model has to answer many people at once: a support tool fielding a hundred agents, an internal assistant a whole engineering org opens at 9am, an API a dozen services call. The piece of software that takes your model file and turns it into that shared, always-on, many-users-at-once service is the serving engine. And which engine you pick is not a detail — it decides your cost per answer, your latency under load, and whether the same setup even runs on your laptop, your CI box, and your production cluster.

That is the question this module answers: given a model and a place to run it, which engine serves it, and why. By the end you will select an engine from a defensible framework rather than by habit, you will know what continuous batching and PagedAttention actually buy you when the load arrives, and you will have served the identical model behind the identical API from two different engines — swapping them under a client that never changed a line. This is also where the OpsMate stack stops being a single terminal command and becomes a real service, in a file that grows with you for the rest of the course.

In M1 you learned what a model does at runtime — prefill, decode, the KV cache that sets your capacity. In M2 you learned to read and size the model as an artefact, and you met the OpenAI-compatible contract every backend speaks. This module is about the engine that sits between them: the thing that loads the artefact and honours the contract, for many callers at once. We will use everything from M1 and M2 without re-explaining it.

Why the engine is a real decision, not a default​

Reach for the analogy first. Choosing a serving engine is like choosing a vehicle for a trip. A scooter is perfect for one person darting across town — cheap, instant, no overhead. A city bus is wrong for that one person and exactly right for forty people all going the same way — it costs more to run, but the cost per passenger is tiny because everyone rides together. Nobody argues "the bus is better than the scooter." You ask what the trip is. Serving engines are the same: some are built for one rider (a developer, a laptop), some are built to carry a full load together (a production service), and the whole skill is matching the engine to the trip.

Three questions decide the trip, and you should be able to answer all three before you pick:

Read it as three axes, not a flowchart to memorise:

  • Dev vs prod. On your own box you want the model running in seconds with no ceremony and an easy way to swap models — that is Ollama's whole design. In production you want throughput under concurrent load, predictable memory, and metrics — that is what vLLM and, at CPU scale, llama-server are built for.
  • CPU vs GPU. This is the hardware axis, and it is the one that surprises people. A GPU-class engine on a CPU-only box is not just slow — as you will see later in this module and in the deep dive, some of them do not run at all on the wrong architecture. CPU serving and GPU serving are genuinely different engines, not one engine with a slider.
  • Single vs multi-tenant. One user at a time is a different problem from a hundred users at once. The engines that win at multi-tenant do it with two mechanisms — continuous batching and PagedAttention — that a single-user engine never needs. Those two mechanisms are the heart of this lesson, so hold that thought.

None of these axes has a "best" answer. They have a fit answer, and the fit changes with the trip.

The three engines, placed on those axes​

You have already met one of these. Here is where each sits.

Ollama is the dev-box engine. Its entire reason to exist is ollama pull then ollama run — a model server up in seconds, native on your machine, with a friendly model library and effortless swaps between models. That convenience is why the course started on it and why you will keep it running as your host model server. It is not built to be your production multi-tenant serving tier, and it does not pretend to be — it wraps llama.cpp underneath and adds the developer experience on top.

llama.cpp — run as llama-server, its built-in OpenAI-compatible HTTP server — is the portable CPU engine. It is what Ollama is built on, exposed directly. It runs a quantized GGUF model efficiently on plain CPUs and on Apple-Silicon Metal, it speaks /v1/chat/completions, it exposes a Prometheus /metrics endpoint, and — the property that matters for this course — it runs the same inside a container on your Mac, on a Linux node, and on WSL2. It even does continuous batching. It is the engine you will containerize in this lab, because it is the one CPU engine that gives you a real, portable, observable serving surface on an 8 GB laptop.

vLLM is the production engine. It is built from the ground up for GPU serving at high concurrency, and it is where continuous batching and PagedAttention were popularised. When your service has a GPU and real load, vLLM is the default answer in the industry, and it is the engine this course serves OpsMate on in production (M8 onward). You will learn it properly here — its mechanisms, its API surface, its metrics — and run it hands-on where the hardware allows. There is an honest wrinkle in running it on a laptop, and we meet it head-on in this module rather than hiding it.

Here is the through-line that makes all three interchangeable: they all speak the same OpenAI-compatible API. That M2 contract is exactly why you can develop on Ollama, serve on llama-server, and run production on vLLM without your client code knowing. You prove that in this lab by pointing one unchanged script at two of them.

The Apple-Silicon pattern — why the Mac runs the model differently​

M1 promised this module would explain a gap you may already have noticed: on your Mac, Ollama runs native on the host, not in a container — and yet this course is about containers and Kubernetes. Here is the pattern, because it governs how every model server in this course is placed, and getting it wrong is a real source of "it works on my machine, it dies in the cluster."

The analogy: think of the GPU as a workshop with one door, and that door only opens from inside the building. A program running natively on the Mac is inside the building — it can walk straight into the workshop and use the tools. A program inside a container is in a separate building next door; there is no corridor to that workshop. It can still get work done, but only with the hand tools it brought — the CPU.

Concretely: containers on a Mac cannot reach Apple's Metal GPU. The container runtime (Docker Desktop, Rancher Desktop) runs your containers inside a Linux VM, and that VM has no path to the Mac's Metal graphics stack. So a model server in a container on a Mac is CPU-only, always. That is why:

  • On a Mac, the fast path is native. Ollama running natively on your host reaches Metal (you saw ollama ps report 100% GPU in M2 — that is Metal), so it is quick. Put that same engine in a container on the Mac and it drops to CPU and slows down.
  • On a Linux box with an NVIDIA GPU, the container reaches the GPU. There the container runtime does pass the GPU through (via the NVIDIA container toolkit), so a containerized GPU engine like vLLM runs on the GPU inside the container. This is the production shape.
  • The portable middle is CPU-in-a-container. A llama-server container runs CPU inference identically on your Mac, on a Linux node, and on WSL2 — no GPU on any of them, so nothing to pass through, so nothing to differ. That sameness is the point: it is the one serving shape that behaves the same everywhere, which is exactly what you want for a course stack that has to run on every learner's machine.

So the rule you carry out of here: native on the Mac when you want its GPU; containerized CPU when you want portability; containerized GPU on Linux when you want production throughput. The OpsMate stack you start today uses the portable containerized-CPU path deliberately — so the exact same compose.yaml runs on every machine in this course, and the only thing that changes in production is that the container lands on a GPU node with vLLM instead.

Continuous batching — the lift that stops for every floor​

Now the mechanism that separates a toy server from a production one. Analogy first, because the idea is genuinely simple once you see it, and the words make it sound harder than it is.

Picture an old lift with a rule: it will not move until it is full, and once it starts it will not stop to pick anyone up until everyone already aboard has reached their floor. Ten people are waiting. The first three get in, and then the lift just... waits, doors open, for enough people to fill it — and the three inside wait too. Finally it fills, the doors close, and now anyone who arrives has to watch it run its whole route before it comes back. Everyone waits on the slowest, fullest trip. That is static batching: the engine collects a batch of requests, runs them all together until every one is finished, and only then starts the next batch. A request that arrives one moment too late waits for the entire current batch to complete. A short request trapped in a batch with a long one waits for the long one.

Now picture a modern lift that picks up and drops off at every floor. It never waits to be full and it never makes you ride to the end — it takes whoever is ready, drops whoever has arrived, and picks up whoever is now waiting, continuously. That is continuous batching (also called in-flight batching): the engine works one token-step at a time across all active requests, and at every step a finished request leaves the batch and a newly arrived request joins it. No request waits for a batch boundary, because there are no batch boundaries — there is just a stream of steps, and the batch membership changes every step.

Why this is the mechanism that wins under load, in one line: it keeps the engine busy and full without making anyone wait for a boundary. Under real traffic — requests arriving at random moments, some short, some long — static batching leaves the engine idle between batches and traps short requests behind long ones. Continuous batching keeps every slot working every step and lets short requests finish and leave the moment they are done. The result is higher total throughput and lower latency for the requests that would otherwise have been stuck waiting — you rarely get both at once, and this is why continuous batching is the single biggest reason a production engine outperforms a naive one. llama-server does it; vLLM does it; it is the price of entry for serving many users from one model. You will feel it in the sim, and see the queue form live in the lab's metrics.

PagedAttention — page-numbered shelves instead of one long plank​

Continuous batching lets many requests share the engine. But each of those requests has a KV cache (M1), and now you have many KV caches living in the same memory at once, each growing a token at a time, each an unpredictable length. How you store all those growing caches is the second production mechanism, and it is the one PagedAttention solves.

Analogy first. Imagine a library where each reader is given one long, unbroken shelf, and they must guess at the start how many books they will end up with, because the shelf length is fixed the moment it is handed out. Readers who guess high waste most of their shelf — reserved wood no one else can use. Readers who guess low run out of shelf mid-session and have to be moved to a longer one, copying everything across. And because every reader holds one long contiguous plank, the library fills with awkward gaps too short for anyone's plank — space that exists but cannot be used. That is the contiguous KV cache: the old way, where each request reserves one continuous block of memory sized to its maximum possible length. It wastes memory to over-reservation and to fragmentation, and it caps how many requests you can pack in.

Now the fix. Give every reader a set of small, numbered cubbies scattered wherever there is room, plus an index card listing which cubby numbers hold their books in order. A reader takes cubbies one at a time as they need them — no guessing, no waste. When they finish, their cubbies free up individually for the next reader. There are no unusable gaps, because any free cubby fits any reader. That is PagedAttention: the KV cache is broken into small fixed-size blocks (pages), a request is given blocks on demand as its cache grows, and a per-request block table records which physical blocks hold its tokens in order — exactly like virtual memory paging in an operating system, which is where the idea comes from.

What PagedAttention buys you, stated as the number that matters: it lets you fit far more concurrent requests into the same GPU memory, because you stop reserving memory for tokens that do not exist yet and you stop leaving unusable gaps. In vLLM's own measurements this is a large multiple of the concurrent capacity of the naive approach — and concurrent capacity is throughput, which is cost per answer. It is the memory-side partner to continuous batching's scheduling side: batching keeps the engine busy, paging keeps the memory dense. Together they are why vLLM serves so many more users per GPU than a naive server. The deep dive reads the block tables and the fragmentation math directly.

Prefix caching — don't re-read the same opening every time​

One more mechanism, smaller but you will see it live in the lab. Every request in a real application tends to start with the same opening — a long system prompt, a set of instructions, a runbook preamble — and only the user's last line differs. Re-running prefill (M1) over that identical opening on every single request is pure repeated work.

The analogy is a book group where everyone has read the same first three chapters. You do not make each person re-read those chapters aloud before they ask their question — you say "you all know the setup, now here's the new part." Prefix caching does exactly that: the engine keeps the KV cache of a prompt prefix it has already processed, and when the next request begins with the same prefix, it reuses that cached work instead of re-prefilling it. The shared opening is computed once and served from cache thereafter; only the new tokens get real prefill.

You will see this as a concrete number in the lab: send the same system prompt twice and the engine reports cached_tokens in the response — the count of prompt tokens it served from cache rather than re-computing. That is prefill you did not pay for. In an application where a 500-token system prompt fronts every request, prefix caching is a large, standing saving, and it is one more reason the engine layer — not your application code — is where serving efficiency is won.

vLLM, positioned honestly​

Everything above — continuous batching, PagedAttention, prefix caching — is why vLLM is the production serving engine, and this lesson has taught you those mechanisms as concepts you now own. Two honest notes on how you meet vLLM in this course, because the course refuses to fake a hands-on experience it cannot deliver on every learner's machine:

First, vLLM's home is the GPU. It is built for CUDA. There is a CPU build, and there are ARM and x86 CPU images, but vLLM on CPU is a compatibility path, not vLLM's purpose. You run vLLM hands-on in this course where the hardware fits it — an x86 box with modern vector instructions (AVX2/AVX-512), a GPU, or a cloud instance — and where it does not fit, you learn it through a recorded demo of the identical steps against a real vLLM, plus its /metrics surface read the same way you read llama-server's.

Second, the cross-architecture reality is itself a lesson. On the Apple-Silicon 8 GB path this course targets, the vLLM CPU image boots but crashes on inference — and rather than paper over that, the deep dive treats it as a forensic case study. It is the M1 KV-memory math surfacing as a real ops failure (an honest "not enough free memory for the KV cache you asked for" error), plus a container-file-mount gotcha that costs people hours, plus the plain fact that a CPU inference image being present for your architecture does not mean it works on your host. That is a genuinely useful thing to have seen before it happens to you in production, which is why it is taught rather than hidden.

So: you leave this module having learned vLLM's mechanisms deeply, seen its real serving surface, and understood exactly when to reach for it — and you get your hands-on containerized-serving reps on llama-server, the engine that actually runs everywhere this course goes.

The compose spine starts here​

Until now, "run the model" has meant one command in your terminal. Starting with this module, OpsMate becomes a stack — a real service defined in a file, brought up and torn down as a unit, that grows one service per module until it is the full production system in M13.

That file is labs/opsmate/compose.yaml, and today it holds exactly one service: model, a llama-server container serving the Qwen3-0.6B GGUF on port 8080 behind the OpenAI-compatible API, under a 2 GB memory limit, with a health check on /health and --metrics turned on. That is the whole file right now — deliberately small, so every line is one you wrote and can defend. In M4 you will add a retriever and a vector database beside it; by M7 it is the full pre-Kubernetes stack; then the Compose phase retires and the same services grow into Kubernetes manifests. The discipline for the whole course: one service added or grown per module, hand-authored, and the service you already understand never changes shape underneath you.

You hand-author it in the lab — line by line, not copy-pasted — because this file is the backbone of everything that follows, and the point of building it yourself is that you can read it in M10 when something is wrong. make up runs a preflight memory check and brings it up healthy; make down tears it down. Those two verbs carry, unchanged, all the way to M13.

What you'll do next​

In the lab you will download the Qwen3-0.6B GGUF, hand-author the first compose.yaml service block, and bring the OpsMate stack up healthy. Then you will prove the endpoint contract physically: point one unchanged client script at Ollama, then at your new llama-server, by changing a single environment variable — same code, two engines, comparable answers. You will read the engine's /metrics for the first time (the token-total and requests-in-flight families you will lean on for the rest of the course), watch cached_tokens prove prefix caching, and run a bounded, laptop-safe load test at rising concurrency while watching the queue form live in requests_deferred. You will open the new Engine lens in the X-Ray and watch those gauges move under load. Finally, the optional vLLM path for learners whose hardware fits it, and Teardown.

The skill you leave with is the one that turns "I have a model" into "I run a service": choosing the engine that fits the trip, knowing what its batching and paging buy you, and standing up a portable, observable serving stack you will grow for the rest of the course.
