Deep Dive — Eval Metrics, Judge Honesty & the Gate That Comes Next

The lesson gave you the eval pyramid, the two-layer golden set, prompts as config, and the baseline ritual. The lab built all of it and produced real numbers. This page goes under those numbers. You will see how the industrial RAG metrics — Ragas faithfulness and context precision — are actually computed, so you know what a "faithfulness of 0.82" really counts. You will measure your local judge disagreeing with itself, which turns the "smoke detector, not examiner" framing from a claim into a number. You will see why a public 24-question set rots the moment it is public, and the rotation strategy that keeps a set honest. And you will read the GitHub Actions workflow that previews the CI gate M12 builds — the moment the golden set stops being something you run by hand and becomes something that blocks a bad merge. These are the layers you reach for when someone asks "how do we know the eval itself is any good?" — which is the question that separates a real eval practice from a green checkmark.

Where this picks up

The judge-agreement probe needs only host Ollama serving the judge model (qwen3:0.6b) — no stack required. The Ragas section is a read (formulae in prose; no library install on the 8 GB path). The CI section reads a real workflow file in the repo. If you want to re-run the lab's evals alongside this, bring the stack up (make -C labs/opsmate up) and have the index ingested, as in the lab.

1 — What Ragas actually computes (and why you should know before you install it)​

The lab graded generation with a wide contains-any net plus a local judge. That is the right starting tier. The industry-standard next tier is Ragas — a library of RAG-specific metrics — and M12 wires it in as the industrial step. But a metric you cannot explain is a metric you will misread, so before any pip install ragas, understand what its two headline numbers are counting. Both are computed by an LLM, decomposed into small yes/no judgements so the model is never asked for a vibe-score directly.

Faithfulness answers: is the answer supported by the retrieved context, or did the model make things up? It is a hallucination detector, and it is a ratio. The recipe:

  1. Break the generated answer into individual claims (atomic statements). "Raise DB_POOL_MAX to 40 and restart pods one at a time" is two claims.

  2. For each claim, ask the judge: can this claim be inferred from the retrieved context? — a yes/no per claim.

  3. Faithfulness is the fraction that can:

    faithfulness = (claims supported by the context) / (total claims in the answer)

An answer of 1.0 invented nothing — every statement traces to a retrieved chunk. A 0.5 means half the answer was ungrounded, which on an incident runbook is dangerous. Notice this metric does not care whether the answer is correct in the world — only whether it is grounded in what was retrieved. That is deliberate: it isolates the generation failure (hallucination-despite-context, the M4 failure mode) from the retrieval failure.

Context precision answers the retrieval-side question: of the chunks we retrieved, how many were actually relevant, and were the relevant ones ranked high? It is precision with a ranking weight. In prose:

  1. For each retrieved chunk at rank k, the judge decides: was this chunk relevant to answering the question? — yes/no.

  2. Compute precision@k at each rank (relevant-so-far / k), and average the precision@k values at the ranks where a relevant chunk appeared:

    context precision = average of precision@k over the ranks that held a relevant chunk

The ranking weight is the important part: a relevant chunk at rank 1 counts for more than the same chunk buried at rank 3, because putting junk ahead of the good chunk is exactly the "lost in the middle" risk from M4. A high context precision means retrieval put the good stuff on top; a low one means it padded the top-k with noise.

See how these map onto the two-layer split you already built: context precision is your retrieval layer, made continuous (top-3 hit/miss becomes a rank-weighted 0–1 score), and faithfulness is your generation layer's honesty check, made continuous (bluff/no-bluff becomes a claim-level ratio). Ragas is not a new idea — it is your two layers with sharper, LLM-computed instruments. Which is also why it is only as trustworthy as the judge computing it, and that is the next section.

2 — Measuring your judge's honesty: does it agree with itself?​

The lesson called the local judge a smoke detector, not an examiner. Here you measure that, because a claim you can measure beats one you take on faith. A judge is a fallible model; ask it to grade the same borderline answer twice and it may split. The script sends one fixed, deliberately-marginal (answer, rubric) pair to the judge several times and reports how often the verdict agrees with itself:

uv run labs/m5/judge_agreement.py --runs 8

Expected output (point-in-time; the number you get and whether it splits depends on the exact answer and temperature — read the reasoning, not just the count)

judge: qwen3:0.6b @ http://localhost:11434  (temperature 0.0)
grading the SAME borderline answer 8 times...

  run  1: FAIL
  run  2: FAIL
  run  3: FAIL
  run  4: FAIL
  run  5: FAIL
  run  6: FAIL
  run  7: FAIL
  run  8: FAIL

verdicts: 0 PASS / 8 FAIL
self-agreement with the majority (FAIL): 8/8 = 100.0%

Fully consistent on THIS run — try --temperature 0.4, or a genuinely
borderline answer, to surface the disagreement a small judge carries.

Read this run carefully, because it is not the naive "small judge flips randomly" story — and the honest version is more useful. At temperature 0 on this particular answer, the judge was fully consistent: 8/8 FAIL, 100% self-agreement. Determinism is not the point being tested, though — correctness is. Recall the lab's Kafka exhibit: the model refused correctly, and the judge FAILed it anyway, every single time. That is what 100% self-agreement on a wrong verdict looks like — a judge can be perfectly repeatable and still perfectly wrong. Consistency is necessary but not sufficient; a broken thermometer that always reads 10° too cold is 100% consistent and 100% useless. Two consequences follow, and both are load-bearing:

  • Consistency ≠ correctness, and temperature 0 buys you the first, not the second. You saw in M1 that temperature 0 makes sampling greedy — so on a clear-to-it call the 0.6B judge repeats itself. But "repeats itself" is not "is right": the honesty-refusal grade above is stable and inverted. Re-run with --temperature 0.4 (or feed a genuinely marginal answer) and you will start to see the split this script is built to surface; at temperature 0 you are measuring repeatability, which is the floor, not the ceiling.
  • Aggregate, and anchor to the deterministic layer. When the judge does split, take the majority of several grades, not one. And whatever the judge says, weight it against the deterministic retrieval layer — "the right source is in top-3" is a fact with no opinion to be wrong about, so it anchors the noisy generation grades. This is why the baseline leans on the retrieval 24/24 and the generation gap, and treats the honesty sub-score as the noisy signal it is.

This is exactly why M12 upgrades the judge. A stronger judge model is both more self-consistent and better calibrated (a better instrument has less noise and less bias), and a production gate needs an instrument you can defend on both counts. For the laptop course, you keep the cheap judge and you know its error bars — including that a stable verdict can still be a wrong one — which is a more honest place to be than trusting a number whose reliability you never measured.

3 — Why 24 public questions rot, and how to rotate​

Here is the failure that kills eval sets slowly. Your golden set is 24-ish questions, committed to the repo, visible to everyone — including, soon, whatever you are testing. The moment a set is public and fixed, it starts to rot, in two distinct ways:

  • Overfitting (Goodhart's law). "When a measure becomes a target, it ceases to be a good measure." Once the team knows the 24 questions, every prompt tweak and every fine-tune is nudged — consciously or not — to pass those 24. The score climbs while real-world quality does not, because you optimized the test, not the capability. A fine-tune in M6 that trained on data derived from the exact golden questions would ace them and still be no better in production. The set stopped measuring and became a target.
  • Contamination. If the golden questions and their answers are in the repo, and a future model is trained on the repo (or on data scraped from it), the model has seen the answer key. Its score is then memory, not capability — the eval equivalent of a student who got the exam paper in advance.

The defences are a discipline, not a gadget:

  • Hold out a private set. Keep a second set of questions that is never committed next to the code the model sees — the eval equivalent of an exam the students never get to photocopy. You develop against the public set and confirm against the private one; a big gap between them is your overfitting alarm.
  • Rotate. Retire and replace a fraction of the questions each cycle (say a quarter every quarter). A question that has been public for a year has taught everyone its answer; a fresh one has not. The corpus makes this cheap — you author new questions from runbook passages you have not used yet.
  • Grow with the corpus. Every new runbook is new golden questions. A set that grows as the system grows resists rot structurally, because there is always material the model has not been tuned against.
  • Separate train from eval provenance. Never let a question that grades the model share a source with data the model trained on. In M6 you will keep the fine-tune's training split and the golden eval split provably disjoint for exactly this reason.

The through-line: a golden set is not a monument you carve once. It is a living suite you maintain, hold part of back, and rotate — the same hygiene a security team applies to a red-team corpus.

4 — The gate that comes next: a CI preview​

Everything so far you ran by hand. The endgame is that no human runs it — the golden set runs itself on every change and blocks the merge if the numbers regress. That is the M12 gate, and here is a preview you can read: a GitHub Actions workflow that runs both eval layers on every pull request and fails the build if retrieval drops below the baseline. It lives in the repo at labs/opsmate/evals/ci-preview.yml:

cat labs/opsmate/evals/ci-preview.yml

Expected output (the workflow — read it, do not run it here; M12 wires the real gate)

# PREVIEW ONLY — the real gate is built in M12. This shows the STRUCTURE of an
# eval gate: run both layers on every PR, fail the build if the baseline regresses.
name: opsmate-evals
on: [pull_request]

jobs:
  golden-set:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Bring up the OpsMate stack
        run: make -C labs/opsmate up
      - name: Ingest the corpus
        run: curl -s -X POST http://localhost:8001/ingest
      - name: Retrieval layer (deterministic — the tripwire)
        # retrieval_check.py exits non-zero if any retrieval check fails,
        # which fails the job. This is the cheap gate that runs first.
        run: uv run labs/m5/retrieval_check.py
      - name: Generation layer (graded)
        run: |
          uv run labs/m5/make_promptfoo_tests.py
          npx -y promptfoo@latest eval \
            -c labs/opsmate/evals/promptfooconfig.yaml \
            -o labs/opsmate/evals/generation-latest.json \
            --max-concurrency 2
      - name: Gate on the baseline
        # Compare this run's pass rate to the committed baseline; fail if it
        # dropped. M12 replaces this stub with a real threshold check.
        run: uv run labs/m5/retrieval_check.py --k 3

Read what makes this a gate rather than a report. The retrieval layer runs first and retrieval_check.py exits non-zero on any failure, so a chunking change that quietly breaks retrieval fails the job before the expensive generation eval even starts — the cheap deterministic tripwire, doing its job in CI exactly as it did on your laptop. The generation layer runs second and writes its JSON. And the final step is where M12 does the real work: compare against the committed baseline.md and fail if the numbers regressed. That is the whole arc of this course's eval story — the baseline you recorded by hand in the lab becomes the number a robot enforces on every merge, so "did this change make OpsMate worse?" is answered before the change lands, not during the next incident.

Where you will use this​

You reach for this material in specific, real moments. When a teammate says "let's add Ragas", you now know faithfulness and context precision are your two layers with sharper instruments — and that they are only as good as the judge underneath, so you check the judge first. When a score looks suspiciously high after a fine-tune, you suspect overfitting to a public set and reach for the held-out private set to confirm. When someone proposes gating deploys on evals, you know the retrieval layer is the cheap tripwire that goes in front, and the judge needs its error bars measured before anyone trusts a threshold. And when you inherit an eval suite that has been green for a year, your first question is "when did we last rotate these questions?" — because a set that never changes stopped measuring a while ago. These are the instincts that separate running an eval from having an eval practice, and M12 turns them into the production gate.
