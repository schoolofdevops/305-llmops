Prompts as Config & the Baseline Eval

Here is the situation this module is built for. A teammate opens the OpsMate repo on Friday afternoon, decides the system prompt "could be sharper", rewrites it, and ships. Monday morning the on-call engineer asks OpsMate the same payments question they asked last week — and gets a different answer. Maybe better, maybe worse. Nobody can say which, because there is no measurement. The change went out on a feeling. When someone in the incident review asks "did that prompt edit help or hurt?", the honest answer is a shrug, and a shrug is not something you can put in a change record.

That shrug is the problem this module removes. By the end you will treat the prompt as what it actually is — a deployable configuration artifact that gets versioned, tested, and rolled back like any other config — and you will build the thing that turns "it looks right to me" into a number: a golden evaluation set and a recorded baseline. The baseline is the yardstick for the entire rest of the course. M6 fine-tunes OpsMate's model and has to beat this baseline to justify shipping. M12 wires it into a promotion gate. M13 replays it against the production capstone. If you build one honest artifact in this whole course, it is the one you build here.

In M4 you learned to debug a wrong answer by hand — retrieval or generation, read the sources, form a judgement. That skill does not scale. You cannot eyeball every answer on every change forever, and "looks fine to me" is not a gate you can put in CI. This module makes that same judgement repeatable and measurable so a machine can run it on every change.

Why "it looks right" is not a test​

Start with something outside of software, because the trap is universal. Imagine a driving examiner who takes every candidate on a different route — one gets the quiet cul-de-sac, the next gets the motorway merge in the rain. At the end each examiner says "yeah, seemed fine to me." Those pass marks mean nothing. You cannot compare two candidates, you cannot tell if standards slipped this month, and you certainly cannot defend a pass to anyone who asks. The fix every driving authority landed on is the fixed test route: the same route, the same manoeuvres, every candidate, every time. Now a pass is comparable, defensible, and repeatable.

An LLM eval set is that fixed test route. "It looks right" is the examiner who improvises a different route each time and grades on vibes. It fails for exactly the same reasons: you cannot compare two versions of the system, you cannot detect a regression, and you cannot defend the result. The moment you have a fixed set of questions with known-good answers that you run identically every time, you can say "v2 scores 18/24, v1 scored 15/24" — and that sentence is worth more than a hundred "seems better to me"s.

There is a second reason this matters right now, and it is about what comes next. M6 is going to fine-tune the model. Fine-tuning is expensive, slow, and easy to fool yourself about — a fine-tuned model always feels better because you wanted it to. Against what do you measure whether it actually improved? You need a baseline that exists before you touch the model, recorded in a file, so the comparison is real and not a memory. This module builds that baseline. You cannot fine-tune responsibly without it.

The eval pyramid — four ways to grade an answer, cheapest first​

Not all grading is the same, and the practical skill is knowing which tool to reach for. Think of it as a pyramid: cheap, fast, deterministic checks at the wide bottom, and expensive, slow, high-fidelity judgement at the narrow top. You want as much of your grading as possible down at the cheap bottom, and you climb the pyramid only when the cheaper layer cannot express what you need.

Read the four layers from the bottom up:

  • Assertions — deterministic checks on the output. Does the answer contain this substring? Match this regex? Did the right source runbook land in the top-3? These are free, instant, and never flaky. Their weakness is rigidity: they check the letter, not the spirit.
  • Similarity — embed the answer and a reference answer and measure the distance (the exact machinery from M4). This tolerates paraphrase — "raise the connection pool" and "increase DB_POOL_MAX" land near each other even with different words. Softer than an assertion, still cheap, still automatic.
  • LLM-as-judge — hand the answer plus a rubric to another model and ask it to grade. This is the only layer that reads nuance: "does this answer actually diagnose pool exhaustion, in any wording?" It is powerful and it is noisy — the judge is itself a fallible model, which we will be very honest about below.
  • Human review — a person reads the answer. Gold standard, and far too slow to run on every change. You reserve it for spot-checks and for calibrating the layers below it.

The lesson of the pyramid is: push grading down as far as it will go. Most of a good eval suite is assertions, because they are free and trustworthy. You climb to a judge only for the questions where exact-phrase checks are too brittle — and this is exactly the wall the M5 spike hit.

The finding that shaped this whole design​

When we first wired an eval against the real OpsMate stack, we wrote the obvious assertion: ask "the payments API is throwing 500s", and check the answer contains the phrase "connection pool". It failed. Not because retrieval was wrong — the payments runbook was retrieved perfectly — but because the 0.6B model paraphrased. It answered "verify the current status of the payments API and check whether connections are being held open" — correct in spirit, but it never said the exact words "connection pool". The assertion was checking the letter and the model spoke the spirit.

That failure is the design. Exact-phrase assertions are brittle against small models, which paraphrase relentlessly. You have two honest ways out, and OpsMate uses both: make the assertion wide (accept any of "pool", "connection", "db_pool_in_use", "exhaustion" — several wordings of the same right idea), and back it with an LLM-judge rubric for the nuance a substring list cannot capture. What you must never do is tighten the assertion to one exact phrase and call a correct-but-paraphrased answer a failure. That does not measure the model; it measures whether the model happened to echo your wording.

The two-layer golden set — separate "right pages" from "right answer"​

Here is the architecture that follows from all of the above, and it is the core idea of the module. A RAG answer can go wrong in two completely different places, and if you grade them together you cannot tell which broke. So OpsMate grades them separately, in two layers.

The analogy is a courier delivery. Two independent things must go right. First, the courier must pick up the correct parcel — the right box off the shelf. Second, that parcel must arrive in good condition — not crushed, not opened. These are different failures with different fixes: the wrong parcel is a warehouse problem; a crushed parcel is a handling problem. If all you know is "the customer is unhappy", you cannot tell which team to call. You have to check the two things separately.

RAG is the same. The retrieval layer is "did we pick up the right parcel" — did the correct source runbook get retrieved? The generation layer is "did it arrive in good condition" — given the right pages, did the model produce a good answer? Grade them apart and a red result tells you where to look. Grade them together and you are back to the M4 shrug.

The two layers are built differently on purpose, and the difference is the point:

  • Retrieval layer — deterministic. It asserts one thing: for this question, the correct source runbook appears in /retrieve's top-k. That is phrase-independent (it does not care how the model would word anything), stable, and fast. This is your regression tripwire — if a chunking change or a stale index quietly breaks retrieval, this layer goes red first and cheapest, before any answer is even generated. A tiny script runs it (retrieval_check.py) because "the right file is in this JSON list" is awkward to express in a general eval runner.
  • Generation layer — graded. Given a real answer from /ask, it grades with the wide contains-any nets and the LLM-judge rubric from the eval pyramid. This is where the paraphrase-tolerance lives, and where the local judge earns its keep. promptfoo runs this layer.

Every question in the golden set is tagged with the layer it lives in, so a run reports two separate numbers — a retrieval score and a generation score — and those two numbers point at two different teams of fixes.

Designing a golden set that actually discriminates​

A golden set is only as good as the questions in it, and there are three principles that separate a real one from a checkbox.

Author every question from a source. Do not brainstorm questions from imagination — walk the corpus and write each question from an actual runbook passage, and record which one. OpsMate's golden.yaml carries a source: field on every question naming the runbook it came from. This does two things: it guarantees the question is answerable (you are looking at the answer as you write it), and it makes the retrieval layer trivial to check (you already know the correct source). It also means M6 can reuse these as training and eval data, because the source link is right there.

Write questions that discriminate. A question a broken system would also pass is a wasted question. "What company is this?" tells you nothing. "The payments API is throwing 500s, what is the most likely cause?" discriminates hard — a system with good retrieval names connection-pool exhaustion (the runbook's actual answer); a system with bad retrieval gives generic web advice. A good golden question is one where the right answer and a plausible-wrong answer clearly diverge.

Include questions you should not be able to answer. This is the beat most people skip. OpsMate's corpus is SRE runbooks for a fictional retailer; it has no runbook for "what is the optimal number of Kafka partitions?" or "how much do we pay for on-call?". So the golden set includes a few of exactly these — deliberately unanswerable-from-corpus questions. The correct behaviour is to admit the gap: "I do not have a runbook for that." If the model instead bluffs a confident, invented answer, that is a failure, and the honesty layer exists to catch it. An assistant that makes things up during an incident is worse than useless — it is dangerous — so we test for honesty on purpose. (The M4 spike stumbled into an unanswerable question by accident and the run caught it. This module turns that accident into a designed probe.)

Prompts as config — version it, test it, roll it back​

Now back to the Friday-afternoon teammate. The reason that prompt edit was scary is that the prompt was buried in the code — changing it meant editing main.py, rebuilding the image, and hoping. That is the wrong shape for something you tune often.

The analogy: the prompt is the recipe card taped inside the kitchen cupboard, not a rule carved into the chef's training. When the dish needs adjusting you change the card — you do not retrain the chef. The card is cheap to change, easy to read, and trivially reversible: swap in the old card and you are back. A recipe carved into the cook is none of those things.

So OpsMate externalizes its system prompt out of the code and into a versioned file — labs/opsmate/prompts/system.txt — mounted into the app read-only. Changing the prompt is now: edit the file (or swap in a different one), restart the app. No rebuild, no code change. Because it is a plain file in the repo, it is versioned in git, it is diffable in a review, and rolling back is git checkout or swapping the file name. This is the whole "prompts as config" idea, and in the lab you will measure its payoff: run the golden suite against system.txt, then against a variant system-v2.txt, and watch the scores move with the code completely untouched. The prompt is a lever, and now it is a lever you can pull, test, and un-pull deliberately.

The local judge — a smoke detector, not an examiner​

The LLM-judge layer needs a model to do the judging, and here we make a deliberate, honest choice. OpsMate's judge is the same small local model — qwen3:0.6b, served by Ollama, no cloud key required. That keeps the whole course running on your laptop with no API bill. But you must be clear-eyed about what a 0.6B judge is and is not.

A local 0.6B judge is a smoke detector, not a fire examiner. A smoke detector is cheap, always-on, and catches the gross failures — the answer that ignored the context entirely, the confident bluff on an unanswerable question, the empty response. That is genuinely useful; those are the failures you most need caught automatically. What it is not is a calibrated examiner — it will be noisy on the margins, it will occasionally grade a borderline answer wrong, and two runs of the same rubric can disagree (you will measure exactly this disagreement in the deep dive). Better judges exist — larger models, or a strong frontier model as judge — and they cost more per grade. M12 upgrades the judging story to something you would gate production on. For now, the honest framing is: trust the local judge to catch the obvious, corroborate it with the deterministic layers, and never treat a single 0.6B grade as ground truth.

The baseline ritual — record the number, then beat it​

Everything above assembles into one ritual you perform at the end of the lab, and it is the payload of the module. You run the golden suite twice and write both numbers into a versioned file:

  • No-RAG — the base model answering directly, with no retrieval. This is the model on its own, with none of your runbooks in front of it.
  • RAG — OpsMate's /ask, with retrieval feeding the model the right pages.

RAG should clearly beat no-RAG on the runbook-grounded questions — that gap is the measured value of retrieval, the thing M4 was worth. And the honesty questions often show the sharpest contrast: the base model with no context happily invents an answer, while the grounded model is more willing to admit the gap. The absolute numbers will be modest — a 0.6B model on CPU is not going to ace anything — and that modesty is honest, not a failure. A believable, recorded 62% is worth more than an invented 95%.

Then you write those numbers into baseline.md and commit it. That committed file is the yardstick:

That is why the file matters more than the run. A number in a chat window is gone tomorrow. A number in a committed file is a contract: this is what we scored, and the next change has to do at least this well. Every later stage of this course holds itself to it.

What you'll do next​

In the lab you will bring the M4 stack back up on its persisted index, then externalize the system prompt into a mounted file and confirm the answers are unchanged. You will read the golden set — walk four representative questions including one unanswerable — and run the two layers: retrieval_check.py for the deterministic top-3 checks, and promptfoo for the graded generation layer, where you will inspect one judge grade honestly. You will run the prompt A/B — system.txt versus system-v2.txt on the same suite — and watch scores move with the code untouched. Then the baseline moment: no-RAG versus RAG, both layers, written into baseline.md and committed as the number M6 must beat. Finally the X-Ray's new Evals lens turns those JSON results into a scoreboard, and Teardown keeps evals/ and prompts/ so the yardstick survives.

The skill you leave with is the one that turns "the prompt edit felt better" into "v2 scores three points higher on the golden set, here is the file" — and that is the difference between shipping on a feeling and shipping on evidence.
