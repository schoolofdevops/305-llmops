Deep Dive — Fine-Tuning: Under the Hood

The core lab ran the loop end to end: synthesize, tune, merge, convert, measure. This Part 2 goes under the hood of the decisions the lab made for you. You will put a number on what the LoRA rank actually buys (without training anything), see the single most common way a fine-tune silently fails and how to detect it, probe your tuned model for what it forgot, and understand the two paths — the training container and QLoRA on a GPU — that carry this pipeline off your laptop. It extends the lab; it does not repeat it.

Every runnable block here is real and has captured output folded in. Run them yourself — most need only the base model and a few seconds.

1. What the rank actually buys — a measured table, no training required​

The lab used r=8 because the spike did. But "why 8?" deserves an answer you can see, and the useful part is that the trainable-parameter count is a pure function of the rank — you do not need to train to compute it. The number of trainable parameters an adapter adds is, per targeted layer, proportional to r × (input_dim + output_dim). Double the rank, double the trainable parameters. rank_sweep.py attaches a LoRA at several ranks to the real base model and reports the count for each, without a single optimizer step:

uv run labs/m6/rank_sweep.py

Expected output (exact for this base and q_proj,v_proj targets — these numbers are deterministic, not point-in-time)

LoRA rank sweep — base labs/opsmate/models/qwen3-0.6b
  targets: q_proj, v_proj   alpha: 16 (fixed)

  rank     trainable          total   trainable %
  ----  ------------  -------------  ------------
     4       573,440    596,623,360       0.0961%
     8     1,146,880    597,196,800       0.1920%
    16     2,293,760    598,343,680       0.3834%
    32     4,587,520    600,637,440       0.7638%

  Read it: trainable grows LINEARLY with rank (double r, double the adapter) ...

Read the table straight. Each doubling of r doubles the trainable count — 573K → 1.15M → 2.29M → 4.59M — while the total barely moves, because the base stays frozen. So what does more rank buy you? Capacity. A higher-rank adapter can represent a more complex adjustment to the layer, which helps if the behaviour you are teaching is genuinely intricate. But that capacity cuts both ways: on a small dataset (a couple hundred synthetic samples, like the lab), a high-rank adapter has more than enough room to memorize the training examples rather than generalize — the overfitting the lesson warned about. r=8 is the lab's sweet spot because it is enough capacity to learn OpsMate's voice on a small set without handing the model enough parameters to just memorize it.

Two more knobs the sweep holds fixed, worth understanding:

  • Alpha is a scaling factor on the adapter's contribution — effectively how loudly the fittings speak relative to the frozen structure. The common rule of thumb is alpha = 2 × r (this lab: r=8, alpha=16), which keeps the adapter's effective scale roughly constant as you change rank. It does not change the parameter count (the sweep holds it fixed and only rank moves the numbers), only the magnitude of the learned update.

  • Which modules you target changes the count as much as the rank does. The lab adapts only q_proj and v_proj — the attention query and value projections — the minimal, well-tested choice. Add k_proj and o_proj, or the MLP projections, and both the trainable count and the capacity rise. Try it:

    uv run labs/m6/rank_sweep.py --targets q_proj k_proj v_proj o_proj

    Expected output (four targets instead of two — every row is doubled versus the table above; deterministic, not point-in-time)

         4     1,146,880    597,196,800       0.1920%
         8     2,293,760    598,343,680       0.3834%
        16     4,587,520    600,637,440       0.7638%
        32     9,175,040    605,224,960       1.5160%

    Every row is exactly double the two-target sweep — r=8 on four targets (2,293,760) equals r=16 on two (2,293,760) — because you doubled the number of adapted matrices. More targets = more capacity = more to overfit, the same trade-off as rank.

The practical takeaway for real work: start small (r=8, attention projections only), and only climb rank or add target modules if the tune is clearly underfitting — the loss barely moving, the behaviour not sticking. Reaching for r=64 on a small dataset is how you get a model that aces its training data and fails on yours.

2. The chat-template pitfall — the silent fine-tune killer​

Here is the mistake that wastes more fine-tunes than any other, and it produces no error — the loss goes down, the run "succeeds", and the tuned model is worse than the base at serve time. The cause: you trained on one text format and the server wraps prompts in a different format at inference.

Every chat model has a chat template — the exact way system/user/assistant turns get serialized into the token string the model actually sees, including special role markers. llama-server applies this template at serve time. If your training data was serialized a different way, the model learned to respond to tokens it will never see in production. It is the "studied for the wrong exam format" failure: you learned the material, but the paper is laid out differently and none of your preparation transfers.

chat_template_demo.py makes the difference concrete. It renders one sample conversation two ways — the model's own template (what training and serving both must use) and a naive ROLE: text concatenation a hand-rolled trainer might produce:

uv run labs/m6/chat_template_demo.py

(A [transformers] PyTorch was not found info line may precede the output — benign; the demo needs only the tokenizer.)

Expected output (the model's real template, folded from an actual run)

======================================================================
1. CORRECT — the model's own chat template (train AND serve use this):
======================================================================
<|im_start|>system
You are OpsMate, an SRE assistant.<|im_end|>
<|im_start|>user
the payments api is throwing 500s, what is the most likely cause<|im_end|>
<|im_start|>assistant
<think>

</think>

Database connection-pool exhaustion — check db_pool_in_use.<|im_end|>

======================================================================
2. WRONG — a naive Q/A concatenation a hand-rolled trainer might use:
======================================================================
SYSTEM: You are OpsMate, an SRE assistant.
USER: the payments api is throwing 500s, what is the most likely cause
ASSISTANT: Database connection-pool exhaustion — check db_pool_in_use.

Look at what rendering #1 has that #2 does not: the <|im_start|> / <|im_end|> role markers, and — specific to Qwen3 — an empty <think></think> block before the assistant's answer. Those special tokens are how the model knows where a turn begins and ends. Train on #2 and the model never learns to associate your good answers with the markers the server emits; at serve time it sees <|im_start|>assistant and has no tuned behaviour attached to it. The tuning silently does not transfer.

This is why train_lora.py calls tokenizer.apply_chat_template(...) to render every training sample — it produces exactly rendering #1, the same string llama-server builds at inference. The rule is absolute: render your training data with the model's own chat template, the same one the server uses. The one time it bites hardest is when you switch base models mid-project — a Llama template and a Qwen template differ, so training data serialized for one is wrong for the other. Regenerate, do not reuse.

3. Catastrophic forgetting — what did the tune cost?​

Fine-tuning teaches new behaviour by moving weights, and moving weights can overwrite what the model already knew. Push a model hard toward your narrow runbook voice and it can get measurably worse at ordinary things that have nothing to do with runbooks. This is catastrophic forgetting, and you should always check for it, because the loss curve will not warn you — it only measures your training data, where forgetting looks like success.

The probe is simple: ask the same out-of-domain questions to the base model and the tuned model, and read the answers side by side. forgetting_probe.py asks three deliberately general questions (a capital city, a word definition, a small arithmetic fact) against whatever model is currently served on /v1. Capture the base first, then the tuned model.

With the base model served (make -C labs/opsmate up, no MODEL_GGUF):

uv run labs/m6/forgetting_probe.py --which base

Expected output (point-in-time; you are reading whether the answers are coherent, not grading them)

catastrophic-forgetting probe — base model @ http://localhost:8080/v1

  Q: In one sentence, what is the capital of Japan?
  A: The capital of Japan is Tokyo.

  Q: In one sentence, what does the word 'ephemeral' mean?
  A: The word 'ephemeral' refers to something that is short-lived or temporary.

  Q: In one sentence, what is 17 multiplied by 4?
  A: 17 multiplied by 4 is 68.

Now swap to the tuned model (MODEL_GGUF=opsmate-tuned-q8_0.gguf make -C labs/opsmate up) and run the same probe with --which tuned:

uv run labs/m6/forgetting_probe.py --which tuned

Expected output (point-in-time; read it against the base answers above — same three facts, still coherent)

catastrophic-forgetting probe — tuned model @ http://localhost:8080/v1

  Q: In one sentence, what is the capital of Japan?
  A: The capital of Japan is Tokyo.

  Q: In one sentence, what does the word 'ephemeral' mean?
  A: The word 'ephemeral' means short-lived or temporary.

  Q: In one sentence, what is 17 multiplied by 4?
  A: 17 multiplied by 4 is 68.

Read the two side by side. A healthy tune answers these about as well as the base — the general knowledge survived. On this reference run it did: all three tuned answers are correct and phrased almost identically to the base, so this tune cost no measurable general knowledge. A tune that has forgotten too much goes incoherent or wrong on questions the base handled: it might mangle the arithmetic, or answer the definition in fractured runbook-speak. If you see that, the tune was too aggressive — the fixes are gentler tuning (lower rank, fewer epochs) or mixing some general-purpose data into your training set so the model has a reason to keep its old knowledge.

This clean result is worth connecting to the lab's measurement. In the core lab the tuned model lost to the RAG baseline on the golden set — yet here it has forgotten nothing. Those two facts together are the diagnosis: the regression was not the model getting dumber (knowledge is intact), it was the tune pushing the model toward a terse runbook voice that, on this small synthetic set, made it answer more confidently and sometimes invent where the base would hedge. That is a behaviour shift the golden set penalises, not knowledge loss — exactly the distinction this probe exists to draw. On this course's small, gentle tune (a couple hundred samples, two epochs, r=8) you should see little to no forgetting — which is itself the lesson: a proportionate tune adjusts behaviour without wrecking the base. But you only know that because you checked, and checking is the habit. In production you would probe a much wider set of held-out general questions before promoting a tuned model.

4. Off the laptop — the training container and QLoRA on a GPU​

The lab ran the tune with uv run directly on the host. That is the right call for an 8 GB CPU laptop — a CUDA torch image is several gigabytes and adds nothing to a CPU run, and pinned uv dependencies already make the run reproducible. But you will not train on your laptop forever, and there are two well-worn paths off it.

The training container. In a real pipeline — CI, a shared runner, a GPU node — you want the training environment frozen and shareable so a result that later gates promotion (M12) is not at the mercy of "works on my machine" library drift. labs/m6/Dockerfile.train is that pattern: a slim Python image with pinned training dependencies and train_lora.py as its entrypoint. Confirm it builds the shape you expect:

grep -E 'FROM|train_lora|torch==' labs/m6/Dockerfile.train

Expected output (the base image, the pinned torch, and the trainer as entrypoint)

FROM python:3.12-slim
      "torch==2.4.1" \
COPY train_lora.py /work/train_lora.py
ENTRYPOINT ["python", "/work/train_lora.py"]

You run it by mounting the models and train directories in and passing the same flags you used on the host:

docker build -f labs/m6/Dockerfile.train -t opsmate-train labs/m6
docker run --rm \
  -v "$PWD/labs/opsmate/models:/work/models:ro" \
  -v "$PWD/labs/opsmate/train:/work/train" \
  opsmate-train --base /work/models/qwen3-0.6b --train /work/train/train.jsonl --out-dir /work/train

The adapter and progress.jsonl land on the mounted volume exactly as the host run wrote them — same artifacts, frozen environment. On a GPU node you would swap the base image for an nvidia/cuda one and add bitsandbytes for the QLoRA path below. (This module authored the pattern; M11 is where Argo Workflows actually runs a pipeline like this on the cluster — the training container is the unit it will schedule.)

The QLoRA / GPU track. labs/m6/colab_qlora.ipynb is the optional enrichment notebook: the same LoRA loop, but with the base loaded in 4-bit (bitsandbytes NF4) so a much larger model fits on a single small GPU. It is the technique for when the base you want to tune is too big to hold in fp16 — which the 0.6B model of this course never is, so it stays enrichment. The honest note in the notebook is the important part: bitsandbytes 4-bit is CUDA-only. It will not run on the course's CPU laptop path, on Apple Silicon, or on Colab's CPU runtime — you need a real GPU (a free Colab T4, availability permitting). The adapter it produces is the same kind of artifact as the CPU lab's; you would download it and run the lab's merge_and_convert.py locally to get a servable GGUF. QLoRA changed how the base was held during training, not what you ship.

5. The tooling landscape — an honest paragraph each​

The lab used raw transformers + peft on purpose: it is the most transparent path, and you saw every step. In production you would likely reach for one of these higher-level tools. Here is an honest read on each, so you know what you are choosing between.

  • Axolotl — a config-file-driven trainer that wraps transformers/peft/trl. You describe the run in a YAML (base model, dataset format, LoRA/QLoRA settings, sequence length) and it handles the plumbing. Its value is reproducibility and breadth: it supports a wide range of models and training recipes with a consistent interface, and the config is your run's documentation. It is the common default for serious LoRA/QLoRA work on GPUs. On a CPU laptop it is overkill — you would not see the mechanism the way this lab showed it.

  • Unsloth — a set of hand-optimized training kernels that make LoRA/QLoRA fine-tuning substantially faster and more memory-efficient on NVIDIA GPUs, often 2× or more, letting bigger models or longer sequences fit on the same card. It is a drop-in accelerator for the exact loop you ran, not a different paradigm. The catch is that it is GPU-specific (CUDA), so it does nothing for the CPU path — its whole value is squeezing more out of a GPU you already have.

  • MLX — Apple's array framework for Apple Silicon, with an mlx-lm package that does LoRA fine-tuning on the Mac's unified-memory GPU (the Metal path). For Mac users this is the natural way to actually use the Apple GPU that a Docker container cannot reach (the containerized-CPU limitation you have hit since M3). It is Apple-only by design. If you are on a Mac and want a faster tune than the CPU path gives, mlx-lm is the tool — at the cost of a Mac-specific, non-portable workflow.

The through-line: the concepts you learned here — LoRA rank, target modules, the chat template, synthetic data, the measurement — are identical across all of them. The tools differ in speed, hardware, and how much they hide. Learn the mechanism once, as you did, and every one of these becomes a matter of reading its config.

Where you will use this​

  • Diagnosing a fine-tune that "trained fine" but serves badly — reach for the chat-template check (§2) first. It is the highest-probability cause and the easiest to miss, because nothing errors.
  • Sizing an adapter for a new tuning job — the rank/target table (§1) is how you reason about capacity before you spend GPU hours: start minimal, climb only on evidence of underfitting.
  • Deciding whether a tuned model is safe to promote — the forgetting probe (§3) is the check that catches a regression the training loss cannot see. You run a wide version of it before any promotion gate (M12).
  • Moving the pipeline to CI or a cluster — the training-container pattern (§4) is the unit M11 schedules with Argo; freezing the environment is what makes a promotion-gating result trustworthy.
