Lab — Fine-Tuning: Synthetic Data, LoRA & the Measurement

Resource path: 8 GB core — everything here runs

The whole fine-tune runs on the 8 GB core path with no GPU and no cloud. The one twist versus earlier modules: you run this with the OpsMate stack down. Training wants the RAM the three containers were using, so the course's one-stack-at-a-time rule now applies to training — the model, app, and ui services come down before you train, and the tuned model goes back up at the end. The training itself is plain LoRA on CPU (the spike measured about 0.5 s/step); a full run here is a few minutes, not hours. The optional QLoRA track needs a GPU and is enrichment only — skip it with nothing lost.

Before you start

All commands run from the root of the labs repo (305-labs/). You need docker, curl, jq, uv, node, git, and ollama responding. This lab builds on the M4/M5 stack — the persisted Chroma index, the golden set, and baseline.md all carry over. The first train_lora.py run downloads about 2 GB of PyTorch through uv (once); do it on a decent connection. New here? Do the Setup section first.

This is the lab where OpsMate stops borrowing a stock model and starts running one you trained. You will build synthetic training data from the runbook corpus, run a real LoRA fine-tune while watching the loss curve live, merge and convert the result to a servable GGUF, swap it into the stack with one env var, and then — the part that matters — measure it honestly against the M5 baseline. By the end you have OpsMate v1.0: a tuned model, weighed on the same scale as the baseline, with the result read straight.

Step 1 — Bring the stack DOWN and preflight the training​

Training and the serving stack compete for the same RAM, so first make sure the stack is down. This is the one-stack-at-a-time rule, applied to training:

make -C labs/opsmate down

Expected output (if the stack was already down, Compose reports nothing to remove and prints only the closing line — that is fine)

==> Stopping the OpsMate stack ...
    Stopped. The GGUF model file on disk stays for the next module.

Confirm the training generator is available. Synthetic data is generated by host Ollama serving qwen3:0.6b — the same small model you already pulled for the M5 judge, now put to a different job. Confirm it responds:

ollama list | grep qwen3:0.6b || ollama pull qwen3:0.6b

Expected output (the model line; if it was missing, the pull fetches it once)

qwen3:0.6b    7df6b6e09427    522 MB    About an hour ago

The base model you will tune is the safetensors copy of Qwen3-0.6B at labs/opsmate/models/qwen3-0.6b/ — the same weights the GGUF was built from, in the format the training libraries read. Confirm it is there:

ls labs/opsmate/models/qwen3-0.6b/

Expected output (the config plus the weights file — the exact list depends on the model)

config.json  generation_config.json  merges.txt  model.safetensors
tokenizer_config.json  tokenizer.json  vocab.json

If that directory is missing, follow the setup page to fetch it — training reads the safetensors, not the GGUF.

Step 2 — Synthesize the training data (generate → filter → split)​

Now build the practice question bank. synthesize.py walks each runbook section, asks the local model for a few grounded question/answer pairs, quality-filters them, and writes train.jsonl / eval.jsonl in the app's chat format. It reads only the corpus — never golden.yaml — so your training data and your held-out test set never overlap:

uv run labs/m6/synthesize.py

Expected output (per-section progress then the split; the counts are point-in-time — the generator is a small model, so your kept/rejected numbers will differ)

OpsMate synthetic data — 14 runbooks, 78 sections
generator: qwen3:0.6b @ http://localhost:11434  (think:false)
asking for 3 Q&A per section — this takes a few minutes on CPU

  [1/78] backup-restore.md :: Purpose                          +3 kept  -0 rejected  (running total 3)
  ...
  [13/78] capacity-review-guide.md :: Gathering the demand signals     +0 kept  -3 rejected  (running total 36)
  ...
  [73/78] vpn-access.md :: Symptoms                         +1 kept  -2 rejected  (running total 194)
  ...
  [78/78] vpn-access.md :: Break-glass                      +3 kept  -0 rejected  (running total 205)

kept 205 pairs, rejected 26 (11% filtered out)
  train: 185  ->  labs/opsmate/train/train.jsonl
  eval:  20  ->  labs/opsmate/train/eval.jsonl
  rejects (inspect these): labs/opsmate/train/rejects.jsonl

next: uv run labs/m6/train_lora.py

The full corpus is 78 sections, and at a few pairs each you land a couple hundred grounded samples in three or four minutes. The rejected count is the filter earning its keep — malformed pairs, duplicates, and answers that drifted off the section, thrown out before they could teach the model bad habits.

Now inspect what you built — this is the "read your data" habit, and it is the difference between a good tune and a mysterious one. Look at two kept samples first:

head -2 labs/opsmate/train/train.jsonl | jq -c '{q: .messages[1].content, a: .messages[2].content, source}'

Expected output (your questions differ; the shape — a grounded question, a concrete answer, and the source runbook — is the constant)

{"q":"What is the first step for restoring a point-in-time recovery?","a":"Identify the target recovery point. Use the command `SELECT max(ts) FROM audit_log WHERE ts < '<incident time>;'` on a scratch restore.","source":"backup-restore.md"}
{"q":"How to handle jittered TTLs?","a":"spread expiries so many keys do not lapse on the same tick.","source":"cache-stampede.md"}

Each sample carries the app's system prompt in messages[0], then the generated question and answer — the same chat shape the server applies at inference, which is what makes the tuning transfer (the Deep Dive shows what breaks if it does not). Now look at a rejected one, because seeing the garbage you kept out is how you learn what "good data" means:

head -1 labs/opsmate/train/rejects.jsonl | jq -c '{q: .question, a: .answer, reason}'

Expected output (point-in-time; the reason field is the value here — it names exactly why the filter refused the pair)

{"q":"Pull four signals for the trailing two quarters:","a":"Peak requests per second per service, error budget burn, saturation of the top three resources, and forecast growth from product.","reason":"question has no question mark"}

Read the reason. This one is malformed at the structural level — the "question" is an instruction with no question mark, so it never was a question the model could learn to answer. The filter caught it on shape alone, before the answer's content mattered. Your reject will likely be a different pair with a different reason (ungrounded answer, duplicate, or malformed like this one) — the reason field is the value, because it names the specific failure the filter refused. (If rejects.jsonl is empty on your run, you got a clean generation batch; run wc -l labs/opsmate/train/rejects.jsonl to confirm — this run rejected 26 — and know the filter is still there for the run where it is not clean.) That is the garbage-in-garbage-out rule made concrete: the filter is why the data is worth training on.

Step 3 — Run the LoRA fine-tune (real, minutes-scale)​

Now the tune. train_lora.py loads the base model, attaches a LoRA adapter (r=8, alpha=16, on q_proj/v_proj), trains a couple of epochs over your train.jsonl, and writes one line per step to labs/opsmate/train/progress.jsonl — the file the X-Ray Train lens tails. The first run downloads PyTorch (about 2 GB, once); after that it starts in seconds:

uv run labs/m6/train_lora.py

(Real console output through Steps 3–6 is noisier than these blocks — progress bars, an image-build transcript on make up, and a dumped chat template during conversion all scroll past. The Expected blocks show the end-state lines that matter; if those match, the step worked.)

Expected output (the trainable-parameter line is the LoRA lesson; the per-step loss and timings are point-in-time — read the loss falling, not the exact values)

OpsMate LoRA fine-tune — base labs/opsmate/models/qwen3-0.6b
  device: CPU (fp32)  |  r=8 alpha=16 target=q_proj,v_proj
trainable params: 1,146,880 || all params: 597,196,800 || trainable%: 0.1920
    model loaded in 4.4s
    185 training samples from labs/opsmate/train/train.jsonl

  training — watch labs/opsmate/train/progress.jsonl (the X-Ray Train lens tails it)

  step    2  loss 4.6995  lr 1.99e-04  6.7s
  step   41  loss 0.8567  lr 1.57e-04  86.1s
  step   91  loss 0.7854  lr 1.03e-04  175.0s
  step  141  loss 0.7140  lr 4.95e-05  250.4s
  step  186  loss 2.0722  lr 1.08e-06  305.8s

  done — 186 steps, loss 4.9905 -> 2.0722 in 305.4s
  adapter saved to labs/opsmate/train/adapter

There is the whole LoRA story in one line: 1,146,880 trainable of 597,196,800 — 0.19%. You are tuning two-tenths of one percent of the model and freezing the rest, which is why this fits on a laptop CPU. And the loss curve is the healthy shape from the lesson: it falls from about 5.0 into the low 0.7s through the middle of the run — the adapter learning your data, then running out of easy gains. (Two things to read correctly on this run. The done line reports 4.9905 -> 2.0722, and the last-step loss of 2.07 is higher than the mid-run 0.71 — that is a single-sample last-batch spike, not the model getting worse; the running loss through the middle is the real trajectory. And the per-step lines here are sampled: the log writes every step to progress.jsonl, but the console prints a subset.) Your absolute losses, step count, and duration depend on how many samples you generated — this run did 185 samples over 186 steps in about five minutes — but the shape, a clear descent that flattens, is what a good run looks like. (A run whose loss barely moves means the data was too thin or too noisy; a run whose loss crashes to near zero on very few samples is overfitting — the Deep Dive shows both.)

The adapter that just landed is tiny — check it:

ls -la labs/opsmate/train/adapter/adapter_model.safetensors | awk '{print $5, $NF}'

Expected output (a few megabytes — the "removable fittings" made literal)

4602248 labs/opsmate/train/adapter/adapter_model.safetensors

About 4.6 MB of adapter, next to a base model of hundreds of megabytes. That small, self-contained artifact is what M7 will version and package as OpsMate v1.0.

Step 4 — Watch the loss curve live: the X-Ray Train lens​

The X-Ray tool has a new Train lens that reads progress.jsonl and plots the loss curve, step counter, learning rate, and elapsed time — the same static-file pattern as the Evals lens, pointed at the training log. Start the tool:

bash labs/tools/xray/serve.sh

Open http://127.0.0.1:8010/ and go to the Train tab. You have two honest ways to use it:

  • Replay (simplest): the run from Step 3 already wrote the full progress.jsonl, so the lens shows the completed curve — the descent and the final loss, with the adapter path in the done-state.
  • Live (if you want to watch it stream): open the Train tab, then in another terminal re-run uv run labs/m6/train_lora.py and watch the curve extend step by step as the file grows. The lens tails the file, so the plot moves while training runs.

Either way, read the curve as the lesson described: a fall that flattens is a healthy tune. This is the same read you would do on any training job at work — the loss curve is the first thing you look at to know whether a run is learning, stuck, or overfitting. Stop the X-Ray server with Ctrl-C when you are done looking (you can leave it running through the next steps if you like — it only reads files).

The lens plots what the trainer wrote line by line to progress.jsonl. If you would rather read the log directly — or want to confirm the lens is showing you the real file — the same numbers are one jq away. Count the steps and read the first and last:

wc -l labs/opsmate/train/progress.jsonl
head -1 labs/opsmate/train/progress.jsonl | jq .
tail -1 labs/opsmate/train/progress.jsonl | jq .

Expected output (point-in-time; one JSON object per step — your step count and losses match your own training run)

     186 labs/opsmate/train/progress.jsonl
{
  "step": 1,
  "loss": 4.9905,
  "lr": 0.0002,
  "elapsed_s": 4.0
}
{
  "step": 186,

One well-formed JSON object per step — step, loss, lr, elapsed_s — which is exactly what the lens tails. The first line's loss is above the last line's on the done summary, and every line in between is a point on the curve. This is the plumbing under the plot: a plain append-only log any tool (the lens, jq, a notebook) can read.

Step 5 — Merge the adapter and convert to a servable GGUF​

The adapter is trained but it is not yet something llama-server can load. Two steps fix that, both in one script: merge the adapter into the base weights (producing a standalone model), then convert that merged model to a q8_0 GGUF. merge_and_convert.py does both, shallow-cloning llama.cpp on first run for its converter:

uv run labs/m6/merge_and_convert.py

Expected output (the clone happens once; the convert is quick; sizes and timings are point-in-time)

==> merge: labs/opsmate/models/qwen3-0.6b  +  labs/opsmate/train/adapter
    merged model saved to labs/opsmate/train/merged  (5.7s)
==> cloning llama.cpp (shallow) into labs/m6/.llama.cpp ...
Cloning into 'labs/m6/.llama.cpp'...
Installed 40 packages in 568ms
INFO:hf-to-gguf:Model architecture: Qwen3ForCausalLM
==> convert: labs/opsmate/train/merged  ->  labs/opsmate/models/gguf/opsmate-tuned-q8_0.gguf  (q8_0)
    wrote labs/opsmate/models/gguf/opsmate-tuned-q8_0.gguf  (610 MB, 36.6s)

done — serve it by swapping the compose model file:
  MODEL_GGUF=opsmate-tuned-q8_0.gguf make -C labs/opsmate up

Confirm the tuned GGUF landed beside the base one — this is the v0-base / v1.0-tuned pair M7 packages:

ls labs/opsmate/models/gguf/

Expected output

opsmate-tuned-q8_0.gguf  qwen3-0.6b-q8_0.gguf

Two models in the same directory, same format, both servable by the same engine. The merge folded your adapter permanently into these weights (the "leave the fittings in the building" choice from the lesson), and the convert produced exactly the file shape M3's llama-server already knows how to serve.

Step 6 — The swap: serve the model you trained​

Here is the payoff of making the GGUF file switchable in the compose model service. Bring the stack up with MODEL_GGUF pointed at the tuned file — one env var, no code change, no rebuild of the model service:

MODEL_GGUF=opsmate-tuned-q8_0.gguf make -C labs/opsmate up
Keep your host overrides on the same line

make up re-runs the preflight and passes your environment through. If your host needed OLLAMA_URL=... in earlier modules (Rancher Desktop, Colima, plain Docker Engine — the app reaches host Ollama for embeddings), keep prefixing it here too: OLLAMA_URL=... MODEL_GGUF=opsmate-tuned-q8_0.gguf make -C labs/opsmate up. The preflight also now checks the file you are serving — if the tuned GGUF is missing or truncated it fails here with a clear message, not in a container crash loop.

Expected output (the preflight validates the tuned file, then the stack comes up as always)

==> OpsMate preflight
    ✓ Model file present and looks like a real GGUF.
    ✓ 4804 MB free (need ~2200 MB).
    Preflight passed.
==> Starting the OpsMate stack ...
 Container opsmate-model  Healthy
==> Waiting for the model service to report healthy (up to 90s) ...
    Model service is healthy at http://127.0.0.1:8080/health.
    Stack is up.

Confirm the model service is actually serving the tuned file. The /v1/models endpoint reports the loaded model's name, and the app answers through it:

curl -s http://localhost:8080/v1/models | jq '.data[0].id'

Expected output (the served model's alias, not its file path — see the note below)

"qwen3-0.6b"

Do not be thrown by this. The compose model service starts llama-server with --alias qwen3-0.6b, so /v1/models reports that stable alias regardless of which GGUF file is loaded. That is deliberate: it is what keeps the app's CHAT_MODEL constant across the swap, so nothing downstream has to change when you switch base for tuned. The /v1/models id therefore does not tell you which file is loaded. To confirm the file, read the container's actual command line:

docker inspect opsmate-model --format '{{join .Args " "}}' | grep -o '\-m [^ ]*'

Expected output (the -m flag names the file the server actually loaded — the tuned GGUF)

-m /models/opsmate-tuned-q8_0.gguf

There is the real proof the swap took effect: the served file is opsmate-tuned-q8_0.gguf, even though the reported model name stayed qwen3-0.6b. Now a quick sanity check that the app answers end to end through the tuned model (the index carried over from M4/M5, so RAG works unchanged):

curl -s "http://localhost:8001/ask?q=the%20payments%20api%20is%20throwing%20500s%2C%20what%20is%20the%20most%20likely%20cause" \
  | jq '{answer, sources: [.sources[] | .source]}'

Expected output (wording varies — this is a tuned 0.6B model; the grounding in the payments runbook is the constant to look for. Some tuned runs return a very terse or even empty answer on this exact question while the sources stay correct — do not treat that as a broken stack. It is the answer-discipline regression you are about to measure, showing itself early; the measurement in Step 7 is where it gets quantified)

{
  "answer": "The most likely cause is database connection-pool exhaustion, not a code bug.",
  "sources": ["payments-api-5xx.md", "payments-api-5xx.md", "payments-api-5xx.md"]
}

The app is answering through a model you trained, in the same stack, with nothing but a filename changed. That is the whole deployment story for a fine-tuned model on this course's spine.

Step 7 — THE MEASUREMENT: tuned model vs the M5 baseline​

This is the module. You now weigh the tuned model on the exact scale M5 built — the same golden set, the same graders — and read the result against the committed baseline. Three arms, in order.

First the retrieval layer — your control. Tuning changed the model, not the index, so this score should be unchanged from M5. Run it:

uv run labs/m5/retrieval_check.py

Expected output (the same 24/24 as the M5 baseline — a control that stays put; your count matches whatever M5 recorded)

...
retrieval layer: 24/24 passed (100.0%)
wrote labs/opsmate/evals/retrieval-latest.json

If retrieval moved, stop and find out why before trusting anything else — nothing you did should have touched the index, so a change here is a bug, not a result. A control that holds is what makes the rest of the comparison clean.

Now the generation layer, RAG arm — the tuned model answering with retrieval, graded by the same wide nets and local judge as M5. Regenerate the test file (no-op if unchanged) and run it:

uv run labs/m5/make_promptfoo_tests.py
npx -y promptfoo@latest eval \
  -c labs/opsmate/evals/promptfooconfig.yaml \
  -o labs/opsmate/evals/generation-tuned-latest.json \
  --no-cache --max-concurrency 2

--no-cache matters here for the same reason it did in M5: the request promptfoo sends is byte-identical to the baseline run (the question is the same; the model lives server-side), so without it you would score the cached baseline answers, not the tuned model. Writing to a separate -tuned- file keeps your baseline run intact for comparison.

Expected output (point-in-time; compare the pass rate to the M5 baseline's 6/15 — it may be higher, equal, or lower. On this course reference run it was lower)

✓ Eval complete (ID: eval-Kul-2026-07-19T22:05:58)

Now put the three numbers next to the M5 baseline and read the result. Here is the course reference run:

ArmTunedM5 baselineVerdict
Retrieval (control)24/24 (100%)24/24unchanged — as expected
RAG generation2/15 (13.3%)6/15 (40%)lost, −4
No-RAG direct1/15 (6.7%)3/15 (20%)lost, −2

The tuned model lost on both graded arms while the control held. That is the climax of this module, and it is taught straight: the tune did not beat the baseline, so this model does not ship. Retrieval was untouched (it is model-independent, so 24/24 was never going to move), and — importantly — general knowledge survived the tune (the Deep Dive's forgetting probe confirms it). What regressed was answer discipline: a 0.6B model tuned on 185 synthetic pairs got worse at producing the grounded, on-rubric answers the golden set grades, even as it kept its world knowledge.

This is exactly the result the whole M4–M6 arc was built to catch. The yardstick did its job. Without the committed baseline you might have shipped the tuned model on the strength of "it sounds more like OpsMate now"; with it, you have a defensible number that says not yet. Tuning is not an automatic win — and the discipline that turns that from an opinion into a decision is the measurement you just ran. M12 is where this exact comparison becomes an automated gate that refuses to promote a model that regresses the baseline; here you are running that gate by hand, and reading a real failure.

Why did it regress? Keep these as hypotheses, not settled facts — the golden set gives you the what, not the why:

  • Answer-discipline drift. Tuning moved the model toward the phrasing of its synthetic training answers, which do not match what the rubric rewards. The model may be answering differently, not worse in general, but the graded set measures the rubric's notion of a good answer, and the tune drifted off it.
  • Small-set overfit to Q&A phrasing. 185 pairs from a 0.6B generator is a thin, narrow set; the adapter can learn the shape of those specific Q&A phrasings rather than a generalizable runbook voice, then apply that shape to the golden questions where it does not fit.

Neither is proven by these numbers alone — confirming which one would mean inspecting the per-question failures (the jq habit from M5) and reading the tuned answers against the rubric. What the numbers do prove is the decision: not shipped.

Your run may land differently — and every outcome teaches

This is one run of a small model on a small synthetic set; your kept/rejected counts and your tuned scores will differ. You might land a tie (no regression — a real, shippable result: you got the voice you tuned for at no cost to graded quality) or even a narrow beat (record the delta, and note the no-RAG arm especially, since that isolates tuning's contribution from retrieval). Whichever you get, record it honestly against your own M5 baseline and read it the same way: the skill is the measurement and the honest read, not the direction of the number. Do not paper over a loss with a nicer one, and do not distrust a tie — a loss on this set (which grades knowledge-grounded answers, RAG's job) can coexist with a real voice improvement the set does not measure. Note what the set does and does not measure.

Record your run. Create baseline-mine.md from the template if you have not already (cp labs/opsmate/evals/baseline-template.md labs/opsmate/evals/baseline-mine.md), or reopen the one you made in M5, and fill the M6 rows from the JSON you just produced — the tuned retrieval count, the tuned RAG and tuned-no-RAG generation rates, the deltas versus your M5 baseline, and the verdict in words:

cp labs/opsmate/evals/baseline-template.md labs/opsmate/evals/baseline-mine.md   # or edit your existing one
$EDITOR labs/opsmate/evals/baseline-mine.md

Then commit your recorded run:

git -C labs/opsmate add evals/baseline-mine.md && \
  git -C labs/opsmate commit -m "M6: record tuned-model measurement vs baseline"

One choice is yours to make. The compose model service defaults back to the base GGUF when you next run a plain make -C labs/opsmate up (no MODEL_GGUF), which is the safe default for later modules that expect the base. M7 picks the tuned artifact up from disk regardless of which one you are currently serving.

Troubleshooting
  • First train_lora.py / merge_and_convert.py run seems to hang — it is downloading PyTorch (about 2 GB) the first time. Watch it with uv run --with torch python -c "import torch; print(torch.__version__)" first to prime the download, then re-run.
  • synthesize.py produces very few pairs or errors per section — host Ollama must be serving qwen3:0.6b (ollama list | grep qwen3) and reachable at OLLAMA_URL (default http://localhost:11434). On a runtime where the host address differs, export OLLAMA_URL to the address that reaches your Ollama. A section producing 0 kept pairs occasionally is normal for a 0.6B generator; the run continues.
  • Training is killed / the machine swaps hard — the stack must be down during training (Step 1). If a KIND cluster or another Compose project is running, it is eating the RAM the trainer needs — stop it. This is the one-stack-at-a-time rule applied to training. Lower --batch 1 if a very tight box still struggles.
  • merge_and_convert.py fails at the clone — it needs git to fetch the llama.cpp converter (shallow, into labs/m6/.llama.cpp). Confirm git --version. Behind a proxy, clone https://github.com/ggml-org/llama.cpp manually into that path and re-run; the script reuses an existing checkout.
  • /v1/models shows qwen3-0.6b and you expected the tuned filename — that is correct, not a bug: the model service runs with --alias qwen3-0.6b, so /v1/models reports the alias regardless of which file is loaded (this keeps the app's CHAT_MODEL stable across the swap). To check which file is actually served, read the container args: docker inspect opsmate-model --format '{{join .Args " "}}' | grep -o '\-m [^ ]*' — it should print -m /models/opsmate-tuned-q8_0.gguf. If it names the base file instead, you ran make up without MODEL_GGUF; re-run with MODEL_GGUF=opsmate-tuned-q8_0.gguf make -C labs/opsmate up. The model file is read at container start, so serving a different file is always a restart.
  • The tuned model container OOM-restarts under the eval — the tuned GGUF is the same size class as the base, so this is the same memory pressure as M5's no-RAG arm: re-run the failing arm with --max-concurrency 1 (add --delay 1500 to space calls), and make sure no other heavyweight stack is running alongside OpsMate.
  • The generation eval scores look identical to your M5 baseline — you probably dropped --no-cache. promptfoo caches by request, and the tuned run's request is byte-identical to the baseline's (the model lives server-side), so without --no-cache you re-score the cached baseline answers. Add it and re-run.
  • preflight fails with "Model file missing" after the swap — the preflight now checks the file named by MODEL_GGUF. If it names opsmate-tuned-q8_0.gguf and that file is absent, you skipped or failed Step 5 — re-run merge_and_convert.py. Unset MODEL_GGUF to fall back to the base file.
  • A visibly correct answer scored FAIL — inspect it with the M5 jq pattern before you trust the tally. In our validated run the tuned model's payments answer was verbatim-correct and the contains-any net passed, yet the 0.6B llm-rubric judge failed it with self-contradictory reasoning. That is M5's smoke-detector caveat biting in the other direction: some of any LOSE margin is judge noise. It does not rescue this tune (the deterministic nets and the honesty arm regressed too), but it is why M12 upgrades the judge before scores gate anything.
