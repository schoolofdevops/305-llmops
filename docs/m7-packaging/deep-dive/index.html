Deep Dive — Ship the Model: Under the Hood

The core lab packaged, pushed, and signed a model as an OCI artifact. This Part 2 opens the artifacts up. You will read a real ModelKit manifest byte for byte and see the media types and per-layer digests that kit list summarized; place KitOps' format against the emerging ModelPack interchange standard; scan the serving image — because model provenance is only half the supply chain, and the image that runs the model is the other half; and understand keyless signing (Fulcio + Rekor) and the generic ORAS client that sit under everything you did. It extends the lab; it does not repeat it.

Every runnable block here is real and has captured output folded in. The registry from the lab must be up (make -C labs/opsmate up, or docker compose -f labs/opsmate/compose.yaml up -d registry) with the kits from Steps 3–4 pushed.

1. Read a real manifest — what kit list was summarizing​

kit list showed you 609.8 MiB and a digest. That friendly line is a summary of a JSON document the registry stores: the manifest, the packing list from the lesson. You can fetch it raw over the standard OCI API and read exactly what a ModelKit is made of. Ask the registry for the 1.0.0 manifest:

curl -s -H 'Accept: application/vnd.oci.image.manifest.v1+json' \
  http://localhost:5100/v2/opsmate/model/manifests/1.0.0 \
  | jq '{schemaVersion, mediaType, config: {mediaType: .config.mediaType, size: .config.size}, layers: [.layers[] | {mediaType, size, digest: (.digest[0:19])}]}'

Expected output (the manifest's shape — a config blob plus three layers, each a media type, a size in bytes, and a digest; your digests differ)

{
  "schemaVersion": 2,
  "mediaType": "application/vnd.oci.image.manifest.v1+json",
  "config": {
    "mediaType": "application/vnd.kitops.modelkit.config.v1+json",
    "size": 1112
  },
  "layers": [
    {
      "mediaType": "application/vnd.kitops.modelkit.model.v1.tar",
      "size": 639449600,
      "digest": "sha256:33d0d362a7a3"
    },
    {
      "mediaType": "application/vnd.kitops.modelkit.code.v1.tar",
      "size": 4608,
      "digest": "sha256:932b4824b9a0"
    },
    {
      "mediaType": "application/vnd.kitops.modelkit.dataset.v1.tar",
      "size": 16384,
      "digest": "sha256:4853b3d5c2bd"
    }
  ]
}

This is the whole artifact, demystified. Read it top to bottom:

  • mediaType: application/vnd.oci.image.manifest.v1+json — this is a standard OCI image manifest. That single field is why any OCI registry stores a ModelKit without knowing it is a model: structurally it is the same kind of document as a container image manifest.
  • The config blob (...modelkit.config.v1+json, 1112 bytes) — the ModelKit's metadata, the digested equivalent of your Kitfile's package: block plus the layer map. In a container image this slot holds the image config (entrypoint, env); here it holds the kit's identity. Small, but it is what a client reads first to understand the artifact before pulling anything heavy.
  • The three layers — and here is the payoff of the whole layer lesson, in bytes: the model layer is 639449600 (610 MB), the code layer is 4608 bytes, the dataset layer is 16384 bytes. That four-orders-of-magnitude gap between the model layer and the metadata layers is why selective pull matters. kit unpack --filter=code reads this manifest, finds the ...code.v1.tar layer at 4608 bytes, and fetches only that blob by its digest — the registry never sends the 610 MB model layer because the client never asks for it.
  • The KitOps media types (application/vnd.kitops.modelkit.model.v1.tar, .code.v1.tar, .dataset.v1.tar) — this is how the kit knows a layer is weights versus code versus a dataset. --filter=code is not magic; it is "fetch the layer whose media type ends in code.v1.tar." The media type is the label on the crate.

The digest addressing is worth pausing on. Each layer's digest is a SHA-256 of that layer's exact bytes. Push the identical bytes twice and you get the identical digest — which is why, when you re-pack after the spike, kit prints "Already saved" for unchanged layers: it recognizes the content by hash and does not store it twice. Content-addressing gives you deduplication and tamper-evidence in one mechanism: the same bytes always have the same name, and different bytes never can.

2. ModelKit media types vs the ModelPack interchange standard​

Look again at those media types: application/vnd.kitops.modelkit.model.v1.tar. The vnd.kitops part is the tell — these are KitOps-vendor-specific media types. They are valid OCI (any registry stores them), but a different tool that packaged a model would use its media types, and a naive reader would not know one tool's model layer from another's. That is the interoperability gap the ecosystem is working to close.

ModelPack is the emerging answer: an effort (under the CNCF umbrella, alongside the AI/ML working group) to standardize the media types and structure of a model OCI artifact, so that a model packaged by any conforming tool can be read by any other. Think of it as the difference between "every courier prints its own manifest format" and "there is one standard customs form everyone fills out." KitOps' vnd.kitops.* types are a concrete, working implementation today; ModelPack is the direction of travel toward a vendor-neutral vnd.modelpack.* (or similar) that tools converge on.

Why this matters for your decision-making: the concept you learned — a model as a layered OCI artifact with typed layers — is stable and standards-bound. The specific media-type strings are still settling. So when you adopt KitOps today, you are betting on the durable idea (OCI artifacts) with a current implementation (KitOps types), and the migration path if ModelPack becomes dominant is a re-tag/re-pack, not a rebuild — because the artifact was OCI all along. You can see the vendor prefix yourself in the manifest above; that prefix is exactly what standardization aims to neutralize.

3. The other half of the supply chain — scan the serving image​

Here is a blind spot the model-signing story can create: you signed the model, so you might feel the supply chain is covered. It is not. The model does not run itself — it runs inside a container image (llama-server, in this course), and that image has its own supply chain: a base OS, system libraries, and the server binary, any of which can carry a vulnerability. Provenance of the model and provenance of the image that runs it — you need both, or you have signed the cargo and ignored the ship.

The tool is Trivy (or Grype, or docker scout — same job). Scan the serving image for known vulnerabilities. Start with the severities that gate a deploy:

trivy image --quiet --severity HIGH,CRITICAL --scanners vuln ghcr.io/ggml-org/llama.cpp:server

Expected output (point-in-time — vulnerability counts change as CVEs are disclosed and the base image is rebuilt; on this scan the gating severities were clean)

Report Summary

┌──────────────────────────────────────────────────┬────────┬─────────────────┐
│                      Target                      │  Type  │ Vulnerabilities │
├──────────────────────────────────────────────────┼────────┼─────────────────┤
│ ghcr.io/ggml-org/llama.cpp:server (ubuntu 24.04) │ ubuntu │        0        │
└──────────────────────────────────────────────────┴────────┴─────────────────┘

Zero HIGH/CRITICAL is the result you want on an image you are about to serve — but do not read it as "no vulnerabilities." Drop the severity filter and the picture is fuller:

trivy image --quiet --scanners vuln ghcr.io/ggml-org/llama.cpp:server | grep -A6 'Report Summary'

Expected output (point-in-time; hundreds of lower-severity CVEs in the OS packages — normal for any general-purpose base image)

Report Summary

┌──────────────────────────────────────────────────┬────────┬─────────────────┐
│                      Target                      │  Type  │ Vulnerabilities │
├──────────────────────────────────────────────────┼────────┼─────────────────┤
│ ghcr.io/ggml-org/llama.cpp:server (ubuntu 24.04) │ ubuntu │       433       │
└──────────────────────────────────────────────────┴────────┴─────────────────┘

Read those two numbers together: 0 HIGH/CRITICAL, but 433 total. That is the honest state of essentially every real image — no image built on a general-purpose OS is CVE-free, because its base carries hundreds of low- and medium-severity issues in libraries you never call. This is why you gate on severity, not on zero: a policy of "block on HIGH or CRITICAL" is enforceable and meaningful; a policy of "block on any CVE" would block every image on earth. The scan is a decision input, not a pass/fail oracle — you look at what is HIGH/CRITICAL, decide whether it is reachable in your use, and gate accordingly.

The companion artifact is an SBOM — a Software Bill of Materials, the itemized list of every package in the image. Where the scan answers "what is wrong," the SBOM answers "what is in here," which is what lets you respond in minutes when tomorrow's CVE names a package: you grep your SBOMs instead of re-scanning the world. Generate one with syft:

syft ghcr.io/ggml-org/llama.cpp:server -o syft-json=/tmp/sbom.json
jq '.artifacts | length' /tmp/sbom.json

Expected output (point-in-time; the count is the number of packages catalogued in the image — a general-purpose Ubuntu base ships a few hundred)

388

That number is the itemized cargo list — every OS package and library the serving image ships (zlib1g, openssl, libc6, and hundreds more), each with a name and version. In a real pipeline you would store the SBOM as an attestation attached to the image (an OCI referrer, the same mechanism Cosign uses for signatures), so the image carries its own bill of materials and its own signature, and a cluster can verify both before admitting it. Model provenance (Section 1's signed ModelKit) and image provenance (this scan + SBOM) are the two halves; a production supply-chain policy checks both.

4. Keyless signing — Fulcio and Rekor, and why the lab used keys​

The lab signed with a key pair you generated and guarded. That works, but it has a well-known operational problem: a long-lived private key is a long-lived liability. If cosign.key leaks, an attacker can sign artifacts as you until you notice and rotate — and key distribution and rotation across a fleet is genuinely hard. Production Sigstore setups mostly avoid it with keyless signing, and it is worth understanding because it is where the industry is heading.

Keyless signing removes the standing key by binding a signature to an identity instead of a stored secret. Two services make it work:

  • Fulcio — a certificate authority that, when you sign, verifies your identity through OIDC (your Google/GitHub/corporate SSO, or a CI job's workload identity) and issues a short-lived certificate — valid for minutes. You sign with an ephemeral key tied to that certificate, and both are discarded right after. There is no long-lived key to leak, because the key exists only for the moment of signing.
  • Rekor — a public, append-only transparency log. The signature and certificate are recorded in Rekor with a timestamp, so anyone can later verify that "this artifact was signed by this identity at this time" even though the signing key is long gone. The tlog you kept disabling in the lab (--tlog-upload=false, --insecure-ignore-tlog) is Rekor — it is the piece that makes keyless verification auditable after the fact.

So why did the lab use keys? Because keyless needs two things the 8 GB offline lab does not have: an OIDC identity provider to authenticate you, and internet access to Fulcio and Rekor (the public instances, or a private deployment). A local, air-gapped Zot with no identity provider cannot do the OIDC dance. Keys are the honest choice for an offline lab — they demonstrate the sign/verify mechanism completely, and the concepts (a signature binds to a digest; verify-before-deploy is the gate) transfer unchanged. The production upgrade is to swap "a key I stored" for "an identity I proved," and you would do it exactly where M12/M8 wire signing into CI and admission.

You can see the referrer mechanism keyless uses, though — it is the same one your keyed signature used. Cosign v3 attaches signatures as OCI referrers on the artifact's digest (not the legacy .sig tag). List them:

DIGEST=$(curl -sI -H 'Accept: application/vnd.oci.image.manifest.v1+json' \
  http://localhost:5100/v2/opsmate/model/manifests/1.0.0 \
  | awk 'tolower($1)=="docker-content-digest:"{print $2}' | tr -d '\r')
cosign tree --allow-insecure-registry "localhost:5100/opsmate/model@${DIGEST}"

Expected output (the signature hangs off the model's digest as a referrer — the "supply chain artifacts" tree; your digests differ)

📦 Supply Chain Security Related artifacts for an image: localhost:5100/opsmate/model@sha256:e240b0ea...
└── 🔗 https://sigstore.dev/cosign/sign/v1 artifacts via OCI referrer: localhost:5100/opsmate/model@sha256:0bebfecd...
   └── 🍒 sha256:f693bc22...

That tree is why the signature travels with the artifact: it is stored beside the model in the registry, addressed off the model's digest, so wherever the model goes its signature (and, in production, its SBOM attestation) goes too. Keyless changes who vouches — an identity instead of a stored key — not how the signature attaches.

5. ORAS — the generic OCI client underneath it all​

kit and cosign are specialized clients: one packs models, one signs. Underneath both is a general truth you have been relying on — a ModelKit is just an OCI artifact — and there is a generic tool that makes that concrete: ORAS (OCI Registry As Storage). ORAS pushes and pulls arbitrary artifacts to any OCI registry, model or not, and it is the tool that proves your model kit is nothing special to the registry.

ORAS is not part of the course toolchain (it is an optional install), so this is a read-along unless you have it. The demonstration is that ORAS can list and inspect the very kit kit pushed, because to a registry it is all just OCI:

# If you have oras installed (brew install oras):
oras manifest fetch --plain-http localhost:5100/opsmate/model:1.0.0 | jq '.layers[].mediaType'

Expected output (ORAS reads the same manifest kit wrote — the KitOps media types, fetched by a tool that knows nothing about KitOps)

"application/vnd.kitops.modelkit.model.v1.tar"
"application/vnd.kitops.modelkit.code.v1.tar"
"application/vnd.kitops.modelkit.dataset.v1.tar"

That a generic OCI client can read a ModelKit's manifest is the whole thesis of the module in one command: you did not build a model-distribution system, you put models on the container-distribution system everyone already runs. kit gave you model-shaped ergonomics (a Kitfile, typed layers, selective unpack); ORAS shows there is standard OCI plumbing underneath, which is exactly why any registry — Zot, Harbor, ECR, GHCR — stores your model without special support. When you need to script against artifacts generically (a cleanup job, a promotion pipeline, an SBOM attach), ORAS is the tool; when you want model ergonomics, kit is. Both speak the same registry.

Where you will use this​

  • Auditing what a deployed model actually contains — fetch its manifest (§1) and read the layers and digests. When someone asks "what is in the model we are serving," the manifest is the authoritative, tamper-evident answer, not a wiki page.
  • Choosing a packaging tool without lock-in fear — the ModelKit-vs-ModelPack read (§2) is how you reason about it: bet on OCI (durable), accept a current tool's media types (migratable), and know the switch is a re-pack, not a rebuild.
  • Passing a supply-chain review — reviewers ask for both model provenance and image provenance. §3 is the image half: a severity-gated scan plus an SBOM attestation, the evidence a security team actually wants.
  • Moving signing to production — §4 is the upgrade path: swap stored keys for keyless (Fulcio + Rekor) the moment you have an identity provider and network, which is where M8's admission gate and M12's CI signing land.
