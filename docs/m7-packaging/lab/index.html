Lab — Ship the Model: KitOps, OCI Artifacts & Signing

Time

Roughly 45–60 min hands-on, depending on your machine.

Resource path: 8 GB core — everything here runs

The whole lab runs on the 8 GB core path with no GPU and no cloud. The new service is a local registry (Zot) capped at 256 MB — it is light. Nothing here trains or serves under heavy load; you are packaging, pushing, and signing artifacts that already exist on disk from M6. The one large object that moves is the 610 MB model layer, and it moves once to your own local registry, not over the internet.

Before you start

All commands run from the root of the labs repo (305-labs/). You need docker, curl, jq, git, plus two new tools this module introduces: kit (KitOps CLI) and cosign (Sigstore). The Setup page installs both. This lab uses the M6 artifacts — the base and tuned GGUFs under labs/opsmate/models/gguf/, the LoRA adapter under labs/opsmate/train/adapter/, the golden set, and the prompts — so run it after M6 leaves those on disk. If you are jumping in fresh, the Setup page tells you how to fetch the base GGUF; the tuned GGUF and adapter come from completing M6.

This is the lab where OpsMate's model stops being a loose file and becomes a versioned, signed artifact. You will grow the stack with a registry, author a Kitfile, pack and push both the base model (1.0.0, what ships) and the M6 tuned candidate (1.0.0-candidate, what lost and was recorded), package the adapter on its own, pull a single layer without the weights, and sign the base while deliberately leaving the candidate unsigned so you watch a deploy gate reject it. By the end you have opsmate/model in a registry with two honest tags, one of them signed — OpsMate v1.1.

Console output is trimmed

Real kit and cosign output is noisier than these blocks — progress bars on push, a tlog-deprecation warning on sign, layer-by-layer save lines on pack. The Expected blocks show the end-state lines that matter; if those match, the step worked. Digests, sizes shown to the byte, and timings are point-in-time — yours will differ in the exact hash and the odd byte, not in shape.

Step 1 — Grow the compose spine with a registry service​

This is the last service the OpsMate compose file grows, and like every service before it, you write it by hand. Open labs/opsmate/compose.yaml. Beneath the ui service, here is the registry block, walked line by line:

  # --- M7: the model registry ------------------------------------------------
  registry:
    image: ghcr.io/project-zot/zot-linux-${ZOT_ARCH:-arm64}:latest
    container_name: opsmate-registry
    ports:
      - "5100:5000"                 # host 5100 -> Zot's 5000; everything talks to localhost:5100
    volumes:
      - ./registry/config.json:/etc/zot/config.json:ro   # Zot needs a config; ours turns off TLS
      - ./data/zot:/var/lib/registry                      # persist pushed kits across make cycles
    mem_limit: 256m
    restart: unless-stopped

Three lines carry the lesson. The image is arch-specific — Zot publishes zot-linux-arm64 and zot-linux-amd64 as separate tags, not one multi-arch tag, so the ${ZOT_ARCH:-arm64} picks arm64 by default and you override it on x86. The config mount is there because this image ships with no default config; labs/opsmate/registry/config.json (already in the repo) points storage at the volume and disables TLS so the lab can use plain HTTP. The data volume persists the registry, because M8 pulls from it — the artifacts must outlive this Compose phase.

First, check your architecture so you pick the right Zot image:

uname -m

Expected output (one of these — arm64/aarch64 on Apple Silicon or ARM Linux; x86_64 on Intel/AMD)

arm64

On an x86_64 host, export ZOT_ARCH=amd64 before every make up in this module (arm64/aarch64 hosts need nothing — it is the default). Now bring the stack up. Because the registry is a service in the same file, plain make up brings it along with the model, app, and ui:

make -C labs/opsmate up

Expected output (the preflight passes, then Compose starts all four services; the registry needs no health gate, so the wait is still just the model service)

==> OpsMate preflight
    ✓ Model file present and looks like a real GGUF.
    ✓ 4210 MB free (need ~2200 MB).
    Preflight passed.
==> Starting the OpsMate stack ...
==> Waiting for the model service to report healthy (up to 90s) ...
    Model service is healthy at http://127.0.0.1:8080/health.
    Stack is up. Try:  curl -s http://127.0.0.1:8080/health

Now confirm the registry is up and empty — this is the clean slate you are about to fill. The registry speaks the standard OCI HTTP API; /v2/_catalog lists its repositories:

curl -s http://localhost:5100/v2/_catalog

Expected output (an empty repository list — nothing pushed yet)

{"repositories":[]}

An empty catalog and a 200 from /v2/ mean the registry is live and ready. That empty list is the "before" picture; every step from here adds to it.

Step 2 — Author the Kitfile block by block​

A ModelKit is described by a Kitfile — the packing list. You will author it the same way you authored the compose file: one section at a time, understanding each. The repo already has the final labs/opsmate/Kitfile as a reference, but read and build it up so you know what each layer is.

Every top-level section becomes a layer. Start with the package metadata and the model:

manifestVersion: 1.0.0

package:
  name: opsmate-model
  version: 1.0.0
  description: OpsMate SRE assistant — Qwen3-0.6B base, the shipped 1.0.0 baseline holder
  authors: ["School of DevOps & AI"]

model:
  name: opsmate-base
  path: models/gguf/qwen3-0.6b-q8_0.gguf
  description: Qwen3-0.6B, q8_0 GGUF — the base model OpsMate serves in production

Then the datasets and code sections — the golden eval set and the prompts, each its own layer:

datasets:
  - name: golden-set
    path: evals/golden.yaml
    description: the held-out golden eval set this model version was measured on

code:
  - path: prompts
    description: versioned system prompts (the config surface from M5)

Notice every path is relative — models/gguf/..., evals/..., prompts. The directory the Kitfile lives in (labs/opsmate) is the pack context, and paths resolve against it, exactly like a Docker build context. This is not a style preference; the tool enforces it. To see why, try to break the rule on purpose. Make a throwaway Kitfile with an absolute model path and pack it:

printf 'manifestVersion: 1.0.0\npackage:\n  name: bad\n  version: 1.0.0\nmodel:\n  name: bad\n  path: %s/labs/opsmate/models/gguf/qwen3-0.6b-q8_0.gguf\n' "$PWD" > /tmp/Kitfile.abs
kit pack labs/opsmate -f /tmp/Kitfile.abs -t localhost:5100/opsmate/bad:1

Expected output (the pack is rejected — absolute paths are not portable, so the tool refuses them)

[ERROR] Failed to pack model kit: errors while validating Kitfile: 
  * absolute paths are not supported in a Kitfile (path /.../labs/opsmate/models/gguf/qwen3-0.6b-q8_0.gguf in model bad)

That is the rule made concrete: an artifact you push must be reproducible anywhere, and an absolute path is a promise about your machine. Delete the throwaway and use the real, relative-path Kitfile from here on:

rm -f /tmp/Kitfile.abs
cat labs/opsmate/Kitfile

Expected output (the reference Kitfile — relative paths throughout, three layers: model, dataset, code)

manifestVersion: 1.0.0

package:
  name: opsmate-model
  version: 1.0.0
  description: OpsMate SRE assistant — Qwen3-0.6B base, the shipped 1.0.0 baseline holder
  authors: ["School of DevOps & AI"]
...
model:
  name: opsmate-base
  path: models/gguf/qwen3-0.6b-q8_0.gguf
  ...
datasets:
  - name: golden-set
    path: evals/golden.yaml
    ...
code:
  - path: prompts
    ...

Step 3 — Pack and push BOTH tags: the shipped model and the recorded candidate​

Now the module's spine. You will build two ModelKits from the same repository: the base model as 1.0.0 (what ships), and the M6 tuned model as 1.0.0-candidate (what was measured, lost, and is kept as honest history). kit pack reads the Kitfile and bundles the referenced paths into one OCI artifact — each section a layer.

Pack the base first, tagged 1.0.0:

kit pack labs/opsmate -t localhost:5100/opsmate/model:1.0.0

Expected output (one "Saved … layer" line per section — model, code, dataset — then the manifest; your digests differ)

Saved model layer: sha256:33d0d362a7a383957b2c620e8119abcd6217d94f94625734c6b3f2bb53c3053c
Saved code layer: sha256:932b4824b9a065ebbf55a243881ae034554afc2732eb3ff5f611b09afbc005f0
Saved dataset layer: sha256:4853b3d5c2bd6a787baddcb2c6744d3c99ff6a93959b0f052303ca9ef91229c8
Saved configuration: sha256:91b31f021c1f4a9c14a39af8c99842aba510dc56e9e231460ad11d1a571d6ddb
Model saved: sha256:e240b0ea8b9ed4f36b02dfb57fdfb3db39d79e406c6966ae14cbe282dea156e5

(Re-running a pack with kit's local cache warm prints Already saved … / Configuration already exists in storage instead of Saved … — same result, the store deduplicates; the Deep Dive explains the mechanism.)

Each layer got its own sha256 digest — that is the content-addressing from the lesson: the digest is the bytes. The last line is the manifest digest, the address for the whole artifact. Push it to the registry:

kit push localhost:5100/opsmate/model:1.0.0 --plain-http

Expected output (the push, then the pushed manifest digest — matching the "Model saved" line above)

Pushing localhost:5100/opsmate/model:1.0.0
Pushed sha256:e240b0ea8b9ed4f36b02dfb57fdfb3db39d79e406c6966ae14cbe282dea156e5

--plain-http is required because your local Zot has no TLS. In production this is never used — real registries speak HTTPS and you would drop the flag. It is a local-lab convenience, and forgetting it produces a confusing TLS error (see Troubleshooting).

Now the candidate. It is the same Kitfile with the model swapped to the tuned GGUF. Edit the two model lines in labs/opsmate/Kitfile:

  • change path: models/gguf/qwen3-0.6b-q8_0.gguf to path: models/gguf/opsmate-tuned-q8_0.gguf
  • change the model description to reflect the M6 verdict, for example: Qwen3-0.6B + OpsMate LoRA merged; M6 run — measured, did not beat baseline, recorded honestly

Then pack and push it as 1.0.0-candidate:

kit pack labs/opsmate -t localhost:5100/opsmate/model:1.0.0-candidate
kit push localhost:5100/opsmate/model:1.0.0-candidate --plain-http

Expected output (a different model-layer digest — different bytes, the tuned weights — and a different manifest digest for the candidate)

Saved model layer: sha256:7001c9a7fbaffdb142b9df80d43468fa2ae1553122e674121e87dffe6a2c2be0
...
Model saved: sha256:21ab6d75ba40c12f46898a92f18c4964d0d15178b52c20aa16187e57eca9ca60
Pushing localhost:5100/opsmate/model:1.0.0-candidate
Pushed sha256:21ab6d75ba40c12f46898a92f18c4964d0d15178b52c20aa16187e57eca9ca60

The model-layer digest is different from the base's — different weights, different bytes, different hash. That is the point: content-addressing means the candidate is provably a different artifact, not a relabelled copy. (After pushing, restore the Kitfile's model lines to the base for the rest of the lab, or leave them — you have both tags in the registry now either way.)

See both tags with kit list:

kit list localhost:5100/opsmate/model --plain-http

Expected output (two tags of one repository, both ~610 MiB, each with its own manifest digest)

REPOSITORY      TAG               MAINTAINER              NAME            SIZE        DIGEST
opsmate/model   1.0.0             School of DevOps & AI   opsmate-model   609.8 MiB   sha256:e240b0ea8b9ed4f36b02dfb57fdfb3db39d79e406c6966ae14cbe282dea156e5
opsmate/model   1.0.0-candidate   School of DevOps & AI   opsmate-model   609.8 MiB   sha256:21ab6d75ba40c12f46898a92f18c4964d0d15178b52c20aa16187e57eca9ca60

There is the two-tags story made real: one repository, the shipped 1.0.0 and the recorded 1.0.0-candidate, each addressable by digest. The registry now records both what shipped and what did not. Confirm the registry sees it too:

curl -s http://localhost:5100/v2/opsmate/model/tags/list

Expected output (the registry's own view — the same two tags)

{"name":"opsmate/model","tags":["1.0.0","1.0.0-candidate"]}

Step 4 — Package the adapter as its own tiny kit​

The M6 adapter — the 4.6 MB LoRA "removable fittings" — deserves its own artifact, and packaging it separately teaches how light adapters travel. labs/opsmate/Kitfile.adapter (in the repo) packs just the adapter weights and its config as opsmate/adapter. Pack it with the -f flag (same context, a different Kitfile), then push. Note the -f value is relative to the context directory (labs/opsmate), not your shell's directory — so it is -f Kitfile.adapter, not -f labs/opsmate/Kitfile.adapter; kit resolves it against the pack context just like the paths inside the Kitfile:

kit pack labs/opsmate -f Kitfile.adapter -t localhost:5100/opsmate/adapter:1.0.0
kit push localhost:5100/opsmate/adapter:1.0.0 --plain-http

Expected output (packs and pushes fast — the whole payload is a few megabytes)

Saved model layer: sha256:eaf4d88fce8b5d3ac58a46b7f195d787d1f2484658cfb800a1a959cdcab022c8
Saved code layer: sha256:4aedd7b449c9680b3c7a5e6179ae157849932d705870ec9d76348d3eccb63065
...
Pushing localhost:5100/opsmate/adapter:1.0.0
Pushed sha256:2aebe0e9ead7e521efe3626f3d9d8fae09d2230a42e4007e5ff07f5916e3434f

Now put the adapter kit's size next to the model kit's:

kit list localhost:5100/opsmate/adapter --plain-http

Expected output (a few MiB — three orders of magnitude smaller than the 609.8 MiB model kit)

REPOSITORY        TAG     MAINTAINER              NAME              SIZE      DIGEST
opsmate/adapter   1.0.0   School of DevOps & AI   opsmate-adapter   4.3 MiB   sha256:2aebe0e9ead7e521efe3626f3d9d8fae09d2230a42e4007e5ff07f5916e3434f

4.3 MiB versus 609.8 MiB. That is the adapters-travel-light lesson from M6, now visible as artifact sizes. In a world where you keep one base model and many adapters — one per team, per domain — you ship and version megabytes, not gigabytes, each time you tune. The base is the ship; the adapter is a single small crate you can send on its own.

Step 5 — Selective pull: take one crate without unloading the ship​

This is the layer lesson made physical. You want only the prompts a model ships with — not its 610 MB of weights. Because the manifest lists each layer separately, kit unpack --filter=code fetches just the code layer. Unpack it to a scratch directory:

rm -rf /tmp/opsmate-prompts-only
kit unpack localhost:5100/opsmate/model:1.0.0 --filter=code -d /tmp/opsmate-prompts-only --plain-http

Expected output (it unpacks the code layer only — the "Unpacking code to prompts" line, and no model download)

Unpacking to /tmp/opsmate-prompts-only
Unpacking code to prompts

Now look at what landed — and, more importantly, how little:

find /tmp/opsmate-prompts-only -type f
du -sh /tmp/opsmate-prompts-only

Expected output (only the prompt files, a few kilobytes total — the 610 MB model layer never moved)

/tmp/opsmate-prompts-only/prompts/system.txt
/tmp/opsmate-prompts-only/prompts/system-v2.txt
8.0K	/tmp/opsmate-prompts-only

Eight kilobytes, not six hundred megabytes. You pulled exactly the crate you asked for and left the heavy one on the registry. This is how a cluster inspects a model's config before committing to pulling its weights, and how you update the prompts a model ships with by replacing one small layer. Selective pull is the operational payoff of layered artifacts.

--filter=code vs the old --code

Older kit versions used a flag per layer type — --code, --model, --datasets. Those still work but are deprecated in favour of --filter=code (and --filter=model, --filter=datasets). Use --filter=; if you see a deprecation note on --code, that is why. You can pass --filter more than once to pull several layers but not all.

Step 6 — Sign the base by digest, and leave the candidate unsigned​

Packaging says what is inside; signing proves nobody changed it. You will sign the base 1.0.0 with Cosign and verify it, then deliberately not sign the candidate — so you can watch verification reject it. That contrast is the gate story.

First generate a key pair. Keep the keys in labs/opsmate/signing/ (gitignored — the private key is your signet ring). Run with an empty password for the lab:

mkdir -p labs/opsmate/signing
cd labs/opsmate/signing && COSIGN_PASSWORD="" cosign generate-key-pair && cd -

Expected output (two files — the private key you guard, the public key you share for verification)

Private key written to cosign.key
Public key written to cosign.pub

A signature binds to a digest, not a tag, so resolve 1.0.0 to its manifest digest first (the registry returns it in a header):

DIGEST=$(curl -sI -H 'Accept: application/vnd.oci.image.manifest.v1+json' \
  http://localhost:5100/v2/opsmate/model/manifests/1.0.0 \
  | awk 'tolower($1)=="docker-content-digest:"{print $2}' | tr -d '\r')
echo "$DIGEST"

Expected output (the manifest digest for 1.0.0 — matches the "Model saved" line from Step 3)

sha256:e240b0ea8b9ed4f36b02dfb57fdfb3db39d79e406c6966ae14cbe282dea156e5

Now sign that digest. Cosign v3 needs a specific flag pair to sign to a local, keyed, no-transparency-log setup — --use-signing-config=false and --tlog-upload=false together, plus --allow-insecure-registry for the plain-HTTP Zot:

COSIGN_PASSWORD="" cosign sign --key labs/opsmate/signing/cosign.key \
  --allow-insecure-registry \
  --use-signing-config=false \
  --tlog-upload=false \
  --yes \
  "localhost:5100/opsmate/model@${DIGEST}"

Expected output (a tlog-deprecation warning is expected and harmless; the signature is pushed beside the artifact)

Flag --tlog-upload has been deprecated, prefer using a --signing-config file with no transparency log services
Signing artifact...
Pushing signature to: localhost:5100/opsmate/model

The --tlog-upload warning is not an error — it prints and the sign proceeds. (Passing --tlog-upload=false without --use-signing-config=false is the mistake that actually fails; see Troubleshooting.) Now verify the base — this is the check a deploy gate runs:

cosign verify --key labs/opsmate/signing/cosign.pub \
  --allow-insecure-registry --insecure-ignore-tlog \
  "localhost:5100/opsmate/model@${DIGEST}"

Expected output (the checks pass — the claims validated and the signature verified against your public key; the tlog warning is expected)

WARNING: Skipping tlog verification is an insecure practice ...

Verification for localhost:5100/opsmate/model@sha256:e240b0ea... --
The following checks were performed on each of these signatures:
  - The cosign claims were validated
  - Existence of the claims in the transparency log was verified offline
  - The signatures were verified against the specified public key
[{"critical":{"identity":{"docker-reference":"localhost:5100/opsmate/model@sha256:e240b0ea..."},...}}]

That green verify is what "safe to deploy" looks like: these exact bytes were sealed by your key and have not changed. Now the contrast. Resolve the candidate's digest and try to verify it — you never signed it:

CDIGEST=$(curl -sI -H 'Accept: application/vnd.oci.image.manifest.v1+json' \
  http://localhost:5100/v2/opsmate/model/manifests/1.0.0-candidate \
  | awk 'tolower($1)=="docker-content-digest:"{print $2}' | tr -d '\r')
cosign verify --key labs/opsmate/signing/cosign.pub \
  --allow-insecure-registry --insecure-ignore-tlog \
  "localhost:5100/opsmate/model@${CDIGEST}"

Expected output (verification FAILS — there is no signature on the candidate; this is the gate working)

WARNING: Skipping tlog verification is an insecure practice ...
Error: no signatures found
error during command execution: no signatures found

Read that failure as a success. The candidate is real, addressable, and preserved — but it carries no seal, so anything that verifies-before-deploy will refuse it. The model that lost the M6 measurement cannot be served by accident, because it was never signed for release. Signing did not hide the candidate; it gated it.

Step 7 — Wire the gate into preflight: verify before you serve​

A signature nobody checks is decoration. The OpsMate preflight now has an optional signature gate: set VERIFY_SIGNATURE=1 and it verifies the model artifact before letting the stack start. Unset (the default), it is skipped silently, so earlier modules and CI are unaffected.

Bring the stack down, then up with the gate on, verifying the signed base. The preflight runs before Compose starts the services, so the registry it verifies against must already be up — bring it back on its own after down, then run the gated up (this is the "gate needs the registry" note below, applied):

(Compose flavour: hosts with only the standalone binary write docker-compose wherever this lab prints docker compose — the make targets pick the right one automatically, raw commands do not.)

make -C labs/opsmate down
docker compose -f labs/opsmate/compose.yaml up -d registry
VERIFY_SIGNATURE=1 VERIFY_TAG=1.0.0 make -C labs/opsmate up

Expected output (the signature gate runs, the base passes, the stack starts)

==> OpsMate preflight
    ✓ Model file present and looks like a real GGUF.
    ✓ 2727 MB free (need ~2200 MB).
==> Signature gate: verifying localhost:5100/opsmate/model:1.0.0 before serving
    ✓ Signature valid for localhost:5100/opsmate/model@sha256:… — cleared to serve.
    Preflight passed.
==> Starting the OpsMate stack ...
The gate needs the registry up

The preflight verifies against the registry, but make up runs the preflight before Compose starts any service — so on the first gated up after a make down, the registry is not up yet and the gate's digest lookup fails with a curl-style error (exit 7), not the clean gate message. That is why both commands above start the registry on its own first (docker compose -f labs/opsmate/compose.yaml up -d registry) — it seats the one service the gate needs before the gated up runs. If your Docker ships only the standalone binary, use docker-compose in place of docker compose. Keep any host overrides (OLLAMA_URL=…, ZOT_ARCH=amd64) on the same line as always.

Now watch the gate stop a bad deploy. Try to bring the stack up serving the candidate (MODEL_GGUF points at the tuned file) with the gate verifying the candidate tag — which is unsigned:

make -C labs/opsmate down
docker compose -f labs/opsmate/compose.yaml up -d registry
VERIFY_SIGNATURE=1 VERIFY_TAG=1.0.0-candidate MODEL_GGUF=opsmate-tuned-q8_0.gguf make -C labs/opsmate up

Expected output (preflight refuses — the candidate has no valid signature, so the stack never starts)

==> OpsMate preflight
    ✓ Model file present and looks like a real GGUF.
    ✓ 2716 MB free (need ~2200 MB).
==> Signature gate: verifying localhost:5100/opsmate/model:1.0.0-candidate before serving
    ✗ NO valid signature for localhost:5100/opsmate/model:1.0.0-candidate (digest sha256:21ab6d75...).
      Refusing to serve an unsigned/unverified model. This is the gate:
      an unsigned candidate (e.g. 1.0.0-candidate) fails here by design.
      Sign it (Lab Step 6) or serve the signed tag (VERIFY_TAG=1.0.0).

That is verify-before-deploy in one command. The unsigned candidate could not start the stack; the signed base could. This exact pattern becomes a Kubernetes admission policy in M8 — the cluster refuses to admit a model image whose signature does not verify. Here you ran it by hand; there it runs on every deploy. Bring the stack back to the safe default (base model, no gate) before moving on:

make -C labs/opsmate up

Step 8 — The X-Ray Artifacts lens: your registry, drawn​

The X-Ray grew its M7 lens. Start the tool and open the Artifacts tab:

bash labs/tools/xray/serve.sh
# open http://127.0.0.1:8010/ → Artifacts

The left panel lists every repository and tag in your real registry — opsmate/model:1.0.0 carrying a green SIGNED ✓ badge, 1.0.0-candidate marked unsigned, and opsmate/adapter:1.0.0. Click the candidate: the layer table draws the shipping-container crates as bars — the 610 MB model layer dwarfing the KB code and dataset layers — with the config digest underneath. The badge logic is real, not cosmetic: the lens resolves each tag's manifest digest and asks the registry's OCI referrers API whether a sigstore signature is attached — exactly the check your cosign verify performed, read from the other side.

Everything the lens draws comes from the standard OCI /v2/ API. Read the same scoreboard yourself, because these two commands are the authoritative cross-check when the picture surprises you.

The signed/unsigned scoreboard, by hand. A tag is "signed" when it has a Cosign signature attached as an OCI referrer on its digest. The base 1.0.0 has one; the candidate has none:

BASE=$(curl -sI -H 'Accept: application/vnd.oci.image.manifest.v1+json' \
  http://localhost:5100/v2/opsmate/model/manifests/1.0.0 \
  | awk 'tolower($1)=="docker-content-digest:"{print $2}' | tr -d '\r')
CAND=$(curl -sI -H 'Accept: application/vnd.oci.image.manifest.v1+json' \
  http://localhost:5100/v2/opsmate/model/manifests/1.0.0-candidate \
  | awk 'tolower($1)=="docker-content-digest:"{print $2}' | tr -d '\r')
echo "1.0.0            signed referrers: $(curl -s http://localhost:5100/v2/opsmate/model/referrers/$BASE | jq '.manifests | length')"
echo "1.0.0-candidate  signed referrers: $(curl -s http://localhost:5100/v2/opsmate/model/referrers/$CAND | jq '.manifests | length')"

Expected output (the two-tags story as a number — the signed base carries one signature referrer, the unsigned candidate carries none)

1.0.0            signed referrers: 1
1.0.0-candidate  signed referrers: 0

The layer table. For any tag, the manifest lists each layer's media type and size — the 610 MB model layer dwarfing the KB code and dataset layers. This is the "shipping-container crates, listed" the lens draws as a bar chart:

curl -s -H 'Accept: application/vnd.oci.image.manifest.v1+json' \
  http://localhost:5100/v2/opsmate/model/manifests/1.0.0 \
  | jq -r '.layers[] | "\(.size)\t\(.mediaType)"'

Expected output (three layers — the model layer in the hundreds of MB, the code and dataset layers in KB; your sizes differ by the odd byte)

639449600	application/vnd.kitops.modelkit.model.v1.tar
4608	application/vnd.kitops.modelkit.code.v1.tar
16384	application/vnd.kitops.modelkit.dataset.v1.tar

That is the picture of everything this lab produced — what is packaged (opsmate/model with two tags, opsmate/adapter with one), how it is layered (the size gap), and what is sealed (the referrer count) — read from the live registry, and drawn by the lens from the same /v2/ contract. Stop the X-Ray with Ctrl-C when you are done.

Step 9 — Teardown​

Bring the stack down. As always the model files stay — and now the registry and its artifacts stay too, because M8 pulls the signed model from here:

make -C labs/opsmate down

Expected output

==> Stopping the OpsMate stack ...
 Container opsmate-registry  Removed
 Container opsmate-ui        Removed
 Container opsmate-app       Removed
 Container opsmate-model     Removed
 Network opsmate_default     Removed
    Stopped. The GGUF model file on disk stays for the next module.

down removes the containers, but the registry's storage is on the ./data/zot volume, so the pushed kits survive. Confirm your artifacts persisted teardown — bring just the registry back and list them:

docker compose -f labs/opsmate/compose.yaml up -d registry
sleep 3
curl -s http://localhost:5100/v2/_catalog

Expected output (both repositories survived — the signed model, the candidate, and the adapter are all still there)

{"repositories":["opsmate/adapter","opsmate/model"]}

Everything M7 built is now persistent and portable: opsmate/model:1.0.0 (signed), opsmate/model:1.0.0-candidate (recorded, unsigned), and opsmate/adapter:1.0.0 — all in a registry M8 will pull from. Your cosign keys stay in labs/opsmate/signing/ (gitignored) for re-signing. You can leave the registry running or bring it fully down with make -C labs/opsmate down; either way the artifacts are on the volume.

Troubleshooting
  • kit pack says "absolute paths are not supported in a Kitfile" — a path: in your Kitfile is absolute (starts with /). That is Step 2's deliberate error, and the fix is the rule: every path must be relative to the Kitfile's directory (the pack context). Change /Users/you/.../models/... to models/... and re-pack.
  • kit push fails with "server gave HTTP response to HTTPS client" — you dropped --plain-http. Your local Zot has no TLS, so kit must be told to use plain HTTP: add --plain-http to the push (and --plain-http to kit list/kit unpack, --allow-insecure-registry to cosign). In production you would keep TLS and drop these flags.
  • cosign sign errors: "--tlog-upload=false is not supported with --signing-config or --use-signing-config" — you passed --tlog-upload=false without --use-signing-config=false. Cosign v3 changed this: the two flags go together. Add --use-signing-config=false alongside --tlog-upload=false and the sign proceeds (with a harmless deprecation warning).
  • cosign verify fails with "no signatures found" on the base — either you verified the wrong digest (verify the digest you signed — re-resolve 1.0.0 with the curl from Step 6) or the sign step did not complete. Re-run the sign, confirm "Pushing signature to: …" printed, then verify. On the candidate this same message is expected — the candidate is unsigned by design.
  • Registry container will not start / exits immediately — most often the arch-wrong image: on x86_64 you must export ZOT_ARCH=amd64 (Zot has no multi-arch tag). Check docker logs opsmate-registry; an exec format error means the wrong architecture. Also confirm labs/opsmate/registry/config.json exists — the image ships no default config and will not start without it.
  • Port 5100 already in use — something else holds it. Find it (lsof -i :5100 or docker ps) and stop it, or change the published port in compose.yaml ("5101:5000") and use localhost:5101 throughout.
  • The X-Ray Artifacts lens is empty or shows no signature — it reads the live registry, so the registry must be up (make up or docker compose … up -d registry) and you must have pushed in Step 3. Signature status comes from the OCI referrers on each tag; if 1.0.0 shows unsigned, re-run the Step 6 sign and refresh.
  • preflight signature gate fails even though you signed — the gate resolves the tag to a digest and verifies that. If you signed a different tag than VERIFY_TAG, they will not match. Sign 1.0.0 and gate VERIFY_TAG=1.0.0; the gate against 1.0.0-candidate is meant to fail.
