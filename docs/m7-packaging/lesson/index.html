Ship the Model — KitOps, OCI Artifacts & Signing

Here is the situation this module is built for. It is your on-call week, and the payments service is degraded. You bring up OpsMate to help you work the incident, and it answers from a model file on the serving box. Then a teammate asks the question you cannot answer: which model is that, exactly? Is it the base Qwen you started with, or the tuned one from M6 that lost the measurement and was never supposed to ship? Who put that file on the server? Has anyone changed it since? You look, and the honest answer is a filename — opsmate-tuned-q8_0.gguf — sitting in a directory, with no version, no record of where its bytes came from, and no way to prove it is the file anyone signed off on. During a real incident, "I think it is the right model" is not an answer you want to give.

That is the gap this module closes. Through M6 the model has been a loose file — copied onto the box, swapped by changing an env var, versioned by nothing more than its name. That was fine while you were the only person touching it on your own laptop. It stops being fine the moment the model is something a team serves in production, because a loose file cannot answer the three questions that matter when something goes wrong: what version is this, where did it come from, and has it been tampered with? This module turns the model from a file into an artifact — versioned, addressable, and signed — so those three questions have answers you can prove.

Why a filename is not a version — the courier without a manifest​

Think about how a parcel moves through a courier network. A parcel with just a name scrawled on the side — "Gourav's box" — is a problem the moment it leaves your hands. Nobody down the line knows what is inside, whether it is the box you meant to send, or whether someone opened it in transit and swapped the contents. A parcel that travels properly carries a manifest: a label that states exactly what is inside, a tracking number that is unique to this parcel and no other, and a tamper-evident seal so the recipient can tell if it was opened on the way. The name is for humans; the manifest is what makes the parcel trustworthy across a chain of hands nobody in it fully controls.

Copying a model file onto a server is shipping the parcel with a name and nothing else. It works right up until the model passes through more than one pair of hands — a build step, a registry, a deploy, a rollback — and then every one of those handoffs is a place where you can no longer say for certain what you are serving. The fix is the same as the courier's: give the model a manifest. That is what the rest of this module builds — a way to package the model with a label of exactly what is inside, a unique address that names these bytes and no others, and a seal that proves nobody changed them.

What a model actually is on disk (one recap, not a re-teach)​

You already know this from M2, so this is a callback, not a lesson. A model on disk is not one thing — it is a small bundle of files that only mean something together: the weights (the giant pile of numbers, the bulk of the bytes), the tokenizer (how text becomes token IDs), the config (the architecture and hyperparameters the runtime needs to load it), and, for a chat model, the chat template (how turns get serialized into the string the model sees). In the GGUF format you have been serving, those are packed into a single file; in the safetensors format you trained from in M6, they are a directory of files. Either way, "the model" is that bundle.

The packaging job of this module follows straight from that fact. If a model is a bundle of related files, then shipping it well means shipping the whole bundle as one versioned unit — not just the weights, but the things that were true about this model when it was built: the prompts it expects, and the eval set it was measured on. A model artifact that carries its own eval set is an audit trail made physical: anyone who pulls it can re-run the measurement instead of trusting a number in a report.

OCI artifacts and layers — the shipping container with a manifest​

The good news is you do not need a new system to ship models. The container world already solved "package a bundle of files, address it by a unique ID, push and pull it from a registry, and verify it did not change" — that is what a container image is. The standard underneath container images, the OCI (Open Container Initiative) format, turned out to be general enough to package anything, not just container filesystems. A thing packaged that way is an OCI artifact, and a model packaged as an OCI artifact rides the exact same rails your container images already do: the same registries, the same push/pull, the same digests.

The analogy is a standardized shipping container. The reason a shipping container can move from a truck to a train to a ship to a crane at any port on earth is that its dimensions and fittings are standardized — every crane knows how to lift it without knowing or caring what is inside. OCI is that standard for software artifacts. Package your model as an OCI artifact and every registry, every CI system, every cluster that already speaks OCI can handle it, sight unseen. You are not inventing a model-distribution system; you are putting the model in the container everyone already knows how to move.

Inside the container, the goods are not one solid mass — they are separately-listed crates, and the container's manifest lists each one. In OCI those crates are layers, and this is the single most important structural idea in the module. A model artifact is not one opaque blob; it is a set of layers, each with its own content address, listed in a manifest. OpsMate's model kit has three:

Read the sizes, because the whole point is in them. The model layer is hundreds of megabytes; the dataset and code layers are kilobytes. Because each is a separately-addressed crate, you can take one crate without unloading the whole ship — pull just the prompts layer without dragging the 610 MB of weights along with it. That is not a party trick; it is how a cluster pulls a model's config to inspect it before deciding whether to pull the weights, and how you update the prompts a model ships with by replacing a 5 KB layer instead of re-uploading everything. Layers are why "the model plus its metadata" is one artifact but not one indivisible lump.

ModelKit and the Kitfile — a Dockerfile for models​

You have a tool for this, and it will feel familiar. KitOps packages a model bundle as an OCI artifact it calls a ModelKit, and you describe what goes in the kit with a Kitfile — which is to a ModelKit exactly what a Dockerfile is to a container image: a plain text manifest that names the pieces, read by a pack command that builds the artifact.

Here is the honest positioning, because you should know what you are adopting. KitOps is a CNCF Sandbox project — real, open, and OCI-native, but early-stage, not a graduated CNCF project like Kubernetes or Prometheus. Its kit CLI is what this lab uses because it makes the layer story concrete and it packs to any OCI registry. There is also an emerging interchange effort — ModelPack — aiming to standardize the media types a model artifact uses so that kits from different tools can be read by any of them; the Deep Dive reads the real media types and shows where that standardization is headed. The thing to take away is that this is a moving space: the concept — a model as a layered, versioned OCI artifact — is durable and vendor-neutral; the specific tool is a current, reasonable choice, not a permanent commitment.

One rule the lab makes you feel deliberately: every path in a Kitfile is relative, never absolute. An artifact has to be portable — a path like /Users/you/models/... only exists on your machine, so kit pack rejects it. The pack context (the directory the Kitfile sits in) is the root everything resolves against, the same way a Docker build context works. You will hit the absolute-path error on purpose in the lab, because reading the error once is how you remember the rule.

Push, pull, and the crate you actually want​

Once packed, a ModelKit moves like any OCI artifact: kit push sends it to a registry, kit pull brings it back. The move that matters is selective pull — retrieving one layer without the others. Because the manifest lists each layer by digest, the client can fetch exactly the crate you ask for. Want just the prompts a model ships with? kit unpack --filter=code pulls the 5 KB code layer and leaves the 610 MB of weights on the registry. You will do this live: unpack only the prompts and watch a few kilobytes arrive where a naive "download the model" would have moved half a gigabyte. That is the layer lesson stops being abstract.

Signing — the wax seal, not the locked box​

Packaging answers "what is inside" and "how do I address it." It does not answer "did anyone tamper with it." For that you sign the artifact, and it is worth being precise about what signing does and does not do, because the word misleads people.

The analogy is a wax seal on a letter, pressed with a signet ring. The seal does not hide the letter — anyone can read it. What the seal does is prove two things: that the letter was sealed by whoever holds the ring (authenticity), and that nobody has opened it since (integrity). Break the seal and it cannot be re-formed without the ring. Signing a model artifact is exactly this: it is tamper-evidence, not secrecy. A signed model is not encrypted or hidden; anyone can pull it. What the signature proves is that the person with the signing key vouched for these exact bytes, and that the bytes have not changed since. If someone swaps the weights after signing, verification fails — the seal is broken.

The precision that makes this work is that a signature is bound to a digest, not a tag. A tag like 1.0.0 is a human-friendly label that someone can move to point at different bytes tomorrow; a digest like sha256:acbf90cc… is the bytes — it is a cryptographic hash of the exact content, and it cannot point at anything else. So you always sign and verify by digest. This module uses Cosign (the Sigstore signing tool) with a local key pair: cosign generate-key-pair makes the keys, cosign sign seals the artifact by its digest, cosign verify checks the seal. Keep the private key secret — it is your signet ring; anyone who has it can sign as you.

That bottom branch — no signature means refuse to deploy — is the whole reason to sign. It is not paperwork; it is a gate. Later in this module you wire it into the preflight: with a flag set, OpsMate refuses to start unless the model it is about to serve has a valid signature. In M8 that same check becomes a Kubernetes admission policy on the cluster. Signing is only useful if something downstream verifies before it runs — a seal nobody checks is decoration.

Semver for models — edition numbers on a textbook​

A version number should tell you what changed without making you diff two artifacts. Software uses semantic versioning — MAJOR.MINOR.PATCH — and it carries over to models with one honest caveat: the field has no universal standard for what bumps what, so you adopt a convention and state it. The convention this course uses:

  • MAJOR — the model's capability changed in a way that could break callers: new base model, a retrain that shifts behaviour, a different architecture. Treat it like an API break.
  • MINOR — the model improved compatibly: a better tune on the same base, measurably better on your evals, same interface.
  • PATCH — nothing about the weights changed; you updated the packaging — a new prompt template, a corrected eval set, fixed metadata.

The analogy is editions of a textbook. A new edition (major) reorganizes chapters and changes content — your old page references break. A revised printing (minor) fixes and improves within the same edition — same structure, better content. A corrected reprint (patch) fixes typos — the words on the page are unchanged, the errata are not. Reading 1.0.0 versus 2.0.0 versus 1.1.0 tells a downstream consumer whether they can drop in the new model blindly (patch), should re-test (minor), or must treat it as a breaking change (major) — the same signal semver gives an API consumer.

The one addition models borrow from software is the pre-release suffix — 1.0.0-candidate. A -candidate build is one that exists, is real, is packaged and pushed — but has not been promoted to the plain 1.0.0 release. It is a version you can point at, measure, and talk about precisely, without it being the thing that ships. That suffix is the hinge of this module's story.

The two-tags story — the registry records history, not just winners​

This is the spine of the module, and it comes straight out of M6. In M6 you did something disciplined: you tuned a model, measured it honestly against the committed baseline, and it lost — the tuned model scored worse on the golden set than the RAG baseline, so it did not ship. That was the right call. But here is the question packaging forces: what happens to that tuned model now? A loose-file world has two bad answers — delete it (and lose the record that you tried), or leave it lying in a directory (and risk someone serving it by accident). Versioning gives you a third, honest answer.

You push both models, as two tags of the same repository:

  • opsmate/model:1.0.0 is the base model — the one that actually serves, the baseline holder. You sign it, and it passes the deploy gate.
  • opsmate/model:1.0.0-candidate is the M6 tuned model — measured, lost, and recorded as exactly that. You deliberately do not sign it, so when the verify-before-deploy gate runs against it, it fails. The candidate is preserved and addressable, but it cannot be served by accident, because it was never sealed for release.

Each kit carries the golden set it was measured on, so the comparison is not a claim in a document — it is reproducible from the artifacts themselves. This is what "the registry records history, not just winners" means. A month from now, when someone asks "did we ever try tuning this?", the answer is not a Slack search — it is kit list opsmate/model, and there is the candidate, with the eval set it was weighed on, and the fact that it was never signed for release telling you how it turned out. That is an audit trail made of artifacts instead of memory.

The registry landscape — Zot here, others in production​

The registry is where artifacts live, and you have choices. This lab runs Zot — a lightweight, OCI-native, CNCF registry — because it starts in seconds, needs no cloud account, and stores OCI artifacts (including ModelKits and their signatures) correctly, which is all the lab needs. It is a genuinely good choice for local and self-hosted use, not a toy.

In production you would likely meet one of these instead, and the point is that your artifact does not change — only where it is stored does:

  • Harbor — the common self-hosted enterprise registry (CNCF graduated): adds projects, RBAC, replication, vulnerability scanning, and signing-policy enforcement on top of OCI storage.
  • Artifactory / cloud registries (JFrog, AWS ECR, GCP Artifact Registry, GHCR) — managed registries you already use for container images; because ModelKits are OCI artifacts, they push to these unchanged.
  • Hugging Face Hub — the model-native distribution channel most teams pull base models from. It is git-LFS-based rather than pure-OCI, so it is the odd one out structurally, but it is where the open-model supply chain starts.

The through-line: because you packaged the model as an OCI artifact, moving from Zot to Harbor to ECR is a change of address, not a change of format. That portability is the payoff of not inventing your own model-distribution scheme.

What you'll do next, and the hand-off to M8​

In the lab you grow the compose stack one last time — adding the Zot registry service beside the model, app, and ui — and then you turn OpsMate's model into an artifact end to end. You author the Kitfile block by block (and hit the absolute-path error on purpose), pack and push both tags, package the M6 adapter as its own tiny kit to feel how light adapters travel, pull just the prompts layer to see selective pull live, and then sign the base by digest and verify it — while deliberately leaving the candidate unsigned so you watch the verify-before-deploy gate reject it. You wire that gate into the preflight, and you read the whole thing in the X-Ray Artifacts lens.

This is the last module of the Compose phase, and it sets up the next one precisely. Everything M8 does — running OpsMate on Kubernetes with a real serving engine — begins with the cluster pulling the model from a registry. You just built that registry and put a signed, versioned model in it. M8's cluster pulls opsmate/model:1.0.0 from here, verifies its signature before admitting it, and serves it. The loose file is gone; from here on, the model is an artifact with a version, an address, and a seal — which is exactly what it needs to be to run in production.
