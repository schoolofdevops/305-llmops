Lab — Serve OpsMate on Kubernetes: from Capacity Sum to Running Pod

Resource path: 8 GB core — everything required runs

Every required step runs on the 8 GB core path: a slim single-node KIND cluster plus one llama-server pod under a 2 GiB limit, and the M7 registry service alongside it (~30 MB). The whole cluster-plus-model footprint measured ~1.76 GiB in the spike — comfortably in budget. You bring the Compose stack down first, so you never hold both stacks at once. Step 9 (the vLLM variant) is optional and needs x86 / 16 GB+ — arm64 learners read the manifest and watch the recorded demo.

Before you start

All commands run from the root of the labs repo (305-labs/). You need docker, kind, kubectl, kit, curl, jq, and uv responding — check the Setup section if any are missing. You must have completed M7: this lab pulls opsmate/model:1.0.0 (signed) from the registry M7 filled, so labs/opsmate/data/zot must hold your pushed kits. Every kubectl command carries --kubeconfig k8s/kubeconfig — that is the isolated-kubeconfig discipline, not a typo; it keeps the lab off your default context.

This is the module where OpsMate leaves your laptop and lands on Kubernetes. You will bring the Compose stack down, stand up a slim cluster with its own kubeconfig, do the capacity sum on paper before you write the memory limit, then hand-author the serving manifest — hitting the registry two-paths wall on purpose and fixing it — until the signed 1.0.0 artifact lands on a PVC and the pod reports 1/1 Running. Then you point the same M3 client at the cluster, break the pod with a bad probe and fix it, and time the loading patterns against each other. By the end OpsMate is v2.0: served by the cluster, from the artifact you signed.

Step 1 — One stack at a time: Compose down, cluster up​

The Kubernetes phase begins, and the rule is one heavyweight stack at a time. First assert the Compose model service is down — you do not want it holding memory while KIND runs (the registry service is the exception; it is the model source and stays up):

make -C labs/opsmate down
curl -s --max-time 2 http://localhost:8080/health || echo "compose model down — good"

Expected output

==> Stopping the OpsMate stack ...
 Container opsmate-model     Stopping
 Container opsmate-model     Stopped
 Container opsmate-model     Removing
 Container opsmate-model     Removed
 Network opsmate_default     Removing
 Network opsmate_default     Removed
    Stopped. The GGUF model file on disk stays for the next module.
compose model down — good

The exact Stopping/Removed lines vary by Compose implementation — Docker Compose v2 prints a [+] Running summary, the Rancher Desktop / nerdctl backend prints them one per line as above, and if only the registry service was up you will see it removed instead of opsmate-model. What matters is the compose model down — good line — port 8080 is free. Now bring up the cluster with the new make k8s-up. It runs a free-memory preflight, makes sure the registry (your model source) is up, creates the slim single-node KIND cluster with the isolated kubeconfig, and waits for the node to report Ready:

The preflight measures free memory inside the Docker VM (that is the real budget your containers draw from on a VM runtime like Rancher Desktop or Docker Desktop), so the figure reflects the VM, not your whole laptop. The Container opsmate-registry ... Started lines appear only when the registry was down and k8s-up starts it; if it was already up you will not see them. The node reached Ready in about 26 seconds on the spike host (here, ~60 s including a first-time node-image step); yours depends on whether the node image is already pulled (first run pulls it, adding a minute or two). The kindest/node version tracks your installed kind. Confirm the cluster answers through the isolated kubeconfig — note the --kubeconfig flag, which every command in this lab carries:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig get nodes

Expected output (the AGE and version are point-in-time)

A single Ready control-plane node is the whole cluster — slim by design for an 8 GB box. Because you passed --kubeconfig, this query went to the lab cluster and only the lab cluster; your default kubectl context is untouched. Prove that to yourself if you like: run kubectl config current-context (no --kubeconfig) and you will see whatever you had before, not kind-opsmate.

Step 2 — The capacity worksheet: derive the limit before you write it​

Before you write a single line of manifest, do the sum from the lesson. Booking the hall before you count the guests is how pods get OOM-killed on the third user. Open labs/m8/capacity-worksheet.md and fill it in with OpsMate's real numbers — the file has the blanks and the formulae; here is the reasoning you commit to it.

The pod's working set is three terms (all from M1/M2):

weights   : Qwen3-0.6B at Q8_0                 ≈ 0.65 GiB   (fixed)
runtime   : llama-server buffers/graph          ≈ 0.30 GiB   (roughly fixed)
KV cache  : 112 KiB/token × ctx × concurrency
            at ctx=2048, concurrency=1          ≈ 0.22 GiB
            at ctx=2048, concurrency=8          ≈ 1.75 GiB

So a single-request working set is about 0.65 + 0.30 + 0.22 ≈ 1.17 GiB, and at eight concurrent requests the KV term alone grows to ~1.75 GiB, pushing the working set toward ~2.7 GiB. Read those two numbers against an 8 GB box and the manifest answers write themselves:

  • requests.memory — the honest working set at expected load. We size for a small concurrency and set 1200Mi (the single-request number, rounded), so the scheduler reserves what the pod actually uses at rest.
  • limits.memory — the ceiling before the kernel OOM-kills the pod. We set 2Gi (the same cap M3 used as mem_limit), which holds the single-request working set with headroom but would be tight at 8 concurrent 2048-token requests — exactly the signal that says "add a replica" in M9.
  • Replicas — one. One pod's KV budget holds the low concurrency this lab drives; the queue in M3's load test (requests_deferred climbing) is the trigger to scale out, and that is M9's job.
  • Context — 2048, the lever. Bump it to 8192 and the KV term quadruples; that is the knob you turn when the box will not fit.

Commit your worked answers to the file so the check can read them:

# fill in the blanks in labs/m8/capacity-worksheet.md (your editor), then verify it is filled:
grep -E 'requests.memory|limits.memory|replicas' labs/m8/capacity-worksheet.md

Expected output (your committed answers — the shape, not the exact prose)

- requests.memory = 1200Mi   (weights 0.65 + runtime 0.30 + KV@2048×1 0.22 ≈ 1.17 GiB)
- limits.memory   = 2Gi      (ceiling before OOM-kill; tight at 8× concurrency → M9 scale-out)
- replicas        = 1        (one pod's KV budget holds this concurrency)

These are the exact numbers you will see in model-server.yaml in Step 4 — derived here, not copied there.

Step 3 — Confirm the model source: the M7 kits are still in the registry​

The cluster pulls the model from the M7 registry, so confirm it is up and the signed 1.0.0 is present. This is the M7 seam — the artifact you sealed is the artifact you deploy:

curl -s http://localhost:5100/v2/_catalog
curl -s http://localhost:5100/v2/opsmate/model/tags/list

Expected output (repositories/tags are what M7 pushed; order may vary)

{"repositories":["opsmate/adapter","opsmate/model"]}
{"name":"opsmate/model","tags":["1.0.0","1.0.0-candidate"]}

opsmate/model:1.0.0 is the signed base — what ships. 1.0.0-candidate is the M6 tune that lost and was recorded unsigned. The cluster will deploy 1.0.0. If the catalog is empty or the registry is unreachable, your M7 artifacts did not persist — re-run M7's push (its seed.sh self-seeds), because there is no model to serve without them.

Step 4 — Hand-author the model server manifest, and hit the two-paths wall​

Now you write the serving manifest. A reference copy sits at labs/opsmate/k8s/model-server.yaml — open it and read every block, because you will re-read this file in M9–M13 as the stack grows. It has four parts: a PVC (the model's home), an initContainer (the advance man that pulls the signed kit), the llama-server container (probes and limits from your worksheet), and a ClusterIP Service. The resources block is exactly the numbers you derived in Step 2.

Here is the heart of it — the initContainer that runs the artifact chain:

initContainers:
  - name: fetch-model
    image: ghcr.io/kitops-ml/kitops:latest   # official, multi-arch; entrypoint is `kit`
    command: ["/bin/sh", "-c"]
    args:
      - |
        set -e
        if [ -f /model/models/gguf/qwen3-0.6b-q8_0.gguf ]; then
          echo "model already present on PVC — skipping unpack"; exit 0
        fi
        kit unpack registry.local:5100/opsmate/model:1.0.0 \
          --filter=model -d /tmp/kit --plain-http
        mkdir -p /model/models && cp -r /tmp/kit/models/* /model/models/
    volumeMounts:
      - name: model-store
        mountPath: /model

First, hit the wall on purpose. The manifest ships with registry.local deliberately pinned to 127.0.0.1 — which, inside a pod, is the pod itself, not your machine. That is the exact naive mistake the lesson warned about, committed on purpose so every learner hits the same wall the same way. Apply it as-is and watch the initContainer fail:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig apply -f labs/opsmate/k8s/model-server.yaml
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig get pods -w

Expected output (if the pinned IP is wrong for your host, the init errors when the dial is refused — Ctrl-C the watch)

NAME                             READY   STATUS       RESTARTS     AGE
opsmate-model-66fdff887b-fdvz7   0/1     Init:0/1     0            2s
opsmate-model-66fdff887b-fdvz7   0/1     Init:Error   1 (4s ago)   6s

If the wrong IP is a reachable host with nothing on port 5100, the dial is refused fast as above; if it is an unreachable address the dial instead hangs until it times out (Init:0/1 for a minute or more). Either way the init never completes. Read the init log to see the wall in plain text:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig logs -l app=opsmate-model -c fetch-model

Expected output (the unpack cannot reach the registry — a connection error, not a "not found")

unpacking signed ModelKit opsmate/model:1.0.0 (model layer only) ...
Unpacking to /tmp/kit
[ERROR] Failed to find reference registry.local:5100/opsmate/model:1.0.0: unexpected error retrieving reference from remote: Head "http://registry.local:5100/v2/opsmate/model/manifests/1.0.0": dial tcp 127.0.0.1:5100: connect: connection refused

That is the two-paths lesson made physical: the name registry.local resolved (to the pinned IP) but nothing was listening there, because that IP is not your host's node-resolved address. The IP printed in your error is whatever the manifest currently pins — it is what you are about to correct. Now discover the right IP — the address the KIND node actually resolves for your host — and correct the manifest:

docker exec opsmate-control-plane getent hosts host.docker.internal

Expected output (the IP is runtime-specific — yours may differ)

192.168.5.2      host.docker.internal

If that IP matches what is already in model-server.yaml, the init failure was something else (check the registry is up). If it differs, edit the hostAliases block in labs/opsmate/k8s/model-server.yaml to your IP:

      hostAliases:
        - ip: "192.168.5.2"          # <-- YOUR getent result (192.168.5.2 on this host; yours may differ)
          hostnames:
            - "registry.local"

Re-apply and watch the initContainer pull the model onto the PVC, then the pod go 1/1 Running:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig apply -f labs/opsmate/k8s/model-server.yaml
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig get pods -w

Expected output (the first deploy pulls ~610 MB then the server loads — the init pull dominates the time; point-in-time)

NAME                             READY   STATUS            RESTARTS   AGE
opsmate-model-5685d8bfbf-vjbf6   0/1     Init:0/1          0          4s
opsmate-model-5685d8bfbf-vjbf6   0/1     PodInitializing   0          34s
opsmate-model-7b657d5cc5-5zqzj   0/1     Running           0          4s
opsmate-model-7b657d5cc5-5zqzj   1/1     Running           0          16s

Watch the sequence: Init:0/1 (the advance man pulling the kit) → PodInitializing (init done, server container starting) → Running but 0/1 (server up, model loading, startupProbe holding readiness off) → 1/1 Running (startupProbe green, model loaded, in the Service). The first deploy pays the ~610 MB registry pull in the Init/PodInitializing phase (that can be a minute or more on a laptop — the pull, not the load, is the slow part); once the model is on the PVC the server load itself is the short Running 0/1 → 1/1 gap that the startupProbe protects. Confirm the initContainer did its job:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig logs -l app=opsmate-model -c fetch-model

Expected output (the model layer landed on the PVC — the size is the real GGUF)

unpacking signed ModelKit opsmate/model:1.0.0 (model layer only) ...
Unpacking to /tmp/kit
Unpacking model opsmate-base to models/gguf/qwen3-0.6b-q8_0.gguf
model on PVC:
total 610M
-rw-r--r--    1 kit      kit       609.8M Jul 20 05:00 qwen3-0.6b-q8_0.gguf

Step 5 — Completion through the cluster: the same M3 client, unchanged​

The pod is 1/1 Running; now serve a completion through it. The Service is ClusterIP — internal only — so reach it from your host with kubectl port-forward, then point the unchanged M3 client at the forwarded port. This is the course promise again: the client from M3 does not change one line to talk to Kubernetes.

Open a port-forward (leave it running in one terminal):

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig port-forward service/opsmate-model 8080:8080

Expected output

Forwarding from 127.0.0.1:8080 -> 8080
Forwarding from [::1]:8080 -> 8080

In another terminal, first a raw health check, then the M3 client:

curl -s http://localhost:8080/health
OPENAI_BASE_URL=http://localhost:8080/v1 MODEL=qwen3-0.6b \
  uv run labs/m3/client.py "In one sentence, what does an SRE runbook contain?"

Expected output (the answer wording varies run to run)

{"status":"ok"}
engine  : http://localhost:8080/v1
model   : qwen3-0.6b
prompt  : In one sentence, what does an SRE runbook contain?

answer  : An SRE runbook contains documentation, procedures, and configurations for managing and maintaining systems.
finish  : stop
usage   : prompt=41 completion=23 total=64
cached  : 0 prompt tokens served from the prefix cache

Read what just happened. The exact same client.py you ran against a container in M3 and against Ollama in M1 answered — this time from a pod on Kubernetes, serving a model pulled as the signed 1.0.0 artifact. Nothing in the client changed; only OPENAI_BASE_URL points at the forwarded Service. The endpoint contract held across the whole journey from laptop to cluster. OpsMate is v2.0.

Step 6 — The probe-failure demo: break the pod, then fix it​

Now see the outage the lesson warned about, in a safe place. labs/opsmate/k8s/bad-liveness.yaml is a deliberately wrong patch: it removes the startupProbe and sets an aggressive liveness probe (check every second, one miss means dead) — perfectly reasonable for a 200 ms web service, catastrophic for a 40 s model loader. Apply it as a patch and watch the pod flap:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig patch deployment opsmate-model \
  --patch-file labs/opsmate/k8s/bad-liveness.yaml
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig get pods -w

Expected output (the RESTARTS column climbs until the pod flaps CrashLoopBackOff — Ctrl-C after you see it loop)

NAME                             READY   STATUS             RESTARTS      AGE
opsmate-model-5774bdcb94-xtl7j   0/1     Running            0             7s
opsmate-model-5774bdcb94-xtl7j   1/1     Running            0             16s
opsmate-model-5774bdcb94-xtl7j   0/1     Running            1 (1s ago)    36s
opsmate-model-5774bdcb94-xtl7j   1/1     Running            2 (2s ago)    69s
opsmate-model-5774bdcb94-xtl7j   0/1     CrashLoopBackOff   2 (4s ago)    73s

Exactly how the loop looks depends on how fast your pod loads. If the model is already on the PVC it may briefly reach 1/1 Running before the aggressive liveness starts killing it (as above); on a cold load it flaps while still 0/1. Either way the RESTARTS column climbs and the pod lands in CrashLoopBackOff — the probe never lets the engine settle. Read the events to see why Kubernetes is killing a healthy pod:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig describe pod -l app=opsmate-model | grep -A2 -i liveness

Expected output (the liveness probe fails while the engine is loading/reloading, so K8s restarts it — forever)

    Liveness:   http-get http://:http/health delay=1s timeout=1s period=1s #success=1 #failure=1
  Warning  Unhealthy  19s (x3 over 83s)  kubelet  Liveness probe failed: HTTP probe failed with statuscode: 503
  Normal   Killing    18s (x3 over 83s)  kubelet  Container llama-server failed liveness probe, will be restarted

There it is: the liveness probe fired every second with zero tolerance, and while the model is loading /health is not yet serving traffic (it answers 503, or refuses the connection outright on a cold start), so Kubernetes declared the container dead and restarted it — which starts the load over, which fails the probe again. The engine was never broken; the probe never gave it time. Revert by re-applying the good manifest, and the pod recovers:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig apply -f labs/opsmate/k8s/model-server.yaml
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig rollout status deployment opsmate-model --timeout=120s

Expected output

deployment "opsmate-model" successfully rolled out

The good manifest's startupProbe (30 × 5 s = 150 s of grace) covers the load, and its liveness is lenient (20 s period), so the pod loads once and stays up. You have now seen the restart loop and its fix — you will diagnose it in seconds if it ever happens for real.

Step 7 — Loading-pattern timing: registry pull vs a pre-pulled file​

The lesson compared four loading patterns on one axis: pay at start time or pay at build time. Now measure two of them. First, time the initContainer-from-registry load you already use — delete the pod and let the Deployment recreate it, timing from delete to Ready:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig delete pod -l app=opsmate-model
time kubectl --kubeconfig labs/opsmate/k8s/kubeconfig wait --for=condition=Ready \
  pod -l app=opsmate-model --timeout=120s

Expected output (timings are point-in-time; the shape is what matters)

pod/opsmate-model-5fbcb87ddd-qrksx condition met

real    0m5.0s

Note the PVC guard kicks in here: because the model is already on the PVC from the first run, the initContainer's idempotency check skips the 610 MB pull (model already present on PVC — skipping unpack), so this recreate is faster than the very first cold pull. Confirm it:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig logs -l app=opsmate-model -c fetch-model | head -1

Expected output

model already present on PVC — skipping unpack

That is the loading-pattern trade-off, measured: the first deploy pays the pull cost, but the PVC turns every subsequent pod start into a near-instant mount — which is exactly the hostPath pattern's advantage (model already on disk, no pull) achieved without tying the pod to a specific node. A pure hostPath variant would be fastest of all on the first start too, at the cost of preparing the node's disk by hand; the PVC gives you most of that speed with none of the node-pinning. This is the "pay once, mount fast after" shape you want for a model that ships as an artifact.

Step 8 — Read the cluster through the API proxy: pods and metrics​

The whole X-Ray idea since M1 is reading your real runtime through a same-origin proxy. For Kubernetes that proxy is built in: kubectl proxy serves the API on localhost with your credentials already applied, and the API server will proxy straight through to a Service's /metrics. That is the mechanism the module's Kubernetes X-Ray lens builds on — the lens UI ships with this module's live-tool pass; here you drive the same reads by hand so you know exactly what the lens is showing you. Start the proxy (leave it running):

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig proxy --port=8011

Expected output

Starting to serve on 127.0.0.1:8011

In another terminal, read the pod's phase, restart count, and readiness straight from the API — the same fields the lens surfaces:

curl -s "http://127.0.0.1:8011/api/v1/namespaces/default/pods?labelSelector=app%3Dopsmate-model" \
  | jq -r '.items[] | "\(.metadata.name)  phase=\(.status.phase)  restarts=\(.status.containerStatuses[0].restartCount)  ready=\(.status.containerStatuses[0].ready)"'

Expected output (the pod name is point-in-time)

opsmate-model-5fbcb87ddd-qrksx  phase=Running  restarts=0  ready=true

Now scrape the model server's /metrics through the API proxy — note the :http port name on the Service in the path, which selects the named port to proxy to:

curl -s "http://127.0.0.1:8011/api/v1/namespaces/default/services/opsmate-model:http/proxy/metrics" \
  | grep -E '^llamacpp:(requests_processing|requests_deferred|prompt_tokens_total|n_decode_total)'

Expected output (the counter values are point-in-time; drive a completion or two and they climb)

llamacpp:prompt_tokens_total 328
llamacpp:n_decode_total 1923
llamacpp:requests_processing 0
llamacpp:requests_deferred 0

Those are the same llama-server gauges you watched in M3's Engine lens (requests_processing, requests_deferred, the token counters), now read from a pod through the Kubernetes API instead of from a container directly. Same signals, one layer up the stack: this is the pods-and-metrics picture the Kubernetes lens renders, and the one you will lean on in M10 when you wire real observability. Stop the proxy with Ctrl-C when you are done.

Step 9 — Optional: the vLLM variant (x86 / 16 GB+ path)​

Optional — x86_64 with 16 GB+ free, or a GPU box. arm64 8 GB learners: read the manifest diff and watch the recorded demo.

labs/opsmate/k8s/model-server-vllm.yaml is the production-engine variant. It is the same shape as the llama-server manifest — same PVC, same initContainer artifact chain, same probe design — differing only in the container image and its args. That two-file diff is the lesson: swapping the serving engine is an image-and-args change, not a manifest rewrite, because the OpenAI /v1 contract holds the client stable.

On the arm64 / 8 GB path this course targets, do not apply it — vLLM's CPU build boots but crashes on inference on that VM kernel (M3 measured this across five configs; a KIND pod runs on the identical kernel, so it does not change). Read the manifest, diff it against the llama-server one, and watch the recorded vLLM-on-Kubernetes demo in this module's video section, which walks the identical steps against real vLLM on an x86 box.

See the fork in one command — the two manifests differ only where they must:

diff labs/opsmate/k8s/model-server.yaml labs/opsmate/k8s/model-server-vllm.yaml \
  | grep -E '^[<>]' | grep -vE '^[<>] *#' \
  | grep -E 'image:|"--model"|"--served-model-name"|"--max-model-len"|"-m"|containerPort'

Expected output (the real differences are the engine image, its args, and the port — the shape is identical)

<           image: ghcr.io/kitops-ml/kitops:latest   # official, multi-arch; entrypoint is `kit`
>           image: ghcr.io/kitops-ml/kitops:latest
<           image: ghcr.io/ggml-org/llama.cpp:server
>           image: vllm/vllm-openai:latest
<             - "-m"
>             - "--model"
>             - "--served-model-name"
>             - "--max-model-len"
<               containerPort: 8080
>               containerPort: 8000      # vLLM's default port (llama-server used 8080)

The first pair is not a real difference — the kitops initContainer image is identical, differing only by a trailing comment. The substance is the rest: the serving container's image (llama.cpp:server → vllm/vllm-openai:latest), its args (-m <path> becomes vLLM's --model / --served-model-name / --max-model-len), and the port (8080 → vLLM's default 8000). Same PVC, same initContainer artifact chain, same probe design — the engine swap is an image-and-args change, nothing more.

On a fitting x86 box you would apply it exactly like the llama-server variant — kubectl --kubeconfig labs/opsmate/k8s/kubeconfig apply -f labs/opsmate/k8s/model-server-vllm.yaml — port-forward service/opsmate-model-vllm 8080:8080, and point the same M3 client at it. Its /metrics exposes vllm:num_requests_running, vllm:num_requests_waiting, and vllm:gpu_cache_usage_perc (PagedAttention occupancy) — the same serving picture as llama-server with production internals. The Deep Dive dissects vLLM's KV management and the GPU serving concepts in full.

Step 10 — Teardown​

Tear the cluster down with make k8s-down. The cluster is cheap to recreate (~30 s), so the module deletes it — but the registry and its data persist, so the next module re-creates the cluster and pulls the same signed artifact:

make -C labs/opsmate k8s-down

Expected output

==> Deleting the KIND cluster 'opsmate' ...

Troubleshooting
  • initContainer fails with connection refused / no route to host — the two-paths wall. The hostAliases IP in model-server.yaml is wrong for your runtime. Discover the right one with docker exec opsmate-control-plane getent hosts host.docker.internal (the node name is <cluster>-control-plane) and put that IP in the manifest. Remember: the containerd mirror covers image pulls only, not the initContainer's HTTP kit unpack — that needs the hostAliases.
  • The host IP differs every time / after a runtime restart — some runtimes reassign the host IP. Re-run the getent command and update hostAliases whenever the init step suddenly can't reach the registry. This is why the value is a single, clearly-commented line in the manifest.
  • First make k8s-up is slow / hangs on "Ensuring node image" — KIND is pulling the node image (~1 GB) on first use. It is a one-time download; subsequent creates reuse it and take ~30 s. Let it finish.
  • Pod stuck Pending, describe says no storageclass — the PVC cannot bind. On KIND the default standard (local-path) storageClass should exist; confirm with kubectl --kubeconfig labs/opsmate/k8s/kubeconfig get storageclass. If it is missing, your KIND version is unusual — recreate the cluster with make k8s-down && make k8s-up.
  • Pod loops CrashLoopBackOff and you did NOT apply the bad probe — check describe pod for the reason. OOMKilled means the memory limit is too low for your context/concurrency (revisit the Step 2 sum); a liveness failure with the good manifest usually means the model genuinely failed to load (check the llama-server container logs, not just fetch-model).
  • make k8s-up preflight refuses to start — under ~3 GB free, the KIND phase is refused. Close the Compose stack (make -C labs/opsmate down), browsers, and other containers. One heavyweight stack at a time is the rule; the preflight enforces it.
  • port-forward says "address already in use" — a stray forward or the old Compose model still holds 8080. Find it (lsof -i :8080), stop it, or forward to a different local port (port-forward service/opsmate-model 8081:8080) and use 8081 in the client URL.
  • X-Ray Kubernetes tab is empty — it needs the proxy running with the isolated kubeconfig: KUBECONFIG=labs/opsmate/k8s/kubeconfig bash labs/tools/xray/serve.sh. If the pod is not 1/1 Running, the metrics scrape through the proxy will 503 until the model finishes loading.
