Serving on Kubernetes — Capacity, the Artifact Chain & Probes for Slow Starters

Here is the situation this module is built for. The platform team hands you a namespace and a short brief: put OpsMate's model behind a Service in the cluster, and before you open a pull request, answer three questions. How many replicas? What memory limit on the pod? What probes? You have deployed dozens of ordinary services — a web API, a worker, a cache — and for those you could answer all three in your sleep. But this service is different in one way that breaks every reflex you have: it takes about forty seconds to load six hundred and ten megabytes of model into memory before it can answer anything. Not slow to warm up. Dead until it is ready, then fine.

That one fact changes all three answers. The replica count is not a guess — it falls out of a capacity sum you can do on paper before you write a line of YAML. The memory limit is not a round number you copy from another service — it is derived from the model's weights plus its KV cache at the context you configure, the exact math from M1. And the probes are the part that bites hardest: the readiness and liveness probes you would set for a normal service will kill this pod while it is still loading, restart it, and put it in a loop that never recovers — a self-inflicted outage caused by a probe doing exactly what you told it to. Every Kubernetes instinct you have about probes and limits needs re-deriving for a model server, and that re-derivation is this module.

By the end you will have OpsMate served by the cluster — pulled as the signed 1.0.0 artifact you sealed in M7, loaded onto a volume, served behind a Service, with probes shaped for a slow starter and limits that came from a worksheet, not a template. This is OpsMate v2.0: no longer a container on your laptop, but a workload on Kubernetes.

The stack phase changes here

Through M7 you ran a Compose stack. From this module the serving stack lives on Kubernetes, and the rule is one heavyweight stack at a time — you bring the Compose model service down before you start the cluster, so your 8 GB box never holds both at once. The only Compose service that keeps running is the registry from M7: it is the model source the cluster pulls from. The lab opens by asserting the Compose stack is down.

Capacity first — book the hall before you sign the contract​

Start with the sum, because everything else on the manifest is downstream of it. This is the part most people skip and then pay for in a 2 GB memory limit that OOM-kills the pod on the third concurrent user.

Think about booking a wedding hall. You do not sign the contract and then count the guests. You count first: how many guests, how many plates each, how much space per table — and only then do you know the hall you need. Booking the hall before you know the numbers is how you end up with two hundred people in a room built for eighty. Capacity planning a model server is the same discipline in the same order: you work out what one request costs and how many you want at once, and that tells you the size of the box. The manifest's memory limit is the hall you book; the capacity sum is the guest count you do first.

Here is the sum, built from numbers you already computed in M1 and M2. The memory a model server pins down is three terms added together:

  • Weights — the model's numbers, a fixed chunk. For OpsMate's Qwen3-0.6B at Q8_0, about 0.65 GiB. This term does not move with load; it is the same for one user or fifty.
  • Runtime buffers — the engine's own working memory: activation scratch, the compute graph. Call it ~0.3 GiB for this model on llama-server. Also roughly fixed.
  • KV cache — the term that grows with use, and the one that decides your capacity. From M1: each token in flight costs about 112 KiB for this model, and the cache holds every token of every request currently alive. So KV memory ≈ 112 KiB × (context length) × (concurrent requests). At 2048 context and one request, that is about 0.22 GiB. At 2048 context and eight concurrent requests, about 1.8 GiB. At the model's maximum 40960 context, a single request's KV alone would be ~4.5 GiB — which is why you configure the context you need, not the maximum the card advertises (the M2 lesson, now a line item).

Add the three and you have the pod's working set. Turn the sum around and it answers the platform team's questions directly:

  • Memory limit = weights + runtime + KV at your configured context and target concurrency, plus headroom. Not a round number — a derived one.
  • Replica count = if one pod's KV budget holds your target concurrency, one replica. When concurrency outgrows what one pod's KV can hold (the queue in M3's load test, requests_deferred climbing), that is when you add a replica — an M9 decision, but the trigger is this sum.
  • Context length is the lever you pull when the box will not fit: shorter context shrinks the KV term directly.

You will fill in this exact worksheet in the lab, with OpsMate's real numbers, and the memory limit you write into the manifest will be the number you computed — not one you copied.

The habit to carry

Before you write a pod's resources block for a model, do the three-term sum. requests.memory is the honest working set (weights + runtime + KV at expected load); limits.memory is the ceiling before the kernel OOM-kills the pod. A limit pulled from another service's YAML is a guess, and for a model server a wrong guess is a crash loop.

An isolated kubeconfig — a visitor badge, not the master key​

Before the cluster comes up, one discipline that separates a lab from a liability. When you run kubectl, it talks to whatever cluster your current context points at. If your default context points at a real cluster — a dev cluster, a shared cluster, anything with other people's work on it — then a lab that creates and deletes namespaces, applies manifests, and patches deployments is one kubectl apply away from touching something it should not.

Think of it as the difference between a visitor badge and the building's master key. A visitor badge opens exactly the rooms you were let into and nothing else; you can do your work and you physically cannot wander into a server closet by accident. The master key opens everything, which is precisely why you do not carry it around for a job that only needs one room. This lab's cluster runs with its own isolated kubeconfig — a separate credentials file, written to k8s/kubeconfig, that names only this throwaway KIND cluster. Every command in the lab carries --kubeconfig k8s/kubeconfig, so kubectl can only ever reach the lab cluster. Your default context is never touched, never switched, never at risk. This is not lab pedantry; it is the same hygiene you want on a real bastion where one shell has access to many clusters.

Getting the model into the pod — four patterns, one chosen​

The model has to get from the registry onto the running pod somehow, and there is more than one way. The choice matters because it decides two things you care about: how long the pod takes to become ready, and what a rollout does. Here are the four you will meet, compared honestly.

  • Image-baked — copy the model into the container image. Startup is instant (the model is already in the layers), but every model change means rebuilding and repushing a multi-gigabyte image, and your registry fills with near-identical fat images. Fine for a model that never changes; painful for one that does.
  • initContainer from the registry — a small init step pulls the model artifact at pod start and puts it on a volume, then the server container starts and reads it. Startup pays a one-time pull-and-unpack cost (~40 s here), but the serving image stays small, and a model change is just a different tag — no image rebuild. This is the pattern this course uses, because it makes the model version a deploy-time choice and keeps the artifact chain from M7 intact.
  • hostPath / pre-pulled file — the model already sits on the node's disk and the pod mounts it. Fastest possible startup (no pull at all), but it ties the pod to a node that has the file, and preparing every node is manual work. Useful as an optimization on fixed infrastructure; you will time it against the initContainer in the lab.
  • Object store at runtime — the pod pulls the model from S3/GCS on start. Common in cloud setups, but it needs cloud credentials, egress, and it is network-bound; a rollout is a change of object key.

The trade-off is always the same axis: pay at build time (image-baked, big images, instant start) versus pay at start time (initContainer/object-store, small images, a load wait). For a model that ships as a versioned, signed artifact — which is exactly what M7 gave you — the initContainer pattern is the natural fit, and it is worth seeing why.

The artifact chain — the advance man who sets the stage​

Here is the payoff of everything M7 built. You did not sign opsmate/model:1.0.0 for its own sake. You signed it so that this, the deploy, could pull it by name and trust the bytes. The signed kit in the registry is what deploys — the artifact chain is unbroken from the seal you applied to the pod that serves it.

Think of a touring musician's advance man. The artist does not walk into a cold, empty venue and start setting up. Someone goes ahead — the advance man — and does all the preparation: the stage is built, the instruments are in place, the sound is patched, everything the show needs is ready before the artist arrives. Then the artist walks on and performs. An initContainer is Kubernetes' advance man. It runs to completion before the main container starts, and it does exactly one job here: fetch the model artifact and put it on the volume, so that when the serving container starts, the model is already there waiting for it.

Read the chain left to right. The initContainer runs kit unpack registry.local:5100/opsmate/model:1.0.0 --filter=model — the same selective pull from M7, taking only the model layer, not the eval set or prompts. It writes the GGUF onto a PersistentVolumeClaim, the model's home inside the cluster. Then the serving container starts, mounts that volume, and finds the model already in place. Change the tag from 1.0.0 to a future 1.1.0 and you have redeployed a different model version — the manifest itself never changes. And because the artifact you pull is the one M7 signed, the M7 verify-before-deploy gate becomes, in a real cluster, an admission policy: the cluster refuses to admit a model whose signature does not verify. You ran that gate by hand in M7's preflight; here it is the same check, moved to the cluster's front door.

The PVC (not a throwaway emptyDir) matters for one concrete reason: if the serving container restarts — say a liveness probe fires — you do not want it to re-pull 610 MB from the registry. The model stays on the volume across restarts; only the server process comes back. The initContainer even guards for this: if the GGUF is already on the PVC, it skips the pull.

The two-paths registry lesson — the wall you will hit on purpose​

Now the part that trips up everyone the first time, taught here before the lab hits it so you recognize the wall when you walk into it. The cluster reaches the registry by two different paths, and confusing them is the single most common failure in this whole setup.

Path one is image pulls. When the KIND node pulls a container image — the llama-server image, the kitops image — it goes through containerd, and kind-config.yaml configures a containerd mirror so localhost:5100 on the node maps to your host's Zot registry. That path works, and it is why the images come down.

Path two is the initContainer's HTTP call to the registry to kit unpack the model. This is not an image pull — it is an ordinary HTTP request from inside a pod. And here is the wall: inside a pod, localhost:5100 is the pod itself, not your host. The containerd mirror does nothing for it — mirrors cover image pulls, not application HTTP. The node can reach your host by a special name (host.docker.internal), but pods do not inherit that name. So the first, naive attempt — point the initContainer at localhost:5100 — fails: the pod is talking to itself, finds no registry, and the unpack gets nothing.

The fix is hostAliases: pin a stable name — registry.local — to the host IP the node actually resolves. You discover that IP once, on your machine (the lab runs getent hosts host.docker.internal inside the node and reads the address — 192.168.5.2 on the spike host, but it varies by container runtime), and put it in the manifest's hostAliases. Now the initContainer's kit unpack registry.local:5100/... resolves to your host's Zot, and the model comes down. In the lab you will hit the localhost wall on purpose, read the init log to see it fail, then apply the hostAliases fix and watch it work — because a failure you have seen once and understood is a failure you will diagnose in seconds when it happens for real.

Probes for a slow starter — the sound-check versus the show-must-go-on check​

The last piece, and the one where a normal-service reflex causes a real outage. Kubernetes has three probes, and for a model server each does a distinct job that only makes sense once you separate them.

Go back to the touring musician. Before the show there is a sound-check: is everything set up, are the levels right, is the artist ready to go on? You do not open the doors and let the audience in until the sound-check passes. That is the startupProbe — it runs only during bring-up, and it holds everything else off until the model is loaded. During the show there is a different question: is the performer still on stage and playing, or have they collapsed and the show must be stopped? That is the livenessProbe — it decides whether to restart a wedged container. And there is a third, quieter check running throughout: should we be sending this performer more of the audience right now, or are they mid-song and not taking anyone new? That is the readinessProbe — it gates traffic, adding and removing the pod from the Service's endpoints without ever killing it.

Here is why the order matters so much for a slow loader. The startupProbe's failureThreshold × periodSeconds is your load budget — the total time the model is allowed to take before Kubernetes gives up on it. Set it to, say, 30 failures × 5 seconds = 150 seconds of grace, comfortably more than the ~40 s load. Crucially, while the startupProbe is still running, the liveness and readiness probes do not fire at all. They only begin after the model is loaded. That is what protects the load.

Now the failure mode, because you will demonstrate it live. Suppose you skip the startupProbe and set an aggressive liveness probe — check every second, one failure means dead — the kind of tight probe that is perfectly reasonable for a stateless web service that starts in 200 ms. On a model server, that probe starts firing immediately, during the 40-second load, while /health is not up yet. It fails, Kubernetes declares the container dead and restarts it, the restart begins loading the model again from scratch, the probe fails again before it finishes, and you are in a restart loop that never lets the model finish loading. The engine was never broken. The probe never gave it time. You watch the RESTARTS column climb and the pod flap CrashLoopBackOff — a self-inflicted outage. That is why a slow starter needs a startupProbe to cover the load and a lenient liveness (long period, tolerant threshold) that only guards the steady state. In the lab you apply exactly this bad probe as a patch, watch the loop form in the pod events, then revert — so you have seen the outage in a safe place and will never ship it.

The engine fork — stated honestly, no drama​

One last thing so you are not surprised in the lab. The serving engine you deploy has two variants, and which one you run depends on your hardware.

On the arm64 / 8 GB laptop path this course targets, the engine is llama-server — the same one from M3, now in a pod. It is the path that was validated end to end for this module: pod 1/1 Running, a completion served through the cluster, 1.76 GiB total footprint, comfortably in budget.

The production engine is vLLM, and its manifests ship right beside the llama-server ones. They differ only in the container image and its arguments — same PVC, same initContainer artifact chain, same probe shape — which is the whole point: swapping the serving engine is an image-and-args change, not a manifest rewrite, because the OpenAI /v1 contract holds the client stable (the course promise, again). But vLLM's home is the GPU; its CPU build is a compatibility path, and M3 already measured that it crashes on inference on the arm64 VM kernel. A KIND pod runs on that identical kernel, so the result does not change. So vLLM is taught line by line and validated on the x86 / 16 GB / cloud path plus a recorded demo; arm64 learners read the manifest, apply the llama-server variant, and watch the recording. No drama, just an honest fork you can see in a two-file diff.

What you'll do next​

In the lab you will bring the Compose stack down, stand up a slim single-node KIND cluster with its own isolated kubeconfig, and fill in the capacity worksheet with OpsMate's real numbers — deriving the memory limit before you write it. You will verify the M7 kits are still in the registry, hand-author the model server manifest, hit the two-paths registry wall on purpose and fix it with hostAliases, and watch the initContainer pull the signed 1.0.0 artifact onto the PVC and the pod reach 1/1 Running. Then you will point the same M3 client at the cluster and get a completion back — the client unchanged, again. You will apply the bad liveness probe and watch the restart loop form, then revert. You will time the initContainer-from-registry load against a hostPath variant. You will see it all in the Cluster X-Ray. And, optionally on the x86 path, you will apply the vLLM variant and read its metrics. By the end OpsMate is v2.0 — served by Kubernetes, from the artifact you signed.
