Deep Dive — KServe Anatomy, the llm-d Frontier, and the Decision Tree

The core lab built a canary by hand: two backends, an nginx split_clients weight, a golden-set gate. That is the right tool for one split on a laptop, and building it by hand is why the abstractions below now have meaning instead of magic. This Part 2 goes under the hood of the two rungs above the router — KServe and the llm-d frontier — reads their real object shapes, and walks the serving decision tree branch by branch. It closes on the two things the router pattern fundamentally cannot do, which is the honest reason the frontier exists.

You do not install anything here (the dependency stacks are off the 8 GB path); you read real manifests and match each field to the manual mechanic it replaces. The samples are in labs/m9/ so you can read them locally.

KServe — the InferenceService, field by field​

KServe collapses the whole M9 lab into one declarative object. Where you ran two Deployments, two Services, an nginx ConfigMap, and a rollout restart, KServe reconciles an InferenceService and does the rest. Read the sample:

grep -vE '^\s*#|^\s*$' labs/m9/kserve-sample.yaml

Expected output (the canary you hand-built, declared — comment header stripped)

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: opsmate
spec:
  predictor:
    canaryTrafficPercent: 10
    model:
      modelFormat:
        name: gguf
      storageUri: oci://registry.local:5100/opsmate/model:1.0.0-candidate
    minReplicas: 0
    maxReplicas: 3

Map each field to what you did by hand:

  • canaryTrafficPercent: 10 — this one integer is your two split_clients lines. When you change it, the controller shifts the Knative revision weights for you — no ConfigMap edit, no rollout restart. Your staged ladder (10 → 50 → 100) becomes a series of edits to this field, and KServe can even automate the climb.
  • storageUri: oci://…:1.0.0-candidate — the model source. KServe pulls the OCI artifact itself; there is no initContainer to write, because the abstraction owns the artifact chain. (Your M8 initContainer is what this replaces.)
  • minReplicas: 0 — scale-to-zero, the capability the router cannot match. An idle model releases its node entirely and KServe cold-starts it on the next request. The nginx router has no such power: an upstream with no pod behind it does not queue the request, it returns 502 (you saw this in the lab's troubleshooting).
  • predictor — the serving component. KServe also models transformer (pre/post-processing) and explainer components in the same object; for a plain LLM you use predictor alone.

Underneath, KServe rides Knative Serving, which is what actually holds two revisions and splits traffic between them by weight:

The dependency honesty. That depends on box is the whole reason this is a survey and not a lab step. KServe needs Knative Serving, a networking layer (Istio or Kourier), and cert-manager for webhook certs — three subsystems you install, run, and keep patched. On an 8 GB single node, that stack is larger than the problem — you needed one split, and you got it from a 64Mi nginx. The rule from the lesson holds: adopt KServe when a fleet of models plus scale-to-zero justifies the dependency stack. On a real cluster where you serve many models and want a standardized rollout, it pays; on a laptop, the router is the honest choice.

The frontier — Gateway API Inference Extension and llm-d​

The router splits per request by a blind hash. That is fine for a canary, but at scale it leaves value on the floor, because it cannot see inside the request. The frontier fixes exactly that: it makes the routing decision inference-aware. Read the frontier sample:

grep -vE '^\s*#|^\s*$' labs/m9/inferencepool-sample.yaml

Expected output (the object shapes — read, do not apply; comment header stripped)

apiVersion: inference.networking.x-k8s.io/v1alpha2
kind: InferencePool
metadata:
  name: opsmate-pool
spec:
  selector:
    app: opsmate-model
  targetPortNumber: 8080
  extensionRef:
    name: opsmate-endpoint-picker
---
apiVersion: inference.networking.x-k8s.io/v1alpha2
kind: InferencePool
metadata:
  name: opsmate-prefill-pool     # compute-bound: builds the KV cache from the prompt
  labels:
    llm-d.ai/role: prefill
spec:
  selector:
    llm-d.ai/role: prefill
  targetPortNumber: 8080
---
apiVersion: inference.networking.x-k8s.io/v1alpha2
kind: InferencePool
metadata:
  name: opsmate-decode-pool      # bandwidth-bound: emits tokens off the KV cache
  labels:
    llm-d.ai/role: decode
spec:
  selector:
    llm-d.ai/role: decode
  targetPortNumber: 8080

Two ideas define the frontier, and both connect straight back to M1.

1. KV-cache- and prefix-aware routing. The InferencePool is a set of model-server pods, and the extensionRef names an endpoint-picker — a component that chooses which pod answers based on inference state, not round-robin. Its highest-value trick is prefix affinity: if a request's prompt shares a long prefix with one a pod recently served, that pod still holds the prefix's KV cache, so routing there lets the new request reuse that cache instead of recomputing it. For OpsMate, every request carries the same long system prompt (the M5 prompt) — so prefix-aware routing would send them all to a warm pod and skip re-encoding that prompt every time. nginx cannot do this: split_clients hashes a request id it cannot interpret, with zero knowledge of what any pod holds.

2. Disaggregated prefill and decode. This is the M1 call-back made physical. Recall M1's two phases:

  • Prefill — read the whole prompt at once, build its KV cache. Compute-bound; one big parallel matmul.
  • Decode — emit output tokens one at a time, each reading the whole KV cache. Memory-bandwidth-bound; a long sequential tail.

They have opposite bottlenecks, so packing both on the same pod means neither is sized right. llm-d runs them as two pools — a prefill pool and a decode pool — each scaled for its own limit, with the router handing a request's prefill to one pool and its decode to another (moving the KV cache between them):

The phases you first met as a memory diagram in M1 become, at scale, two independently-scaled fleets with a cache-aware router between them. You will not run this on a laptop — the point is fluency: when a design doc says "InferencePool" or "disaggregated serving," you now know it means an inference-aware endpoint-picker over pools split by the prefill/decode bottleneck, and you know what it buys (cache reuse, right-sized scaling) and costs (a Gateway implementation, the inference extension, pool operators).

The decision tree, walked branch by branch​

labs/opsmate/k8s/DECISION-TREE.md is the capstone artifact. Here is the reasoning behind each branch — the questions in order, and the honest cost at each landing.

Branch 1 — "Do you shift traffic between two versions at once?" If no, you are in M8's world: one version, one Service, no extra dependencies. This is the default and where you should start. Do not add a router because you might canary someday; add it the day you actually must run two versions against real traffic.

Branch 2 (the "no" side) — "Do you need scale-to-zero or a managed fleet?" Still one version, but if you run many models, or want idle ones to release their nodes, a plain Deployment makes you hand-manage all of it. That is when KServe pays: canaryTrafficPercent, scale-to-zero, and a standardized rollout across the fleet — at the cost of the Knative + networking + cert-manager stack. If you have one model that is always on, KServe's stack is pure overhead; stay on the Deployment.

Branch 3 (the "yes" side) — "Small/manual, or cache-aware at scale?" You need two versions live. If you are on a laptop or a few nodes and are content editing a weight by hand, the router + canary (M9) is the cheapest honest tool — one nginx, a ConfigMap, a Service each. If instead you are at a scale where the routing decision itself must be KV-cache- and prefix-aware, you have outgrown the router and want llm-d / the Gateway API Inference Extension.

The tree is a ladder of capability against a ladder of dependency cost. Each rung up buys something concrete and costs concrete dependencies. You climb only when the problem forces you.

What the router pattern fundamentally cannot do​

Close on the honest limits, because they are the reason the frontier is not just "nginx but fancier." Three things the M9 router structurally cannot do:

  1. Per-token / KV-cache-aware routing. nginx routes a whole request to a backend by a blind hash of a request id. It has no visibility into KV-cache state, token counts, or queue depth per pod. It cannot send a request to the pod best able to serve it, because it cannot see what any pod holds.
  2. Prefix affinity. Because it cannot see cache state, it cannot route a request to the pod that already holds its prompt's prefix KV — so every request risks recomputing a prefix another pod already has warm. For a workload with a shared system prompt (OpsMate), that is real waste the frontier reclaims.
  3. Scale-to-zero. An nginx upstream is a static list of Services. If a backend has no ready pod, nginx returns 502 — it cannot cold-start a scaled-to-zero model on demand the way KServe/Knative does.

These are not nginx bugs; they are the ceiling of "split traffic by weight at the HTTP layer." When your problem needs per-token routing, cache affinity, or scale-to-zero, you have hit that ceiling — and that is precisely the signal to climb the decision tree past the router.

Where you will use this​

  • Reviewing a serving design. Someone proposes KServe for a single always-on model on a small cluster. You can now say why the Knative + cert-manager dependency stack outweighs the one split they need, and point them at a router — or vice versa, justify KServe when a real fleet and scale-to-zero are on the table.
  • A rollout that "passed staging" but degrades in production. You reach for the canary + golden-set gate: split a slice, run the eval against both versions, promote or roll back on the pass-count. You do not swap the tag and hope.
  • Reading a frontier architecture doc. "InferencePool," "disaggregated prefill/decode," "prefix-aware routing" stop being jargon — you know each maps to a concrete win (cache reuse, right-sized scaling) at a concrete cost, and you can judge whether your scale justifies it.
  • Capacity and cost conversations. Disaggregation and prefix affinity are how large deployments cut GPU spend; knowing the shape lets you ask the right question — "are we recomputing shared prefixes?" — before signing off on a bigger cluster.
