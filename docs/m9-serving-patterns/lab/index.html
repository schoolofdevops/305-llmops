Lab — Canary a Model on Quality: Router, the Golden-Set Gate, and Rollback

Resource path: 8 GB core — everything required runs

Every required step runs on the 8 GB core path: the slim single-node KIND cluster from M8, plus the base model pod, one canary pod, and a 64Mi nginx router — three pods, measured ~1.9 GiB in the spike, comfortably in budget. You bring the Compose stack down first (one heavyweight stack at a time). Step 7 (KServe) is a read-along only — no install; its live path is a 16 GB+ cluster and a recorded demo.

Before you start

All commands run from the root of the labs repo (305-labs/). You need docker, kind, kubectl, kit, curl, jq, and uv responding — check the Setup section if any are missing. You must have completed M6 (it produced the tuned GGUF the candidate serves) and M7 (it pushed opsmate/model:1.0.0 signed AND 1.0.0-candidate); this lab pulls both tags from the registry on labs/opsmate/data/zot. Every kubectl carries --kubeconfig k8s/kubeconfig (path shorthand for labs/opsmate/k8s/kubeconfig — M10 onward prints the full labs-root form) — the isolated-kubeconfig discipline from M8, not a typo.

This is the module where OpsMate learns to change what it serves safely. You will bring up the M8 base server, stand a canary beside it serving the M6 loser, hit a designed model-load crash and fix it, put an nginx router in front and split 90/10, read that split honestly at n=20 then n=100, and then run the module's climax — the golden-set quality gate that measures the canary against the base and prints ROLLBACK because the candidate regressed. You act on it (weight → 0), then drill the promote ladder upward, read a KServe InferenceService, and tear down. By the end you promote and roll back on data, not on the absence of a crash.

Step 1 — Cluster up, base model server up (the M8 replay)​

The Kubernetes phase resumes. Assert the Compose model service is down, bring the cluster up (make k8s-up runs the free-memory preflight, ensures the registry is up, and creates the isolated-kubeconfig cluster), then apply the M8 base server and wait for it Ready:

make -C labs/opsmate down
make -C labs/opsmate k8s-up
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig apply -f labs/opsmate/k8s/model-server.yaml
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig rollout status deployment opsmate-model --timeout=240s

Expected output (timings, the free-memory figure, and pod hashes are point-in-time)

==> Stopping the OpsMate stack ...
    Stopped. The GGUF model file on disk stays for the next module.
==> KIND preflight (free memory) ...
==> OpsMate preflight
    ✓ Model file present and looks like a real GGUF.
    ✓ 6720 MB free (need ~3000 MB).
    Preflight passed.
==> Ensuring the registry (model source) is up on localhost:5100 ...
==> Creating the slim KIND cluster 'opsmate' (isolated kubeconfig: k8s/kubeconfig) ...
node/opsmate-control-plane condition met
    Node Ready. Cluster is up. Your default context was NOT touched.

This is the M8 end-state re-created: a single Ready node, ready to take the base opsmate-model pod from the signed 1.0.0 kit.

The hostAliases fix carries over from M8 — expect to redo it here. model-server.yaml ships the deliberate 127.0.0.1 placeholder (the M8 exhibit), so applying it as-is fails the init pull the same way M8 did:

deployment "opsmate-model" configured

then the pod goes Init:CrashLoopBackOff. Read the init log to confirm it is the registry-unreachable wall, not something new:

$ kubectl --kubeconfig labs/opsmate/k8s/kubeconfig logs -l app=opsmate-model -c fetch-model --tail=3
unpacking signed ModelKit opsmate/model:1.0.0 (model layer only) ...
Unpacking to /tmp/kit
[ERROR] Failed to find reference registry.local:5100/opsmate/model:1.0.0: unexpected error retrieving reference from remote: Head "http://registry.local:5100/v2/opsmate/model/manifests/1.0.0": dial tcp 127.0.0.1:5100: connect: connection refused

Re-discover the host IP the same way M8 taught, set it in model-server.yaml's hostAliases, and re-apply:

$ docker exec opsmate-control-plane getent hosts host.docker.internal
192.168.5.2     host.docker.internal

(Your IP will differ — use whatever getent prints.) After the edit, the rollout completes:

deployment "opsmate-model" successfully rolled out

The base opsmate-model pod is now 1/1 Running. Confirm both backends' source tags are in the registry before you build the canary:

curl -s http://localhost:5100/v2/opsmate/model/tags/list

Expected output (both tags — the base and the M6 candidate — are what M7 pushed)

{"name":"opsmate/model","tags":["1.0.0","1.0.0-candidate"]}

1.0.0 is the signed base that serves today. 1.0.0-candidate is the M6 tune that lost the baseline and was recorded unsigned — the model your canary is about to serve, so the gate has something real to reject. If 1.0.0-candidate is missing, you did not complete M6's fine-tune (the tuned GGUF is its source) — re-run M7's seed.sh, which packs it if the GGUF is present.

Step 2 — The canary backend, and the designed model-load crash​

Now stand a second backend beside the base. Open labs/opsmate/k8s/canary/canary-server.yaml and read it — it is the M8 server pattern cloned for a different version: its own PVC, an initContainer pointed at opsmate/model:1.0.0-candidate, and the same probes. Apply it as shipped and watch it fail on purpose:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig apply -f labs/opsmate/k8s/canary/canary-server.yaml
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig get pods -l app=opsmate-canary -w

Expected output (the init completes, then the server container crashes and loops — Ctrl-C the watch once you see CrashLoopBackOff)

NAME                              READY   STATUS             RESTARTS      AGE
opsmate-canary-85bd6dc545-24thm   0/1     Pending            0             0s
opsmate-canary-85bd6dc545-24thm   0/1     Init:0/1           0             5s
opsmate-canary-85bd6dc545-24thm   0/1     Error              0             37s
opsmate-canary-85bd6dc545-24thm   0/1     CrashLoopBackOff   1 (8s ago)    45s
You fix TWO separate things in this step
  1. The hostAliases IP — same as Step 1: the canary ships the 127.0.0.1 placeholder, so apply the same getent IP so its init can reach the registry.
  2. The -m filename — once the init succeeds, the pod still crashes, this time on model load. That is the new lesson below.

Do them in order: fix (1), watch the init succeed, then meet crash (2).

The init succeeds — the candidate's model layer lands on the PVC — but the server container crashes. This is the designed exhibit: read the crash log to see exactly why.

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig logs -l app=opsmate-canary -c llama-server --tail=8

Expected output (llama-server cannot find the model file at the path in -m)

0.00.009.642 E common_fit_params: encountered an error while trying to fit params to free device memory: failed to load model
0.00.009.649 E gguf_init_from_file: failed to open GGUF file '/model/models/gguf/qwen3-0.6b-q8_0.gguf' (No such file or directory)
0.00.009.656 E llama_model_load: error loading model: llama_model_loader: failed to load model from /model/models/gguf/qwen3-0.6b-q8_0.gguf
0.00.009.657 E llama_model_load_from_file_impl: failed to load model
0.00.009.661 E cmn  common_init_: failed to load model '/model/models/gguf/qwen3-0.6b-q8_0.gguf'
0.00.009.663 E srv    load_model: failed to load model, '/model/models/gguf/qwen3-0.6b-q8_0.gguf'
0.00.009.664 I srv    operator(): operator(): cleaning up before exit...
0.00.010.973 E srv  llama_server: exiting due to model loading error

There it is in plain text: the server was told to load /model/models/gguf/qwen3-0.6b-q8_0.gguf — the base model's filename — but this pod pulled the candidate kit, whose model layer unpacks to a different file. Confirm what actually landed on the PVC:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig logs -l app=opsmate-canary -c fetch-model | tail -4

Expected output (the candidate's model layer is opsmate-tuned-q8_0.gguf, not the base name)

Unpacking model opsmate-base to models/gguf/opsmate-tuned-q8_0.gguf
candidate model on PVC:
total 610M
-rw-r--r--    1 kit      kit       609.8M Jul 20 06:28 opsmate-tuned-q8_0.gguf

This is the lesson: every ModelKit carries its own packed filename, and you cannot assume it. The candidate's model layer unpacks to opsmate-tuned-q8_0.gguf (the Unpacking model ... line names the packed file — see M7's Kitfile); a copy-pasted base manifest points -m at the wrong file. Fix the one marked line in canary-server.yaml:

          args:
            - "-m"
            # FIX ME: was the base filename; the candidate kit unpacks to this:
            - "/model/models/gguf/opsmate-tuned-q8_0.gguf"   # <-- the candidate's real file

Re-apply and watch the canary come up 1/1 Running:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig apply -f labs/opsmate/k8s/canary/canary-server.yaml
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig rollout status deployment opsmate-canary --timeout=180s
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig get pods -l 'app in (opsmate-model,opsmate-canary)'

Expected output (both backends up — base and canary side by side; hashes point-in-time)

deployment "opsmate-canary" successfully rolled out
NAME                             READY   STATUS    RESTARTS   AGE
opsmate-canary-9b9668cd4-97lqg   1/1     Running   0          11s
opsmate-model-7b657d5cc5-q4hhf   1/1     Running   0          4m17s

The model was already on the PVC from the failed run, so this restart skips the 610 MB pull (the idempotency guard) and just loads — fast. Two versions now serve concurrently, each on its own Service. Note what the crash was not: it was not the init, not the registry, not a probe. The pod was reporting its state honestly the whole time — the model file simply was not where you told the server to look.

Step 3 — The router, and reading the split (n=20 lies, n=100 tells the truth)​

Now put the router in front. Open labs/opsmate/k8s/canary/router.yaml and read the ConfigMap — the split_clients block with 10% canary / * base, the X-Served-By header, a self-answered /ping location the readiness probe uses (so the router is Ready when nginx is up, not gated on a backend), and a 64Mi nginx Deployment. Apply it and wait Ready:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig apply -f labs/opsmate/k8s/canary/router.yaml
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig rollout status deployment opsmate-router --timeout=120s
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig get pods

Expected output (three pods now — base, canary, router — all in budget)

deployment "opsmate-router" successfully rolled out
NAME                              READY   STATUS    RESTARTS   AGE
opsmate-canary-9b9668cd4-97lqg    1/1     Running   0          3m34s
opsmate-model-7b657d5cc5-q4hhf    1/1     Running   0          7m40s
opsmate-router-649d5f5465-l9jjv   1/1     Running   0          1s

Port-forward the router (clients now dial it, not a backend), leave it running in one terminal:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig port-forward service/opsmate-router 8090:8080

In another terminal, read the split at n=20 first — count the X-Served-By header over 20 quick health requests:

for i in $(seq 1 20); do
  curl -s -o /dev/null -D - http://localhost:8090/health | grep -i 'x-served-by'
done | awk '{print $2}' | tr -d '\r' | sort | uniq -c

Expected output (the illusion — at n=20 the canary count is tiny and noisy; yours will vary run to run)

  18 base
   2 canary

That draw says base 18, canary 2 — and a different run might say 20 base, 0 canary. The split is not broken. A 10% canary getting zero hits in 20 requests happens about 12% of the time (0.9²⁰ ≈ 0.12); a couple of hits is just as likely. Either way, 20 requests cannot read a 10% split; it is judging a coin from three flips. Now do the same at n=100:

for i in $(seq 1 100); do
  curl -s -o /dev/null -D - http://localhost:8090/health | grep -i 'x-served-by'
done | awk '{print $2}' | tr -d '\r' | sort | uniq -c

Expected output (at n=100 the ~90/10 shape shows; your exact split varies)

  87 base
  13 canary

Now the split is legible: ~87 base / ~13 canary, converging on the 90/10 weights. The number will not be exactly 90/10 — it is a random draw — but at n=100 it is close enough to read. This is the discipline for the rest of the module: measure a split at a sample size that can actually show it.

Step 4 — Drive real completions through the router​

The split above used /health for speed; now drive real completions and watch X-Served-By name the backend per request. The client is unchanged — it dials the router's /v1:

for i in $(seq 1 5); do
  curl -s -D /tmp/h.$i -o /tmp/b.$i http://localhost:8090/v1/chat/completions \
    -H 'Content-Type: application/json' \
    -d '{"model":"qwen3-0.6b","messages":[{"role":"user","content":"the payments api is throwing 500s, most likely cause?"}]}'
  echo "req $i -> $(grep -i x-served-by /tmp/h.$i | awk '{print $2}' | tr -d '\r')  $(jq -r '.usage.total_tokens' /tmp/b.$i) tokens"
done

Expected output (which backend answers each request is random by the split; token counts vary — the base is a reasoning model, so its totals run high)

req 1 -> canary  318 tokens
req 2 -> base  904 tokens
req 3 -> base  765 tokens
req 4 -> base  592 tokens
req 5 -> base  953 tokens

Read what happened: five real completions went through the router, the OpenAI /v1 contract held, and X-Served-By named the backend for each — most base, occasionally canary. The client sent identical requests; the router decided. You now have a working canary. But notice: every one of these returned a clean answer with a usage block. Nothing here tells you the canary is any good — only that it answers. That is the gap Step 5 closes.

Step 5 — The quality gate: the golden set kills the canary​

This is the climax. The canary is 1/1 Running and answers every request — and it is the M6 loser. canary_gate.py runs the golden generation questions against the canary AND the base directly (no RAG in the loop, the way M6's no-RAG arm measured), scores with the golden set's own wide nets, and compares. Port-forward both backend Services to local ports (two more terminals, or background them):

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig port-forward service/opsmate-model  8091:8080 &
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig port-forward service/opsmate-canary 8092:8080 &
sleep 3
uv run labs/m9/canary_gate.py --base http://127.0.0.1:8091/v1 --canary http://127.0.0.1:8092/v1 --n 6

Expected output (which specific questions pass varies with the model; the DIRECTION — canary below base — is the point, and is the M6 result)

OpsMate canary quality gate — 6 generation questions, direct /v1 spot-run (no RAG)
base   : http://127.0.0.1:8091/v1
canary : http://127.0.0.1:8092/v1

=== BASE  (opsmate-model, 1.0.0)  (http://127.0.0.1:8091/v1) ===
  PASS  gen-payments-pool          (net: pool|connection|db_pool_in_use|exhaustion)
  FAIL  gen-db-failover-find-primary (net: pg_is_in_recovery|recovery|leader|patroni)
  PASS  gen-crashloop-previous-logs (net: --previous|previous|kubectl logs|describe)
  PASS  gen-disk-reclaim           (net: prune|image|log|build)
  PASS  gen-deploy-rollback-cmd    (net: rollout undo|undo|rollout|previous revision)
  FAIL  gen-cache-stampede-fix     (net: single-flight|coalesc|jitter|recompute|probabilistic)

=== CANARY (opsmate-canary, 1.0.0-candidate)  (http://127.0.0.1:8092/v1) ===
  PASS  gen-payments-pool          (net: pool|connection|db_pool_in_use|exhaustion)
  FAIL  gen-db-failover-find-primary (net: pg_is_in_recovery|recovery|leader|patroni)
  PASS  gen-crashloop-previous-logs (net: --previous|previous|kubectl logs|describe)
  FAIL  gen-disk-reclaim           (net: prune|image|log|build)
  PASS  gen-deploy-rollback-cmd    (net: rollout undo|undo|rollout|previous revision)
  FAIL  gen-cache-stampede-fix     (net: single-flight|coalesc|jitter|recompute|probabilistic)

====================================================
BASE    passed 4/6
CANARY  passed 3/6

VERDICT: ROLLBACK — canary (3) < base (4); the candidate regresses quality. Set its weight to 0 and restart the router.

Read what the gate did. The base passed more golden questions than the canary — exactly the M6 result (the tuned model's generation regressed below baseline), now enforced against live production backends. The readiness probe said the canary was healthy; the golden set said it was worse. The gate exits non-zero, so a CI system (M12) could block promotion on this directly. Your exact pass-counts will differ (small model, judge-free wide-net scoring) and the margin is often narrow — one run here read 4 vs 3, another 4 vs 2 — but the candidate lands at or below the base, because it is the recorded loser. If a run ever prints PROMOTE, that is sampling noise on a hard, small-model gate, not a real win; the honest reading is still ROLLBACK. The manager tasted the food, and the food was worse.

Why the base needs a generous token budget

The base model (1.0.0) is a reasoning model: it writes a <think> pass before its answer. The gate sends max_tokens: 1024 so the base has room to finish reasoning and answer — at a tight budget it would spend the whole allowance thinking, return an empty answer, and score zero on every net, which would flip the verdict to a false PROMOTE. The tuned candidate answers directly (no reasoning pass), so it is not the one that needs the headroom. This is why the gate scores the final answer, not the scratchpad, and gives both models the same generous budget.

Stop the two backend port-forwards when the gate is done (leave the router forward on 8090 running):

jobs                    # confirm the two port-forward job numbers first
kill %1 %2 2>/dev/null   # the two port-forwards you backgrounded

Step 6 — Act on it: roll the canary back to 0, then drill the promote ladder​

The gate said ROLLBACK, so do it. Rollback is a weight edit: drop the canary to zero traffic in the ConfigMap and restart the router so nginx re-reads it. nginx split_clients rejects a literal 0% bucket (it refuses to start — invalid percent value "0%"), so zero traffic is expressed by removing the canary line — everything then falls through to the * (base) bucket. Edit labs/opsmate/k8s/canary/router.yaml's split_clients block:

      split_clients "${request_id}" $backend_pool {
        # canary line removed -> 0% to canary
        *       base;          # 100% base — the canary receives nothing
      }

Apply, restart, and verify 100/0:

kubectl --kubeconfig labs/opsmate/k8s/kubeconfig apply -f labs/opsmate/k8s/canary/router.yaml
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig rollout restart deployment opsmate-router
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig rollout status deployment opsmate-router --timeout=60s
# re-forward the router if the restart dropped your port-forward, then:
for i in $(seq 1 40); do
  curl -s -o /dev/null -D - http://localhost:8090/health | grep -i 'x-served-by'
done | awk '{print $2}' | tr -d '\r' | sort | uniq -c

Expected output (all base — the canary is off; the count reflects your 40 requests)

  40 base

The canary now receives nothing; every request goes to the base. That is a rollback done on data — the golden set decided it, not a crash. Important: if you edit the ConfigMap but forget the rollout restart, nginx keeps serving the old config — the pod does not reload a mounted ConfigMap on its own. The restart is the step that makes the edit take effect.

Now drill the promote ladder in the other direction so you have felt it. The candidate lost, so use the base as a harmless stand-in to practise the mechanic — raise the "canary" bucket in stages. Set it to 50%, apply, restart, read the split:

      split_clients "${request_id}" $backend_pool {
        50%     canary;
        *       base;
      }
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig apply -f labs/opsmate/k8s/canary/router.yaml
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig rollout restart deployment opsmate-router
kubectl --kubeconfig labs/opsmate/k8s/kubeconfig rollout status deployment opsmate-router --timeout=60s
for i in $(seq 1 100); do
  curl -s -o /dev/null -D - http://localhost:8090/health | grep -i 'x-served-by'
done | awk '{print $2}' | tr -d '\r' | sort | uniq -c

Expected output (at 50/50 the split reads roughly even at n=100; exact numbers vary)

  55 base
  45 canary

That is the middle rung: 10% → 50% → 100%, each gated on the golden set, each rollout restart a visible act. labs/opsmate/k8s/canary/promote-staged.yaml documents every rung as a copy-in block. In production the candidate would only climb a rung after the gate stayed green at the current one; here you drove the mechanic. Before moving on, restore the safe 10% (or 0%) split so the cluster is in a known state, apply, and restart the router.

Step 7 — KServe read-along: the split as a declared field (no install)​

Everything above you did by hand. KServe does it declaratively. Read the sample InferenceService — do not apply it (it needs Knative + a networking layer + cert-manager, off the 8 GB path):

grep -vE '^\s*#|^\s*$' labs/m9/kserve-sample.yaml

Expected output (the canary you built by hand, as one field — the file's comment header stripped for the spec)

apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: opsmate
spec:
  predictor:
    canaryTrafficPercent: 10
    model:
      modelFormat:
        name: gguf
      storageUri: oci://registry.local:5100/opsmate/model:1.0.0-candidate
    minReplicas: 0
    maxReplicas: 3

Match it to what you built: canaryTrafficPercent: 10 is your two split_clients lines; the controller runs both revisions and shifts the weight for you; minReplicas: 0 is scale-to-zero — something the nginx router cannot do (an upstream with no pod behind it just 502s). That capability costs the dependency stack, which is why this is a read on your hardware and a recorded demo on a 16 GB+ cluster. The Deep Dive walks the full anatomy and the llm-d frontier.

Step 8 — Teardown​

Tear the cluster down. The registry and its kits persist, and the decision-tree artifact stays — it is the capstone deliverable this module leaves behind:

make -C labs/opsmate k8s-down

Expected output

==> Deleting the KIND cluster 'opsmate' ...
Deleted nodes: ["opsmate-control-plane"]
    Cluster gone. The registry and its data on ./data/zot PERSIST — the
    signed kits survive, so the next module re-creates the cluster and
    pulls the same 1.0.0 artifact. (Cluster create is ~30s — cheap by design.)

Stop any port-forwards with Ctrl-C. Confirm the artifact survives teardown and the cluster is gone:

test -s labs/opsmate/k8s/DECISION-TREE.md && echo "decision tree kept"
kind get clusters | grep -q opsmate && echo "cluster still up?!" || echo "cluster gone — teardown clean"

Expected output

decision tree kept
cluster gone — teardown clean

What M10 reuses: the registry and both kits stay on labs/opsmate/data/zot, and k8s/model-server.yaml plus the canary/ manifests are the serving surface M10 puts observability on. OpsMate can now change versions safely — the next module makes those changes visible the moment they start.

Troubleshooting
  • Base or canary init CrashLoopBackOff, log says dial tcp 127.0.0.1:5100: connection refused — the hostAliases IP in the manifest does not match your host, so the init cannot reach the registry. Both model-server.yaml and canary-server.yaml ship the 127.0.0.1 placeholder. Run docker exec opsmate-control-plane getent hosts host.docker.internal, set that IP in the manifest's hostAliases, and re-apply. This is the same M8 fix — it does not carry over automatically because the manifest is checked in with the placeholder.
  • Canary pod CrashLoopBackOff, init succeeded — the designed Step 2 exhibit (or you hit it for real): the -m arg points at a filename this kit did not unpack. Read kubectl logs -l app=opsmate-canary -c fetch-model to see the actual file name the kit placed (opsmate-tuned-q8_0.gguf for the candidate) and set -m to match. Every kit carries its own packed filename.
  • Router CrashLoopBackOff after setting the canary to 0%, log says invalid percent value "0%" — nginx split_clients will not accept a literal 0% bucket. To route zero traffic to the canary, remove the … canary; line entirely; everything then falls through to the * (base) bucket. That is how split_clients expresses 0%.
  • n=20 split shows 0 canary hits — not a bug. A 10% canary gets zero hits in 20 requests ~12% of the time. Read the split at n=100, where the shape (~90/10) is legible. Small samples lie.
  • Base pod restarts (RESTARTS ≥ 1) while the gate runs, port-forward drops — the base is a reasoning model; under back-to-back gate requests on CPU it can miss a liveness /health deadline and get restarted, which kills its port-forward. Re-run kubectl wait --for=condition=Ready pod -l app=opsmate-model, re-establish the 8091 forward, and re-run the gate. It is load, not a broken pod.
  • Router returns 502 Bad Gateway — nginx got no answer from the upstream it picked. Usually the backend it routed to is not 1/1 Running yet (still loading — the model takes ~40 s), or you rolled the canary weight to a backend that is down. Check kubectl get pods; wait for both backends Ready before driving traffic. Unlike KServe, the nginx router has no scale-to-zero — an upstream with no ready pod is a 502, not a queued request.
  • ConfigMap edit not taking effect — you edited router.yaml but did not kubectl rollout restart deployment opsmate-router. A pod does not reload a mounted ConfigMap on its own; the restart is what makes nginx re-read the split. Always: apply → rollout restart → re-read.
  • Both backends serve the same model name — that is correct. Both use the qwen3-0.6b alias so the client cannot tell them apart; you distinguish them by the X-Served-By header, not the model field in the response.
  • Port-forward dropped after a rollout restart — a rollout restart recreates the router pod, which ends the forward to the old pod. Re-run the port-forward service/opsmate-router 8090:8080 after each restart.
  • make k8s-up preflight refuses to start — under ~3 GB free the KIND phase is refused; three pods (base + canary + router) need the headroom. Close the Compose stack, browsers, other containers. One heavyweight stack at a time.
