Environment

This page takes you from a bare machine to a fully verified lab environment. Install in the order given, then run the verification probe at the end. When every probe command passes, you are lab-ready. Every lab in this course was validated against exactly this toolchain.

The toolchain at a glance​

The labs run on one evolving GenAI stack — a local model server first, containers around it, and a small Kubernetes cluster from Module 8 onwards. That needs these tools:

ToolWhat it does in this courseProbe
docker (any OCI runtime)Runs every containerised service in the stackdocker version
gitClones the labs repo, drives the GitOps modulesgit --version
python3Runs lab scripts (tokenizer playground, X-Ray server)python3 --version
uvRuns Python lab scripts with their dependencies, no venv ceremonyuv --version
ollamaYour local model server for the Compose phase (M1–M7)ollama --version
nodeRuns eval tooling (promptfoo) and sim/check harnessesnode --version
jqReads JSON API responses in lab commandsjq --version
kindThe local Kubernetes cluster for the K8s phase (M8–M13)kind version
kubectlTalks to that clusterkubectl version --client

Three explicit resource paths run through the course: 8 GB core (every core lab), 16 GB comfort (richer optional variants), and cloud/recorded frontier (GPU topics — watch, or bring your own cloud machine). Every lab is labelled with its path up front. One stack phase runs at a time: the Compose stack (M1–M7) is torn down before the KIND phase (M8–M13) begins, and every lab ends with a teardown step, so the footprint on your machine stays flat.

Step 0 (container runtime) — pick one, any OCI runtime works​

The course is runtime-agnostic: Rancher Desktop (what the labs were validated on), Colima, OrbStack, Podman, or plain Docker Engine on Linux. If you already have a working docker command, keep what you have and skip ahead.

Rancher Desktop: one setting matters

In Rancher Desktop → Preferences → Container Engine, select dockerd (moby) — not containerd. The labs use the docker CLI against the standard Docker socket. Give the VM at least 4 GB memory (Preferences → Virtual Machine) on an 8 GB host, more if you have it.

Install order​

Install in dependency order — runtime first, then the rest (any order among independent tools).

macOS (Homebrew)​

# Step 0 — container runtime (skip if `docker version` already works)
brew install --cask rancher

# Core tools
brew install git python uv node jq
brew install ollama            # CLI + server; `ollama serve` runs it (or use the Ollama app)

# Kubernetes phase (M8+ — fine to install now)
brew install kind kubectl helm

# Model packaging (M7+)
brew tap kitops-ml/kitops && brew install kitops

Start Ollama once so it runs as your local model server:

ollama serve &   # or launch the Ollama menu-bar app; either keeps :11434 listening

Linux — and Windows WSL2 (run inside your Ubuntu terminal)​

Substitute arm64 for amd64 in any download URL if you are on an ARM machine.

# Step 0 — container runtime (Docker Engine)
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker "$USER" && newgrp docker

# Core tools
sudo apt-get update && sudo apt-get install -y git python3 python3-venv jq
curl -LsSf https://astral.sh/uv/install.sh | sh                    # uv
curl -fsSL https://ollama.com/install.sh | sh                      # ollama (installs + starts service)
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash - && sudo apt-get install -y nodejs

# Kubernetes phase (M8+ — fine to install now)
curl -Lo ./kind "https://kind.sigs.k8s.io/dl/v0.27.0/kind-linux-amd64" && chmod +x kind && sudo mv kind /usr/local/bin/
curl -LO "https://dl.k8s.io/release/$(curl -Ls https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl" && chmod +x kubectl && sudo mv kubectl /usr/local/bin/
curl -fsSL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash

# Model packaging (M7+)
curl -Lo kitops.tar.gz "https://github.com/kitops-ml/kitops/releases/latest/download/kitops-linux-x86_64.tar.gz" \
  && tar -xzf kitops.tar.gz kit && sudo mv kit /usr/local/bin/ && rm kitops.tar.gz
WSL2 users

Install everything above inside the Ubuntu terminal, including Docker Engine — you do not need Docker Desktop. Ollama inside WSL2 works CPU-only unless you have an NVIDIA GPU with the WSL CUDA driver; CPU is exactly what the course expects.

Troubleshooting​

These are the failures learners actually hit. Check here before asking for help.

Ollama runs but nothing answers on :11434

ollama --version passing does not mean the server is running. Check with curl -s http://localhost:11434/api/version — if that fails, start the server (ollama serve, or the desktop app) and re-check. On Linux the installer sets up a systemd service: sudo systemctl status ollama.

Editor / file-watcher: "too many open files" (ENOSPC / inotify)

On Linux (and WSL2), running any file-watching tool can exhaust the kernel's inotify watch limit, failing with ENOSPC: System limit for number of file watchers reached. Raise it:

echo fs.inotify.max_user_watches=524288 | sudo tee -a /etc/sysctl.conf
sudo sysctl -p
Environment creation fails with a cryptic timeout — check where you cloned

If standing up the lab environment times out or hangs, the most common cause is a repo cloned outside a VM-shared path. If your runtime runs in a lightweight VM (common on macOS and Windows), files are only shared into that VM from specific host paths — your home directory almost always, /tmp and system paths often not. Move the repo under your home directory and retry. (See the clone warning on the Prerequisites page.)

Cannot connect to the runtime socket

If tools report they cannot connect to the Docker socket (a "connection refused" or "cannot connect to ... .sock"), the runtime is not running or its VM is still starting. Start it, wait for it to report ready, and re-run the probe. If a second, conflicting runtime is installed (two daemons fighting over one socket), quit the one this course does not use.

macOS: a stale binary shadows your install

An older copy in /usr/local/bin or a runtime's bundled shims (e.g. under ~/.rd/bin) can shadow a tool you just installed. Check with which -a <tool>. If the fresh install is not first, put its directory first on PATH for your lab sessions (e.g. export PATH="/opt/homebrew/bin:$PATH" on Apple Silicon) and add it to your shell rc file.
